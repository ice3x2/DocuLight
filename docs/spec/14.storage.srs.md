## 1. Scope Overview

이 scope 는 데이터가 어디에 어떤 형태로 앉는가를 규정한다 — 문서 본문의 SSOT 는 서버 로컬 파일시스템이고 메타데이터는 SQLite 라는 두 저장소의 분담, 그 둘을 잇는 노드 ID 와 어긋났을 때의 재조정, 편집 결과가 디스크에 반영되는 방식(자동 저장 · 충돌 감지 · 버전), 지워진 것이 가는 곳(휴지통), 파일시스템 경로가 서빙되는 규칙, 그리고 백업.

축은 **영속**이다. 그 데이터가 화면에서 어떻게 보이는가는 `SHELL`·`EDITOR` scope 가 갖고, 누가 그것에 도달할 수 있는가는 `ACL` scope 가 갖는다. 이 scope 는 그 아래에서 무엇이 실제로 남는가를 갖는다.

## 2. Scope Boundaries

### In Scope

- 두 저장소의 분담 — 문서 본문의 SSOT 는 파일시스템, 사용자·그룹·ACL 메타데이터는 SQLite 단일 저장소 (`DR-STORAGE-001`·`DR-STORAGE-002`)
- 노드 ID — 경로에 독립적인 안정 ID 의 부여와, 그 값이 추측 불가한 랜덤이어야 한다는 제약 (`DR-STORAGE-003`·`SEC-STORAGE-001`)
- 재조정 — 기동 시와 주기적인 파일시스템·DB 전체 재조정, 서버에서 직접 옮긴 파일의 노드 상관 판정을 fail-closed 로 두는 규칙 (`REL-STORAGE-001`·`REL-STORAGE-002`)
- 저장 거동 — 버튼 없는 자동 저장, 충돌 판정의 근거를 읽은 시점의 내용 해시로 두는 규칙 (`FR-STORAGE-001`·`FR-STORAGE-002`)
- 버전 — 편집 세션당 1회 스냅샷, 보관 개수 초과분의 폐기, 항목별 사이드카 메타, 비교·복원 UI 가 충돌 병합과 같은 컴포넌트를 재사용한다는 규정 (`FR-STORAGE-003`·`FR-STORAGE-004`·`DR-STORAGE-005`·`IR-STORAGE-001`)
- 휴지통 — 삭제가 곧 휴지통 이동이고 노드 ID 로 물리 격리한다는 규정, 항목별 사이드카 메타, 열람 범위, 복구의 필요 권한과 부모 체인 소실 시의 처분, 영구 삭제의 필요 권한, 보존 기간 기본값과 경과분의 자동 영구 삭제, 휴지통·아카이브의 소재 (`FR-STORAGE-005`·`DR-STORAGE-004`·`SEC-STORAGE-002`·`FR-STORAGE-006`·`SEC-STORAGE-003`·`FR-STORAGE-007`·`DR-STORAGE-006`)
- 서빙 보안 — 점으로 시작하는 항목의 숨김과 직접 접근 거부, 그런 이름의 생성·업로드·개명 거부, DB 레코드가 없는 파일시스템 경로 요청의 거부 (`SEC-STORAGE-004`·`SEC-STORAGE-005`·`SEC-STORAGE-006`)
- 경로가 바뀌어도 깨지지 않는 참조 — 문서를 옮겨도 첨부가 움직이지 않고 본문을 재작성하지 않는다는 규정, 문서 간 링크를 이름 기반 위키링크로 해석하고 상대경로를 삽입하지 않는다는 규정 (`FR-STORAGE-008`·`FR-STORAGE-009`)
- 벡터 인덱스의 동기 갱신과 없는 노드 엔트리의 배제 (`SEC-STORAGE-007`)
- 백업 — `docsRoot` 와 DB 를 같은 시점으로 묶는다 (`OPS-STORAGE-001`)

### Out of Scope

- 충돌 이후의 병합 화면과 그 진입·해소 — `EDITOR` scope 가 소유한다. `FR-STORAGE-001`·`FR-STORAGE-002` 는 자동 저장의 중단·재개와 감지 규칙만 정한다 (`FR-STORAGE-001`·`FR-STORAGE-002` Implementation Notes).
- 저장이 거부된 뒤의 화면 — 본문 보존과 로컬 내보내기는 `EDITOR` scope 가 소유한다. 이 scope 는 거부 판정 쪽만 갖는다.
- 새 버전 올리기 진입점과 문서 헤더 메뉴의 소재·md 전용 노출 — `SHELL` scope 가 소유한다. 비-md 파일의 덮어쓰기 경로에서 md 는 버전을 만들고 바이너리는 복구 불가라는 갈림이 이 scope 의 버전 조항과 만나지만, 진입점 자체는 그쪽이다 (`FR-STORAGE-004`·`IR-STORAGE-001` Implementation Notes).
- 설정 화면에서의 소재와 설정 값의 저장소 — `SHELL` scope 가 소유한다. 이 scope 는 그 설정이 가리키는 값(보존 기간·보관 개수)의 의미만 정한다 (`FR-STORAGE-004`·`FR-STORAGE-007` Implementation Notes).
- 여러 워크스페이스를 한 목록으로 보여주는 휴지통 화면과 행 단위 판정 — `SHELL` scope 가 소유한다. `SEC-STORAGE-002` 는 범위 규칙만 정한다 (`SEC-STORAGE-002` Implementation Notes).
- 이름 충돌 시의 자동 접미사 규칙(항상 자동 접미사 + 동일한 안내, 확인 단계 없음) — `SHELL` scope 가 정본으로 소유한다. `FR-STORAGE-006` 은 복구 시 그 규칙을 따른다는 것만 갖는다 (`FR-STORAGE-006` Implementation Notes).
- 삭제·복구·영구 삭제가 감사 로그에 남는 형식과 감사 로그의 보존 기간 — `AUDIT` scope 가 소유한다. `FR-STORAGE-007` 은 휴지통 쪽 값만 정하며, 두 보존 기간의 대소 관계는 `G27` 로 열려 있다 (`FR-STORAGE-006`·`FR-STORAGE-007` Implementation Notes).
- 휴지통 일괄 영구 삭제를 Phase 1 에 도입하지 않는다는 결정(R142)과 보존 기간 축소·영구 삭제에 붙는 확인 등급 — `CONFIRM` scope 가 소유한다.
- 워크스페이스 경계를 넘는 인덱싱과 자동완성 후보를 포함한 표시 필터 — `WORKSPACE` scope 가 소유한다. 백링크 탭의 존재는 `SHELL` scope 가 소유하고, `EDITOR` scope 는 링크 계열의 Phase 범위 선언만 갖는다. `FR-STORAGE-009` 는 해석 규칙과 삽입 형식만 정한다 (`FR-STORAGE-009` Implementation Notes).
- 첨부의 저장 레이아웃과 소유 판정, 소유 문서 영구 삭제 시의 동반 삭제 — `ATTACH` scope 가 소유한다. `FR-STORAGE-008` 은 문서를 옮겨도 첨부가 움직이지 않는다는 결과만 정한다.
- 워크스페이스의 물리 저장 레이아웃과 사이드카 파일의 식별 권위, 그리고 아카이브 — `WORKSPACE` scope 가 소유한다. `SEC-STORAGE-006` 의 fail-closed 서빙 규칙은 그 아카이브 조항의 하위이면서도 **Phase 1** 이며, 아카이브가 Phase 2 로 미뤄졌다는 사실이 이 규칙까지 미루지 않는다.
- 재조정이 발견한 것을 담는 대기열의 정체·스키마·소재·권한 — `AUDIT` scope 가 소유한다. `REL-STORAGE-001`·`REL-STORAGE-002` 는 재조정 자체와 상관 판정만 갖는다.
- 어느 노드에 누가 도달할 수 있는가의 판정 — `ACL` scope 가 소유한다. `SEC-STORAGE-002`·`FR-STORAGE-006`·`SEC-STORAGE-003` 은 그 판정 결과를 필요 권한으로 인용할 뿐 값을 정의하지 않는다.
- MCP 읽기 결과와 벡터검색 결과의 ACL 필터링 — `ARCH` scope 가 소유한다. `SEC-STORAGE-007` 은 인덱스의 갱신 시점과 엔트리 배제만 정한다.

## 3. Assumptions and Constraints

- 파일시스템이 문서의 SSOT 라는 것이 이 scope 의 축이자 다른 조항들의 전제다 (`DR-STORAGE-001`). DB 가 손상돼도 파일시스템만으로 재구성이 가능해야 한다는 원칙이 사이드카 조항들의 근거이며, 그 원칙의 첨부 축 적용은 `ATTACH` scope 가 갖는다.
- 문서 본문의 정본은 CodeMirror 이고 React state 로 올리지 않는다 — `ARCH` scope 가 소유하는 제약이며, 자동 저장의 트리거가 그 위에서 성립한다.
- 인스턴스 규모와 운영 프로세스 수 전제는 `ARCH` scope 가 소유한다. 기동 시 전체 재조정과 주기 재조정이 감당 가능하다는 판단이 그 규모 전제 위에 있다.
- 미결 `G27` 이 이 scope 에 걸려 있다 — 감사 로그 보존 기간이 휴지통 30일보다 짧으면 삭제 기록이 휴지통보다 먼저 사라지는 역전이 생기고, 삭제가 기록 대상이므로 실제 문제가 된다. 두 값을 함께 정할 때 역전을 막아라.
- `G14`(화면의 최신성 — 다른 사용자의 변경이 언제 반영되는지 규정이 없고 `R77` 은 서버 측 재조정만 다룬다)와 `G28`(본문을 누가 고쳤는지가 제품 어디에도 없다 — `DR-STORAGE-005` 버전 사이드카에 행위자 칸이 없어 `R63-a` 복원 UI 가 "누가"를 표시할 수 없다)도 이 scope 에 걸려 있다. 이 scope 에 걸린 미결의 등재 정본은 `00.index.md` §9 의 `Impact` 열이며, 그 열이 바뀌면 이 목록도 함께 훑는다.

#### Requirement

시스템은 모든 md 문서를 서버 로컬 파일시스템에 마크다운 원문 그대로 저장한다. 문서 본문의 단일 진실 원천(SSOT)은 파일시스템이며, 데이터베이스는 본문을 보관하지 않는다.

#### Rationale

옵시디언 볼트와 동일한 방식이다. 본문을 DB 로 옮기면 볼트를 그대로 넣어 열고 편집한다는 제품 정의가 성립하지 않고, 파일시스템 쪽 사본과 DB 쪽 사본이 갈린다. 메타데이터(사용자·그룹·ACL)의 저장소는 이 요구가 아니라 R20 이 소유한다 — 본문은 파일시스템, 메타는 DB 라는 분담이 저장 계층의 기본 구도다.

#### Acceptance Criteria

- [ ] AC-1: 문서를 저장하면 그 내용이 서버 로컬 파일시스템의 md 파일에 마크다운 원문 그대로 기록된다.
- [ ] AC-2: 서버에서 md 파일을 직접 열어 읽은 내용과 화면에서 읽은 본문이 동일하다.
- [ ] AC-3: 문서 본문은 데이터베이스에 보관되지 않는다 — DB 를 비우고 재구성해도 파일시스템의 문서 본문은 그대로 남는다.

### DR-STORAGE-002 — 사용자·그룹·ACL 메타데이터는 SQLite 단일 저장소에 둔다

| Field | Value |
| --- | --- |
| Type | data |

| Priority | medium |
| Tags | sqlite, metadata, single-store |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

시스템은 사용자·그룹·ACL 메타데이터를 SQLite 데이터베이스 한 곳에 저장한다. 같은 메타데이터를 다른 저장소에 함께 두지 않으며, 둘 이상의 메타데이터를 함께 바꾸는 조작은 하나의 트랜잭션으로 처리한다.

#### Rationale

기각된 대안은 JSON 파일 저장소이고 사유는 셋이다. ① 읽기 빈도 — 트리 렌더링·검색·MCP 호출마다 권한 판정이 필요한데 수천 명 × 수천 문서 규모에서 매 요청마다 전체 JSON 을 순회하는 구조는 성립하지 않는다. ② 동시 쓰기 — 가입 승인·그룹 변경·ACL 변경이 겹치면 JSON 전체 rewrite 에 경합이 나고, 락으로 막는 것은 DB 를 손으로 다시 만드는 일이다. ③ 원자성 — 사용자 생성과 default 그룹 배정은 한 트랜잭션이어야 한다.

#### Acceptance Criteria

- [ ] AC-1: 사용자·그룹·ACL 메타데이터는 SQLite 데이터베이스 한 곳에만 저장되며 같은 사실을 담은 별도의 파일 저장소가 존재하지 않는다.
- [ ] AC-2: 사용자 생성과 default 그룹 배정처럼 둘 이상을 함께 바꾸는 조작은 하나의 트랜잭션으로 처리되어 일부만 반영된 상태가 남지 않는다.
- [ ] AC-3: 가입 승인·그룹 변경·ACL 변경이 동시에 일어나도 전체 재기록 없이 각각이 반영된다.

#### Requirement

서버 파일시스템에서 직접 이동·개명된 파일에 대해 시스템은 chokidar 의 unlink 와 add 를 관측해 동일 노드 여부를 판정하고, 동일 노드로 인정된 경우에만 ACL 이 새 경로를 따라가게 한다. 판정은 fail-closed 다 — 내용 해시가 동일하고 짧은 시간 창 안에 발생한 쌍만 동일 노드로 인정하며, 불확실하면 이식하지 않고 add 쪽을 신규 노드로 만들고 unlink 쪽 노드는 tombstone 으로 남긴다.

#### Rationale

감사 C10 해소. 파일 감시가 관측하는 것은 unlink 와 add 두 사건뿐이고 「같은 파일이 옮겨진 것」이라는 사실 자체는 관측되지 않으므로 판정은 언제나 추측이다. 추측이 틀리는 두 방향 중 ACL 오이식은 권한 상승이고 이식 실패는 이력 단절인데, 뒤의 것만 사람이 사후에 고칠 수 있으므로 판정을 fail-closed 로 둔다. 대가는 상관 실패 시 이력이 끊기고 관리자가 재조정 대기열에서 수동으로 연결해야 한다는 것이며, 그 비용을 감수한다. 기각된 대안 — 이름 유사도나 mtime 근접으로 추측 이식하는 것.

- 시간 창의 구체값을 원장이 정하지 않았다 — 문면은 짧은 시간 창이라고만 한다. 값은 구현 단계에서 정하되 넓힐수록 오이식 위험이 커진다.
- 수동 연결(해소)은 기존 감사 행을 고치지 않고 해소 행위를 새 감사 행으로 추가하는 방식으로만 한다(R139-c) — 판정 실패 자체가 보존돼야 fail-closed 를 택한 이유를 나중에 검증할 수 있다.
- 상관 실패는 신규 노드와 tombstone 두 감사 행을 한 대기열 항목으로 묶는다(R139-a). 그래서 대기열의 참조 감사 행이 복수다.
- UI/API 이동·개명은 노드 ID 를 유지한 트랜잭션이므로 이 경로를 타지 않는다. 둘을 뒤섞으면 정상 이동이 신규 노드가 되어 이력이 끊긴다.
- [2026-08-27] [AC-6 의 증거가 공허했다] 상호검증이 unlink 쪽 거르기를 무력화해도 AC-6 항이 죽지 않는 것을 잡았다. 계수기로 재니 그 항이 단언하는 시점에 감시자가 받은 사건이 unlink 0 · add 0 이었다 — 개명 직후 곧바로 단언해 감시자가 아무것도 보기 전에 통과했고, 감시자를 통째로 지워도 초록이 나오는 항이었다. 지금은 사건이 도착할 때까지 기다린 뒤, 걸러진 개수가 아니라 correlated(상관 판정에 실제로 들어간 사건 수)가 0 인지로 잰다. 조항의 문면이 「이 상관 판정 경로가 실행되지 않는다」이고, 플랫폼마다 개명이 만드는 사건 수가 달라 개수로 재면 흔들린다.
- [2026-08-27] [그 공허한 증거 뒤에 제품 결함이 있었다] 사건을 기다리게 하자 곧바로 드러났다 — 워크스페이스 사이드카 .workspace.json 이 감시 대상에 들어가 문서 노드로 등재됐고 재조정 대기열에 unregistered-file 이 열렸다. 재조정은 점으로 시작하는 이름을 hasDotSegment 로 거르는데 감시자가 그 규칙을 쓰지 않았다. 같은 규칙을 적용해 닫았고 그 되돌림에 AC-6 항이 죽는다. 처음에는 원인을 「개명이 파일을 먼저 옮기고 DB 를 나중에 갱신한다」로 오진해 판정 직전 거르기를 넣었는데, 탐침이 그것을 무력화해도 아무 항도 죽지 않아 뺐다 — 관측되지 않은 위험에 대한 방어를 시험 없이 두면 그것이 도는지 아무도 모른다.

#### Requirement

휴지통의 각 항목에는 원본 노드 ID·원본 경로·삭제 시각·삭제자를 담은 사이드카 메타 파일을 함께 기록한다. DB 의 휴지통 인덱스는 이 사이드카의 캐시이며, DB 가 손상돼도 파일시스템만으로 휴지통 인덱스를 재구성할 수 있어야 한다.

#### Rationale

감사 C11 해소. 파일시스템이 SSOT(R4)라는 원칙은 메타에도 적용된다 — 메타를 DB 에만 두면 DB 손상 시 휴지통 항목이 무엇이었는지 알 수 없어 복구 자체가 불가능해진다. R50-d(첨부 인덱스)·R40-b(워크스페이스 메타)와 같은 원칙이며, 원본 경로가 사이드카에 있어야 복구가 원위치를 판정할 수 있다.

#### Acceptance Criteria

- [ ] AC-1: 항목을 휴지통으로 옮기면 그 항목과 함께 원본 노드 ID·원본 경로·삭제 시각·삭제자 네 값을 담은 사이드카 메타 파일이 기록된다.
- [ ] AC-2: DB 의 휴지통 인덱스를 비운 뒤에도 파일시스템의 사이드카만으로 휴지통 목록을 재구성할 수 있다.
- [ ] AC-3: 사이드카와 DB 인덱스의 값이 어긋나면 사이드카의 값이 정본으로 채택된다.
- [ ] AC-4: 항목을 영구 삭제하면 그 사이드카 메타 파일도 함께 사라진다.

#### Requirement

버전 보관 디렉토리의 각 항목에는 문서 노드 ID·버전 순번·생성 시각·작성자를 담은 사이드카 메타 파일을 함께 기록한다. DB 의 버전 인덱스는 이 사이드카의 캐시이며, DB 가 손상돼도 파일시스템만으로 버전 인덱스를 재구성할 수 있어야 한다. 작성자 칸은 `G28` 판정으로 확정됐다 — 스냅샷이 저장 단위가 아니라 편집 세션 단위여서 이 칸이 기록 볼륨을 늘리지 않고, 이 칸이 없으면 버전 복원 화면이 「누가」를 표시할 출처를 갖지 못한다.

#### Rationale

감사 C11 해소. 휴지통 사이드카와 같은 원칙이다 — DB 인덱스는 캐시이고 파일시스템만으로 재구성 가능해야 한다. 별도 요구로 분리한 이유는 스키마가 다르고 한쪽만 미결이기 때문이다 — 휴지통 사이드카는 네 칸이 확정됐는데 버전 사이드카는 행위자 칸이 열려 있어 스키마를 닫을 수 없다(SRS-MD 29.1-⑦).

#### Acceptance Criteria

- [ ] AC-1: 버전 스냅샷을 만들면 그 항목과 함께 문서 노드 ID·버전 순번·생성 시각·작성자를 담은 사이드카 메타 파일이 기록된다.
- [ ] AC-2: DB 의 버전 인덱스를 비운 뒤에도 파일시스템의 사이드카만으로 문서별 버전 목록과 순번을 재구성할 수 있다.
- [ ] AC-3: 사이드카와 DB 인덱스의 값이 어긋나면 사이드카의 값이 정본으로 채택된다.
- [ ] AC-4: 보관 개수 초과로 버전이 폐기되면 그 사이드카 메타 파일도 함께 사라진다.
- [ ] AC-5: 사이드카의 작성자 칸만으로 그 버전을 만든 주체를 식별할 수 있다 — 감사 로그를 함께 읽지 않아도 된다.

### FR-STORAGE-001 — 저장은 버튼 없는 자동 저장이다

| Field | Value |

#### Requirement

문서 저장은 버튼 없는 자동 저장이다 — 입력이 멈추면 디바운스 뒤에 자동으로 저장한다. 편집 화면에 저장 버튼을 두지 않는다. Ctrl+S 는 즉시 저장과 버전 스냅샷 강제 생성의 보조 수단이다. 자동 저장이 충돌을 감지하면 자동 저장을 일시 중단하고 배너로 안내하며, 사용자가 머지 뷰를 열어 1회 해소하면 재개한다.

#### Rationale

감사 C8 해소이고 R1(옵시디언과 동일한 경험)을 유지한다 — 옵시디언에는 저장 버튼이 없고 저장은 사용자가 의식하지 않는 동작이다. 충돌 시 자동 저장을 중단하는 것은 저장을 시도할 때마다 머지 팝업이 반복해서 뜨는 것을 막기 위해서다. 이 요구가 문서 전환 시 미저장 손실이 없다는 R91 의 전제를 떠받친다. 기각된 대안 — 명시적 저장 버튼과 저장 여부 확인 대화상자.

#### Acceptance Criteria

- [ ] AC-1: 편집 후 입력이 멈추면 사용자가 아무 버튼도 누르지 않아도 본문이 저장된다.
- [ ] AC-2: 편집 화면에 저장 버튼을 두지 않는다.
- [ ] AC-3: Ctrl+S 를 누르면 디바운스를 기다리지 않고 즉시 저장된다.
- [ ] AC-4: Ctrl+S 로 저장하면 편집 세션당 1회라는 스냅샷 규칙과 무관하게 버전 스냅샷이 생성된다.
- [ ] AC-5: 자동 저장이 충돌을 감지하면 자동 저장이 중단되고 배너로 상황이 안내된다.
- [ ] AC-6: 중단 상태에서 사용자가 머지 뷰를 열어 충돌을 1회 해소하면 자동 저장이 재개된다.
- [ ] AC-7: 중단 상태가 지속되는 동안 편집 중인 본문이 유지되고 사용자 입력이 버려지지 않는다.

- [ ] AC-5: 영구 삭제 판정은 행마다 그 행이 속한 워크스페이스를 기준으로 적용된다.

#### Acceptance Criteria

- [x] AC-2: 노드를 이동하면 같은 처리 안에서 그 노드의 인덱스 엔트리가 갱신된다.
- [ ] AC-3: 워크스페이스를 아카이브하면 그 워크스페이스 노드의 인덱스 엔트리가 갱신·제거된다.
- [x] AC-4: 인덱스에 남아 있는 엔트리라도 대상 노드가 존재하지 않으면 검색 결과에 포함되지 않는다.
- [x] AC-5: 삭제된 문서의 요약·본문 조각이 검색 결과로 노출되지 않는다.

#### Requirement

노드를 영구 삭제하면 그 노드의 버전 실체와 사이드카, 버전 인덱스 행이 함께 사라진다. 휴지통으로 보내는 경로에서는 버전을 걷지 않는다 — 복구가 이력을 데려와야 하기 때문이다. 보존 기간 경과에 따른 자동 영구 삭제도 같은 경로를 지난다.

#### Rationale

버전 파일은 본문 그 자체를 담는다. 영구 삭제한 문서의 버전이 남으면 「복구할 수 없다」(`SEC-STORAGE-003` AC-4)는 선언과 디스크의 사실이 어긋난다. 같은 사유로 이미 두 자리가 영구 삭제 시점에 함께 걷힌다 — 첨부(`FR-ATTACH-005`)와 벡터 인덱스(`SEC-STORAGE-007` AC-1)다. 벡터 인덱스를 걷는 사유가 「남으면 삭제된 문서의 내용이 검색으로 새어 나간다」인데, 인덱스는 조각과 요약을 들고 버전은 본문 전문을 든다. 서빙에는 노출되지 않으므로(`SEC-STORAGE-006` 이 점 디렉터리를 서빙 루트에서 빼고 dot-path-guard 가 직접 접근을 거부한다) 웹 경로의 유출은 아니지만, 백업·워크스페이스 이전 때 따라가고 파일시스템 접근권을 가진 사람에게 보인다. 휴지통 이동에서 걷지 않는 이유는 첨부와 같다 — 복구할 수 있는 상태에서 지우면 복구된 문서가 이력을 잃은 채 돌아온다(`FR-STORAGE-006` AC-3).

- [x] AC-2: 버전 사이드카도 실체와 함께 사라진다.
- [x] AC-3: 버전 인덱스 행도 함께 사라져 목록에 남지 않는다.

- [x] AC-5: 보존 기간 경과에 따른 자동 영구 삭제도 같은 소거를 수행한다.
- [x] AC-6: 버전이 하나도 없던 노드를 영구 삭제해도 실패하지 않는다.

### REL-STORAGE-003 — 휴지통으로 옮긴 파일의 사라짐은 고아가 아니다

#### Requirement

삭제로 파일이 휴지통 자리로 옮겨진 것을 파일 감시가 「사라짐」으로 판정해 그 노드를 고아로 표시하지 않는다. 서버가 스스로 옮긴 것이며 복구가 그것을 되돌린다.

#### Rationale

삭제는 노드 행을 남기고 파일을 `.trash/<노드ID>/` 로 옮긴다. 원래 자리에서는 파일이 사라지므로 감시가 그것을 짝 없는 사라짐으로 보고 `markOrphaned` 를 부른다. 복구는 `trashedAt` 만 지우고 `orphanedAt` 은 그대로 두므로, 되살린 문서가 트리에는 서는데 `isServable` 이 고아를 막아 열리지 않는다. 사용자에게는 「지웠다 되살렸더니 문서가 열리지 않는다」로 보이고, 트리에 이름이 있으니 잃어버린 줄도 모른다. 같은 축의 조각 둘이 2026-08-29 에 섰다 — 서버가 직접 옮긴 파일을 따라가게 하는 규칙과 그 상관 판정의 fail-closed 화다. 휴지통 이동은 그때 빠진 셋째 조각이며, 노드 경로가 `.trash` 로 바뀌지 않으므로 「노드가 이미 그 경로를 갖고 있으면 우리가 옮긴 것」 규칙에 걸리지 않는다.

#### Acceptance Criteria

- [x] AC-1: 휴지통에 든 노드의 파일이 원래 자리에서 사라져도 그 노드를 고아로 표시하지 않는다.
- [x] AC-2: 삭제하고 감시가 한 바퀴 돌은 뒤에 복구해도 그 문서를 다시 열 수 있다 — 트리에 이름만 서고 열리지 않는 상태를 두지 않는다.
- [x] AC-3: 휴지통과 무관하게 사라진 파일은 그대로 고아로 표시된다 — 이 예외가 감시의 본래 역할을 지우지 않는다.
- [x] AC-4: 사용자가 화면에서 지우고 휴지통에서 되살리는 왕복이 실제 브라우저에서 성립한다.
