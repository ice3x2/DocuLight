### SEC-AUTH-001 — 1.0 로그인 기반 이식 — bcrypt · HttpOnly 세션 쿠키 · 소스 IP 단위 rate limit

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | login, session, rate-limit |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

로그인은 1.0 의 기반을 그대로 이식한다 — 비밀번호는 bcrypt 로 해시해 저장하고, 로그인 성공 시 세션은 HttpOnly 쿠키로 유지하며, 로그인 시도에 `express-rate-limit` 기반 rate limit 을 건다. rate limit 의 적용 단위는 소스 IP 이며 인스턴스 전역 카운터를 쓰지 않는다.

#### Rationale

R57 은 1.0 자산을 그대로 재사용하는 결정이라 원장이 별도 근거를 달지 않았다. rate limit 의 적용 단위는 설치 마법사 교차 검증(`G13` 종결)에서 R72-i 로 보충됐다 — 전역 카운터를 쓰면 익명 요청 몇 번으로 설치 자체를 봉쇄할 수 있어 완화책이 그대로 DoS 경로가 된다. 독립 심의 둘이 각자 같은 지적을 냈다. 기각된 대안 — 전역 카운터.

#### Acceptance Criteria

- [ ] AC-1: 비밀번호는 bcrypt 해시로 저장되고, 로그인 검증은 평문이 아니라 그 해시와 대조해 수행된다.
- [ ] AC-2: 로그인에 성공하면 세션 쿠키가 `HttpOnly` 속성으로 발급된다.
- [ ] AC-3: 로그인 시도가 rate limit 임계값을 넘으면 그 시도는 거부된다.
- [ ] AC-4: rate limit 카운터는 소스 IP 별로 유지되며, 한 소스 IP 의 시도 누적이 다른 소스 IP 의 시도를 제한하지 않는다.
- [ ] AC-5: 인스턴스 전역 단일 rate limit 카운터를 두지 않는다.

### SEC-AUTH-002 — 세션·토큰에 권한 스냅샷을 담지 않고 매 요청 principal 을 조회한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | authorization, session, pat |
| Risk | medium |
| Stability | evolving |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

세션과 PAT 어디에도 권한 스냅샷을 담지 않는다. 서버는 매 요청마다 principal 을 조회해 유효 권한을 계산하고, 그 결과로 권한 변경이 다음 요청부터 즉시 반영된다.

#### Rationale

권한 회수가 즉시 반영되어야 한다는 것이 이 조항의 전부다. 원장 §4 Phase 1 수용 기준 9(권한 회수 즉시성)가 이 조항을 명시로 지목하며 검증 방법을 통합 테스트로 정한다. 기각된 대안 — 세션·토큰 발급 시점의 권한을 캐싱해 요청마다의 조회를 줄이는 것.

#### Acceptance Criteria

- [ ] AC-1: 세션 쿠키와 PAT 어느 쪽에도 사용자의 유효 권한·그룹 멤버십·ACL 값이 담기지 않는다.
- [ ] AC-2: 서버는 매 요청마다 principal 을 조회해 유효 권한을 계산한다.
- [ ] AC-3: 권한을 회수한 뒤 같은 세션으로 보낸 다음 요청부터 그 노드 접근이 거부된다.
- [ ] AC-4: 권한을 회수한 뒤 같은 PAT 로 보낸 다음 요청부터 그 노드 접근이 거부된다.
- [ ] AC-5: 권한을 부여한 뒤 재로그인·토큰 재발급 없이 다음 요청부터 그 노드 접근이 허용된다.

### SEC-AUTH-003 — 계정 상태 게이트 — active 외 상태는 로그인·토큰 인증 단계에서 차단한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | account-state, login, gate |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정·설치 화면 설계](./04.screen-design-settings.md) |

#### Requirement

계정은 `active` · `pending`(승인 대기) · `suspended`(정지) · `rejected`(가입 거절) 네 상태 중 하나를 가진다. `active` 가 아닌 계정은 로그인 단계와 토큰 인증 단계 양쪽에서 차단된다.

#### Rationale

R7(가입 모드)과 R14-c(감사·역질의)를 한 메커니즘으로 충족한다. `rejected` 는 감사 M14 로 추가된 상태이며, 거절과 정지를 구분해 거절 이력을 보존하기 위한 것이다. 기각된 대안 — 거절을 정지로 대신 표기해 상태를 셋으로 줄이는 것(거절 이력이 사라진다).

#### Acceptance Criteria

- [ ] AC-1: 계정은 `active` · `pending` · `suspended` · `rejected` 넷 중 정확히 하나의 상태를 갖는다.
- [ ] AC-2: `active` 가 아닌 계정의 로그인 시도는 비밀번호가 올바르더라도 로그인 단계에서 차단된다.
- [ ] AC-3: `active` 가 아닌 계정의 PAT 를 제시한 요청은 토큰 인증 단계에서 차단된다.
- [ ] AC-4: `rejected` 는 `suspended` 와 구분되는 별개 상태로 저장되어 거절 이력이 보존된다.

### FR-AUTH-001 — 상태별 로그인 안내 문구

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |

| Verification Method | test |
| GitHub Issue | - |

#### Requirement

`active` 가 아닌 계정의 로그인 시도가 차단될 때 시스템은 계정 상태에 대응하는 안내를 표시한다 — `pending` 은 "승인 대기 중", `suspended` 는 "계정이 정지됨", `rejected` 는 "가입이 거절됨" 이다.

#### Rationale

원장은 이 조항의 근거 칸을 비워 두었다. 세 문구는 R60 의 4상태 중 `active` 외 셋에 하나씩 대응하며, 원장이 문구를 직접 지정했으므로 표현을 여기서 다시 정하지 않는다.

#### Acceptance Criteria

- [ ] AC-1: `pending` 계정으로 로그인을 시도하면 "승인 대기 중" 안내가 표시된다.
- [ ] AC-2: `suspended` 계정으로 로그인을 시도하면 "계정이 정지됨" 안내가 표시된다.
- [ ] AC-3: `rejected` 계정으로 로그인을 시도하면 "가입이 거절됨" 안내가 표시된다.
- [ ] AC-4: 세 상태의 안내가 서로 다른 문구로 구분되며 하나의 공통 문구로 통합되지 않는다.

### FR-AUTH-002 — 거절 계정을 pending 으로 되돌려 재심사한다

| Field | Value |
| --- | --- |
| Type | functional |

| Verification Method | test |
| GitHub Issue | - |

#### Requirement

슈퍼유저는 가입 승인 화면에서 `rejected` 계정을 `pending` 으로 되돌릴 수 있고, 되돌린 계정은 다시 가입 심사 대상이 된다.

#### Rationale

원장은 이 조항의 근거 칸을 비워 두었다. R60 이 `rejected` 를 `suspended` 와 구분되는 별개 상태로 둔 이유가 거절 이력 보존이므로, 재심사는 거절 기록을 지우는 형태가 아니라 `pending` 으로 되돌리는 형태를 취한다.

#### Acceptance Criteria

- [ ] AC-1: 슈퍼유저가 가입 승인 화면에서 `rejected` 계정을 `pending` 으로 되돌리면 그 계정의 상태가 `pending` 으로 바뀐다.
- [ ] AC-2: `pending` 으로 되돌린 계정은 가입 승인 대상 목록에 다시 나타난다.
- [ ] AC-3: 슈퍼유저가 아닌 사용자는 이 되돌리기 조작을 수행할 수 없다.
- [ ] AC-4: 되돌리기는 계정을 새로 만들지 않고 기존 계정의 상태만 전환한다.

### SEC-AUTH-004 — 가입 사용자의 default 그룹 자동 소속은 active 전환 시점에 이뤄진다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | default-group, membership, account-state |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

가입한 사용자는 자동으로 `default` 그룹에 소속된다. 소속이 이뤄지는 시점은 계정이 `active` 로 전환되는 시점이며, `pending` 사용자는 어떤 그룹 ACL 로부터도 유효 권한을 갖지 않는다.

#### Rationale

감사 H9 해소. R8 의 "가입하면 소속"을 R60-a 가 정밀화한 것이며, 두 문면을 각각 별개 요구사항으로 두면 `pending` 사용자가 가입 시점에 이미 default 그룹 ACL 의 권한을 얻는 것으로 읽혀 R60 게이트를 우회하는 해석이 살아남는다. 한쪽만 고쳐지면 다른 쪽이 조용히 어긋나는 형태이므로 SRS-MD §29.2 에 따라 하나로 병합했다. 기각된 대안 — 가입 신청 시점에 소속시키고 권한만 따로 막는 것.

#### Acceptance Criteria

R72-a 는 문면이 열거(차단 목록)인데 근거 칸은 기준(*"설치 화면 외의 표면이 존재하지 않아야 한다"*)을 말한다 — R84 가 R137 로 고쳐진 것과 정확히 같은 형태다. 열거로 두면 목록에 없는 경로(헬스체크·메트릭·정적 서빙·나중에 추가될 것)가 fail-open 이 되고, 구현자가 마법사 자신의 POST 를 예외 처리하며 임기응변으로 구멍을 뚫는다. 그래서 R72-h 가 열거를 허용목록으로 바꿨다(`G13` 종결 · 독립 심의 2인). 기각된 대안 — 차단 목록(deny list) 형태를 유지하는 것.

#### Acceptance Criteria

- [ ] AC-1: 설치 완료 전에는 `설치 화면` · `그 정적 자산` · `토큰 검증` · `설치 커밋` 네 경로만 응답한다.
- [ ] AC-2: 설치 완료 전에 일반 가입 경로로 보낸 요청은 차단된다.
- [ ] AC-3: 설치 완료 전에 로그인 경로로 보낸 요청은 차단된다.
- [ ] AC-4: 설치 완료 전에 API 경로로 보낸 요청은 차단된다.
- [ ] AC-5: 설치 완료 전에 MCP 경로로 보낸 요청은 차단된다.
- [ ] AC-6: 허용목록에 없는 경로는 헬스체크·메트릭·정적 서빙처럼 나중에 추가된 것이라도 기본이 차단이다.

#### Requirement

설치 마법사는 서버 콘솔에 출력된 1회용 설치 토큰을 요구한다. `1회용` 은 설치를 성공적으로 완료하면 소진된다는 뜻이고, 소진 시점은 최초 슈퍼유저를 만드는 트랜잭션이 커밋되는 순간이며, 그 전까지는 실패·중단과 무관하게 같은 토큰을 재입력할 수 있다.

#### Rationale

사내망에서 먼저 접속한 사람이 인스턴스를 선점하는 경로를 차단한다 — 서버 콘솔에 접근할 수 있는 운영자만 설치를 완료할 수 있다(R72-b). 소진 시점을 커밋으로 못박은 이유는 "한 번 입력하면 소진"으로 읽으면 오타 한 번이 인스턴스를 잠그기 때문이다(R72-f) — 복구는 재기동뿐인데 그 사실을 아는 사람이 없을 수 있다. 반복 시도는 R57 rate limit 이 맡는다. `G21` 종결이며 독립 심의 2인이 다섯 항 전부에서 일치했다. 기각된 대안 — `1회용` 을 "입력 시 소진"으로 해석하는 것.

#### Acceptance Criteria

- [ ] AC-1: 서버가 기동하면 설치 토큰이 서버 콘솔에 출력된다.
- [ ] AC-2: 올바른 설치 토큰 없이는 설치를 진행할 수 없다.
- [ ] AC-3: 토큰을 잘못 입력해도 같은 토큰을 다시 입력해 진행할 수 있다.
- [ ] AC-4: 설치가 중단됐다가 재개되어도 같은 토큰을 다시 입력해 진행할 수 있다.
- [ ] AC-5: 최초 슈퍼유저를 만드는 트랜잭션이 커밋되는 순간 그 토큰이 소진된다.
- [ ] AC-6: 소진된 토큰으로는 더 이상 설치를 진행할 수 없다.

### SEC-AUTH-015 — 설치 마법사의 모든 서버 요청은 토큰 검증으로 발급된 설치 세션을 요구한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | install-session, install-wizard, server-side-validation |
| Risk | medium |
| Stability | stable |

#### Requirement

설치 토큰 검증에 성공하면 설치 세션을 발급하고, 그 이후 설치 마법사의 모든 서버 요청은 유효한 설치 세션을 요구한다. 토큰을 진입 시점에만 검사하지 않는다.

#### Rationale

심의가 찾은 치명 결함이다. `04` §4.2~§4.8 이 단계 전환을 클라이언트 상태로만 그려, 그대로 구현하면 `[설치 완료]` 엔드포인트가 토큰 없이 호출된다 — 사내망 누구나 1단계를 건너뛰고 자기 계정을 최초 슈퍼유저로 만들 수 있고 R72-b 전체가 장식이 된다. R72-b 의 근거 칸이 이미 *"설치를 **완료**할 수 있다"* 로 완료를 지목했으므로 이는 의도 변경이 아니라 문면이 빠뜨린 것의 보충이다. 기각된 대안 — 토큰을 진입 시점에만 검사하고 이후 단계는 클라이언트 상태로 잇는 것.

#### Acceptance Criteria

- [ ] AC-1: 설치 토큰 검증에 성공하면 설치 세션이 발급된다.
- [ ] AC-2: 토큰 검증 이후의 모든 설치 마법사 서버 요청은 유효한 설치 세션을 요구한다.
- [ ] AC-3: 설치 세션 없이 설치 커밋 엔드포인트를 호출하면 거부된다.
- [ ] AC-4: 클라이언트가 단계 전환 상태를 조작해도 설치 세션 없이는 다음 단계의 서버 요청이 성립하지 않는다.

심의 5인 만장일치이며 소재는 4:1(소수 의견은 셸)이었다. R57 이 bcrypt 를 확정해 비밀번호의 존재는 이미 확정됐고 R101 이 계정 삭제를 폐기해 계정이 영구인데 자격증명을 갱신할 수단이 없었다. R58-c 의 "PAT 발급·폐기는 본인만" 과 같은 축이며, 그 축에 비밀번호만 빠져 있던 것은 근거 없는 비대칭이다. 기각된 대안 — 소재를 셸에 두는 것 · 슈퍼유저 대리 변경을 허용하는 것.

#### Acceptance Criteria

- [ ] AC-1: 사용자는 설정 모달 개인 구역의 `계정` 카테고리에서 자기 비밀번호를 변경할 수 있다.
- [ ] AC-2: 변경 뒤 새 비밀번호로 로그인할 수 있다.
- [ ] AC-3: 변경 뒤 이전 비밀번호로는 로그인할 수 없다.
- [ ] AC-4: 슈퍼유저를 포함해 어느 사용자도 타인의 비밀번호를 변경할 수 없다.

#### Implementation Notes

- `blocked` 인 이유 — 변경이 기존 세션·PAT 에 미치는 파급이 `G33` 미결이다. ① 비밀번호 변경이 그 계정의 PAT 를 무효화하는가(R58-d 는 `active` 아님·삭제만 무효 사유로 든다) ② 다른 기기의 세션을 끊는가(R59 는 세션 무효화를 다루지 않아, 유출된 비밀번호를 바꿔도 탈취 세션이 살아 있으면 회전이 무의미하다) ④ 현재 비밀번호 재입력을 요구하는가. 원장은 화면은 이 공백과 무관하게 그릴 수 있고 갈리는 것은 확인 문구와 사후 상태라고 적었다.
- 길이·복잡도 규칙은 이 요구사항이 정하지 않는다 — `04`-Q21 로 이미 열려 있는 별개 축이다.
- 원장 §4 Phase 1 수용 기준 13개에 비밀번호 변경이 없다. §4 의 〔판정 필요 · 2026-08-19〕가 R144 를 명시로 열거하며 *"그대로면 로그인할 수 없는 빌드도 이 관문을 통과한다"* 고 적고 판정을 열어 두었다.
- 비밀번호를 잊어 로그인할 수 없는 사용자의 복구 경로는 `G32` 로 별개 미결이다 — 이 요구사항은 로그인할 수 있는 사용자의 자발적 변경만 다룬다.

#### Requirement

사용자는 설정 모달 개인 구역의 `계정` 카테고리에서 자기 세션을 종료할 수 있다(로그아웃).

#### Rationale

심의 5인 만장일치이며 소재는 4:1(소수 의견은 셸 크롬)이었다. R57 이 HttpOnly 세션 쿠키를 못박은 이상 세션은 실재하고, 만들 수 있는데 끝낼 수 없는 것은 설계 선택이 아니라 누락이다. `03` §6.7 과 `04` EC4 는 이미 세션에 끝이 있음을 전제하며 빠진 것은 사용자 주도 종료뿐이다. 형식은 R58-d 의 비고(*"R60 게이트가 토큰 인증에도 걸린다는 것의 명시화"*)와 같다 — 도출 가능한 귀결의 명시화다. 기각된 대안 — 소재를 셸 크롬에 두는 것.

#### Acceptance Criteria

- [ ] AC-1: 사용자는 설정 모달 개인 구역의 `계정` 카테고리에서 로그아웃할 수 있다.
- [ ] AC-2: 로그아웃하면 그 브라우저의 인증된 상태가 해제된다.
- [ ] AC-3: 로그아웃 뒤 보호된 화면에 접근하면 로그인 화면으로 유도된다.
- [ ] AC-4: 로그아웃 조작은 다른 사용자의 세션에 영향을 주지 않는다.

#### Implementation Notes

- `blocked` 인 이유 — 로그아웃이 쿠키만 지우는지 서버 측 세션을 무효화하는지가 `G33` ③ 미결이다. 후자여야 R59 의 즉시성이 로그아웃에도 성립한다. 원장은 화면은 이 공백과 무관하게 그릴 수 있고 갈리는 것은 확인 문구와 사후 상태라고 적었다.

- 로그인 세션의 수명·만료 규정 자체가 원장에 없다 — `만료` 를 정한 조항은 ACL(R110) · 설치 토큰(R72-c) · PAT(R58-a) 뿐인데 `03` §6.7 과 `04` EC4 는 세션 만료의 존재를 전제한다. `G33` 을 닫을 때 함께 정하지 않으면 "만료는 있는데 규정이 없는" 상태가 남는다.
- 원장 §4 Phase 1 수용 기준 13개에 로그아웃이 없다 — §4 의 〔판정 필요 · 2026-08-19〕가 R145 를 명시로 열거했다.
