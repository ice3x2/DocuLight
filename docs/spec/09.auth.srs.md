## 1. Scope Overview

이 scope 는 "이 요청이 누구인가" 를 확정하는 경로와, 그것이 아직 확정되지 않았을 때의 화면을 규정한다 — 로그인과 세션, 개인 액세스 토큰(PAT), 계정 상태 게이트, 인스턴스가 비어 있을 때의 설치 마법사, 그리고 1.0 에서 2.0 으로 계정과 콘텐츠를 넘기는 이행.

경계는 **인증 경계**다. 주체가 확정된 뒤 그 주체가 무엇을 할 수 있는가는 `ACL`·`PRINCIPAL` scope 가 갖고, 이 scope 는 주체를 확정하는 일과 확정 전의 표면만 갖는다. 원장 조항 하나가 이 경계에 걸쳐 갈리는 경우가 실제로 있다 — 가입 모드 3종에서 ①②(인증 전 폼)는 이 scope 에 남고 ③(슈퍼유저 직접 등록)은 인증 후 관리 기능이 된다.

## 2. Scope Boundaries

### In Scope

- 로그인 기반 — 비밀번호 해시, HttpOnly 세션 쿠키, 소스 IP 단위 rate limit (`SEC-AUTH-001`)
- 세션·토큰에 권한 스냅샷을 담지 않고 매 요청 principal 을 조회한다는 원칙 (`SEC-AUTH-002`)
- 계정 4상태의 정의와 인증 단계 차단 게이트, 상태별 로그인 안내 문구, 거절 계정의 재심사 (`SEC-AUTH-003`·`FR-AUTH-001`·`FR-AUTH-002`)
- 가입 — 가입 모드 3종과 그 설정 표면, 슈퍼유저 직접 등록의 소재, `default` 그룹 자동 소속이 발생하는 시점 (`FR-AUTH-004`·`FR-AUTH-003`·`SEC-AUTH-004`)
- 인증 전 화면이 모달이 아니라 전체 화면이라는 구성 원칙 (`IR-AUTH-001`)
- PAT — 전역 API Key 폐기와 PAT 도입, 해시 저장과 발급 시 1회 노출, 발급·폐기 권한, 스코프가 상한만 낮춘다는 성질, 계정 상태 변화에 따른 즉시 무효화, MCP 의 Bearer 식별 (`SEC-AUTH-005`~`SEC-AUTH-009`·`IR-AUTH-002`)
- 설치 마법사 — 슈퍼유저 0명 시 강제 진입, 허용목록 밖 경로 차단, 설치 토큰의 요구·수명·재기동 시 갱신, 설치 세션, 최초 슈퍼유저 생성, 기본 워크스페이스에 대한 `default` 초기 권한 선택 (`SEC-AUTH-010`~`SEC-AUTH-015`·`SEC-AUTH-017`)
- 슈퍼유저 그룹의 `active` 멤버 수를 0 으로 만드는 조작의 거부 (`SEC-AUTH-016`)
- 접근 가능한 노드가 0개인 사용자의 빈 상태 안내 화면 (`FR-AUTH-005`)
- 본인의 비밀번호 변경과 본인의 세션 종료 (`SEC-AUTH-018`·`SEC-AUTH-019`)
- 1.0 → 2.0 읽기 전용 컷오버와 1.0 계정·자격증명의 이행 (`MIG-AUTH-001`·`MIG-AUTH-002`)

### Out of Scope

- 인증 후 화면의 골격 — 설정 모달의 구조와 카테고리 구성, 사용자 관리가 놓이는 자리는 `SHELL` scope 가 소유한다. `IR-AUTH-001` 은 인증 전 화면이 그 구조의 예외라는 사실만 담고, `FR-AUTH-003`·`FR-AUTH-004` 는 그 구조 안의 한 자리를 가리킨다 (`IR-AUTH-001` Implementation Notes).
- 사용자·그룹 관리 화면 자체와 계정 수명주기 — 슈퍼유저 여부의 판정 규칙, 그룹의 성질과 시스템 그룹, 계정을 삭제하지 않고 `suspended` 로만 관리한다는 결정(R101), 사용자 관리 화면의 4상태 표시는 `PRINCIPAL` scope 가 소유한다. 이 scope 는 그 상태를 인증 단계에서 어떻게 쓰는지만 정한다.
- 유효 권한의 정의와 계산 — `ACL` scope 가 소유한다. `SEC-AUTH-008` 의 교집합은 한쪽 항으로 그 값을 받아 쓸 뿐 그 값을 정의하지 않는다.
- 접근 가능한 노드가 0개가 되는 조건, 즉 완전 숨김 규칙 — `ACL` scope 가 소유한다. `FR-AUTH-005` 는 그 결과 상태의 화면만 갖는다.
- 권한 요청 워크플로를 Phase 2 로 미루고 Phase 1 은 안내 문구만 둔다는 결정(R103) — `ACL` scope 가 소유한다. `FR-AUTH-005` 의 안내 화면이 그 규칙의 적용 사례이며, 이 scope 가 그 규칙을 다시 정하지 않는다.
- 워크스페이스 자체와 최초 기동 시의 기본 워크스페이스 생성 — `WORKSPACE` scope 가 소유한다. `SEC-AUTH-017` 은 설치 마법사에서 그 워크스페이스에 대한 `default` 초기 권한을 고른다는 것만 정한다.
- 설치 마법사에서 이뤄지는 권한 부여에 붙는 확인 등급 — `CONFIRM` scope 가 소유한다. 그쪽이 설치 마법사 경로를 워크스페이스 생성 시점 부여와 같은 규칙으로 다루며, 이 scope 는 마법사 자체의 토큰·차단 규칙만 갖는다.
- 인증·계정 상태 변경이 감사 로그에 남는 형식과 보존 — `AUDIT` scope 가 소유한다.
- 인스턴스 설정 값이 저장되는 곳 — `SHELL` scope 가 DB 단일 저장소로 소유한다. `FR-AUTH-004` 는 가입 모드가 그 저장소에 든다는 사실만 갖는다.
- 비밀번호의 길이·복잡도 규칙 — 어느 요구도 소유하지 않는다. `04`-Q21 로 열려 있는 별개 축이며 `SEC-AUTH-018` 이 정하지 않는다.
- 세션 만료 후 로그인 화면에서 원래 URL 로 복귀하는 동선 — `03` §11-34 의 〔판단〕 상태이며 어느 요구도 소유하지 않는다 (`IR-AUTH-001` Implementation Notes).

## 3. Assumptions and Constraints

- 계정·자격증명·PAT 해시가 앉는 저장소는 SQLite 단일 저장소다 — `STORAGE` scope 가 소유하는 전제다.
- 인스턴스는 사내 단일 인스턴스다 (`ARCH` scope). 멀티테넌트를 전제한 테넌트 식별이 인증 경로에 없다.
- 인증 전 화면의 소유 설계 문서는 `04.screen-design-settings.md` 다(2026-08-19 심의). `03` 은 로그인·가입 신청 폼·설치 마법사를 명시로 범위 밖에 둔다.
- Phase 1 은 데스크탑 전용이다 — 그 구속은 `EDITOR` scope 가 소유하며, 인증 전 전체 화면도 데스크탑 기준으로 규정된다.
- `G33` 의 두 갈래가 이 scope 에 열려 있다 — ①(비밀번호 변경이 기존 PAT 를 무효화하는가) · ②(로그아웃이 다른 기기의 세션까지 끊는가). 그 결과 살아 있는 PAT 무효 사유가 사실상 `active` 아님 하나로 좁혀져 있다.
- `G10`(사용자 스키마)이 슈퍼유저 직접 등록으로 만든 계정의 생성 직후 상태를 미결로 남긴다.
- `G32`(잠긴 계정의 복구 경로 부재)가 이 scope 에 열려 있다 — 비밀번호를 잊은 사용자가 다시 들어올 수단이 어느 조항에도 없고, 메일 자기 서비스와 슈퍼유저 대리 재설정 둘 다 반론이 있다. 이 scope 에 걸린 미결의 등재 정본은 `00.index.md` §9 의 `Impact` 열이며, 그 열이 바뀌면 이 목록도 함께 훑는다.
- 원장 §4 Phase 1 수용 기준 13개 중 로그인·로그아웃·비밀번호 변경을 시험하는 항목이 없다는 사실이 원장 자신에 의해 〔판정 필요〕로 열려 있다. 기준 추가 여부는 원장 개정의 판정 사항이며 이 scope 의 요구가 대신 결정하지 않는다.

#### Requirement

로그인은 1.0 과 같은 기술 선택을 쓰되 구현은 신규 작성한다 — 비밀번호는 bcrypt 로 해시해 저장하고, 로그인 성공 시 세션은 HttpOnly 쿠키로 유지하며, 로그인 시도에 `express-rate-limit` 기반 rate limit 을 건다. 1.0 의 로그인 소스를 옮겨 온 파일을 두지 않는다. rate limit 의 적용 단위는 소스 IP 이며 인스턴스 전역 카운터를 쓰지 않는다.

#### Rationale

R57 개정(2026-08-19)이 근거다 — 1.0 과 같은 기술 선택을 쓰되 구현은 신규 작성한다. 초판 "로그인 기반을 그대로 이식한다" 는 `R21` 개정(코드가 아니라 기능을 물려받는다)과 정면으로 어긋났고, 바뀌는 것은 경로이지 값이 아니어서 세 기술 선택은 그대로 유지한다. rate limit 의 적용 단위는 설치 마법사 교차 검증(`G13` 종결)에서 R72-i 로 보충됐다 — 전역 카운터를 쓰면 익명 요청 몇 번으로 설치 자체를 봉쇄할 수 있어 완화책이 그대로 DoS 경로가 된다. 독립 심의 둘이 각자 같은 지적을 냈다. 기각된 대안 — 전역 카운터.

#### Acceptance Criteria

- [ ] AC-1: 비밀번호는 bcrypt 해시로 저장되고, 로그인 검증은 평문이 아니라 그 해시와 대조해 수행된다.
- [ ] AC-2: 로그인에 성공하면 세션 쿠키가 `HttpOnly` 속성으로 발급된다.
- [ ] AC-3: 로그인 시도가 rate limit 임계값을 넘으면 그 시도는 거부된다.
- [ ] AC-4: rate limit 카운터는 소스 IP 별로 유지되며, 한 소스 IP 의 시도 누적이 다른 소스 IP 의 시도를 제한하지 않는다.
- [ ] AC-5: 인스턴스 전역 단일 rate limit 카운터를 두지 않는다.
- [ ] AC-6: 소스 IP 는 서버가 프록시 홉 수를 선언한 때만 전달 헤더에서 읽으며, 선언하지 않은 배포는 그 헤더를 신뢰하지 않는다.

#### Implementation Notes

- 원장 §4 Phase 1 수용 기준 13개 중 어느 것도 로그인 자체를 시험하지 않는다. 원장 §4 가 〔판정 필요 · 2026-08-19〕로 그 사실을 스스로 적고 *"로그인(R57·R60·R60-b) · 로그아웃(R145) · 비밀번호 변경(R144) 중 어느 것도 13개에 없다. 그대로면 로그인할 수 없는 빌드도 이 관문을 통과한다"* 고 판정을 열어 두었다. ① 기준을 추가할지 ② 추가하지 않을 사유를 남길지는 다음 원장 개정의 판정 사항이며, 이 요구사항이 대신 정하지 않는다.
- 
- 설치 마법사의 설치 토큰 재입력 시도도 이 rate limit 이 맡는다(R72-f).
- 
- 로그인 세션의 수명·만료 규정은 원장에 없다 — `만료` 를 정한 조항은 ACL(R110) · 설치 토큰(R72-c) · PAT(R58-a) 뿐인데 화면 설계(`03` §6.7 · `04` EC4)는 세션 만료의 존재를 전제한다. 이 축은 `G33` 을 닫을 때 함께 정해야 한다.
- [2026-08-19] 원장 `R57` 개정으로 이 조항의 제목·문면·Rationale 을 고쳤다. 초판은 "1.0 의 기반을 그대로 이식한다" 였고 `CON-ARCH-002` AC-2("1.0 의 백엔드 소스를 옮겨 온 파일이 존재하지 않는다")와 정면으로 부딪혔다. 개정이 바꾼 것은 「어떻게 얻는가」이지 「무엇을 쓰는가」가 아니다 — bcrypt · HttpOnly 세션 쿠키 · `express-rate-limit` 라는 기술 선택은 그대로 유지되므로 AC-1~AC-5 는 손대지 않았다.

#### Requirement

인증 전(pre-auth) 화면 — 로그인 · 가입 신청 폼(R7-①②) · 설치 마법사(R72) — 은 R23 의 설정 모달 구조를 따르지 않고 전체 화면으로 구성한다.

#### Rationale

독립 심의 5인 만장일치. R23 의 주어는 `설정 화면`, R24 의 주어는 `관리 기능`이라 어느 쪽도 인증 전 화면을 지배하지 않는다. 더 결정적인 것은 R24-a 가 모달 진입점을 좌하단 기어로 못박았고 그 기어는 셸에 속한다는 점(`03` §2.5)이다 — 인증 전에는 셸이 없으므로 R23 의 구조는 적용해서는 안 되는 것이 아니라 충족할 수 없다. 원장은 이미 같은 판정을 실행했다: R72 설치 마법사는 인증 전 전체 화면인데(`04` §4.1 — *"모달이 아니라 전체 화면이다. 이 시점에는 로그인한 사용자도, 뒤에 깔릴 앱 화면도 존재하지 않는다"*) R23 위반으로 제기된 적이 없다. 이 조항은 예외를 만드는 것이 아니라 이미 내려진 판정을 명시화한다. 원장 R143 자체는 2026-08-19 신설이다. 기각된 대안 — 인증 전 화면에도 R23 모달 구조를 적용하는 것.

#### Acceptance Criteria

- [ ] AC-1: 로그인 화면은 모달이 아니라 전체 화면으로 표시된다.
- [ ] AC-2: 가입 신청 폼은 모달이 아니라 전체 화면으로 표시된다.
- [ ] AC-3: 설치 마법사는 모달이 아니라 전체 화면으로 표시된다.
- [ ] AC-4: 인증 전 화면 뒤에 앱 셸(3분할 레이아웃)이 깔리지 않는다.
- [ ] AC-5: 인증 전 화면에서는 설정 모달 진입점인 좌하단 기어가 노출되지 않는다.

#### Requirement

#### Acceptance Criteria

- [ ] AC-4: 스코프 선택은 사용자의 유효 권한을 넘어서는 권한을 어느 경우에도 부여하지 않는다.

| Field | Value |

#### Requirement

설치 마법사가 완료되기 전에 응답하는 경로는 `설치 화면` · `그 정적 자산` · `토큰 검증` · `설치 커밋` 넷으로 한정한 허용목록이며, 그 밖의 모든 경로는 차단한다. 일반 가입·로그인·API·MCP 경로도 전부 차단 대상이다.

#### Rationale

R72-a 는 문면이 열거(차단 목록)인데 근거 칸은 기준(*"설치 화면 외의 표면이 존재하지 않아야 한다"*)을 말한다 — R84 가 R137 로 고쳐진 것과 정확히 같은 형태다. 열거로 두면 목록에 없는 경로(헬스체크·메트릭·정적 서빙·나중에 추가될 것)가 fail-open 이 되고, 구현자가 마법사 자신의 POST 를 예외 처리하며 임기응변으로 구멍을 뚫는다. 그래서 R72-h 가 열거를 허용목록으로 바꿨다(`G13` 종결 · 독립 심의 2인). 기각된 대안 — 차단 목록(deny list) 형태를 유지하는 것.

#### Acceptance Criteria

- [ ] AC-1: 설치 완료 전에는 `설치 화면` · `그 정적 자산` · `토큰 검증` · `설치 커밋` 네 경로만 응답한다.
- [ ] AC-2: 설치 완료 전에 일반 가입 경로로 보낸 요청은 차단된다.
- [ ] AC-3: 설치 완료 전에 로그인 경로로 보낸 요청은 차단된다.
- [ ] AC-4: 설치 완료 전에 API 경로로 보낸 요청은 차단된다.
- [ ] AC-5: 설치 완료 전에 MCP 경로로 보낸 요청은 차단된다.
- [ ] AC-6: 허용목록에 없는 경로는 헬스체크·메트릭·정적 서빙처럼 나중에 추가된 것이라도 기본이 차단이다.

### SEC-AUTH-012 — 설치 마법사는 콘솔에 출력된 설치 토큰을 요구하고 토큰은 설치 완료 시 소진된다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | implemented |
| Priority | medium |
| Tags | install-token, install-wizard, bootstrap |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정·설치 화면 설계](./04.screen-design-settings.md) |

#### Requirement

설치 마법사는 서버 콘솔에 출력된 1회용 설치 토큰을 요구한다. `1회용` 은 설치를 성공적으로 완료하면 소진된다는 뜻이고, 소진 시점은 최초 슈퍼유저를 만드는 트랜잭션이 커밋되는 순간이며, 그 전까지는 실패·중단과 무관하게 같은 토큰을 재입력할 수 있다.

#### Rationale

사내망에서 먼저 접속한 사람이 인스턴스를 선점하는 경로를 차단한다 — 서버 콘솔에 접근할 수 있는 운영자만 설치를 완료할 수 있다(R72-b). 소진 시점을 커밋으로 못박은 이유는 "한 번 입력하면 소진"으로 읽으면 오타 한 번이 인스턴스를 잠그기 때문이다(R72-f) — 복구는 재기동뿐인데 그 사실을 아는 사람이 없을 수 있다. 반복 시도는 R57 rate limit 이 맡는다. `G21` 종결이며 독립 심의 2인이 다섯 항 전부에서 일치했다. 기각된 대안 — `1회용` 을 "입력 시 소진"으로 해석하는 것.

#### Acceptance Criteria

- [ ] AC-1: 서버가 기동하면 설치 토큰이 서버 콘솔에 출력된다.
- [ ] AC-2: 올바른 설치 토큰 없이는 설치를 진행할 수 없다.
- [ ] AC-3: 토큰을 잘못 입력해도 같은 토큰을 다시 입력해 진행할 수 있다.
- [ ] AC-4: 설치가 중단됐다가 재개되어도 같은 토큰을 다시 입력해 진행할 수 있다.
- [ ] AC-5: 최초 슈퍼유저를 만드는 트랜잭션이 커밋되는 순간 그 토큰이 소진된다.
- [ ] AC-6: 소진된 토큰으로는 더 이상 설치를 진행할 수 없다.

#### Requirement

#### Acceptance Criteria

- [ ] AC-3: 토큰과 함께 만료 시각이 상대 시간이 아니라 절대시각으로 콘솔에 출력된다.

### SEC-AUTH-015 — 설치 마법사의 모든 서버 요청은 토큰 검증으로 발급된 설치 세션을 요구한다

#### Requirement

설치 토큰 검증에 성공하면 설치 세션을 발급하고, 그 이후 설치 마법사의 모든 서버 요청은 유효한 설치 세션을 요구한다. 토큰을 진입 시점에만 검사하지 않는다.

#### Rationale

심의가 찾은 치명 결함이다. `04` §4.2~§4.8 이 단계 전환을 클라이언트 상태로만 그려, 그대로 구현하면 `[설치 완료]` 엔드포인트가 토큰 없이 호출된다 — 사내망 누구나 1단계를 건너뛰고 자기 계정을 최초 슈퍼유저로 만들 수 있고 R72-b 전체가 장식이 된다. R72-b 의 근거 칸이 이미 *"설치를 **완료**할 수 있다"* 로 완료를 지목했으므로 이는 의도 변경이 아니라 문면이 빠뜨린 것의 보충이다. 기각된 대안 — 토큰을 진입 시점에만 검사하고 이후 단계는 클라이언트 상태로 잇는 것.

#### Acceptance Criteria

- [ ] AC-1: 설치 토큰 검증에 성공하면 설치 세션이 발급된다.
- [ ] AC-2: 토큰 검증 이후의 모든 설치 마법사 서버 요청은 유효한 설치 세션을 요구한다.
- [ ] AC-3: 설치 세션 없이 설치 커밋 엔드포인트를 호출하면 거부된다.
- [ ] AC-4: 클라이언트가 단계 전환 상태를 조작해도 설치 세션 없이는 다음 단계의 서버 요청이 성립하지 않는다.

- [ ] AC-6: 주체 ACL 일괄 회수(R43-1)는 슈퍼유저 그룹 멤버십을 바꾸지 않으므로 이 가드에 걸리지 않는다.

#### Requirement

1.0 계정은 전원 `active` 상태와 `default` 그룹 소속으로 이행하며 bcrypt 해시를 그대로 쓴다. 1.0 전역 API Key 클라이언트에는 유예 없이 PAT 재발급을 안내한다.

#### Rationale

감사 H19 해소의 계정·자격증명 축이다. R57 이 bcrypt 를 기술 선택으로 유지하고, bcrypt 해시의 호환은 코드 이식의 귀결이 아니라 데이터 형식의 성질이므로 신규 구현에서도 1.0 해시를 그대로 검증할 수 있다 — 그래서 사용자가 비밀번호를 다시 만들지 않아도 된다. 전역 API Key 는 R58 이 폐기했으므로 유예 기간을 두지 않는다. 기각된 대안 — 전역 API Key 를 한동안 병행 인정하는 것.

#### Acceptance Criteria

- [x] AC-1: 1.0 계정은 이행 뒤 전원 `active` 상태다.
- [x] AC-2: 1.0 계정은 이행 뒤 전원 `default` 그룹의 멤버다.
- [x] AC-3: 1.0 의 bcrypt 비밀번호 해시가 그대로 유효해 사용자가 기존 비밀번호로 로그인할 수 있다.
- [x] AC-4: 이행 뒤 1.0 전역 API Key 로는 어떤 요청도 성립하지 않는다.
- [x] AC-5: 전역 API Key 클라이언트에 유예 기간 없이 PAT 재발급 안내가 제공된다.

#### Requirement

사용자는 설정 모달 개인 구역의 `계정` 카테고리에서 자기 비밀번호를 변경할 수 있다. 비밀번호 변경은 본인만 할 수 있다.

#### Requirement

사용자는 설정 모달 개인 구역의 `계정` 카테고리에서 자기 세션을 종료할 수 있다(로그아웃).

#### Rationale

심의 5인 만장일치이며 소재는 4:1(소수 의견은 셸 크롬)이었다. R57 이 HttpOnly 세션 쿠키를 못박은 이상 세션은 실재하고, 만들 수 있는데 끝낼 수 없는 것은 설계 선택이 아니라 누락이다. `03` §6.7 과 `04` EC4 는 이미 세션에 끝이 있음을 전제하며 빠진 것은 사용자 주도 종료뿐이다. 형식은 R58-d 의 비고(*"R60 게이트가 토큰 인증에도 걸린다는 것의 명시화"*)와 같다 — 도출 가능한 귀결의 명시화다. 기각된 대안 — 소재를 셸 크롬에 두는 것.

#### Acceptance Criteria

- [ ] AC-1: 사용자는 설정 모달 개인 구역의 `계정` 카테고리에서 로그아웃할 수 있다.
- [ ] AC-2: 로그아웃하면 그 브라우저의 인증된 상태가 해제된다.
- [ ] AC-3: 로그아웃 뒤 보호된 화면에 접근하면 로그인 화면으로 유도된다.
- [ ] AC-4: 로그아웃 조작은 다른 사용자의 세션에 영향을 주지 않는다.

#### Implementation Notes

- `blocked` 인 이유 — 로그아웃이 쿠키만 지우는지 서버 측 세션을 무효화하는지가 `G33` ③ 미결이다. 후자여야 R59 의 즉시성이 로그아웃에도 성립한다. 원장은 화면은 이 공백과 무관하게 그릴 수 있고 갈리는 것은 확인 문구와 사후 상태라고 적었다.
- 다른 기기의 세션을 함께 끊는지는 `G33` ② 이며 이 요구사항이 정하지 않는다.
- 로그인 세션의 수명·만료 규정 자체가 원장에 없다 — `만료` 를 정한 조항은 ACL(R110) · 설치 토큰(R72-c) · PAT(R58-a) 뿐인데 `03` §6.7 과 `04` EC4 는 세션 만료의 존재를 전제한다. `G33` 을 닫을 때 함께 정하지 않으면 "만료는 있는데 규정이 없는" 상태가 남는다.
- 원장 §4 Phase 1 수용 기준 13개에 로그아웃이 없다 — §4 의 〔판정 필요 · 2026-08-19〕가 R145 를 명시로 열거했다.
