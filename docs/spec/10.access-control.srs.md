# Access Control

| Field | Value |
|---|---|
| Document Type | scope_srs |
| Scope | ACL |
| Scope Name | Access Control |

## 1. Scope Overview

이 scope 는 제품의 차별점 자체를 규정한다 — 문서와 디렉토리 단위의 접근 제어. 무엇에 권한을 걸 수 있는가, 어떤 부여가 있는가, 권한이 어떻게 전파되고(상속·가산) 어떻게 좁혀지며(상속 끊기), 권한이 없는 것을 사용자에게 어떻게 보이지 않게 하는가, 어떤 조작이 어떤 레벨을 요구하는가, 그리고 관리자가 그 상태를 관측할 화면들이 여기 모인다.

이 scope 는 **판정**을 소유한다. 그 판정 결과를 화면에 어떻게 그리는지는 `SHELL`·`EDITOR` scope 가, 판정 대상인 주체는 `PRINCIPAL` scope 가, 판정 뒤 실행에 붙는 마찰은 `CONFIRM` scope 가 갖는다.

## 2. Scope Boundaries

### In Scope

- ACL 의 대상과 부여 종류 — 문서와 디렉토리 둘 다, 노드마다 지정할 수 있는 부여 네 종류, 편집이 보기를 포함한다는 단조 구조 (`SEC-ACL-001`·`DR-ACL-001`·`SEC-ACL-002`)
- 판정 모델 — 상속과 가산으로만 넓히고 좁히기는 상속 끊기뿐, 거부 규칙 없음, 비정규화 없이 요청마다 계산, 부여에 적용 범위 선택지 없음 (`SEC-ACL-003`·`CON-ACL-002`·`CON-ACL-001`·`CON-ACL-003`)
- 완전 숨김 — 권한 없는 노드의 트리 숨김, 접근 가능한 자손을 가진 조상의 이름만 표시와 그 pass-through 미저장, 응답을 존재하지 않는 노드와 구별 불가능하게 하는 규칙, 보이지 않는 동명 노드와의 충돌 처리 (`SEC-ACL-004`·`SEC-ACL-005`·`CON-ACL-004`·`SEC-ACL-006`·`SEC-ACL-007`)
- 상방 게이트 — 슈퍼유저와 워크스페이스 관리 레벨의 ACL 우회, 그 열람의 감사 기록 대상 여부 (`SEC-ACL-008`·`OBS-ACL-001`)
- 부여 권능의 비대칭 — 넓히기와 좁히기의 필요 레벨, 편집자가 부여한 편집 권한의 재부여, 노드 생성자에 대한 자동 편집 권한 (`SEC-ACL-009`·`SEC-ACL-010`·`SEC-ACL-011`)
- 파일 조작별 필요 권한 표와 그 예외 — 숨은 하위가 있는 디렉토리의 이동·삭제 (`SEC-ACL-012`·`SEC-ACL-013`)
- 워크스페이스 경계 — 경계를 넘는 이동의 차단과 복사만의 허용, 복사본의 ACL·첨부·링크 처리 (`SEC-ACL-014`·`FR-ACL-001`)
- 접근자 지표 — 두 지표의 분리, 명단과 수치의 권한 차등, 복사 프리뷰의 목적지 기준 판정 (`IR-ACL-001`·`SEC-ACL-015`·`FR-ACL-002`)
- 권한 감사 부속 화면 — 주체 단위 일괄 회수, 유효 권한 시뮬레이션, 상속 끊김 노드 목록과 상속으로 되돌리기, 공유 모달의 상속 항목 표시, 이동 프리뷰, 권한 지정 UI 의 구성 (`FR-ACL-003`·`FR-ACL-004`·`FR-ACL-005`·`IR-ACL-002`·`FR-ACL-006`·`IR-ACL-003`)
- 권한 요청 워크플로의 Phase 2 이관과, 존재가 구별되지 않는 표면에는 Phase 2 에서도 요청 버튼을 두지 않는다는 규칙 (`CON-ACL-005`·`SEC-ACL-016`)

### Out of Scope

- 확인 등급 — 이 scope 가 정의하는 조작(부여·회수·이동·복사·상속 끊기·상속으로 되돌리기)에 붙는 등급과 타이핑 토큰은 `CONFIRM` scope 가 소유한다. 이 scope 는 조작의 정의와 필요 권한만 정한다 (`SEC-ACL-009`·`SEC-ACL-012`·`FR-ACL-001`·`FR-ACL-002`·`FR-ACL-003`·`FR-ACL-005`·`FR-ACL-006` Implementation Notes).
- 부모 권한 가져오기(R135) — 넓히기이면서 관리 전용인 예외이며 `CONFIRM` scope 가 소유한다. `SEC-ACL-003`·`SEC-ACL-009` 는 그 버튼이 상속 끊기와 분리된 별도 조작이라는 사실만 갖는다 (`SEC-ACL-003`·`SEC-ACL-009` Implementation Notes).
- 접근자 인원 수에 시점을 표기하지 않는 규칙, 그리고 컨테이너 부여의 적용 하위 노드 수 지표 — `CONFIRM` scope 가 소유한다. `IR-ACL-001` 은 접근자 지표 두 개의 정의만 갖는다 (`IR-ACL-001` Implementation Notes).
- 주체 다건 일괄 회수를 허용하는가 — `CONFIRM` scope 가 소유한다. 일괄 회수의 대상에 시스템 그룹이 포함되는가와 오프보딩 흐름에서 이 화면으로 진입하는 방식은 `PRINCIPAL` scope 가 소유한다. `FR-ACL-003` 은 화면과 영향 범위 표만 갖는다 (`FR-ACL-003` Implementation Notes).
- 주체 검색의 구체 규칙 — 최소 질의 길이·결과 상한·계정 상태 노출 범위·중립어 배지, 그리고 주체를 고르는 모든 화면을 단일 공용 컴포넌트로 구현한다는 제약은 `PRINCIPAL` scope 가 소유한다. `IR-ACL-003` 은 그 컴포넌트를 쓰는 쪽의 계약만 고정한다 (`IR-ACL-003` Implementation Notes).
- 감사 로그의 스키마·행위자 값·보존 기간, 경계를 넘는 복사의 감사 기록 형식, 회수 다건의 감사 입도 — `AUDIT` scope 가 소유한다. `OBS-ACL-001`·`SEC-ACL-014` 는 기록 대상과 기록 여부만 고정한다 (`OBS-ACL-001`·`SEC-ACL-014`·`FR-ACL-003` Implementation Notes).
- 이름 충돌 처리를 가시 여부와 무관하게 통일하는 규칙, 자동 접미사의 안내 문구, 덮어쓰기를 별도 경로로만 제공한다는 결정 — `SHELL` scope 가 소유한다. `SEC-ACL-007` 은 보이지 않는 동명 노드가 그 규칙의 대상이 된다는 사실만 갖는다 (`SEC-ACL-007` Implementation Notes).
- 디렉토리 복사에서 무엇이 복사되는가(요청자에게 보이는 노드만)와 복사 항목 수 토스트 — `SHELL` scope 가 소유한다 (`FR-ACL-001` Implementation Notes).
- 첨부의 저장 구조와 소유 판정 — `ATTACH` scope 가 소유한다. `FR-ACL-001` 은 복사 시 첨부가 어떻게 처리되는가의 결과만 정한다 (`FR-ACL-001` Implementation Notes).
- 워크스페이스가 상속 체인의 루트라는 규정과 `관리` 레벨을 워크스페이스에만 부여한다는 규정 — `WORKSPACE` scope 가 소유한다. 이 scope 의 상속·상방 게이트 요구가 그 위에서 성립한다.
- 트리 컨텍스트 메뉴의 항목 노출과 활성/비활성 표시 — `SHELL` scope 가 소유한다. `SEC-ACL-012` 의 권한 표가 그 판정의 정본이지만 메뉴 표면 자체는 이 scope 가 갖지 않는다.
- ACL 항목에 만료일을 두지 않는다는 결정(R110) — `PRINCIPAL` scope 가 소유한다. 이 scope 의 판정 모델이 시간 축 부재를 전제로 단조·가환이 된다.
- 관리자로부터 워크스페이스 안의 문서를 숨기는 수단 — 제품이 제공하지 않는다. 관리자에게도 숨겨야 하는 문서는 워크스페이스 분리로 대응하며, 워크스페이스 자체는 `WORKSPACE` scope 가 소유한다 (`SEC-ACL-008` Implementation Notes).
- 넓히기를 모아 보는 화면 — 존재하지 않는다. 열린 공백 `G15` 이며 아직 어느 scope 도 소유하지 않는다. `FR-ACL-005` 의 목록은 좁히기만 나열한다 (`FR-ACL-005` Implementation Notes).
- 자동 접미사의 구체 형식과 번호 증가 방식, 그리고 응답 시간 동일성의 정량 임계 — 원장이 정하지 않았고 어느 scope 도 소유하지 않는다. `SEC-ACL-006` 의 AC 는 구조(단일 코드 경로)로만 판정하며 통계적 타이밍 측정 기준은 미결이다.

## 3. Assumptions and Constraints

- ACL 메타데이터는 SQLite 단일 저장소에 있다 — `STORAGE` scope 가 소유하는 전제다.
- 유효 권한을 저장하지 않고 요청마다 계산한다 (`CON-ACL-001`). 이 scope 의 다른 요구들이 "매 요청 판정" 을 전제하므로, 캐시를 도입하면 그 전제가 함께 깨진다.
- 판정 구조가 단조·가환이다 — 거부 규칙이 없고(`CON-ACL-002`) ACL 에 시간 축이 없기(`PRINCIPAL` scope) 때문이다. 둘 중 하나라도 뒤집히면 이 scope 의 여러 요구가 함께 흔들린다.
- 워크스페이스가 권한 경계이자 상속 체인의 루트다 — `WORKSPACE` scope 가 소유하는 전제이며, 경계를 넘는 이동을 차단하는 근거가 그것이다.
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가 소유한다.
- 이 scope 에 걸린 미결 — `G15`(넓히기를 모아 보는 화면의 부재) · `G16`(`편집` 사용자에게 부여 결과를 관측할 수단이 전무하다 — 시뮬레이션·상속 끊김 목록·접근자 명단이 전부 `관리` 전용이다) · `G27`(감사 로그 보존 기간과 휴지통 보존 기간의 대소 관계). `G27` 은 상방 게이트 열람 기록의 조회 가능 기간을 미확정으로 남기며, 오프보딩 조사가 수개월 뒤 시작되므로 실무상 문제가 된다. 등재의 정본은 `00.index.md` §9 의 `Impact` 열이며, 그 열이 바뀌면 이 목록도 함께 훑는다.
- 이 scope 의 요구 다수에서 Priority 값은 원장이 배정한 것이 아니라 도구 기본값이다. 원장 §4 수용 기준 4 가 부속 5종을 지목한 자리만 근거를 가진다.

#### Requirement

시스템은 문서 노드와 디렉토리 노드 모두를 ACL 부여 대상으로 삼아야 한다. 어느 한쪽만 권한을 가질 수 있는 구조를 두지 않는다.

#### Rationale

제품 정의가 옵시디언 대비 차별점을 "문서/디렉토리 단위 권한 관리" 하나로 요약하므로, 두 노드 종류가 모두 부여 대상이라는 것이 이 제품의 존재 이유에 해당한다. 디렉토리 부여는 상속의 출발점이 되고 문서 부여는 상속을 쓰지 않고 좁게 여는 경로가 된다.

#### Acceptance Criteria

- [x] AC-1: 문서 노드에 ACL 항목을 부여할 수 있고 그 항목이 그 문서의 유효 권한 판정에 반영된다.
- [x] AC-2: 디렉토리 노드에 ACL 항목을 부여할 수 있고 그 항목이 그 디렉토리의 유효 권한 판정에 반영된다.
- [x] AC-3: 상위 디렉토리에 부여하지 않고 개별 문서에만 부여하는 경로가 존재한다.

#### Requirement

ACL 대상 노드마다 편집 사용자·보기 사용자·편집 그룹·보기 그룹 네 종류의 부여를 지정할 수 있다. ACL 항목은 주체 종류(사용자·그룹)와 레벨(편집·보기)의 조합으로 저장한다.

#### Rationale

주체 축(사용자·그룹)과 레벨 축(편집·보기)의 곱이 넷이므로 열거가 닫혀 있다. 다섯째 종류를 만들지 않는 것이 이후의 판정 규칙(합집합·단조성)을 단순하게 유지한다.

#### Acceptance Criteria

- [ ] AC-1: 노드 하나에 편집 사용자·보기 사용자·편집 그룹·보기 그룹 네 종류를 모두 지정할 수 있다.
- [ ] AC-2: ACL 항목 하나는 주체 종류 하나와 레벨 하나를 갖는다.
- [ ] AC-3: 사용자 부여와 그룹 부여가 같은 ACL 저장소에 같은 구조로 기록된다.
- [ ] AC-4: 노드 ACL 에는 관리 레벨 항목을 두지 않는다.

### SEC-ACL-003 — 권한은 상속과 가산으로만 넓히고 좁히기는 상속 끊기뿐이다

| Field | Value |
| --- | --- |
| Type | security |

| Status | implemented |
| Priority | high |
| Tags | acl, inheritance, permission-model |

| Stability | stable |

| Related Docs | [권한 화면 설계](./05.screen-design-permission.md), [폴더 권한 패널](./06.folder-permission-panel.md) |

#### Requirement

노드마다 상속 플래그를 두고 기본값은 상속 유지다. ACL 항목은 부여(가산)만 하며, 어떤 주체의 유효 권한을 조상보다 좁히는 유일한 수단은 그 노드의 상속을 명시적으로 끊는 것이다.

#### Rationale

Q2 확정(D안). 보안·운영 관점은 C안(상속 끊기 시 부모 ACL 자동 복사, SharePoint 방식)을 추천했으나 구현 관점이 뒤집었고 그 논거를 채택했다 — ① C 와 D 는 스키마와 성능이 완전히 동일하고 차이는 자동 복사 여부 하나뿐이며 D 는 C 의 상위집합이다 ② C 는 "이 문서만 한 명 더 보게 하기"라는 가장 흔한 조작에서 상속을 영구히 끊는데 D 는 그 조작이 순수 가산이라 부작용이 없다 ③ D 에서는 좁히는 것만이 명시적 행위이므로 "좁혔다고 착각하는" 상황이 원천 차단된다 — A안이 탈락한 이유가 정확히 그것이었다. 성능은 결정 근거가 아니었다 — A/B/C/D 모두 요청당 2쿼리와 O(N) 순회로 동일하다. 자동 복사를 하지 않는 것이 C안과의 유일한 차이이며, 그 수요는 별도 버튼으로 받는다.

#### Acceptance Criteria

- [ ] AC-1: 새로 만든 노드의 상속 플래그 기본값은 상속 유지다.
- [ ] AC-2: 상속 유지 상태인 노드의 유효 권한은 자신의 ACL 항목과 조상 노드들의 ACL 항목을 모두 합친 것이다.
- [ ] AC-3: ACL 항목을 추가하는 조작은 어떤 주체의 유효 권한도 줄이지 않는다.
- [ ] AC-4: 상속을 끊은 노드는 조상의 ACL 항목을 더 이상 받지 않고 자신의 항목만으로 판정된다.
- [ ] AC-5: 상속 끊기 전환 시 부모의 ACL 항목이 그 노드로 자동 복사되지 않는다.
- [ ] AC-6: 부모 권한 가져오기는 상속 끊기와 별개의 버튼으로만 실행된다.
- [ ] AC-7: 두 계정으로 같은 서브트리를 열었을 때 상속과 가산의 결과가 각자의 부여 내역대로 다르게 나타난다.

#### Requirement

사용자×노드 유효 권한 테이블을 비정규화해 저장하지 않는다. 유효 권한은 요청마다 계산한다.

#### Rationale

비정규화하면 수천 사용자 × 수천 노드 = 수백만 행이 되고 그룹 멤버 1명 추가에 전체 재계산이 필요하다. 매 요청 계산하면 캐시 무효화 문제 자체가 사라진다. 성능은 상속 모델(A/B/C/D)의 선택 근거가 아니었다 — 네 안 모두 요청당 2쿼리와 O(N) 순회로 동일했다. 여기서 N 은 요청자가 접근 가능한 전 워크스페이스의 노드 수이며(완전 숨김·다중 워크스페이스 병렬 표시의 조합), 이 비용 산정은 트리 지연 로딩을 전제로 성립한다(감사 L6 근거 보강).

#### Acceptance Criteria

- [ ] AC-1: 사용자와 노드의 조합에 대한 유효 권한 테이블이 저장소에 존재하지 않는다.
- [ ] AC-2: 그룹 멤버를 1명 추가하거나 제거한 뒤 별도의 재계산 작업 없이 다음 요청부터 새 유효 권한이 적용된다.
- [ ] AC-3: 권한 판정 결과를 무효화해야 하는 캐시가 존재하지 않는다.
- [ ] AC-4: 한 요청의 권한 판정이 쿼리 2회와 요청자가 접근 가능한 노드 수 N 에 대한 메모리 순회 O(N) 로 끝난다.
- [ ] AC-5: 트리는 지연 로딩으로 조회하며 한 요청이 접근 가능한 전 워크스페이스의 노드를 한꺼번에 적재하지 않는다.

ACL 에 거부(deny) 규칙을 두지 않는다. 유효 권한은 적용되는 허용 항목 전부의 합집합으로만 판정한다.

#### Rationale

#### Acceptance Criteria

- [x] AC-1: 유효 권한은 적용되는 모든 ACL 항목의 합집합이며 어떤 항목도 다른 항목의 권한을 깎지 않는다.
- [x] AC-2: 특정 주체를 특정 노드에서 배제하는 거부 항목을 저장할 수 없다.
- [x] AC-3: ACL 항목의 적용 순서를 바꿔도 유효 권한 결과가 같다.
- [x] AC-4: 계정 정지는 ACL 항목이 아니라 주체 레벨 비활성화 게이트로 처리된다 — 정지된 계정의 ACL 항목은 그대로 남는다.

### CON-ACL-003 — 부여에 적용 범위 선택지를 두지 않는다

| Field | Value |
| --- | --- |
| Type | constraint |
| Target | phase-1 |
| Status | in_progress |
| Priority | medium |
| Tags | acl, grant-scope |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [폴더 권한 패널](./06.folder-permission-panel.md) |

#### Requirement

권한 부여 화면에 "이 폴더에만 적용(하위 제외)" 류의 적용 범위 선택지를 두지 않는다. 비활성 상태로도 노출하지 않는다.

#### Rationale

"이 폴더에만"은 하위에 대한 거부이므로 거부 규칙 부재 원칙이 정면으로 금지한다. 두면 셋이 동시에 깨진다 — ① 넓히기·좁히기의 비대칭이 무너져 편집 사용자가 좁히기를 실행하는 경로가 열린다(상속 끊기를 관리 전용으로 묶어 막은 그 경로다) ② 상속 끊기의 부작용(권한을 잃은 편집자의 저장 거부로 인한 본문 유실)이 서브트리 규모로 증폭되어 한 번에 N 건이 된다 ③ 상속 끊김 노드 감사 목록이 오염된다 — 부여 1회로 상속 끊김 노드가 N 행 생성되어 그 목록의 목적이 자기 부정된다. 비활성 노출까지 막는 이유는 화면 설계가 두 번 확립한 것과 같다 — 있으면 "권한을 올리면 쓸 수 있는 기능"으로 읽혀 관리자에게 요청이 간다. 디렉토리 권한 패널 4:0. 타 제품 대비 — Windows ACL 은 ACE 에 상속 플래그를 달지만 이 제품은 노드에 플래그를 두므로 구조적으로 표현할 수 없고, SharePoint 방식은 상속 모델 심의에서 C안으로 명명해 이미 탈락시켰으며, 구글 드라이브는 채택된 D안과 같은 모델이라 애초에 이 옵션이 없다. 세 제품을 이미 비교해 하나를 골랐으므로 다시 열 사안이 아니다. "폴더 이름은 보이되 내용은 안 보이게"라는 실제 수요는 pass-through 노드가 기본 동작으로 이미 흡수한다 — 하위에만 권한을 주면 조상 폴더는 이름만 노출된다.

#### Acceptance Criteria

- [ ] AC-1: 권한 부여 UI 어느 화면에도 적용 범위를 고르는 선택지가 없다.
- [ ] AC-2: 그 선택지를 비활성·잠금 상태로도 화면에 렌더하지 않는다.
- [ ] AC-3: 하위를 제외하려는 수요에 대한 안내 문구가 제외·거부·차단 이라는 단어를 쓰지 않고 긍정형으로 쓰인다.
- [ ] AC-4: 그 안내는 세 경로를 가리킨다 — 하위 특정 노드에서 상속 끊기, 디렉토리 대신 개별 문서에 부여, 경계가 상시 필요하면 별도 워크스페이스로 분리.

#### Acceptance Criteria

- [x] AC-1: 요청자가 유효 권한을 갖지 않은 문서·디렉토리가 트리 응답에 포함되지 않는다.
- [x] AC-2: 숨긴 노드를 잠금 아이콘·비활성 항목·개수 표시 어느 형태로도 대신 나타내지 않는다.
- [x] AC-3: 트리의 모든 노드가 응답 전에 요청자 권한으로 판정된다.
- [x] AC-4: 유효 권한이 다른 두 계정으로 같은 워크스페이스를 열면 서로 다른 트리가 보인다.
- [x] AC-5: 이 규칙의 예외는 접근 가능한 자손을 가진 조상 디렉토리(pass-through) 하나뿐이다.

#### Requirement

완전 숨김의 유일한 예외로, 사용자가 접근 가능한 자손을 가진 조상 디렉토리는 이름만 트리에 표시한다. 이 노드를 pass-through 노드라 부른다.

#### Requirement

권한 없는 노드에 대한 모든 API·MCP 응답은 존재하지 않는 노드에 대한 응답과 구별할 수 없어야 한다. 404 로 통일하며 오류 메시지와 응답 시간도 동일하게 한다.

#### Acceptance Criteria

- [ ] AC-1: 권한 없는 노드를 지정한 API 요청이 404 를 반환한다.
- [ ] AC-2: 존재하지 않는 노드를 지정한 같은 요청도 404 를 반환하며 두 응답의 본문과 헤더가 동일하다.
- [ ] AC-3: 어느 응답에도 권한 부족을 뜻하는 문구나 코드가 들어가지 않으며 403 을 쓰지 않는다.
- [ ] AC-4: 두 경우의 응답이 같은 코드 경로로 생성된다 — 권한 판정 결과에 따라 조기 반환하거나 추가 조회를 수행하는 분기가 없다.
- [ ] AC-5: 같은 규칙이 MCP 도구 응답에도 적용된다.
- [ ] AC-6: 딥링크로 권한 없는 노드를 열면 화면이 존재하지 않는 노드와 같은 404 를 보여준다.

#### Acceptance Criteria

- [ ] AC-1: 생성·업로드 대상 이름이 요청자에게 보이지 않는 노드와 충돌하면 자동으로 접미사가 붙은 이름으로 생성된다.
- [ ] AC-2: 그 경우 이미 존재합니다 류의 오류나 기존 노드의 존재를 드러내는 안내를 표시하지 않는다.
- [ ] AC-3: 충돌한 기존 노드를 덮어쓰지 않고 그 내용이 그대로 남는다.
- [ ] AC-4: 충돌 상대가 보이는 경우와 보이지 않는 경우의 흐름과 안내 문구가 동일하다.
- [ ] AC-5: 깨진 위키링크 클릭으로 문서를 생성할 때도 같은 규칙이 적용된다.

#### Requirement

R137 기준 ③(상방 게이트로 판정을 우회해 접근)은 이 열람을 기록 대상으로 재도출하는 근거이지 대상을 좁히는 근거가 아니다 — R137-b 가 R84 의 기존 열거는 새 기준으로 전부 재도출된다고 못 박았다. 관리 레벨은 워크스페이스에만 부여되고(R36) 그 도달은 별도 ACL 항목 없이 성립하므로(SEC-ACL-008 AC-5) 관리자의 노드 열람은 상속 상태와 무관하게 게이트 경유다. 한정을 남기면 상속이 끊기지 않은 통상 경로 전체에서 이 기록이 무발화한다.

| Related Docs | [권한 화면 설계](./05.screen-design-permission.md), [폴더 권한 패널](./06.folder-permission-panel.md) |

#### Requirement

권한 부여 조작을 넓히기와 좁히기로 나누고 필요 레벨을 다르게 둔다. 넓히기는 편집 레벨이 실행할 수 있고, 좁히기(상속 끊기)와 관리 레벨 부여는 관리 레벨만 실행할 수 있다.

#### Rationale

감사 CRITICAL C14 해소. 상속·가산 모델이 세운 "가산이 기본, 좁히기는 명시적 행위"라는 비대칭을 부여 조작 자체에도 적용한다. 채택 근거는 모델 선택 논거를 지키는 데 있다 — 상속·가산(D안)을 고른 논거 2번이 "이 문서만 한 명 더 보게 하기"를 가장 흔한 조작이라고 못박았는데, 그 조작이 관리 레벨을 요구하면 일반 사용자에게 불가능해져 채택 근거 자체가 무너진다. 넓히기를 편집에 허용하면 그 논거가 성립하고, 좁히기를 관리로 묶으면 관리 경계는 워크스페이스 한 계층뿐이라는 취지도 유지된다. 좁히기를 관리에 유보하는 별도 이유는 lockout 차단이다 — 일반 사용자가 스스로를 가두는 경로를 막는다. 요약하면 편집자는 경계를 만들 수 없고 넓히기만 한다. 회수 범위를 부여자 기준으로 가르는 것은 부여자 기록이 있어야 성립한다.

#### Acceptance Criteria

- [x] AC-1: 노드에 보기·편집을 부여하는 넓히기는 그 노드에 편집 유효 권한을 가진 주체가 실행할 수 있다.
- [x] AC-2: 넓히기로 부여할 수 있는 레벨은 실행자 자신의 레벨 이하로 제한된다.
- [x] AC-3: 관리 레벨 부여는 관리 레벨 보유자만 실행할 수 있다.
- [x] AC-4: 상속 끊기 전환은 관리 레벨 보유자만 실행할 수 있다.
- [x] AC-5: 편집 보유자는 자신이 부여한 ACL 항목만 회수할 수 있고 관리 보유자는 전부 회수할 수 있다.
- [x] AC-6: ACL 항목에 부여자가 기록된다.

#### Requirement

#### Acceptance Criteria

- [x] AC-1: 편집 사용자가 부여한 편집 권한을 받은 주체가 같은 노드에서 다시 부여를 실행할 수 있다.
- [x] AC-2: 관리자가 준 편집과 편집자가 준 편집을 구별하는 별도 레벨을 두지 않는다.

### FR-ACL-001 — 복사본의 ACL 과 첨부와 링크 처리 규칙

| Field | Value |
| --- | --- |
| Type | functional |

#### Requirement

복사본에는 새 노드 ID 를 부여하고, ACL 은 대상 부모에서 상속하며, 생성자에게 편집권을 부여한다. 첨부는 대상 워크스페이스로 복제하되 본문은 재작성하지 않는다 — 첨부 링크가 워크스페이스 기준 절대경로이고 이름이 내용 해시라 같은 문자열이 대상 워크스페이스에서 그대로 해석된다. 문서 간 위키링크도 재작성하지 않는다.

#### Rationale

복사본과 원본이 각자의 첨부를 소유하므로 소유 문서 기준 첨부 권한 판정이 그대로 성립한다 — 첨부를 공유하면 한쪽의 권한 변경이 다른 쪽 문서의 첨부 접근을 흔든다. 복사본의 ACL 을 원본에서 가져오지 않고 대상 부모에서 상속하는 것이 상속·가산 모델과 일관되며, 그래서 복사가 경계를 넘어도 대상 워크스페이스의 권한 체계 안에 들어온다. 본문을 재작성하지 않는 이유는 재작성할 것이 없기 때문이다 — 첨부 링크는 `DR-ATTACH-003` 으로 워크스페이스 기준 절대경로이고 이름은 내용 해시라(`R50`) 같은 바이트를 대상 워크스페이스로 복제하면 같은 문자열이 그쪽 `.res/` 를 정확히 가리킨다. 문서 간 위키링크는 이름 기반 해석이고 경계를 넘으므로 역시 그대로 둔다.

#### Acceptance Criteria

- [ ] AC-1: 복사본에 새 노드 ID 가 부여된다.
- [ ] AC-2: 복사본의 ACL 은 대상 부모에서 상속하며 원본의 ACL 항목은 복사되지 않는다.
- [ ] AC-3: 복사를 실행한 사용자에게 복사본의 편집 권한이 부여된다.
- [ ] AC-4: 원본 문서의 첨부가 대상 워크스페이스의 첨부 저장소로 복제된다.
- [ ] AC-5: 복사본 본문의 첨부 링크가 대상 워크스페이스에서 그대로 해석된다 — 본문을 재작성하지 않는다.
- [ ] AC-6: 원본의 첨부는 그대로 남으며 원본과 복사본이 각자의 첨부를 소유한다.
- [ ] AC-7: 복사본의 문서 간 위키링크는 재작성되지 않고 원문 그대로 남는다.

### IR-ACL-001 — 접근자 지표를 접근 가능과 ACL 접근자 둘로 분리한다

| Field | Value |
| --- | --- |
| Type | interface |

| Stability | stable |
| Verification Method | test |

#### Requirement

접근자 인원 지표를 둘로 분리한다. 접근 가능 N명은 ACL·상속으로 도달하는 주체와 상방 게이트로 도달하는 주체의 합계이고, ACL 접근자 N명은 ACL·상속 경유 주체만 센다.

#### Rationale

지표가 하나면 고립 노드를 식별할 수 없다. 접근 가능 0명은 성립할 수 없다 — 슈퍼유저와 워크스페이스 관리자가 어떤 노드에도 도달하므로 총계가 0 이 되지 않는다. 그래서 "권한으로 도달할 수 있는 사람이 없는 노드"를 찾는 화면은 상방 게이트를 뺀 지표를 써야 의미를 갖는다. 고립 노드 문구에서 "아무도 볼 수 없습니다"를 쓰지 않는 이유는 그 목록을 보고 있는 요청자 자신이 반례라 거짓 진술이기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 접근 가능 수치는 ACL·상속으로 도달하는 주체와 상방 게이트로 도달하는 주체를 모두 포함한다.
- [ ] AC-2: ACL 접근자 수치는 상방 게이트로만 도달하는 주체를 제외한다.
- [ ] AC-3: 공유 모달과 이동·복사 프리뷰는 접근 가능 을 쓴다.
- [ ] AC-4: 상속 끊김 노드 감사 목록은 ACL 접근자 를 쓴다.
- [ ] AC-5: 어느 노드에서도 접근 가능 수치가 0 으로 표시되지 않는다.
- [ ] AC-6: ACL 접근자가 0 인 노드의 문구는 권한으로 접근할 수 있는 사람이 없으며 지금은 워크스페이스 관리자와 슈퍼유저만 볼 수 있다는 취지로 쓰이며 아무도 볼 수 없다고 쓰지 않는다.
- [ ] AC-7: 두 지표는 서로 다른 라벨로 표시되며 한 화면에서 섞여 하나의 수치로 제시되지 않는다.

#### Acceptance Criteria

주체(사용자 또는 그룹)를 지정해 그 주체 앞으로 부여된 ACL 항목 전량을 한 번에 회수하는 화면을 제공한다. 이 조작은 ACL 항목만 제거하며 그룹 멤버십과 계정 상태는 건드리지 않는다.

상속·가산 모델을 고르면서 함께 확정한 부속 기능 5종 중 하나다. 이 다섯이 없으면 상속·가산은 대안들보다 오히려 위험해진다는 것이 보안과 구현 두 관점의 공통 지적이었다. 이 기능이 없으면 오프보딩 대상자와 폐기 그룹의 부여가 상속 끊긴 노드에 잔존한다 — 상속 끊긴 노드는 부모 정책 변경으로 정리되지 않으므로 주체 축으로 훑는 수단이 따로 있어야 한다.

#### Acceptance Criteria

- [ ] AC-1: 주체 하나를 지정하면 그 주체 앞으로 부여된 모든 ACL 항목이 제거된다.
- [ ] AC-2: 회수 후에도 그 주체의 그룹 멤버십과 계정 상태가 변하지 않는다.
- [ ] AC-3: 상속이 끊긴 노드에 남아 있던 그 주체의 항목도 함께 제거된다.
- [ ] AC-4: 실행 전에 영향 범위를 워크스페이스·경로·레벨·부여자·부여 시각 열을 가진 표로 보여준다.
- [ ] AC-5: 회수 직후의 요청부터 그 주체의 유효 권한에서 제거된 항목이 반영된다.

#### Requirement

- [ ] AC-5: 상속으로 받은 권한과 직접 부여받은 권한을 구별해 보여준다.

### FR-ACL-005 — 상속 끊김 노드 감사 목록과 상속으로 되돌리기를 제공한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | in_progress |
| Priority | high |
| Tags | acl, inheritance, admin-screen |
| Risk | medium |
| Stability | stable |
| Verification Method | Playwright E2E |
| GitHub Issue | - |
| Related Docs | [권한 화면 설계](./05.screen-design-permission.md) |

#### Requirement

워크스페이스에서 상속이 끊긴 노드를 목록으로 조회하고 각 행에서 상속으로 되돌리는 화면을 제공한다.

#### Rationale

상속 끊긴 노드가 누적되면 부모 정책 변경의 실제 적용 범위를 사람이 예측할 수 없게 된다 — 상위 디렉토리에 부여해도 어디까지 내려가는지 아무도 모르는 상태가 된다. 이 목록이 그 누적을 관측하고 되돌리는 유일한 수단이다. 화면은 상방 게이트를 전제로만 성립한다 — 상속이 끊긴 노드는 정의상 관리자 자신의 ACL 로도 보이지 않을 수 있다. 이 목록이 ACL 접근자 지표를 쓰는 이유는 목적이 "권한으로 도달할 수 있는 사람이 없는 노드"를 찾는 것이라 상방 게이트를 빼야 지표가 의미를 갖기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스의 상속이 끊긴 노드를 목록으로 조회할 수 있다.
- [ ] AC-2: 목록의 각 행에서 상속으로 되돌리기를 실행할 수 있다.
- [ ] AC-3: 상속으로 되돌리면 그 노드가 다시 조상의 ACL 항목을 받는다.
- [ ] AC-4: 목록은 ACL 접근자 지표를 쓰고 접근 가능 을 쓰지 않는다.
- [ ] AC-5: ACL 접근자가 0 인 행은 고립 노드 문구를 따른다.
- [ ] AC-6: 목록은 요청한 관리자 자신의 ACL 로는 볼 수 없는 노드도 포함한다.
- [ ] AC-7: 목록은 관리 레벨 보유자에게만 제공된다.

### IR-ACL-002 — 공유 모달에 상속 항목을 출처 경로와 함께 읽기 전용으로 표시한다

| Field | Value |
| --- | --- |
| Type | interface |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | acl, inheritance, share-modal |
| Risk | medium |
| Stability | stable |
| Verification Method | Playwright E2E |
| GitHub Issue | - |
| Related Docs | [권한 화면 설계](./05.screen-design-permission.md), [폴더 권한 패널](./06.folder-permission-panel.md) |

#### Requirement

공유 모달은 그 노드에 직접 부여된 항목뿐 아니라 상속으로 적용되는 항목도 함께 표시하며, 상속 항목은 출처 경로와 함께 회색 읽기 전용으로 표시한다.

#### Rationale

이 표시가 없으면 관리자가 모달에 보이는 목록을 실효 권한으로 오해한다 — 상속·가산 모델에서 노드의 실제 접근자는 직접 항목과 조상 항목의 합집합이므로, 직접 항목만 보여주면 화면이 사실과 다른 그림을 준다. 읽기 전용으로 두는 이유는 상속 항목의 소유가 조상 노드에 있기 때문이다 — 여기서 지우면 조상을 바꾸는 것인지 이 노드에서만 빼는 것인지가 모호해지고, 후자는 거부 규칙이 되어 모델이 금지한다.

#### Acceptance Criteria

- [ ] AC-1: 공유 모달이 그 노드에 상속으로 적용되는 ACL 항목을 직접 항목과 함께 표시한다.
- [ ] AC-2: 상속 항목마다 그 항목이 부여된 조상 노드의 경로가 함께 표시된다.
- [ ] AC-3: 상속 항목은 읽기 전용으로 표시되어 그 자리에서 레벨을 바꾸거나 회수할 수 없다.
- [ ] AC-4: 직접 부여 항목과 상속 항목이 시각적으로 구별된다.
- [ ] AC-5: 상속 항목이 하나도 없는 노드에서도 모달의 구조가 같은 방식으로 렌더된다.

#### Requirement

파일이나 디렉토리를 이동하기 전에 이동 전후의 접근 가능 인원 수를 프리뷰로 표시한다. 인원 수만 표시하고 명단은 표시하지 않는다.

#### Rationale

이동으로 부모가 바뀌면 상속 결과가 달라지는데 사용자가 그 사실을 모른다 — 폴더를 정리했을 뿐인데 접근자가 늘거나 줄어 있는 것이 이 프리뷰가 없을 때 벌어지는 일이다. 명단을 제한하는 것은 감사 M19 의 지적이며, 그 제한을 이 화면에만 두지 않고 명단이 등장하는 전 표면으로 확장한 것이 별도 조항이다.

#### Acceptance Criteria

- [ ] AC-1: 이동 다이얼로그가 이동 전의 접근 가능 인원 수와 이동 후의 인원 수를 함께 보여준다.
- [ ] AC-2: 목적지를 바꾸면 이동 후 수치가 그 목적지 기준으로 갱신된다.
- [ ] AC-3: 프리뷰는 인원 수만 표시하고 명단을 표시하지 않는다.
- [ ] AC-4: 명단이 필요한 경우 관리 레벨 보유자는 시뮬레이션 화면으로 이동해 확인한다.
- [ ] AC-5: 지표명은 접근 가능 을 쓰며 접근 가능자 같은 다른 라벨을 쓰지 않는다.
- [ ] AC-6: 수치가 변하지 않는 이동에서도 프리뷰가 같은 형식으로 표시된다.

#### Requirement

노드 권한 지정 UX 는 구글 독스 방식을 따른다. 사용자와 그룹을 각각 검색해 찾아 추가하고, 추가된 주체마다 레벨을 지정한다.

#### Rationale

검색해서 추가하는 방식은 사용자에게 학습 비용이 없고, 전체 주체 목록을 화면에 펼치지 않으므로 디렉토리 열거 표면도 줄인다. 후자는 이후 원장이 주체 검색에 최소 질의 길이와 결과 상한을 두는 근거가 되었다.

#### Acceptance Criteria

- [ ] AC-1: 주체 지정은 전체 목록을 나열해 고르는 방식이 아니라 검색으로 찾아 추가하는 방식이다.
- [ ] AC-2: 사용자 검색과 그룹 검색이 각각 제공된다.
- [ ] AC-3: 추가된 주체마다 보기와 편집 중 하나를 지정한다.
- [ ] AC-4: 추가된 주체를 같은 화면에서 회수할 수 있다.
- [ ] AC-5: 같은 지정 방식을 문서와 디렉토리 양쪽에 쓴다.

### SEC-ACL-016 — 존재가 구별되지 않는 표면에는 권한 요청 버튼을 두지 않는다

#### Requirement

권한 없음과 존재하지 않음이 구별되지 않는 모든 표면에는 권한 요청 버튼을 두지 않는다. 이 제약은 Phase 2 에서 권한 요청 워크플로가 도입된 뒤에도 유지된다.

#### Rationale

버튼의 존재 자체가 그 자리에 대상이 있다는 사실을 드러낸다 — 404 를 통일해 응답에서 지운 1비트를 UI 가 되살리는 셈이다. 초판은 깨진 링크만 열거했으나 같은 논리가 404 통일 표면 전체에 적용되므로 열거를 열린 형태로 바꿨다.

#### Acceptance Criteria

- [ ] AC-1: 깨진 위키링크를 클릭했을 때 나타나는 화면에 권한 요청 버튼이 없다.
- [ ] AC-2: 딥링크 404 화면에 권한 요청 버튼이 없다.
- [ ] AC-3: 권한 없음과 존재하지 않음이 구별되지 않는 다른 표면에도 같은 규칙이 적용된다 — 위 둘은 예시이지 전량 열거가 아니다.
- [ ] AC-4: 요청 버튼을 대신하는 문의 링크·연락처 표시도 그 표면에 두지 않는다.
