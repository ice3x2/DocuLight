> **문서 규칙**
> 1. 본문의 모든 설계 항목은 근거 요구사항 ID 를 병기한다. ID 가 없는 항목은 **설계자 판단**이며 §9 에 등재한다.
> 2. 결정 로그에 없는 사실을 있다고 서술하지 않는다. 필요한데 없으면 §9 미결 질문으로 올린다.
> 3. 와이어프레임은 배치·정보 밀도를 나타내는 것이며 픽셀 단위 시안이 아니다. 한글은 2열 폭으로 계산했다.
> 4. **용어 규칙** — `관리자` 를 단독으로 쓰지 않고 항상 `워크스페이스 관리자` 또는 `슈퍼유저` 로 명시한다 (R117). 유일한 예외는 `관리자 없음` 배지다(R109-a — 워크스페이스 행에 붙어 문맥이 자명하다). `퇴사 처리` 대신 `오프보딩` 을 쓴다 (R101-b). 계정 상태 배지는 주체 검색 결과에서만 중립어 `비활성` 을 쓰고, 슈퍼유저 전용 사용자 관리 화면은 R60 의 4상태를 그대로 쓴다 (R112-d).
> 5. **확인 등급(L1·L2·L3)의 정의는 `05.screen-design-permission.md` §5 가 소유**하고 이 문서는 참조한다 (R115).
> 6. **한 사실은 한 곳에만 적는다** (R124). 같은 규칙이 여러 절에 필요하면 한 곳을 정본으로 두고 나머지는 참조한다. 이 문서의 정본 위치는 — **이 문서가 소유한 조작의** 확인 등급 배정 §5.3 · 주체 검색 규칙 §2.13 · 대용량 목록 전략 §3 · 상태 표현 §6 이다. **등급 체계 자체와 `05` 가 소유한 조작(워크스페이스 `관리` 부여 등)의 배정은 `05` §5.1 이 정본**이며 §5.3 은 그것을 **인용**한다 (`05` §0.1-a · R124). 요구사항을 개정할 때는 **그것을 인용하는 모든 자리(본문·와이어프레임·표·엣지 케이스)를 함께 훑는다** (R124-a).

**담당 범위 밖** — 메인 작업 화면(트리·에디터·사이드바), 공유 모달(R12), 권한 시뮬레이션(R43-2)·상속 끊김 노드 감사 목록(R43-3)·주체 일괄 회수(R43-1)의 **내부 화면**, 워크스페이스 아카이브/복원 상세(Phase 2, R92). 이 문서는 위 세 화면의 **카테고리 배치와 진입 방식**만 다룬다.

## 1. 모달 전체 구조

### 1.1 진입점과 셸

- 진입점은 **좌하단 기어 버튼 하나**다 (R24-a). 관리 기능을 위한 별도 진입 메뉴·별도 페이지는 만들지 않는다 (R24).
- 문서 단위 기능(공유 R12, 버전 기록 R61·R63-a)은 **이 모달에 없다.** 문서 헤더 메뉴에 있다 (R24-b).
- 구조는 **좌측 카테고리 리스트 + 우측 설정 패널** 2분할이다 (R23).

### 1.4 좌측 카테고리 리스트 — 구역 구분

구역은 **R24-a 표를 그대로** 따른다. 구역 헤더는 클릭 불가한 라벨이며, 구역 사이는 여백으로 구분한다(구분선을 긋지 않는다 — 옵시디언 설정 모달의 구역 표현과 동일한 관행).

| 구역 | 카테고리 | 표시 조건 | 근거 |
|---|---|---|---|
| 개인 | 에디터 · 외모 · 액세스 토큰 | 전원 (인증된 사용자) | R24-a |
| 개인 | **휴지통** | **접근 가능한 워크스페이스가 1개 이상** | **R100** (R24-a 개정) |
| 워크스페이스 관리 | 워크스페이스 · 권한 감사 · 감사 로그 | 요청자가 **`관리` 를 가진 워크스페이스가 1개 이상** | R24-a, R36, R37 |
| 인스턴스 | 사용자 관리 · 그룹 관리 · 가입 승인 · **전체 워크스페이스**(목록·생성) · 인스턴스 설정 | 슈퍼유저 그룹 소속 | R24-a 개정, R81 |

**휴지통이 개인 구역에 있는 이유 (R100)** — R74 는 삭제를 `편집` 에게 허용하는데 개정 전 R24-a 는 휴지통을 `관리` 전용 구역에 두어 **편집자가 자기 문서를 지우고도 복구할 수 없는** 상태였다. R100 이 표시 조건을 넓히고 데이터 범위만 R85 로 분기하도록 확정했다. 화면은 하나이므로 R24 의 단일 진입점 원칙은 유지된다.

**워크스페이스 스코프 선택기 (설계자 판단 — §9-Q2)**
R24-a 의 워크스페이스 관리 구역 카테고리는 전부 "어느 워크스페이스인가"를 필요로 하는데, 사용자는 여러 워크스페이스에서 `관리` 레벨을 가질 수 있다(R41 은 접근 가능한 워크스페이스를 병렬 표시한다). 따라서 **구역 헤더 아래에 워크스페이스 선택 드롭다운 하나**를 두고, 그 아래 3개 카테고리가 선택된 워크스페이스를 대상으로 동작한다. 휴지통은 이 구역을 떠났으므로 자체 워크스페이스 축을 갖는다(§2.4).

- 대안(워크스페이스마다 4개 카테고리 묶음을 반복)은 관리 대상이 5개만 되어도 좌측 리스트가 20행이 되어 폭발한다. 채택하지 않는다.
- 선택기 목록에는 **요청자가 `관리` 를 가진 워크스페이스만** 나열한다. 권한 없는 워크스페이스는 이름조차 나타나지 않는다 (R25).
- 관리 대상이 1개뿐이면 드롭다운을 **비활성 라벨**로 표시한다(선택지가 하나인 컨트롤은 조작 대상이 아니다).

### 1.5 권한에 따라 카테고리가 사라질 때의 처리

**원칙: 좌측 리스트는 클라이언트가 하드코딩 목록을 필터링해 만들지 않는다.** 서버가 요청자의 실시간 권한으로 표시 가능 카테고리 목록을 계산해 내려주고, 클라이언트는 그것을 렌더링만 한다. 근거 — R59 는 세션·토큰에 권한 스냅샷을 담지 않고 매 요청 principal 을 조회한다고 규정한다. 클라이언트 판정은 그 자체로 스냅샷이다.

| 상황 | 처리 |
|---|---|
| 구역의 모든 카테고리가 표시 불가 | **구역 헤더까지 함께 숨긴다.** 항목 없는 헤더를 남기지 않는다 |
| 개인 구역만 남음 | 좌측 리스트가 3항목이 된다. 이것이 일반 사용자의 정상 상태다 |
| 모달 사용 중 권한을 잃음 | 다음 API 응답에서 403/404 를 받으면 ① 카테고리 목록을 재조회하고 ② 현재 패널을 §6 `권한 없음` 상태로 교체한 뒤 ③ 사용자가 확인하면 폴백 카테고리로 이동한다. **말없이 화면을 바꾸지 않는다** |
| 현재 선택 카테고리가 사라짐 | 폴백 순서: 같은 구역의 첫 항목 → 없으면 개인 구역 첫 항목(에디터). 이동 시 인라인 안내를 1회 표시 |
| 워크스페이스 `관리` 를 잃음 | 선택기 목록 재조회 → 남은 첫 워크스페이스 선택 → 하나도 없으면 구역 전체 소멸 후 폴백 |
| 모달 사용 중 슈퍼유저 그룹에서 제외됨 | 인스턴스 구역 전체가 사라진다. 자기 자신을 제외한 경우는 §8-EC2 |

**응답 코드 규칙**
- **노드(문서·디렉토리·워크스페이스)를 대상으로 하는 응답은 404 로 통일한다** (R94). 워크스페이스 스코프 선택기가 권한 없는 워크스페이스를 나열하지 않는 것도 같은 이유다.
- 사용자·그룹·인스턴스 설정처럼 **노드가 아닌 관리 리소스**는 403 으로 구분해도 R94 위반이 아니다. R94 의 목적은 경로 열거 오라클 차단이고, 이들은 경로 공간을 이루지 않는다. (설계자 판단 — §9-Q3)

### 1.6 패널 내부 화면 전환 (중첩 금지)

권한 감사의 3개 하위 화면, **감사 로그의 `재조정 대기열`(§2.7-b)**, 사용자 상세, 그룹 상세 같은 2차 화면은 **모달 위에 모달을 띄우지 않고 우측 패널 안에서 전환**한다. **카테고리 라벨은 바꾸지 않고 브레드크럼으로 구분한다** — 2차 화면이 생겨도 §1.4 의 카테고리 구성은 그대로다(R24-a · R139-d).

```
┌─ 우측 패널 ────────────────────────────────────────────────┐
│ 그룹 관리  ›  기획팀                              [← 뒤로] │
│ ────────────────────────────────────────────────────────── │
│ (그룹 상세 본문)                                            │
```

근거 — 중첩 `Dialog` 는 포커스 트랩과 ESC 처리가 취약해 "ESC 한 번에 설정 전체가 닫히는" 오조작을 만든다. 파괴적 확인 다이얼로그(`AlertDialog`)만 예외로 모달 위에 겹친다. 이때 ESC 는 확인 다이얼로그만 닫는다.

- R58-d(계정이 `active` 가 아니면 전 토큰 즉시 무효)는 이 화면에서 조작할 수 없는 사실이다. 화면 하단에 안내 문구로만 고지한다.

**휴지통은 삭제 이력의 대체물이 아니다 (R137-a · R137-d)**

R137-a 의 판별자는 **`기간 한정 재현은 재현이 아니다`** 이며, 이 화면은 세 겹으로 재현에 실패한다 — ① **R85 로 편집자 A 가 지운 것을 편집자 B 는 못 본다** ② **R86 경과 후 이 목록의 행과 R78 사이드카가 함께 사라지고**, 남는 `영구 삭제` 기록의 행위자는 **`system:retention`**(R139-b · ~~`G26` ②~~ 종결)이라 **원 삭제자가 아니다** ③ **복구가 흔적을 지운다** — 삭제·복구 왕복 1회로 이 화면에서 흔적이 0 이 된다. 그래서 삭제·복구가 감사 로그에 **별도로** 남는다.

- **`영구 삭제` 의 행위자 — R86 자동 정리는 `system:retention` 이다**(**R139-b**). 사용자가 누른 영구 삭제는 그 사람이 행위자이고, **보존 기간 경과로 시스템이 지우는 것**(R86)은 **하위체계별 예약 주체**를 쓴다. ~~`G26` ②~~ 종결 — 등재 당시 *"R101 이 사용자 참조를 전제"* 라고 적었으나 **R101 문면은 계정 수명 주기만 규정**하므로 요구사항 충돌이 아니라 **값 미정**이었다. **주체를 세는 화면은 `is_system` 단일 판정으로 이들을 제외한다**(R139-b · §2.7-b).
- **감사 로그 보존이 휴지통 보존보다 짧으면 삭제 기록이 휴지통 행보다 먼저 사라진다.** R86 은 휴지통 기본 30일을 명시하는데 R84-a 에는 대응 문장이 없다 — 공백 **`G27`** → §9 · §2.12.

**워크스페이스 축 (R100-a)**
`.trash` 는 워크스페이스마다 존재하지만(R67) 휴지통이 개인 구역으로 이동해 워크스페이스 관리 구역의 스코프 선택기를 쓸 수 없다. 휴지통은 **접근 가능한 전 워크스페이스의 통합 목록**이며 `워크스페이스` 열과 필터를 제공한다. 권한은 워크스페이스마다 다를 수 있으므로 **범위 판정(R85)과 영구 삭제 가능 여부(R74)를 행마다 그 행의 워크스페이스 기준으로 적용**한다 — 요청자가 WS-A 에서 `관리`, WS-B 에서 `편집` 을 가졌다면 WS-A 는 전체 항목이, WS-B 는 본인 삭제분만 보인다.

**동작**

- **개명** — 표시 이름만 바꾼다. 물리 경로는 해시 ID 라 불변이며 첨부·백업·링크가 깨지지 않는다 (R40-a). 이름 권위는 DB 이고 `.workspace.json` 은 재구성용 사본이다 (R40-d) — 화면에서 후자를 직접 다루지 않는다.
- **워크스페이스 관리자 지정** — 사용자·그룹을 **각각 검색**해 추가한다. R12 의 구글 독스식 검색 패턴과 동일한 공용 컴포넌트 `PrincipalPicker` 를 쓰며(R112-e), 검색 규칙은 §2.13 을 따른다. 부여되는 레벨은 `관리` 고정이며, 이 조작 자체가 `관리` 를 요구한다 (R70-b).
- **`관리` 부여는 L2 확인을 거친다** (§5.3). **근거는 R125 — 대상이 컨테이너 노드(워크스페이스)이기 때문**이고, `워크스페이스 관리 부여 = L2` 는 **R125-b 가 R115-d 경로로 직접 지정**한다. 넓히기는 가역성 축에서 **비가역으로 취급**한다(R122 — ACL 을 지워도 이미 열람된 내용은 회수할 수 없다). **등급 체계의 정본은 `05` §5.1 이며 이 문서는 인용만 한다**(R124 · `05` §0.1-a).
  > **개정 전 이 자리에 무엇이 잘못 적혀 있었는가** — 근거를 **"`관리` 는 R71-a 로 전 문서 열람권을 주므로 대상 *노드 집합*이 불특정하다(R122-a)"** 로 적었다. 같은 조작에 대해 `05` 는 **"대상이 *그룹*(불특정 집합)"** 이라는 **주체 집합** 근거를 적고 있었다 — **두 문서가 같은 조항 R122-a 를 서로 다른 축으로 적용**한 상태였고, 그 배정은 **어느 규칙으로도 도출되지 않았다**(R122-a 만 보면 단건 주체라 L1, R115-a 만 보면 비가역+전역이라 L3). **R125·R125-b 가 두 축을 분리해 이 충돌을 종결**했다. **2026-08-14 — 충돌의 진짜 원인이 R122-a 의 문면 공백이었음이 확인되어 조항 문언이 `대상 집합` → `주체 집합` 으로 정정**되고 **"주체를 지목하지 않는 조작(복사 · 상속 되돌리기 · 부모 권한 가져오기)은 언제나 불특정 집합이다"** 가 추가됐다. R125 가 축을 나눈 뒤에도 조항 본문이 고쳐지지 않아 남아 있던 것이다 (§5.3 · R124-a).
- **컨테이너 노드에 대한 부여이므로 확인 다이얼로그에 두 가지가 함께 들어간다** — ① **`적용 하위 N개`**(**R126**: 요청자에게 보이는 하위 노드 중 이 부여가 상속으로 실제 도달하는 것의 수) ② **"여기서 부여한 권한이 하위 전체에 상속된다"** 는 고지와 **"상속이 끊긴 하위에는 적용되지 않습니다"**(**R127 · R127-a** — 끊긴 노드의 유무와 **무관하게 항상** 표시한다. 있을 때만 띄우면 문구의 등장이 숨은 노드의 존재를 알린다 → R113 위반).
  - **`적용 하위 N개` 는 존재 오라클이 아니다**(**R126-a**) — 부여가 도달하는 집합은 상속 체인이 이 노드에서 끊기지 않고 이어지는 노드 집합이고(R14), **포함 관계 `도달 노드 집합 ⊆ 요청자에게 이미 보이는 노드 집합` 이 요청자의 접근 경로 두 갈래 모두에서 성립한다**: ① **ACL·상속으로 접근 중**이면 그 `편집` 이 상속이 이어지는 하위로 함께 내려간다 — **이 단계는 R14-c(deny 부재)에 의존한다**(하방 예외가 있으면 상속이 이어져도 요청자가 차단될 수 있다) ② **R71 상방 게이트로 접근 중**(ACL 항목 없음)이면 ①의 논리는 성립하지 않으나 **R71-a 로 그 워크스페이스의 모든 노드에 도달**하므로 포함 관계가 더 강하게 성립한다. 도달 집합은 트리 구조로 정해져 **요청자와 무관**하므로 대조로 역산되지 않는다. R105-b(복사 항목 수)가 같은 논리의 선례다. **초판 논증이 ①만 다루고 ②와 R14-c 의존을 빠뜨려 2026-08-14 원장이 R126-a 를 보강했고, 이 절을 그에 맞춰 갱신했다**(R124-a). 정본 서술은 `05` §1.6 이다.
  - **분모(`24 / 30`)·"적용되지 않는 항목 N개"·하위 집계형 `접근 가능` 을 표시하지 않는다**(**R126-b**). 분모를 주는 순간 차액이 "안 보이는 서브트리의 크기"가 되어 R25·R80-a 위반이다. **`접근 가능`(R121)은 사람 수, `적용 하위 N개` 는 노드 수로 축이 달라 라벨을 공유하지 않는다**(**R126-c**).
  - 소재는 **확인 다이얼로그**이며 모달 본문 상시 표시가 아니다. **§5.2 공통 원칙 4(R116)의 재조회 대상에 포함**한다(**R126-d**) — 다이얼로그를 띄운 사이 하위에서 상속이 끊기면 값이 달라진다.
  - **도달하지 못하는 하위가 있어도 부여를 거부하지 않고, 도달 실패 노드를 개별 열거하지 않는다**(**R127-b**). 거부의 발생 자체가 "이 워크스페이스에 네가 볼 수 없는 무언가가 있다"를 알리고, 열거는 **false assurance** 가 된다. 이동·삭제의 R74-a 거부와 정반대인 이유는 **R74-a 의 실질 근거가 파괴성인데 부여는 아무것도 지우지 않기 때문**이다.
- **워크스페이스 관리자 제거** — 마지막 `관리` 권한자를 제거해도 **차단하지 않고 확인 다이얼로그로 경고**한다 (**R109**). 근거: R29 로 슈퍼유저가 항상 도달하므로 lockout 이 아니며, 차단하면 ① 오프보딩 흐름(R101-b)이 "후임 지정"에서 멈추고 ② 가드를 만족시키려 형식적 워크스페이스 관리자를 끼워 넣게 되는데 **그 계정이 R71-a 로 워크스페이스 전 문서 열람권을 갖는다.**
- **`관리자 없음` 배지** — `관리` 권한자가 0명인 워크스페이스는 **설정 모달의 워크스페이스 목록**(§2.11)**과 이 구역의 워크스페이스 스코프 선택기**에 배지를 **상시 노출**한다 (**R109-a**). 이 배지 문구는 R117 의 유일한 예외다 — 워크스페이스 행에 붙어 문맥이 자명하다. 이 상태가 조용히 누적되면 그 워크스페이스의 모든 ACL 요청이 슈퍼유저 큐로 몰린다.
- **좌측 트리에는 붙이지 않는다** (R109-a) — 트리는 탐색면이고 일반 사용자에게는 조치 수단이 없어 노이즈가 된다. 반대로 **선택기를 보는 사람은 그 워크스페이스의 `관리` 권한자**여서 이 제외 근거가 적용되지 않는다. 이것이 배지가 붙는 두 자리와 붙지 않는 한 자리를 가르는 기준이다.
- **아카이브/복원** — Phase 2 (R92). 버튼 자리만 두고 비활성 + 사유 배지를 표시한다. 근거: R92 는 "Phase 1 에는 워크스페이스를 없애는 수단이 없다"를 인지된 제약으로 명시한다. 자리를 지우면 이 제약이 화면에서 보이지 않게 된다.
- 워크스페이스 **삭제** 버튼은 두지 않는다. R54 가 삭제를 아카이브로 대체했고 아카이브는 Phase 2 다.

### 2.6 워크스페이스 관리 › 권한 감사 (진입점만)

R24-a 는 R43-1·R43-2·R43-3 을 **하나의 카테고리** 안에 묶었다. 따라서 좌측 리스트 항목은 1개이고, 우측 패널이 3개의 진입 카드를 보여준다. 각 화면의 내부 설계는 이 문서의 범위 밖이다.

```
┌─ 권한 감사 · 기술문서 ──────────────────────────────────────────────────┐
│  ! 이 구역의 조회는 감사 로그에 기록된다. (R71-b)                       │
│  ────────────────────────────────────────────────────────────────────── │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ 상속 끊김 노드 감사 목록                                         [ 열기 ] │    │
│  │ 상속이 끊긴 노드를 모아 보고 상속으로 되돌린다.  (R43-3)         │    │
│  ├─────────────────────────────────────────────────────────────────┤    │
│  │ 권한 시뮬레이션                                        [ 열기 ] │    │
│  │ 특정 사용자 관점의 유효 권한을 조회한다.         (R43-2)         │    │
│  ├─────────────────────────────────────────────────────────────────┤    │
│  │ 주체 일괄 회수                                         [ 열기 ] │    │
│  │ 사용자·그룹 하나에 부여된 ACL 항목을 전부 회수한다. (R43-1)      │    │
│  │ 슈퍼유저 그룹 회수는 R71 상방 게이트로 실효가 없다.(R119-a)      │    │
│  └─────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────┘
```

**진입 방식 (설계 결정)**
- 카드의 `[열기]` 는 **우측 패널 내부 화면 전환**이다(§1.6). 브레드크럼 `권한 감사 › 권한 시뮬레이션` + `[← 뒤로]`.
- 상단 감사 로그 고지는 **R71-b 의 UI 대응물**이다. R71-a 에 따라 워크스페이스 관리자는 그 워크스페이스의 모든 문서 본문에 도달하므로, 이 화면들의 조회가 기록된다는 사실을 조회 전에 알려야 억제 장치가 작동한다.
- 세 화면 모두 R71 의 상방 게이트(ACL·상속 판정 우회)를 전제로 동작한다 (R71-c).
- **주체 일괄 회수에 R73 가드가 걸린다고 쓰지 않는다.** R43-1 은 `acl_entry` 만 지우므로 슈퍼유저 그룹의 `active` 멤버 수를 **원리적으로 바꿀 수 없고**, R73 은 열거에서 R43-1 을 명시적으로 제외했다. 슈퍼유저 그룹을 대상으로 회수하면 거부되는 것이 아니라 **R71 상방 게이트 때문에 실효가 없으며 그 사실을 화면이 안내**한다 (R119-a). `default` 그룹 대상 회수는 L3 다 (R119-a).

**넷째 카드를 만들지 않는다 — 재조정 대기열은 §2.7-b 가 소유한다 (~~`G24`~~ 종결 · R139 계열)**

R77·R77-a·R77-b·R40-d 가 지목하던 **`감사 목록`** 은 **`재조정 대기열`** 로 이름이 확정됐고(**R139-g** — `감사 목록` 이라는 용어 자체를 폐기), 화면은 **`감사 로그` 카테고리의 두 번째 화면**(**R139-d** → §2.7-b)이다. 이 카테고리는 R24-a 가 **R43-1·R43-2·R43-3 세 카드로 확정**한 구성이므로 **넷째 카드를 만들지 않는다.**

- **축이 다르다** — 세 카드는 전부 **ACL 축**(누가 무엇에 도달하는가)이고 R71-c 로 *상방 게이트 전제*가 공통이다. 재조정은 **파일시스템 × DB 정합 축**이다. 여기가 자리가 아니었던 것은 정원 문제가 아니라 **분류 문제**였다.
- **`05` 의 `상속 끊김 노드 감사 목록`(R43-3)도 이름을 나눠 갖고 있었다** — R139-g 가 셋(`재조정 대기열` · `상속 끊김 노드 감사 목록` · `감사 로그`)으로 분리했다. **화면 라벨을 정하기 전에 용어를 먼저 닫는 것이 이 결정의 전제였다.**
- **R77-b 의 완화책이 도달해야 할 사람**은 워크스페이스 `관리` 보유자다 — 발견의 다수가 워크스페이스 스코프이기 때문이다. **인스턴스 구역(§1.4 상 슈퍼유저 전용)에 두면 그 사람이 화면에 도달하지 못해 위험 수용 판단이 근거를 잃는다**(R139-d 가 그 안을 기각한 이유).

### 2.7 워크스페이스 관리 › 감사 로그 (R84 · R84-a · **R137 계열**)

```
┌─ 감사 로그 · 기술문서 ──────────────────────────────────────────────────┐
│  스코프 [ 워크스페이스: 기술문서  ▾ ]   기간 [2026-08-01] ~ [2026-08-12] │
│  행위자 [           ]  조작 [ 전체 ▾ ]  대상 [           ]  [ 초기화 ]  │
│                          ↑ 기록된 조작의 distinct 집합에서 파생 (R137-f)│
│  ────────────────────────────────────────────────────────────────────── │
│  ┌────────────────┬──────────┬──────────────────┬───────────────────┐   │
│  │ 시각           │ 행위자   │ 조작             │ 대상              │   │
│  ├────────────────┼──────────┼──────────────────┼───────────────────┤   │
│  │ 08-12 14:03:11 │ 박구름   │ ACL 부여         │ /팀/회의록.md     │ ▸ │
│  │ 08-12 13:58:02 │ 박구름   │ 관리 권한 열람   │ /기획/스펙.md     │ ▸ │

│  │   └ 펼침: 이전값 { 상속: 유지 } → 이후값 { 상속: 끊김 }          │   │
│  └────────────────┴──────────┴──────────────────┴───────────────────┘   │
│  더 불러오는 중… (무한 스크롤)                                          │
└─────────────────────────────────────────────────────────────────────────┘

> **와이어프레임의 세 행은 예시다.** 이 화면이 무엇을 보여줄 수 있는지는 아래 **기록 기준(R137)** 이 정하며, 예시 행을 목록의 범위로 읽지 않는다.

**무엇이 기록되는가 — 열거가 아니라 기준이다 (R137)**

다음 중 **하나라도 참이면 기록**한다.

| # | 기준 | 이 화면에서 |
|---|---|---|
| ① | **노드의 존재·위치·본문이 바뀐다** | 생성·이동·삭제·복구·복사가 여기 걸린다 |
| ② | **누가 그 노드에 도달하는가가 바뀐다** | ACL 부여·회수, 상속 끊기·되돌리기, 그룹 멤버십 변경, 계정 상태 전환이 여기 걸린다 |
| ③ | **R71 상방 게이트로 판정을 우회해 접근한다** | `관리 권한에 의한 열람`(R71-b) |

**순수 읽기는 제외**한다 — R84 의 볼륨 근거다 (R137).

- **R84 의 현행 8개 열거는 규범이 아니라 예시다** (**R137-b**). 그 8개는 위 기준으로 **전부 재도출**되므로 이 개정은 열거 교체가 아니라 **지위 강등 + 누락분 추가**다. **이 문서는 어디에서도 기록 대상을 닫힌 목록으로 적지 않는다** — 그렇게 적는 순간 R137 이 고친 결함(열거가 곧 규범이라 조작이 늘 때마다 낡는다)이 화면 계층에 재발한다.
- **제외축 (R137-a)** — **다른 화면이 행위자·시각까지 영구히 재현하면 기록하지 않는다.** 판별자는 **`기간 한정 재현은 재현이 아니다`** 이다. 이 기준으로 **`md` 새 버전 올리기는 제외**된다(R61·R63-a 의 버전 이력이 영구 보관한다). **바이너리 새 버전은 기록**한다 — **R63 이 버전 대상을 md 로 한정**해 재현 수단이 없다. **`04` §5.3 이 인용하는 R115-i(md L1 / 바이너리 L2)와 같은 갈림선**이지만 축이 다르다 — R115 는 **마찰**의 축, R84 는 **조회 가능성**의 축이다.
- **기준으로 새로 걸리는 것 (R137-c)** — **생성 · 복사 · 이동 · 삭제(휴지통 이동) · 휴지통 복구 · 업로드 · 바이너리 새 버전 · 워크스페이스 생성.** **업로드는 생성에 흡수**된다(R45). **워크스페이스 생성**이 걸리는 이유는 R136 이 그 폼 안의 관리자 지정(R35-a)과 `default` 초기 권한(R111)을 **부여로 확정**했기 때문이고, R136-d 로 **설치 마법사(§4.5)도 같다**.
- **`삭제` 와 `휴지통 복구` 는 짝으로 기록한다** (**R137-d**). 개정 전 무기록이었던 것은 의도가 아니라 누락이다 — **"L1(가역)이라 기록하지 않는다"는 규칙은 원장에 없고 반례가 이미 있다**: `ACL 항목 회수` 는 R115-b 상 **L1** 인데 R84 열거에 있다(`그룹 멤버 제거`·`가입 거절`도 같다). 휴지통(§2.4)이 기간 한정 대체를 하지만 **R137-a 의 판별자로 재현이 아니다** — ① **R85 로 편집자 A 가 지운 것을 편집자 B 는 못 본다** ② **R86 경과 후 휴지통 행과 R78 사이드카가 함께 사라지고**, 남는 `영구 삭제` 행의 행위자는 **`system:retention`**(R139-b · ~~`G26` ②~~ 종결)이라 **원 삭제자가 아니다**(→ EC38) ③ **복구가 흔적을 지운다**(삭제·복구 왕복 1회로 흔적이 0).
- **인스턴스 설정 변경을 기록한다** (**R137-e**) — 특히 **감사 로그 보존 기간(R84-a)과 휴지통 보존 기간(R86)의 축소**다. 개정 전에는 **증거를 없애는 행위가 감사 로그에 남지 않았다** — R115-e 가 그 조작에 L3 를 배정하면서까지 규모를 읽히려 했는데 정작 무기록이었다. 화면 쪽 대응은 §2.12 다.

**동작**

- 열 구성은 감사 로그 스키마를 그대로 따른다. **스키마 정본은 R140 이다** — `audit_log(시각, 행위자, 대상, 조작, 이전값, 이후값, **상대 노드**, **대상 역할**)`. `이전값 → 이후값` 과 **`상대 노드`·`대상 역할`** 은 폭 문제로 **행 펼침**에 둔다. **~~`G26`~~ 은 2026-08-16 에 종결됐다** — ①은 R140 계열, ②는 R139-b, ③은 R141 계열이다.

**2-노드 조작의 표시 (R140 계열)**

| 규칙 | 내용 |
|---|---|
| 어느 조작이 두 칸을 쓰는가 | **`복사` 하나뿐이다**(**R140-a**). 이동·개명·삭제·휴지통 복구는 **노드 ID 를 보존**하므로(R76-a·R85) `이전값 → 이후값` 이 담는다. 두 칸은 그 밖의 모든 조작에서 **비어 있고**, 비어 있음 자체는 `조작` 의 함수라 숨은 상태를 나르지 않는다 |
| `상대 노드` 의 표시 | **R138-a 마스킹을 그대로 적용**한다(**R140-b**) — 열람 워크스페이스 안의 노드면 경로로, 밖이면 `이 워크스페이스 밖` 이라는 **동일 고정 문구**로 표시한다. **이 칸이 없던 동안 R138-a 의 그 분기는 도달할 수 없었다** |
| `대상 역할` | `원본` \| `사본`. **`조작` 값에 밀어 넣지 않는다**(**R140-c**) — 넣으면 distinct 집합이 곱집합으로 부풀어 R137-f 가 막으려던 축이 되고 `조작=복사` 필터가 절반을 놓친다(R139-b 와 같은 판정). 이 칸이 없으면 관리자는 **"나갔다"와 "들어왔다"를 구별할 수 없다** |
| 행 수 | **사본 노드 자리에 1행은 언제나, 원본 노드 자리에 1행은 경계를 넘을 때만**(**R140-d**). 따라서 **내부 복사 1행 · 경계를 넘는 복사 2행**이고, **어느 워크스페이스의 열람자도 복사 1건당 정확히 1행을 본다** |
| 금지 | `상대 노드`·`대상 역할` 을 **필터·정렬·배지·집계의 축으로 쓰지 않는다**(**R140-c** · R138-c 이식). `이 워크스페이스 밖` 으로 표시된 행을 **세는 화면을 만들지 않는다** |

**다건 조작의 표시 — 저장은 낱행, 화면은 묶음 (R141 계열)**

| 규칙 | 내용 |
|---|---|
| 저장 | **그 조작이 실제로 바꾼 것마다 1행**이다(**R141**) — **노드를 바꾸는 조작(삭제·복사·이동)은 노드마다, `acl_entry` 를 바꾸는 조작(부여·회수)은 항목마다.** 원장에 `acl_entry` 의 (주체, 노드) 유일성 제약이 없으므로 **노드 단위로 접으면 `granted_by` 가 다른 항목 하나가 기록되지 않아 R70-d 의 역질의가 깨진다.** 이 단위로 **R142-c 의 토큰(회수될 항목 수)과 행 수가 정의상 같아진다.** `1행 + 영향 건수` 는 쓰지 않는다 — 집계 행의 `대상` 은 노드가 아니라 주체여서 **어느 워크스페이스에도 귀속되지 않아 인스턴스 스코프로 격상되고(**R141** — 감사 행의 스코프 규칙은 이 조항이 정본이다. **R139-e 는 대기열 항목을 규정할 뿐이라 근거가 될 수 없다**), 정작 그 워크스페이스 관리자에게 배달되지 않는다** |
| 표시 | 한 번의 조작에서 나온 행들을 **접힌 1줄**로 보이고 펼치면 낱행이 나온다(**R141-a**). 라벨은 `행위자 · 조작 · 건수` 다. 저장/표시 분리의 정본 선례는 **R138-a**(*"저장은 완전하고 해석만 권한으로 갈린다"*)이며 R76·R139-a·R14-b 가 같은 축이다 |
| 필터 원천 | **묶음 행은 표시 산물이지 기록이 아니므로 `조작` distinct 필터(R137-f)의 원천이 되지 않는다.** 필터는 **낱행의 `조작` 값**에서 파생한다 — 묶음이 원천이 되면 *"코드 상수 목록이 아니다"* 라는 규칙이 표시 계층에서 다시 깨진다 |
| 건수 | **열람자가 볼 수 있는 스코프의 행만 센다**(**R141-b** · R139-f 와 같은 규칙). **총계·분모·`이 밖에 N건 더` 를 표시하지 않는다** — 전역 128 과 자기 몫 40 을 함께 보이면 **차액 88 이 "내 워크스페이스 밖에 이 사람의 권한이 88건 더 있었다"** 를 알려 R36 을 감사 화면에서 관통한다(R138-c · R126-b) |
| 묶음 키 | **화면·API·필터에 노출하지 않는다**(**R141-a**). 그 값은 두 워크스페이스의 행에 같은 값으로 실리므로 노출하면 행 간 상관으로 상대를 복원할 수 있다 — R138-b 가 가명·연번을 금지한 것과 같은 취약점이 묶음 축에서 재현된다. 접기/펼치기의 내부 키로만 쓴다 |
| 서브트리·첨부 | 디렉토리 삭제·복사는 **하위 노드마다 1행**이다(**R141-d**). **R50-c 로 동반 삭제되는 첨부는 행을 만들지 않고 건수도 표시하지 않는다**(**R141-c**) — 첨부는 노드가 아니고(R50-a), 소유 문서의 `영구 삭제` 행이 R137-a 의 제외축을 충족한다. **대가는 명시 수용한다 — 첨부 단위 포렌식은 불가능하다** |

- **`조작` 필터의 선택지는 R84 열거를 하드코딩하지 않고 `실제 기록된 조작의 distinct 집합`에서 파생시킨다** (**R137-f**). 하드코딩하면 R137 이 기준으로 바뀐 의미가 필터 계층에서 사라져 **같은 종류의 낡음이 화면에 재발**한다. 구현상의 귀결:

| 규칙 | 내용 |
|---|---|
| 원천 | 조회 중인 **스코프·기간 안에서 실제로 기록된 조작 값**의 distinct 집합. 코드 상수 목록이 아니다 |
| 갱신 | 새 조작이 기록되기 시작하면 **화면 코드를 고치지 않아도** 필터에 나타난다. 반대로 그 기간에 한 건도 없는 조작은 선택지에 없다 |
| 정렬·라벨 | 값 자체를 라벨로 쓰고 이름순으로 정렬한다. **표시 순서에 의미를 부여하지 않는다** — 순서를 규범으로 두면 그것이 다시 닫힌 열거가 된다 |
| 빈 결과 | 필터를 걸었는데 0건이면 §6 `비어 있음` 규칙대로 **필터가 걸려 있다는 사실을 빈 상태 안에서** 알린다(EC14 와 같은 형태) |

- **일반 문서 열람은 기록되지 않으므로 필터에도 나타나지 않는다** (R84 의 볼륨 근거 · R137 의 "순수 읽기 제외"). 이것은 필터가 값을 감추는 것이 아니라 **애초에 기록이 없어서** 생기는 결과다.
- **읽기 전용 화면이다.** 행 편집·삭제 조작을 두지 않는다 (R84-a). 행 우클릭 메뉴도 없다.
- 보존 기간은 **인스턴스 설정**의 `감사 로그 › 보존 기간` 에서 지정한다 (R84-a, R24-a 개정). `audit_log` 는 인스턴스 단일 테이블이므로 워크스페이스별 값이 아니다. **그 값의 기본값과 휴지통 보존(R86)과의 대소 관계가 원장에 없다** — R137-d 로 삭제가 기록 대상이 되면서 **삭제 기록이 휴지통보다 먼저 사라지는 역전**이 실제 문제가 된다(공백 **`G27`** → §9 · §2.12).
- 대용량 전략: 감사 로그는 유일하게 **커서 기반 무한 스크롤 + 행 가상화**를 쓴다(§3.5). **R137-c 로 기록 대상이 늘어 행 수가 커지므로 이 선택이 더 강해진다.**

**스코프 선택기 (분류 기준은 R141 · 선택기 형태만 설계자 판단 — §9-Q8)**
기록 대상 중 `그룹 멤버십 변경`·`PAT 발급·폐기`·`계정 상태 전환`·**`인스턴스 설정 변경`(R137-e)** 은 **워크스페이스에 속하지 않는 인스턴스 이벤트**다. 감사 로그 카테고리는 워크스페이스 관리 구역에 있으므로, 워크스페이스 관리자에게 인스턴스 이벤트를 그대로 보여주면 관리 경계(R36)를 넘는다. **분류 기준은 "그 이벤트가 특정 워크스페이스의 노드에 귀속되는가" 하나이며(**R141** — 2026-08-16 에 이 판단이 **원장으로 승격**했다. **이제 설계자 판단이 아니라 근거 있는 항목이고, Q8 에 남는 것은 선택기의 형태뿐이다**), 아래 표의 예는 그 기준의 적용례이지 전량 열거가 아니다** (R137-b 와 같은 이유).

| 스코프 | 분류 기준 | 예 (전량 아님) | 선택 가능자 |
|---|---|---|---|
| `워크스페이스: <이름>` | 특정 워크스페이스의 **노드**에 귀속된다 | ACL 부여·회수, 상속 끊기·되돌리기, **생성·이동·삭제·휴지통 복구·복사**(R137-c), 영구 삭제, 아카이브·복원, 관리 권한 열람 | 해당 워크스페이스 `관리` |
| `인스턴스 전체` | 워크스페이스에 귀속되지 않는다 | 위 전부 + 그룹 멤버십 변경, PAT 발급·폐기, 계정 상태 전환, **인스턴스 설정 변경**(R137-e) | 슈퍼유저만 |

슈퍼유저는 R29 로 모든 워크스페이스 관리 권한을 가지므로 이 선택기 하나로 전 범위에 도달한다. 카테고리를 인스턴스 구역에 하나 더 만들지 않아도 된다 — R24-a 표를 바꾸지 않는 안이다.

- **`워크스페이스 생성`(R137-c)의 귀속은 이 기준만으로 갈리지 않는다** — 그 워크스페이스에 귀속된다고 볼 수도, 인스턴스 조작이라고 볼 수도 있다. **임의로 정하지 않고 §9-Q37(Q8 의 확장)로 열어 둔다.**
- **경계를 넘는 복사(R97)는 양쪽에 1행씩, 각자 그 노드가 속한 워크스페이스 스코프로 실린다**(**R138**). 상대편 노드는 **노드 ID 로 저장되고 열람자의 워크스페이스가 아니면 `이 워크스페이스 밖` 이라는 동일 고정 문구**로만 보인다(**R138-a·b**). **나간 건수의 집계·필터·배지는 만들지 않는다**(**R138-c**) · **`조작` 값은 경계와 무관하게 `복사` 하나**다(**R138-d** — 조작명을 가르면 R137-f 로 파생되는 필터 목록 자체가 오라클이 된다). ~~`G25`~~ 종결.
- **재조정 결과는 이 표에 싣지 않는다** — 같은 카테고리의 **별도 화면 §2.7-b `재조정 대기열`** 이 소유한다(**R139-d**). ~~`G24`~~ 종결로 금지가 풀린 것이 아니라 **대상이 정밀해졌다** — 이 표는 R84-a 로 **읽기 전용**인데 대기열은 **사후 처리(R77-a 수동 연결)가 필요**하므로, 섞으면 읽기 전용 규정이 무너지고 이 표의 `조작` distinct 필터(R137-f)와 무한 스크롤 전략(§3.5)도 오염된다.

### 2.7-b 워크스페이스 관리 › 감사 로그 › **재조정 대기열** (R139 계열)

**§2.7 과 같은 카테고리이되 다른 화면**이다(§1.6 패널 내부 전환 — `권한 감사` 3화면과 같은 패턴). **좌측 카테고리 라벨은 `감사 로그` 그대로이고 브레드크럼으로 구분한다** — R139-d 가 *"R24-a 의 구역·카테고리 구성·표시 권한을 바꾸지 않는다"* 이고, **같은 패턴인 `권한 감사` 3화면도 라벨을 바꾸지 않고 브레드크럼만 쓴다**(§2.6).

```
┌─ 감사 로그 › 재조정 대기열 ──────────────────────────────  [← 뒤로] ─┐
│  상태 [ 미해소 ▾ ]   유형 [ 전체 ▾ ]   스코프 [ 워크스페이스: 기술문서 ▾ ] │
│  ─────────────────────────────────────────────────────────────────── │
│  ⚠ 상관 판정 실패   /팀/회의록.md  ↔  (tombstone) /구/회의.md         │
│     2026-08-16 03:00   신규 노드로 처리됨 — 이력이 끊겨 있다          │
│                                          [ 같은 문서로 연결 ]  [ 무시 ] │
│  ─────────────────────────────────────────────────────────────────── │
│  ⚠ 미등록 파일        /팀/신규.md      2026-08-16 03:00  [ 확인함 ]   │
└──────────────────────────────────────────────────────────────────────┘
```

| 규칙 | 근거 |
|---|---|
| 이 화면은 **작업 큐**다 — 항목마다 처리 동선이 있다. §2.7 의 읽기 전용 규정은 여기 걸리지 않는다 | R139 (성질이 반대다) |
| **`미해소` 가 기본 필터**이고 대용량 전략은 **검색 우선**(§3.4)이다. §3.5 무한 스크롤 예외는 §2.7 표 전용이다 | **〔판단〕 §9-Q41** — R139 는 대기열의 **성질**만 규정하고 목록 전략을 정하지 않는다 |
| **처리해도 감사 행을 고치지 않는다** — 항목 상태가 바뀌고 **처리 행위가 새 감사 행으로 추가**된다 | **R139-c** · R84-a |
| 스코프 선택기는 **§2.7 과 같은 기준**("특정 워크스페이스의 노드에 귀속되는가"). 경계를 넘는 것으로 보이는 쌍·무소속 파일·R40-d `id` 중복은 **인스턴스로 격상**되어 슈퍼유저만 본다 | **R139-e** · R138 계열 |
| 좌측 카테고리에 **미해소 건수 배지**가 붙는다. 그 사용자가 볼 수 있는 스코프만 센다 | **R139-f** (`가입 승인 (3)` · R109-a 선례) |
| 항목 행이 참조하는 감사 행으로 **§2.7 로 건너갈 수 있다.** 두 화면이 같은 사실을 양면에서 본다 | R139-a |
| **와이어프레임의 시각·경로·두 노드는 대기열이 가진 값이 아니라 참조 감사 행을 조인한 결과**다 — 대기열 스키마는 `(유형, 참조 감사 행 1..N, 해소 감사 행)` 뿐이고 **스코프도 참조 감사 행의 대상 노드에서 파생**한다 | R139 · R139-a · R139-e |

**행위자 표기** — 재조정이 만든 감사 행의 `행위자` 는 `system:reconciler` 다(**R139-b**). §2.7 의 `행위자` 필터는 자유 입력이므로 이 값으로 **재조정이 한 일 전부**를 한 번에 걷어 올 수 있다.

> **주체를 열거하는 화면은 시스템 주체를 제외한다** — §2.8 사용자 관리 총원, §2.13 주체 검색(R112), ACL 주체 선택기(R43), R43-1 회수 대상, R101-b 오프보딩. **판정은 `is_system` 한 자리를 경유하며 화면마다 따로 쓰지 않는다**(R139-b · R124). **폴백을 두지 않는다**(R139-b) — 조용히 `system` 으로 떨어지면 R139-b 의 이점이 사라진다. **주체 행이 없을 때 어떻게 되는지는 원장이 정하지 않았다** — 화면 문제가 아니라 서버 계약이므로 여기서 단정하지 않는다(**§9-Q42**).

**이 화면이 덮지 못하는 반출 경로 (R137-h — 인지된 잔여 위험)**

R137 을 전부 반영해도 반출 경로는 완결되지 않는다. **R97 이 "경계를 넘는 유일한 수단"인 것은 노드 조작 축에서만 참**이고, **R48 다운로드 · R66-b 첨부 다운로드 · R22·R58-b MCP 읽기**가 같은 반출 결과를 내면서 설계상 무기록이다. **읽기를 기록하면 R84 의 볼륨 근거와 정면 충돌**하므로 확장하지 않고 **위험으로 수용해 기록**한다 — R77-b 가 잔여 위험을 명시 기록한 선례를 따른다. 화면 쪽 귀결은 **오프보딩(§2.8) 후 "이 사람이 무엇을 가져갔는가"를 이 뷰어만으로 완전히 답할 수 없다**는 것이며, 그 한계를 안내 문구로 감추지 않는다.

### 2.8 인스턴스 › 사용자 관리 (R6 · R60 · R73 · R81)

와이어프레임은 §1.3 전체 구조도의 우측 패널과 동일하다. 여기서는 조작만 기술한다.

**열 구성**

| 열 | 폭(px) | 내용 | 근거 |

**행 메뉴**

```
┌ 행 메뉴 ──────────────────────────┐
│ 계정 정지                         │   suspended 로 전환 (R60)
│ 계정 활성화                       │   active 로 전환. default 그룹 소속이

│ ──────────────────────────────────│

- **계정 삭제 조작은 존재하지 않는다** (**R101**). 계정은 `suspended` 로만 관리한다. 삭제가 없으므로 R84 감사 로그의 행위자 참조가 깨지지 않고 고아 `acl_entry` 문제가 애초에 생기지 않는다. 퇴직·이관 수요는 아래 **오프보딩 흐름**(R101-b)이 덮는다.
- **슈퍼유저 지정은 "등급 변경"이 아니라 그룹 멤버십 변경**이다 (R81). 감사 로그에도 `그룹 멤버십 변경` 으로 기록된다 (R84). 그룹 관리 화면에서 같은 조작을 해도 동일한 하나의 사실이 바뀐다 — 진입점이 둘이지만 API·기록은 하나다.
- **R73 가드가 걸리는 조작**: 계정 정지, `pending`·`rejected` 전환, 슈퍼유저 그룹에서 제거. **R73 의 규범은 열거가 아니라 "슈퍼유저 그룹의 `active` 멤버 수가 0 이 되는 결과"라는 조건 자체**이므로, 새 조작을 추가할 때도 이 조건을 만들 수 있는지로 판정한다. 계정 삭제는 R101 로 폐기되었고 R43-1(ACL 만 제거)은 멤버 수를 바꾸지 못해 가드 대상이 아니다.
- 정지·활성화의 즉시 효과는 R58-d(전 PAT 무효) · R60(로그인 차단)이며, 확인 다이얼로그에 명시한다(§5).

**사용자 상세 (패널 내부 전환)**

```
┌─ 사용자 관리 › 김하늘 ──────────────────────────── [← 뒤로] ┐
│  상태   [ 활성 ▾ ]                                가입 08-01│
│  ─────────────────────────────────────────────────────────  │

│   기획팀                                          [ 제거 ]   │
│   슈퍼유저       (시스템)                         [ 제거 ]   │
│  ─────────────────────────────────────────────────────────  │
│                                            [ 오프보딩… ]     │

```

타인의 PAT 목록은 이 화면에 두지 않는다 — R58-c 는 발급·폐기를 본인으로 한정하며, 타인 토큰 **열람** 권한은 결정 로그에 없다(§9-Q11).

**오프보딩 흐름 (R101-b)**

퇴직·이관처럼 한 사람의 접근을 통째로 걷어내는 작업은 4개 조작이 모두 필요한데, 따로 하면 빠뜨려 잔존 권한이 남는다. 그래서 **하나의 안내된 흐름**으로 묶는다. 용어는 "퇴사 처리"가 아니라 **오프보딩**이다 (R101-b).

```
┌─ 오프보딩 · 김하늘 ─────────────────────────────────────────────────────┐
│  이 사용자의 접근을 단계적으로 회수한다. 계정은 삭제되지 않는다.(R101)  │
│  ────────────────────────────────────────────────────────────────────── │
│  [v] 1  계정을 정지한다                                   완료          │
│         상태 활성 → 정지                                  (R60)         │
│  [v] 2  액세스 토큰 무효화                                자동 완료     │
│         1단계의 결과로 토큰 3개가 무효가 되었다           (R58-d)       │
│  [ ] 3  그룹 멤버십 제거                                  3개 그룹      │
│         default · 기획팀 · 슈퍼유저                       (R73 가드)    │
│  [ ] 4  ACL 일괄 회수                                     항목 128건    │
│         주체 일괄 회수 화면으로 이동한다                 (R43-1)        │
│  ────────────────────────────────────────────────────────────────────── │
│  ! R73 으로 거부되면 흐름을 멈추되 이전 단계 결과는 유지한다. (R101-c)  │
│                                                    [ 닫기 ] [ 다음 ]    │
└─────────────────────────────────────────────────────────────────────────┘
```

| 단계 | 조작 | 특성 |
|---|---|---|
| 1 | 계정 `suspended` 전환 | 사용자 확인 필요. **R73 가드 개별 통과** |
| 2 | PAT 무효화 | **자동** — 1단계의 결과다(R58-d). 별도 조작이 아니며 결과만 보여준다 |
| 3 | 그룹 멤버십 제거 | 사용자 확인 필요. **R73 가드 개별 통과**(슈퍼유저 그룹 포함 시) |
| 4 | ACL 일괄 회수 (R43-1) | 회수 항목 수만 카드에 표시하고 **실행 화면은 R43-1 주체 일괄 회수 화면이 소유**한다(R101-e). **ACL 만 제거**하며 그룹 멤버십·계정 상태를 건드리지 않는다. 적용 범위 문구는 요청자 레벨에 따라 다르다(R101-f) |

- **각 단계는 R73 가드를 개별 통과해야 한다** (R101-b). 어느 단계가 거부되면 **흐름을 멈추되 이전 단계의 결과는 유지한다** (**R101-c**). 1단계만 적용된 계정도 R60 으로 이미 로그인·토큰 인증이 차단되므로 부분 진행 상태가 유효하며, **롤백하면 오히려 접근이 되살아난다.**
- **이 카드는 단일 컴포넌트다** (**R101-d**). 사용자 관리(여기)와 주체 일괄 회수(R43-1) **양쪽에서 같은 카드로 진입**한다. 두 화면이 각자 카드를 그리면 두 벌이 된다.
- **진행 상태를 저장하지 않는다** (**R101-d**). 완료 표시는 조회 시점의 실제 상태 — 계정 상태(R60) · PAT 유효성(R58-d) · 그룹 멤버십 · 잔여 `acl_entry` 건수 — 에서 파생한다. 저장하면 중단된 오프보딩이 유령 레코드로 남고, 파생 방식이 R59(권한 스냅샷 금지)와 일관된다. 중간에 닫았다 다시 열면 실제 상태가 그대로 반영된다.
- **4단계는 주체 일괄 회수 화면(R43-1)으로 위임하고, 카드는 진입 버튼과 완료 표시만 갖는다** (**R101-e**). 영향 범위 표(워크스페이스·경로·레벨·부여자·부여 시각)와 L3 확인이 이미 그 화면에 있으므로 카드 안에 다시 그리면 중복 구현이 된다. 회수는 되돌릴 수 없다 — R110 으로 만료 기반 임시 부여가 없다.
- **요청자 레벨에 따라 4단계의 적용 범위 문구가 달라진다** (**R101-f**). 워크스페이스 관리자에게는 "내가 관리하는 워크스페이스에만 적용", 슈퍼유저에게는 **전 인스턴스에 적용됨을 명시**한다. R29 로 슈퍼유저의 "내가 관리하는 워크스페이스"는 전체이므로 논리 모순은 없지만, 문구가 그 사실을 드러내지 않으면 슈퍼유저가 부분 회수로 오해한다.
- **워크스페이스 관리자가 R43-1 쪽에서 진입하면 ①③단계는 상태 표시만** 한다. 계정 상태 전환과 그룹 멤버십 변경은 R24-a 인스턴스 구역의 조작이라 슈퍼유저 전용이다. ②는 애초에 조작이 아니라 R58-d 의 결과 표시다. 따라서 워크스페이스 관리자는 ④만 실행할 수 있고, 카드는 나머지 단계가 왜 잠겼는지를 함께 보여준다.

**오프보딩 후 "이 사람이 무엇을 가져갔는가" — 어디까지 답할 수 있는가 (~~`G22`~~ 종결 · R137 계열)**

이 흐름은 **ACL·멤버십·계정 상태를 걷어낼 뿐 이미 만들어진 사본을 회수하지 못한다.** 남는 질문은 감사 로그(§2.7)가 받으며, R137 이후의 상태는 아래와 같다.

| 질문 | 답할 수 있는가 | 근거 |
|---|---|---|
| 이 사람이 **어떤 노드를 만들었는가** | **부분적으로 가능했고 이제 정면으로 가능하다** | **R137-g 의 정정** — 개정 전에도 **완전한 무기록은 아니었다.** R97-a 가 복사 시 R28(R132 로 "노드 생성자")로 생성자에게 편집권을 주고, Q11 해소절이 그것을 `acl_entry` 1건으로 못박았으며, **R84 는 `ACL 부여` 를 이미 기록**한다. 따라서 생성·복사는 **이미 감사 행을 1건 남기고 있었고**, R84-a 불변성 때문에 **R43-1 이 그 ACL 을 지워도 부여 이벤트는 살아남는다.** 이제 R137-c 로 생성·복사 자체가 기록된다 |
| **신규 생성인가 복사인가** | **가능해진다** | R137-c 가 둘을 **서로 다른 조작 값**으로 기록한다. 개정 전에는 남는 행이 `ACL 부여` 하나뿐이라 **라벨이 없었다** |
| **원본이 무엇이었는가(출처)** | **가능해졌다** | **R140** 이 `상대 노드`·`대상 역할` 두 칸을 추가해 출처가 기록된다(~~`G26`~~ ① 종결). **다만 상대 노드가 다른 워크스페이스면 `이 워크스페이스 밖` 고정 문구까지만 보인다**(R140-b · R138-a) — 목적지 식별은 **R138-e 대로 슈퍼유저 조사가 유일한 경로**다 |
| 이 사람이 **타인 소유 노드**를 이동·개명·삭제했는가 | **이동·삭제는 가능해진다. 개명은 미정** | 개정 전에는 R28 부여가 없어 **행 자체가 없었다.** 이동·삭제는 R137-c·R137-d 가 넣었고, **`개명` 은 패널 1:1 로 갈려 열려 있다** — 공백 **`G29`** → §9 |
| 이 사람이 **다른 워크스페이스로 반출**했는가 | **원본 측 관리자는 "나갔다"까지만 안다** | 양쪽에 1행씩 남지만(**R138**) 상대편은 `이 워크스페이스 밖` 고정 문구로만 보인다(**R138-a·b**). **목적지 식별은 슈퍼유저(R71) 조사가 유일한 경로**다(**R138-e**) — 그 1비트는 지울 수 없고 지우면 유출 감사가 불가능해진다 |
| 이 사람이 **다운로드·MCP 로 읽어 갔는가** | **아니다 — 인지된 잔여 위험** | **R137-h** — R48 다운로드 · R66-b 첨부 다운로드 · R22·R58-b MCP 읽기가 같은 반출 결과를 내면서 무기록이다. **읽기를 기록하면 R84 의 볼륨 근거와 충돌**하므로 확장하지 않고 위험으로 수용한다 |

- **④단계의 안내 문구는 이 한계를 감추지 않는다.** R43-1 은 `acl_entry` 만 제거하므로 "권한을 전부 회수했다"가 "이 사람이 가져간 것이 없다"를 뜻하지 않는다. **문구는 `05` §2.4 가 소유**하므로 이 문서는 사실만 기록한다.
- **개정 전 이 자리의 서술이 틀렸다** — **`G22` 등재 사유가 "복제된 콘텐츠는 추적 대상도 아니다"라고 적었으나 부분적으로 거짓**이었고 R137-g 가 정정했다. 공백의 실체는 "복사가 무기록"이 아니라 **"출처를 표현할 수 없고 타인 소유 노드 조작이 전부 무기록"** 이었다.

### 2.9 인스턴스 › 그룹 관리 (R6 · R6-a · R8 · R30 · R30-a)

```
┌─ 그룹 관리 ─────────────────────────────────────────────────────────────┐
│  [검색: 그룹 이름          ]                        [ + 새 그룹 ]       │
│  ────────────────────────────────────────────────────────────────────── │
│  ┌──────────────────────┬────────┬──────────┬───────────────────────┐   │
│  │ 그룹                 │ 멤버   │ 생성일   │                       │   │
│  ├──────────────────────┼────────┼──────────┼───────────────────────┤   │
│  │ 슈퍼유저  [시스템]   │ 3      │ 설치 시  │ [개명]* [삭제]*       │   │
│  │ default   [시스템]   │ 3,180  │ 설치 시  │ [개명]* [삭제]*       │   │
│  │ 기획팀               │ 24     │ 2026-08-03│ [개명]  [삭제]       │   │
│  │ 기술문서관리자       │ 5      │ 2026-08-05│ [개명]  [삭제]       │   │
│  └──────────────────────┴────────┴──────────┴───────────────────────┘   │
│  * 시스템 그룹은 삭제·개명할 수 없다. (R30 · R30-a)                     │
└─────────────────────────────────────────────────────────────────────────┘
```

**시스템 그룹 처리 (R30 · R30-a)**
- `슈퍼유저` 와 `default` 에 `[시스템]` 배지를 붙이고 `[개명]`·`[삭제]` 를 **사전 비활성화**한다. 비활성 버튼에 호버하면 사유 툴팁("시스템 그룹은 삭제·개명할 수 없다 — R30-a")을 띄운다.
- 사전 비활성화를 택한 근거: 시스템 그룹 여부는 **불변 속성**이라 UI 상태가 stale 해질 수 없다. 눌러서 실패하게 두는 것은 학습 가치가 없고 오조작 스트레스만 만든다. 서버도 동일하게 거부해 권위를 유지한다(§5).
- **비활성화되는 것은 삭제·개명뿐이다** (**R119**). R30-a 는 삭제·개명만 금지하며 ACL 회수를 다루지 않으므로, **시스템 그룹도 주체 단위 일괄 회수(R43-1)의 대상**이다. 특히 `default` 그룹 앞으로 부여된 초기 권한(R83·R111)은 일반 `acl_entry` 이므로 회수하면 영구히 사라진다 — R8·R60-a 는 **멤버십** 규정이라 ACL 을 재생성하지 않는다. 이 화면의 `[시스템]` 배지 툴팁이 "삭제·개명만 불가"임을 명시해, 회수까지 막혀 있다는 오해를 만들지 않는다. 회수 진입점은 권한 감사 카테고리(§2.6)이고 `default` 대상은 R119-a 로 L3 이다.

**그룹 상세 (패널 내부 전환)**

```
┌─ 그룹 관리 › 기획팀 ────────────────────────────── [← 뒤로] ─────────┐
│  이름 [ 기획팀            ] [ 변경 ]                 멤버 24명       │
│  ──────────────────────────────────────────────────────────────────  │
│  [검색: 멤버              ]                        [ + 멤버 추가 ]   │
│  ┌────────────────┬────────────────────┬────────┬─────────────────┐  │
│  │ 김하늘         │ sky@co.kr          │ 활성   │ [ 제거 ]        │  │
│  │ 이바다         │ sea@co.kr          │ 정지   │ [ 제거 ]        │  │
│  └────────────────┴────────────────────┴────────┴─────────────────┘  │
│  1–24 / 24                                                           │
└──────────────────────────────────────────────────────────────────────┘
```

- **멤버는 사용자만이다.** 그룹을 멤버로 추가하는 UI 는 존재하지 않는다 (R6-a). 멤버 추가는 `PrincipalPicker` 를 사용자 전용 모드로 쓰며(R112-e) 검색 규칙은 §2.13 을 따른다.
- **`default` 그룹의 멤버 목록은 읽기 전용**이다 — `[+ 멤버 추가]`·`[제거]` 를 두지 않는다. **읽기 전용은 멤버십 조작에 대한 제한이며 그 그룹 앞으로 부여된 ACL 회수와는 무관하다**(R119). 근거: R8 과 R60-a 가 소속을 시스템이 결정한다고 규정하므로(계정이 `active` 로 전환되는 시점에 자동 소속), 수동 제거를 허용하면 "왜 이 사람만 없는가"를 추적할 수 없고 R8 의 불변식이 깨진다. (설계자 판단 — §9-Q12)
- **`default` 그룹은 전 `active` 사용자를 담으므로 수천 행이다.** 상세 화면의 멤버 목록도 §3 의 서버 페이징을 그대로 쓴다 — 사용자 관리 테이블과 동일한 규모 문제가 여기서도 발생한다.
- `슈퍼유저` 그룹의 멤버 제거는 R73 가드 대상이다(§5).
- **그룹 삭제는 그 주체의 `acl_entry` 제거를 같은 트랜잭션에 포함한다** (**R101-a**). 계정과 달리 그룹은 감사 로그의 행위자가 될 수 없으므로 삭제해도 이력이 끊기지 않는다. 확인 다이얼로그는 회수될 권한 항목 수를 명시한다(§5.4).

### 2.10 인스턴스 › 가입 승인 (R7 · R60 · R60-b)

```
┌─ 가입 승인 ─────────────────────────────────────────────────────────────┐
│  [ 대기 중 (3) ] [ 거절됨 (2) ]                                         │
│  ────────────────────────────────────────────────────────────────────── │
│  [ ] 전체 선택                            선택 2건  [ 승인 ] [ 거절 ]   │
│  ┌───┬────────────────┬────────────────────┬────────────┬───────────┐  │
│  │[v]│ 최소나          │ sona@corp.kr       │ 08-12 09:11│ [승인][거절]│ │
│  │[v]│ 정하람          │ haram@corp.kr      │ 08-11 17:40│ [승인][거절]│ │
│  │[ ]│ 오늘새          │ sae@corp.kr        │ 08-11 09:02│ [승인][거절]│ │
│  └───┴────────────────┴────────────────────┴────────────┴───────────┘  │
│                                                                         │
│  승인하면 계정이 active 가 되고 그 시점에 default 그룹에 소속된다.      │

└─────────────────────────────────────────────────────────────────────────┘
```

**동작**

| 조작 | 결과 | 근거 |
|---|---|---|
| 승인 | `pending` → `active`. **이 시점에 default 그룹 소속**이 이뤄진다 | R60, R60-a, R8 |
| 거절 | `pending` → `rejected`. 계정과 이력은 보존된다 | R60 |
| 거절됨 탭 › 재심사 | `rejected` → `pending` 으로 되돌린다 | R60-b |
| 일괄 승인·거절 | **허용한다** | 설계 판단 — 아래 |

**일괄 조작을 여기만 허용하는 근거**
대기열은 조작이 동질적(승인 또는 거절 둘뿐)이고, 대상이 전부 화면에 보이며, 규모가 사용자 전체가 아니라 대기 건수다. 그리고 어느 결과도 되돌릴 수 있다(R60-b 재심사, 정지 해제). 반면 사용자 관리 테이블의 일괄 조작은 §3.6 의 이유로 제공하지 않는다.

**가입 모드에 따른 빈 상태**
R7-① 자유 가입 모드에서는 `pending` 이 생기지 않아 대기열이 항상 비어 있다. 이때 빈 상태 문구는 일반적인 "항목이 없습니다"가 아니라 **원인을 설명**한다: "현재 자유 가입 모드라 승인 대기가 발생하지 않는다. [인스턴스 설정에서 가입 모드 보기]". 근거 — 원인을 모르면 사용자는 시스템 고장으로 오인한다.

### 2.11 인스턴스 › 전체 워크스페이스 (목록·생성) — R29 · R35-a · R109-a · R111

**카테고리명** — R24-a 개정으로 `워크스페이스 생성` 에서 **`전체 워크스페이스`(목록·생성)** 으로 바뀌었다. 워크스페이스 관리 구역의 동명 카테고리(§2.5)는 스코프 드롭다운으로 **한 워크스페이스에 한정된** 화면이므로 이름이 구별되어야 한다.

**목록 화면** — R109-a 가 `관리자 없음` 배지의 상시 노출을 요구하는데, 인스턴스 전체 워크스페이스를 볼 수 있는 화면이 이 카테고리뿐이다. 따라서 생성 폼 앞에 목록을 둔다.

```
┌─ 전체 워크스페이스 ─────────────────────────────────────────────────────┐
│  인스턴스의 전체 워크스페이스다.               [ + 새 워크스페이스 ]    │
│  ────────────────────────────────────────────────────────────────────── │
│  ┌──────────────────────┬──────────┬────────────┬───────────────────┐   │
│  │ 이름                 │ 관리 권한│ 생성일     │                   │   │
│  ├──────────────────────┼──────────┼────────────┼───────────────────┤   │
│  │ workspace            │ 2        │ 설치 시    │                   │   │
│  │ 기술문서             │ 2        │ 2026-08-03 │                   │   │
│  │ 신제품기획           │ 0        │ 2026-08-09 │ [ 관리자 없음 ]   │   │
│  └──────────────────────┴──────────┴────────────┴───────────────────┘   │
│  `관리자 없음` 은 슈퍼유저만 ACL 을 부여할 수 있는 상태다. (R109-a)     │
└─────────────────────────────────────────────────────────────────────────┘
```

**생성 폼** — `[+ 새 워크스페이스]` 로 패널 내부 전환한다.

```
┌─ 전체 워크스페이스 › 새 워크스페이스 ───────────── [← 뒤로] ───────────┐
│  1  이름                                                                │
│     표시 이름 [ 신제품기획                        ]                     │
│     물리 경로는 해시 ID 로 생성되며 이름을 바꿔도 변하지 않는다.(R40-a)  │
│  ────────────────────────────────────────────────────────────────────── │
│  2  워크스페이스 관리자 지정  (필수 — R35-a)                            │
│     [ 사용자·그룹 검색                                    ]             │
│     · 박구름 (사용자)                                     [ 제거 ]      │
│  ────────────────────────────────────────────────────────────────────── │
│  3  default 그룹의 초기 권한                             (R111)         │
│     ( ) 없음      가입한 사용자는 이 워크스페이스에 접근하지 못한다     │
│     (•) 보기      ← 예시에서 고른 값 · 기본값은 `없음` 이다  (R111)     │
│     ( ) 편집                                                            │
│  ────────────────────────────────────────────────────────────────────── │
│  ! 워크스페이스는 상속 체인의 루트라 상위에서 물려받는 권한이 없다.     │
│    생성 직후엔 지정한 `관리` 권한자와 슈퍼유저만 접근한다. (R111-b)     │
│                                                                         │
│  ⓘ 여기서 부여한 권한이 이 워크스페이스의 하위 전체에 상속된다. (R127)  │
│    상속이 끊긴 하위에는 적용되지 않는다.                     (R127-a)   │
│                                                                         │
│                                             [ 취소 ]  [ 생성 ]          │
└─────────────────────────────────────────────────────────────────────────┘
```

**`[생성]` 을 누르면 확인 다이얼로그가 한 번 더 뜬다 — L2 이며 확인은 하나다** (**R136** · ~~Q36~~ 종결).

> **위 생성 폼과 아래 확인 다이얼로그는 같은 시나리오의 예시다** — `default` 초기 권한으로 **`보기` 를 고른 경우**이며, 확인이 무엇을 보여주는지 드러내기 위해 그렇게 골랐다. **R111 의 기본값은 `없음`** 이고 폼은 그 상태로 열린다.

```
┌─ 이 워크스페이스에 권한을 부여한다 ────────────────────────────────────┐
│                                                                        │
│  신제품기획  (워크스페이스)                                            │
│  ㉿ 박구름  →  관리                                       (R35-a)      │
│  ⊞ default  →  보기                                       (R111)       │
│                                                                        │
│  ⚠ 볼 수 있는 사람이 늘어난다.                                         │
│     박구름 님은 이 워크스페이스의 모든 문서를 열람하고 권한을          │
│     부여·회수할 수 있게 된다. 열람은 감사 로그에 기록된다. (R71-a·b)   │
│     default 그룹은 가입한 전원을 포함한다.                (R8·R60-a)   │
│                                                                        │
│  ⓘ 여기서 부여한 권한이 이 워크스페이스의 하위 전체에 상속된다.        │
│     상속이 끊긴 하위에는 적용되지 않는다.              (R127 · R127-a) │
│                                                                        │
│  ⓘ 지금은 아무 문서에도 적용되지 않는다. 이 워크스페이스에 문서가      │
│     만들어지는 순간부터 위 권한이 함께 적용된다.          (R115-f)     │
│                                                                        │
│                                        [ 취소 ]  [ 만들고 부여 ]       │
└────────────────────────────────────────────────────────────────────────┘
```

- **워크스페이스 관리자 지정은 생성 절차에 포함된 필수 단계**다 (R35-a). 미지정 시 `[생성]` 을 비활성화한다. **없으면 워크스페이스가 동작하지 않는 필수 항목**이라 이 폼에 있다.
- **이 폼의 두 부여(2 관리자 지정 · 3 `default` 초기 권한)는 합쳐서 L2 확인 1개를 거친다** (**R136** · ~~§9-Q36~~ 종결). **R125 계열에 "기존 노드" 한정 문언이 없다** — 개정 전 이 문서가 "생성 시점을 다루지 않는다"고 읽은 것은 **예시의 범위를 조항의 범위로 오인**한 것이었다. 노드 축으로도 두 경로가 같은 답을 낸다 — 관리자 지정은 **워크스페이스 `관리` 부여**(R125-b, R35-a 로 필수)이고 `default` 초기 권한은 **컨테이너 × 그룹**(R125).
  - **확인을 둘로 나누지 않는다.** 연속 다이얼로그는 **확인 피로를 학습시킨다** — 두 번째를 읽지 않고 넘기는 습관이 붙으면 확인 자체가 무력해진다. 하나의 다이얼로그에 두 부여를 나란히 적는다(위 와이어프레임).
  - **`[생성]` 버튼은 확인 관문이 아니다** (**R122-c · R136-c**). 소재가 폼 안이기 때문이다. 소수 의견은 `[생성]` 을 관문으로 삼자고 했으나, **그것을 인정하면 이동·복사의 `[복사]` 도 관문이 되어 R122-c 가 무력화**된다.
  - **기존 장치는 확인을 대체하지 못한다** (**R136-c**). R111-a(기본값 `없음`)는 **부주의**를 막고 확인은 **오판**을 막아 층이 다르다. R111-c(자유 가입 + `편집` 경고)는 ① **승인 모드**(사실상 전사)를 놓치고 ② **`보기` 를 포함하지 않아 R125-a 가 닫은 구멍이 그대로 남으며** ③ 소재가 폼 안이라 R122-c 문면상 **관문 자격이 없다.**
- **확인 다이얼로그에 `적용 하위 N개`(R126)를 표시하지 않는다** (**R136-a**). 생성 시점에는 **항상 0** 이라 **공허하다** — R131 이 워크스페이스를 대상에서 뺀 것과 같은 유형(공허하게 참인 값을 화면에 두지 않는다)이다. 대신 **R115-f 의 지연 고지**를 넣는다: "지금은 아무 문서에도 적용되지 않는다. 이 워크스페이스에 문서가 만들어지는 순간부터 위 권한이 함께 적용된다."
  - **`적용 하위 = 0` 은 등급을 낮추는 근거가 아니라 오히려 R115-a 둘째 축(효과의 잠재·지연)의 독립 근거다** (**R136-b**). **R115-e 가 "영향 건수 0" 을 L3→L2 강등 근거로만 썼지 L1 근거로 쓰지 않았다.** 그 워크스페이스는 곧 문서로 채워지고, **R8·R60-a 로 수혜자에 아직 계정도 없는 사람들이 포함**되는 무한 휴면 부여라 R115-b 의 `비활성 계정 부여`(L2)보다 강하다.
- **상속 파급 고지(R127·R127-a)를 폼과 확인 다이얼로그 양쪽에 넣는다.** 개정 전 이 절에는 이 고지가 **없었다** — §2.5(기존 워크스페이스)에만 있었다. 그러나 **`default` 초기 권한은 정확히 컨테이너 노드에 대한 부여**이고, R127 은 그 고지를 **컨테이너 노드 공통**으로 승격했다. 한쪽에만 두면 사용자는 "생성 시 고른 권한은 국소적"이라는 거짓 명제를 배운다. 둘째 줄("상속이 끊긴 하위에는 적용되지 않는다")은 **끊긴 노드의 유무와 무관하게 항상** 표시한다(R127-a). **이것이 `적용 하위`(숫자)와 갈리는 지점이다** — 공허한 **수치**는 빼고(R136-a) 조건 없는 **고정 문구**는 남긴다. 문구를 조건부로 만들면 그 등장 자체가 오라클이 되기 때문이다(R113).
- 워크스페이스는 상속 체인의 루트이므로 상속 플래그·"부모 권한 가져오기" 버튼을 노출하지 않는다 (R35-a). **여기서 R35-a 는 두 컨트롤 모두의 근거로 성립한다** — 상속의 시작점이라 끊을 상위도, 가져올 부모도 없기 때문이다. **`부모 권한 가져오기` 의 필요 레벨은 R135 로 확정**됐다(~~`G19`~~ 종결 — **`관리` 전용 · L2 · `편집` 에게 미노출**). 이 폼은 그와 무관하게 버튼을 렌더하지 않으며(R35-a), 그 규칙이 걸리는 곳은 디렉토리·문서 모달(`05` §1.4)이다.
- **`default` 그룹의 초기 권한을 생성 폼에서 선택한다. 기본값은 `없음`(fail-closed)** 이다 (**R111**). R35-a 로 이 폼은 이미 **워크스페이스 관리자 지정을 묻는 접근 설정 폼**이므로, 관리 접근만 묻고 일반 접근을 묻지 않으면 반쪽 질문이 되어 사용자가 생성 직후 공유 모달을 한 번 더 열게 된다.
- **R83 의 기본값 `편집` 을 답습하지 않는다** (**R111-a**). R83 은 부여할 사람이 아직 없고 1.0 데이터가 전원에게 도달해야 하는(R56·R93) **부트스트랩 순간의 예외**다. 새 워크스페이스를 만드는 통상 목적은 **경계 분리**(R69-d·R71-d)이므로 좁은 쪽이 기본값이다.
- **"접근자 0명"이라고 쓰지 않는다** (**R111-b**). `관리` 는 ACL 판정을 우회하며 열람을 함의하므로(R71·R71-a) 생성 직후 접근자는 **지정된 워크스페이스 관리자와 슈퍼유저**다. 비어 있는 것은 `default` 그룹에 대한 부여뿐이며, 화면 문구도 그렇게 쓴다.
- **자유 가입 모드(R7-①)에서 `편집` 을 고르면 경고를 표시한다** (**R111-c**). 문안과 형태는 설치 마법사 3단계의 R83 경고와 **동일**하다(§4.5) — 두 화면의 규칙이 갈리면 안 되므로 같은 컴포넌트를 재사용한다. 경고는 차단이 아니다.
- 표시 이름의 검증 규칙(중복 허용 여부, 길이, 공백)은 결정 로그에 없다. R40-e 의 노드 이름 검증은 문서·디렉토리 계층 규정이고, 워크스페이스 표시 이름은 R40-a 로 파일시스템 제약을 회피한 계층이다 → §9-Q15.
- 이 카테고리에 **삭제·아카이브는 없다.** R54·R92 에 따라 Phase 1 에는 워크스페이스를 없애는 수단이 없다.

### 2.12 인스턴스 › 인스턴스 설정 (R7 · R51 · R62 · R84-a · R86 · R96 · **R137-e**)

**저장 방식 — 개인 설정과 다르다 (설계 결정)**
개인 설정(§2.1·§2.2)은 필드 변경 즉시 저장한다. 인스턴스 설정은 **하단 sticky 액션 바의 명시적 `[저장]`** 을 거친다.

- 근거: 가입 모드를 잘못 눌러 `자유 가입` 이 되면 그 순간부터 외부 영향(누구나 계정 생성)이 발생한다. 개인 취향 설정과 인스턴스 정책은 오조작 비용이 다르므로 확정 방식을 다르게 둔다.
- 미저장 변경이 있는 상태에서 카테고리를 벗어나거나 모달을 닫으려 하면 "저장하지 않은 변경 3건" 확인을 띄운다.
- 저장 대상은 **DB 단일 저장소**다 (R96). config 파일은 부트스트랩 전용(포트·docsRoot·DB 경로)이므로 이 화면에 나타나지 않는다 (R96). 부트스트랩 값을 읽기 전용으로 표시할지는 §9-Q16.

**조합 경고 (설계자 판단 — §9-Q17)**
R83 은 **설치 마법사에서** 자유 가입 + default 편집 권한 조합에 경고를 표시하라고 규정한다. 같은 조합은 이 화면에서 사후에도 만들어질 수 있으므로 동일 경고를 표시한다.

```
  ( • ) 자유 가입 — 누구나 즉시 사용
  ┌──────────────────────────────────────────────────────────────────┐
  │ ! 기본 워크스페이스의 default 그룹이 `편집` 권한을 갖고 있다.     │
  │   자유 가입과 함께 두면 누구나 계정을 만들어 문서를 고칠 수 있다.│
  │                                        [ default 권한 확인하기 ] │
  └──────────────────────────────────────────────────────────────────┘
```

경고는 **차단이 아니다.** 저장을 막지 않는다 — R83 은 "경고를 표시한다"고만 규정한다.

**이 화면의 변경은 감사 로그에 기록된다 (R137-e)**

**인스턴스 설정 변경은 감사 로그(§2.7)의 기록 대상**이며, 특히 **감사 로그 보존 기간(R84-a)과 휴지통 보존 기간(R86)의 축소**가 그렇다. 개정 전에는 **증거를 없애는 행위가 감사 로그에 남지 않았다** — R115-e 가 그 조작에 L3 를 배정하면서까지 규모를 읽히려 했는데 정작 무기록이었다. 화면 쪽 귀결:

- **한 번의 `[저장]` 은 필드마다 1행을 남긴다** (**R141**). R137-e 는 **"인스턴스 설정 변경을 기록한다"** 까지만 정하고 입도를 정하지 않았는데, ~~`G26`~~ ③ 종결로 **R141 이 이 자리를 직접 덮는다** — 규범이 *"그 조작이 실제로 **바꾼 것**마다 1행"* 이고 여기서 바뀐 것은 **필드**다. 후단(`1행 + 영향 건수` 를 쓰지 않는다)도 같은 답을 낸다 — `1행 + 변경 건수` 가 정확히 그 형태다. 뒷받침 — **`이전값 → 이후값` 두 칸은 필드 단위로만 의미를 갖는다.** 3개 필드의 변경을 한 행에 담으면 그 두 칸이 무엇의 전후인지 말할 수 없다. 표시는 R141-a 대로 **`변경 3건` 묶음 1줄로 접히고 펼치면 3행**이 되어 위 와이어프레임의 수와 일치한다.
- **기록은 이 화면의 조작이 아니라 서버의 결과**다. 화면에 "기록되었습니다" 같은 별도 표시를 두지 않는다 — 감사 로그로 가는 동선은 **좌측 카테고리의 `감사 로그` 항목**(§2.7)이 이미 갖고 있다.
- **인스턴스 이벤트이므로 `인스턴스 전체` 스코프에서만 보인다**(§2.7 스코프 표) — 슈퍼유저 전용이며, 이 화면 자체가 슈퍼유저 전용이라 관측자와 조작자의 범위가 일치한다.
- **`감사 로그 보존 기간` 을 줄이는 조작은 그 자신의 기록도 언젠가 지운다.** 축소 이력이 축소된 보존 창 밖으로 나가면 사라진다 — R84-a 가 정하는 것은 **수정·삭제 불가**이지 **만료 불가**가 아니다. 이 성질은 아래 **`G27`** 과 같은 자리에서 나온다.

**필드별 부수 효과 안내**
- 보관 버전 개수를 **줄이면** 기존 초과분의 처리가 문제가 된다(R62 는 "개수를 초과하면 오래된 버전부터 폐기"라고만 규정). 값을 낮추면 인라인 경고를 표시한다 → 실제 시점 규칙은 §9-Q18.
- 휴지통 보존 일수를 **줄이면** 이미 그 기간을 넘긴 항목이 다음 정리에서 사라진다. 확인 등급은 **그 순간의 영향 건수로 정한다** — 건수 > 0 이면 **L3**(타이핑 토큰 = 건수 자체), 0 이면 **L2** (R115-e). 지연 효과 문구는 두 경우 모두 표시한다 (R115-f).
- 감사 로그 보존 기간을 **줄이면** 이미 그 기간을 넘긴 기록이 사라진다. R84-a 가 감사 로그를 수정·삭제 불가로 규정하므로 이 값의 축소는 **유일하게 허용된 기록 소멸 경로**다. 확인 등급은 휴지통과 동일하게 **영향 건수로 정한다** (R115-e).

**두 보존 기간에 대해 원장이 정하지 않은 것 (`G27` → §9)**

| 미정 | 화면에서의 증상 |
|---|---|
| **감사 로그 보존 기간의 기본값** | 위 와이어프레임의 `365` 는 **자리를 보이기 위한 예시값**이며 근거가 없다. R86 은 휴지통에 대해 기본 30일을 명시하는데 **R84-a 에는 대응 문장이 없다** |
| **`0` 의 의미** | 휴지통 필드는 R86 이 `0 = 무제한` 을 명시해 안내 문구를 쓸 수 있다. **감사 로그 필드에는 그 규정이 없어** 같은 문구를 쓰지 못한다 — 임의로 복사해 넣지 않는다 |
| **휴지통 보존과의 대소 관계** | **R137-d 로 삭제가 기록 대상이 되면서 실제 문제가 된다** — 감사 보존 < 휴지통 보존이면 **삭제 기록이 휴지통 행보다 먼저 사라지는 역전**이 생긴다. 오프보딩 조사는 수개월 뒤 시작된다(§2.8) |

**정해지기 전까지 화면은 두 값을 독립 필드로 두고 대소 검증을 걸지 않는다** — 검증을 넣으면 원장에 없는 제약을 화면이 만든다.

### 2.13 공통 — 주체 검색 규칙 (R112)

사용자·그룹을 검색해 추가하는 UI 는 이 문서에서 두 곳에 등장한다 — 워크스페이스 관리자 추가(§2.5)와 그룹 멤버 추가(§2.9). **둘 다 공유 모달(R12)과 같은 단일 공용 컴포넌트 `PrincipalPicker` 를 쓴다** (**R112-e**). 화면마다 자체 검색 UI 를 만들지 않는다 — 규칙만 정하고 부품을 묶지 않으면 부품 계층에서 규칙이 다시 갈린다.

| 규칙 | 내용 | 근거 |
|---|---|---|
| 노출 범위 | `active` 와 `pending` 을 노출하고 **상태 배지를 붙인다**. `rejected` 는 제외한다 | R112 |
| `pending` 노출 이유 | 입사 전 사전 세팅이라는 실제 수요가 있고, R60-a 로 활성화 시점에 자동 유효화된다 | R112, R60-a |
| `suspended` 부여 | **L2 확인**을 거친다. 재활성화 시 되살아나는 휴면 부여이기 때문이다 | R112-a, R115-a |
| 배지 문구 | 중립어 **`비활성`** 을 쓴다. 제3자에게 징계·오프보딩을 함의하는 표현을 쓰지 않는다 | R112-a |
| 중립어의 적용 범위 | **주체 검색 결과에 한정**된다. 슈퍼유저 전용 사용자 관리 화면(§2.8)은 R60 의 4상태를 그대로 쓴다 | **R112-d** |
| 열거 방지 | **최소 질의 길이 2자 · 결과 건수 상한 20건** | R112-b |

**명단 노출 재검토 (R118)** — R118 은 접근자 명단(공유 모달의 접근자 목록·그룹 멤버 전개·시뮬레이션 결과 명단)을 **어디서든 `관리` 전용**으로 두고 수치만 `편집` 까지 허용한다. 이 문서가 명단을 보여주는 화면은 세 곳이며 **전부 `관리` 이상 게이트를 이미 통과한다** — 워크스페이스 관리자 목록(§2.5, 해당 워크스페이스 `관리`) · 그룹 멤버 목록(§2.9, 슈퍼유저) · 사용자 관리(§2.8, 슈퍼유저). 따라서 R118 로 인한 변경은 없다. 새 화면을 추가할 때는 이 기준으로 먼저 검사한다.

**접근자 지표 재검토 (R121)** — R121 은 지표를 `접근 가능 N명`(상방 게이트 포함)과 `ACL 접근자 N명`(ACL·상속 경유만)으로 분리한다. **이 문서의 화면은 접근자 지표를 표시하지 않으므로 적용 지점이 없다** — §2.11 의 `관리 권한` 열은 그 워크스페이스의 `관리` 부여 건수이고 접근자 총계가 아니다. R121-b 가 금지하는 "아무도 볼 수 없습니다" 류의 문구도 이 문서에 없다. §2.11 의 "생성 직후엔 지정한 `관리` 권한자와 슈퍼유저만 접근한다"는 이미 R121-b 와 같은 어법이다.

**적용 범위 (R112-c)** — R112 계열은 공유 모달뿐 아니라 **주체를 고르는 모든 화면**에 적용한다. 같은 사용자 디렉토리를 조회하는 화면들에 규칙을 다르게 두면 R112-b 가 막으려는 열거 표면이 다른 화면에 그대로 남기 때문이다. 따라서 이 규칙은 화면별 재량이 아니라 **`PrincipalPicker` 컴포넌트에 내장**한다 — R112-b 의 구체값(2자·20건)도 여기에 박는다 (R112-e, §7).

## 3. 대용량 목록 처리 전략

### 3.1 문제 정의

R19 는 수백~수천 명 규모를 전제한다. R24 는 그 사용자 목록을 **설정 모달 안에** 넣으라고 요구한다. 옵시디언의 설정 모달은 개인 환경설정용이라 이 규모의 목록을 담아본 적이 없다. **모달 크기 안에서 성립하는지를 먼저 검증한다.**

### 3.2 세로 예산 검증

| 항목 | 1200×820 (기준) | 1366×768 (사내 노트북) |
|---|---|---|
| 모달 높이 | 820 | 691 (`90vh`) |
| − 모달 헤더 | 56 | 56 |
| − 패널 제목 + 툴바 | 88 | 88 |
| − 테이블 헤더 | 40 | 40 |
| − 페이지네이션 바 | 48 | 48 |
| − 상하 패딩 | 32 | 32 |
| **= 행 영역** | **556px** | **427px** |
| 행 높이 40px 기준 | **13.9행** | **10.7행** |

**결론: 한 화면에 11~14행이다.** 3,214명을 이 창으로 훑는 것은 250스크린 분량이며 **탐색(browse)으로는 성립하지 않는다.** 성립하는 것은 **검색(search)** 뿐이다. 이 사실이 아래 전략 전체의 근거다.

### 3.3 가로 예산 검증

패널 콘텐츠 폭 891px(§1.2)에 대해 §2.8 의 6열 구성은 합계 886px 로 성립한다. 열이 7개를 넘으면 성립하지 않으므로 **관리 테이블의 열 상한을 6으로 고정**하고, 그 밖의 정보는 행 펼침 또는 상세 화면으로 보낸다.

### 3.4 채택 전략 — 검색 우선(search-first)

| # | 전략 | 내용 |
|---|---|---|
| 1 | **탐색이 아니라 검색을 기본 동선으로** | 첫 진입 시 최근 가입순 1페이지를 보여주되, 툴바의 검색 입력에 자동 포커스한다. "전량을 훑을 수 있다"는 인상을 주지 않는다 |
| 2 | **서버 사이드 페이징** | 페이지 크기 50 고정. 전량을 클라이언트로 내리지 않는다. 정렬·필터·검색도 전부 서버 파라미터다 |
| 3 | **검색 디바운스 300ms + 요청 취소** | 타이핑 중 요청이 쌓이지 않게 이전 요청을 취소한다 |
| 4 | **페이지 전환 시 이전 데이터 유지** | `@tanstack/react-query` 의 `placeholderData` 로 로딩 중 테이블이 비는 깜빡임을 없앤다(§7 버전 확인 필요) |
| 5 | **행 가상화는 쓰지 않는다** | 페이지당 50행은 DOM 에 그대로 렌더해도 문제없다. 가상화는 오히려 스크롤 위치·포커스 버그를 부른다. 예외는 §3.5 |
| 6 | **컴팩트 행(40px) + 열 6개 상한** | §3.2·§3.3 예산 준수 |
| 7 | **패널 본문만 스크롤** | 툴바와 페이지네이션 바는 sticky. 스크롤을 내려도 검색과 페이지 이동이 항상 손에 있다 |

**성립 판정: 성립한다.** 단 "모달 안에서 수천 명을 훑을 수 있다"가 아니라 **"모달 안에서 수천 명 중 원하는 사람을 찾아 조작할 수 있다"** 로 성립한다. 슈퍼유저의 실제 작업(특정 사용자 정지, 특정 사용자 그룹 변경)이 후자이므로 요구를 만족한다.

### 3.5 예외 — 감사 로그만 무한 스크롤 + 가상화

감사 로그(§2.7)는 성격이 다르다. 행이 수만~수십만이고, 조작 대상이 아니라 **읽고 지나가는 흐름**이며, 페이지 번호에 의미가 없다(시간순 연속체다). 따라서 여기만 **커서 기반 무한 스크롤 + `@tanstack/react-virtual` 행 가상화**를 쓴다.

2. **R73 이 "`active` 멤버 수 0" 이라는 결과 조건으로 걸리는 거부 규칙**이라 일괄 조작은 부분 실패가 필연이다. "50명 중 1명이 마지막 슈퍼유저라 거부됨"을 사용자가 이해 가능한 형태로 되돌리는 UI 는 조작 자체보다 복잡하다.
3. 검색 결과 전체 선택("3,214명 전체 선택")은 **대상이 화면에 보이지 않는 상태의 파괴적 조작**이다. R60 의 정지는 R58-d 로 그 계정의 전 PAT 를 즉시 무효화하므로 되돌려도 발급된 토큰은 돌아오지 않는다.

## 4. 설치 마법사 (R72 · R72-a · R72-b · R83)

### 4.1 성격

- **모달이 아니라 전체 화면**이다. 이 시점에는 로그인한 사용자도, 뒤에 깔릴 앱 화면도 존재하지 않는다.
- 진입 조건: **슈퍼유저 그룹의 멤버가 0명인 상태로 서버가 기동**하면 모든 요청을 설치 화면으로 돌린다 (R72). 슈퍼유저 판정은 그룹 멤버십 하나다 (R81).
- 완료 전까지 **일반 가입·로그인·API·MCP 경로를 전부 차단**한다 (R72-a). 브라우저 요청은 설치 화면으로, 비-브라우저 요청은 차단 응답으로 처리한다(응답 형태는 §9-Q20).

### 4.2 단계 흐름

4단계까지는 자유롭게 뒤로 갈 수 있다. **5단계 이후 뒤로 가기는 없다** — 설치는 1회용 토큰을 소비하는 비가역 조작이다.

**4단계는 입력 요약이지 확인 관문이 아니다** (R122-c · R136-c). `default` 그룹 초기 권한(R83)은 **부여 조작**이므로 `[설치 완료]` 뒤에 **별도 L2 확인 1개**를 거친다 (**R136-d** → §4.5).

**근거** — R72-b 는 "서버 콘솔에 출력된 1회용 설치 토큰"을 요구한다. 목적은 사내망에서 먼저 접속한 사람이 인스턴스를 선점하는 경로 차단이며, 따라서 화면은 **콘솔 접근 방법을 안내하는 것**까지가 역할이다.

**수명·복구는 R72-c~f 가 정한다** (2026-08-16 신설 — `G21` 종결).

- **30분 수명**(R72-c)이고 콘솔이 **만료 시각을 절대시각으로** 함께 낸다. 개정 전 이 와이어프레임은 *"이 프로세스가 살아 있는 동안만 유효하다"* 고 적었는데, **원장에 근거가 없는 단정**이었고 같은 문서 §4.8-F4 가 *"토큰 수명 규칙은 결정 로그에 없다"* 고 적어 **한 문서가 같은 사실을 두 자리에서 다르게 말하고 있었다.**
- **재기동하면 이전 값은 무효가 되고 새 값이 나온다**(R72-d). 이것이 **분실·만료의 유일한 복구 경로**이므로(R72-e) 화면이 그 사실을 안내한다.
- **`1회용` 은 "완료 시 소진"이다**(R72-f) — 오타로 틀려도 재입력할 수 있다. 화면이 입력 실패를 최종 상태로 그리지 않는다.

**이 화면은 토큰을 소비하지 않는다** (R72-g) — 토큰 검증은 **설치 세션을 발급**하고, 2~5단계와 `[설치 완료]` 요청이 그 세션을 요구한다. **단계 전환을 클라이언트 상태로만 그리면 커밋 엔드포인트가 무방비가 된다.**

경고는 **표시하되 진행을 막지 않는다** — R83 은 "경고를 표시한다"고만 규정한다.

이 경고는 **워크스페이스 생성 폼(§2.11, R111-c)과 인스턴스 설정(§2.12, §9-Q17)에도 같은 문안·같은 형태로** 나타난다. 세 화면이 같은 컴포넌트를 재사용하므로 규칙이 갈릴 수 없다 — 같은 위험한 조합을 한 화면에서만 경고하면 나머지 두 경로가 그대로 뚫린다.

**초기 권한 부여에도 §2.11 과 같은 L2 확인 1개를 둔다** (**R136-d**)

**`default` 앞으로 부여된 ACL 은 R119 상 재생성되지 않는데**(R8·R60-a 는 **멤버십** 규정이다) **그 유일한 출생지가 이 마법사와 워크스페이스 생성 폼**이고, **둘 다 무확인이었다.** 여기는 **범위가 인스턴스 전원이라 §2.11 보다 넓다** — 기본값이 `편집`(R83)이고 R56 의 기본 워크스페이스가 1.0 데이터 전량을 받는다(R93). **G13**(설치 마법사가 교차 검증을 받지 않았다)이 등재한 자리와 겹친다.

`[설치 완료]`(4단계 §4.6)를 누르면 확인 다이얼로그가 한 번 더 뜬다.

```
┌─ 이 워크스페이스에 권한을 부여한다 ────────────────────────────────────┐
│                                                                        │
│  workspace  (워크스페이스)                                (R56)        │
│  ⊞ default  →  편집                                       (R83)        │
│                                                                        │
│  ⚠ 볼 수 있는 사람이 늘어난다.                                         │
│     default 그룹은 이 인스턴스에 가입하는 전원을 포함한다. (R8·R60-a)  │
│     아직 계정을 만들지 않은 사람도 가입하는 순간 이 권한을 받는다.     │
│                                                                        │
│  ⓘ 여기서 부여한 권한이 이 워크스페이스의 하위 전체에 상속된다.        │
│     상속이 끊긴 하위에는 적용되지 않는다.              (R127 · R127-a) │
│                                                                        │
│  ⓘ 지금은 아무 문서에도 적용되지 않는다. 이 워크스페이스에 문서가      │
│     만들어지는 순간부터 위 권한이 함께 적용된다.          (R115-f)     │
│                                                                        │
│                                        [ 이전 ]  [ 설치하고 부여 ]     │
└────────────────────────────────────────────────────────────────────────┘
```

- **`[설치 완료]` 버튼도, 4단계 `검토` 화면도 확인 관문이 아니다** (**R122-c · R136-c**). 검토 화면은 **입력 요약**이라 부여의 파급(R127 상속 고지)도 지연 효과(R115-f)도 담지 않으며, 그것을 관문으로 인정하면 §2.11 의 `[생성]` 을 관문으로 삼자던 소수 의견을 되살려 R122-c 가 무력화된다. **R136 이 요구하는 것은 "입력을 마친 뒤의 별도 확인 1개"** 이고 위 다이얼로그가 그것이다.
- **`적용 하위 N개` 를 표시하지 않는다** (**R136-a**) — 설치 시점의 `workspace` 는 비어 있어 **항상 0** 이라 공허하다. **1.0 데이터 이행은 설치 이후의 별도 도구**이므로(R93 ②) 이 시점에 하위가 있을 수 없다. 대신 **R115-f 지연 고지**를 넣는다.
- **`적용 하위 = 0` 이 등급을 낮추지 않는다** (**R136-b**) — 오히려 **R115-a 둘째 축(효과의 잠재·지연)의 독립 근거**다. 여기서는 그 성질이 §2.11 보다 강하다: 이행 후 `workspace` 는 **1.0 문서 전량**을 담고(R93), 수혜자에는 **아직 계정도 없는 사람들**이 포함된다(R8·R60-a).
- **R111-c 계열의 자유 가입 경고는 이 확인을 대체하지 못한다** (**R136-c**) — ① **승인 모드**(사실상 전사)를 놓치고 ② **`보기` 를 포함하지 않아** R125-a 가 닫은 구멍이 그대로 남으며 ③ 소재가 폼 안이라 관문 자격이 없다. **경고와 확인은 층이 다르므로 둘 다 둔다** — 위 경고 블록은 3단계에, 확인 다이얼로그는 4단계 뒤에 있다.
- **가입 모드(R7)와 슈퍼유저 계정은 이 확인의 대상이 아니다.** R136 이 합치라고 한 것은 **같은 조작(부여) 둘**이고, 가입 모드는 부여가 아니라 정책 설정이다. 넓히면 확인이 "설치 요약 재확인"이 되어 §4.6 검토 화면과 중복된다(R124).

**설계 판단 2건**
1. 가입 모드를 마법사에서 고르는 근거: R83 이 "자유 가입 모드(R7-①)와 조합 시 마법사가 경고를 표시한다"고 규정하므로, 마법사가 가입 모드를 알아야 경고가 성립한다. 가장 단순한 형태는 마법사에서 함께 고르는 것이다. (§9-Q22)
2. 가입 모드의 기본 선택을 **②승인**으로 둔다. R7 의 기본값은 결정 로그에 없다. 세 선택지 중 ②가 fail-closed 다(계정은 만들어지되 승인 전에는 R60-a 로 어떤 그룹 ACL 도 갖지 않는다). (§9-Q22)
3. **기본 워크스페이스 이름은 이 화면에서 바꾸지 않는다.** R56 이 이름을 `workspace` 로 확정했고, 개명 수단은 설치 후 §2.5 에 이미 있다.

### 4.6 4단계 — 검토

```
┌──────────────────────────────────────────────────────────────────────────┐
│   검토                                                                   │
│     슈퍼유저          admin (admin@corp.kr)                              │
│     가입 방식         가입 요청 + 슈퍼유저 승인                          │
│     기본 워크스페이스 workspace                                          │
│     default 그룹 권한 편집                                               │
│                                                                          │
│   설치를 완료하면 로그인·API·MCP 경로가 열린다. (R72-a)                  │
│                                    [ 이전 ]  [ 설치 완료 ]               │
│   4/4                                                                    │
└──────────────────────────────────────────────────────────────────────────┘
```

**이 화면은 입력 요약이며 확인 관문이 아니다** (R122-c · R136-c). `[설치 완료]` 를 누르면 **초기 권한 부여에 대한 L2 확인 다이얼로그**가 한 번 더 뜬다 (**R136-d** → §4.5). 이 요약에는 부여의 파급(R127 상속 고지)도 지연 효과(R115-f)도 담기지 않으므로 확인을 대체하지 못한다.

### 4.7 5단계 — 완료

```
┌──────────────────────────────────────────────────────────────────────────┐
│   설치가 끝났다.                                                         │
│   설치 토큰은 사용되어 더 이상 유효하지 않다.                            │
│                                                     [ 시작하기 ]         │
└──────────────────────────────────────────────────────────────────────────┘
```

`[시작하기]` 는 방금 만든 계정으로 **자동 로그인한 상태**의 메인 화면으로 보낸다. 근거: 마법사가 이미 1회용 콘솔 토큰으로 운영자를 인증했고, R72-a 차단이 해제되는 시점에 바로 사용 가능해야 한다. 다만 이 자동 로그인은 결정 로그에 없다 → §9-Q23.

## 5. 위험한 조작의 확인 흐름

### 5.1 사전 비활성화 vs 시도 후 거부 — 판단 기준

거부 규칙을 UI 에서 **미리 막을지**, **눌러보고 거부할지**는 다음 3개 질문으로 정한다.

1. **비활성 사유를 표시하는 것이 정보를 노출하는가?** 노출하면 사전 비활성화를 쓸 수 없다.
2. **판정 근거가 UI 에서 stale 해질 수 있는가?** 그렇다면 사전 비활성화는 보조 수단일 뿐 서버가 권위다.
3. **눌러본 뒤의 거부가 사용자에게 학습 가치가 있는가?** 불변 속성이면 학습 가치가 없다.

### 5.2 규칙별 채택

| 규칙 | 채택 | 근거 |
|---|---|---|
| **R73** — 슈퍼유저 `active` 멤버 수 0 방지 (정지 · `pending`·`rejected` 전환 · 슈퍼유저 그룹에서 제거 · 오프보딩 1·3단계) | **사전 비활성화 + 서버 재검증** | ① 이 화면들은 슈퍼유저 전용이라 "슈퍼유저가 몇 명인가"는 이미 그룹 관리 화면에 보인다 — 비활성화가 새 정보를 노출하지 않는다. ② 다른 탭에서 슈퍼유저가 추가/제거되면 UI 판정이 stale 해지므로 **서버가 최종 권위**이고 거부 시 인라인 오류 + 목록 재조회. ③ 사유를 미리 알려주는 편이 낫다 |
| **R73 의 적용 판정** | 열거가 아니라 **조건으로 판정** | R73 의 규범은 "`active` 멤버 수가 0 이 되는 결과"라는 조건 자체이고 열거는 예시다. 따라서 **계정 삭제(R101 로 폐기)와 R43-1 ACL 일괄 회수는 가드 대상이 아니다** — 전자는 조작이 존재하지 않고 후자는 멤버 수를 바꾸지 못한다. 새 조작을 추가할 때는 이 조건을 만들 수 있는지로 판단한다 |
| **R30-a** — 시스템 그룹(슈퍼유저·default) 삭제·개명 불가 | **사전 비활성화** | 불변 속성이라 stale 해질 수 없고(질문 2 해당 없음), 눌러서 실패하는 데 학습 가치가 없다(질문 3). 서버도 동일하게 거부한다 |
| **R100-b** — 휴지통 영구 삭제(`관리` 필요) | **버튼 미표시** (비활성이 아니라 없음) | R100 으로 휴지통 카테고리는 누구에게나 보이므로 카테고리 숨김에 기댈 수 없다. 목록은 여러 워크스페이스가 섞이므로 **행마다 그 행의 워크스페이스 기준**으로 판정한다(R100-a) |
| **R74-a** — 하위에 볼 수 없는 노드가 있는 디렉토리 삭제·이동 | **시도 후 거부** (참고 — 트리 담당 영역) | 사전 판정을 화면에 반영하면 "여기 숨은 노드가 있다"는 사실이 노출되어 R25 위반이다. 거부 메시지도 존재를 드러내지 않는 일반 문구여야 한다 |
| **R109** — 워크스페이스 마지막 `관리` 권한자 제거 | **차단하지 않고 확인 다이얼로그로 경고** | R29 로 슈퍼유저가 항상 도달하므로 lockout 이 아니다 — **복구 가능한 상태에 하드 차단을 두는 것은 잘못된 fail-closed 다.** 차단하면 오프보딩(R101-b)이 "후임 지정"에서 멈추고, 가드를 만족시키려 형식적 워크스페이스 관리자를 끼워 넣게 되는데 그 계정이 R71-a 로 전 문서 열람권을 갖는다. 대신 R109-a 의 `관리자 없음` 배지로 상태를 상시 노출한다 |
| 자기 자신을 슈퍼유저 그룹에서 제거 | **L3 확인 후 허용** (§5.3) | 다른 `active` 슈퍼유저가 있으면 R73 이 금지하지 않는다. 다만 되돌리려면 타인의 도움이 필요하므로 확인 강도를 높인다 |

**공통 원칙 1** — 사전 비활성화는 UX 장치이고 **거부의 권위는 항상 서버**다. 클라이언트가 막았다는 이유로 서버 검증을 생략하지 않는다 (R59 가 매 요청 판정을 요구하는 것과 같은 이유).

**공통 원칙 2 (R113)** — **확인 다이얼로그를 존재 판정에 쓰지 않는다.** 확인 단계의 유무·문구가 요청자에게 보이지 않는 대상의 존재 여부에 따라 달라져서는 안 된다. 새 확인 흐름을 설계할 때 이 규칙으로 먼저 검사한다. 이 문서에서 조건에 따라 달라지는 확인은 **요청자가 이미 아는 사실**에만 반응한다 — 자기 권한 레벨, 자기가 고른 주체의 계정 상태(R112-a), 시스템 그룹 여부(R30-a). 휴지통 복구의 이름 충돌에 확인 단계를 두지 않는 것(R102)이 같은 원리다.

**공통 원칙 3 (R114)** — 접근자 **인원 수에 시점을 표기하지 않는다**(`12명(08-12 기준)` 금지). R110 으로 ACL 에 시간 축이 없으므로 날짜 접미는 만료·시점 판정이 존재한다는 오해를 만든다.

**공통 원칙 4 (R116)** — **확인 다이얼로그를 열 때 표시할 수치를 재조회하고, 직전 값과 다르면 실행을 잠그고 갱신된 값을 보여준다.** R14-b 가 유효 권한을 매 요청 계산하므로 수치는 언제든 달라진다. 이 문서에서 적용 대상은 그룹 삭제의 `권한 항목 N건`, 휴지통 보존 일수 축소의 `영향 N건`, 감사 로그 보존 기간 축소의 `영향 N건`, 오프보딩 카드의 `항목 N건`, **워크스페이스 `관리` 부여의 `적용 하위 N개`**(R126-d 가 재조회 대상 포함을 직접 요구한다 — 다이얼로그를 띄운 사이 하위에서 상속이 끊기면 값이 달라진다) 이다. 다이얼로그를 띄운 사이에 값이 바뀌면 사용자가 잘못된 규모를 근거로 승인하게 된다.

### 5.3 확인 등급 (R115 · R125 계열 · R129 · R130 · R131 · **R133 계열 · R136 계열**)

**등급 체계는 이 문서가 소유하지 않는다.** 정의는 `05.screen-design-permission.md` §5 가 소유하고 이 문서는 참조한다 — 같은 이름에 다른 의미를 두면 두 문서를 오가며 구현할 때 확인 단계가 통째로 사라진다 (R115).

**등급의 UI 는 R115 가 정의한다.**

| 등급 | 형태 |
|---|---|
| **L1** | 확인 없이 즉시 실행 + **토스트** — **좁히기는 `실행취소` 버튼, 넓히기는 `회수` 버튼**(**R129**, 아래 인용) |
| **L2** | **확인 다이얼로그** |
| **L3** | **타이핑 확인** (토큰은 조작에 따라 갈린다 — 기본은 대상 이름, **규모를 읽혀야 하는 조작은 영향 건수**: R115-e · R131 · R142-c) |

> **L1 토스트 라벨의 예외 (R129)** — **넓히기 L1** 의 토스트는 `실행취소` 가 아니라 **`회수`** 로 표기하고, **되돌려도 이미 열람된 내용은 회수되지 않음**을 문구에 남긴다. R115 가 L1 을 "실행취소 토스트"로 정의하는데 R122 는 넓히기를 비가역으로 정했으므로, 그대로 두면 **되돌릴 수 없는 조작에 `실행취소` 버튼이 붙는 모순**이 된다. **이 문서가 배정한 L1 조작(그룹 멤버 제거·가입 거절)은 넓히기가 아니므로 `실행취소` 를 그대로 쓴다** — 새 넓히기 조작을 이 문서에 추가할 때만 걸리는 규칙이다.

**배정 기준은 R115-a 가 정의한다 — 가역성과 효과의 즉시성 두 축이다.**

| 등급 | 조건 |
|---|---|
| **L1** | 가역이고 **효과가 즉시 드러남** |
| **L2** | 비가역**이거나** 효과가 **잠재·지연**됨 |
| **L3** | L2 조건 + **광범위**(다건 · 서브트리 · 인스턴스 전역) |

> 되돌릴 수 있어도 **지금 아무 일도 일어나지 않는 조작**은 사용자가 결과를 확인할 수 없으므로 확인이 필요하다 (R115-a). 이 축이 들어오면서 아래 배정을 전면 재검토했다.

**`서브트리` 광범위 조건의 대응 조작 (R131 · R125-c)** — 개정 전에는 R115-a 가 든 광범위 예시 셋 중 **`서브트리` 에만 대응 조작이 없었다**(이 문서의 배정은 `다건`·`인스턴스 전역` 만 쓴다). 그 자리는 **R131 — 디렉토리에 대한 `상속 끊기` L3** 가 채운다. **워크스페이스는 대상이 아니다** — R35-a 로 상속의 시작점이라 끊을 상위가 없고 토글 자체를 렌더하지 않으며, **원장이 2026-08-14 R131 의 대상을 `컨테이너 노드`→`디렉토리` 로 정정**했다. R122-b 가 상속 끊기를 L2 로 정한 근거(끊긴 동안 편집 중이던 사용자의 저장이 R91-② 로 거부되어 **본문이 유실**된다)가 **서브트리 규모로 확대**되므로, **실제 본문 유실(진짜 비가역) + 서브트리**로 L3 조건을 정직하게 충족한다. 타이핑 토큰은 **영향 건수**이며(R115-e 선례) 건수 표기에는 R126-b 의 분모 금지가 그대로 걸린다. **화면은 `05` 소유**이므로 이 문서의 배정표에는 인접 조작으로만 싣는다(아래).

**반대 방향은 성립하지 않는다 (R125-c)** — **넓히기는 L2 를 넘지 않는다.** `서브트리` 축은 **좁히기·파괴 조작의 L3 판정에만** 쓴다. R115-b 가 배정한 L3 는 전부 실제 데이터 파괴이고, R122 의 "비가역"은 *이미 열람된 내용을 회수할 수 없다*는 은유적 비가역이지 파괴가 아니다. 운영상으로도 폴더 부여에 타이핑을 걸면 **회피 경로가 "상위 폴더나 워크스페이스에 더 넓게 한 번 부여"** 가 되어 실제 부여 범위를 오히려 넓힌다.

| **주체 일괄 회수** — 주체 **1명이든 여러 명이든** | **비가역**(재부여는 새 부여) | 즉시 | **광범위**(다건) | **L3** | **주체를 여러 명 고르는 것은 R142-a 로 허용되며 새 조작 종류가 아니다**(~~`G9`~~ 종결 — R43-1 의 술어를 `IN (…)` 으로 넓힌 것이다). 화면은 **`05` §2.4 가 소유**한다. **확인은 묶음 1회**(**R142-b** — 항목마다 받으면 각 항목이 단건이라 `일괄 L3` 배정이 애초에 도출되지 않는다) · **토큰은 회수될 `acl_entry` 항목 수**(**R142-c** — R115-e·R131 의 세 번째 적용. **`0건` 은 L2 로 강등하는 것이 아니라 진행 자체를 막는다** — R115-e 의 `0건 → L2` 는 **보존 기간 축소처럼 0건에도 조작이 성립하는 자리**의 규칙이고 회수는 0건이면 바꿀 것이 없다. **위 `보존 기간 축소` 행과 혼동하지 않는다**) · 건수는 R116 재조회 · R116-a 로 토큰 갱신 · **분모를 붙이지 않는다**(R126-b) |
| 오프보딩 4단계 (ACL 일괄 회수) | — | — | — | (위임) | R101-e 로 R43-1 화면이 소유한다. `default` 그룹 대상은 R119-a 로 **L3** 이다 |

**지연 효과 고지 (R115-f)** — 등급 표시와 무관하게, 지연 효과 조작에는 **"지금은 아무 일도 일어나지 않고 다음 정리 시점에 한꺼번에 사라진다"** 는 취지를 문구로 알린다. 영향 건수가 0이어서 L2 로 내려가는 경우에도 이 문구는 유지한다.

**확인 등급과 감사 기록은 서로 다른 축이다 (R137-d)** — 이 표의 등급을 **기록 여부의 근거로 옮겨 적지 않는다.** **R115 는 마찰의 축, R84 는 조회 가능성의 축**이고 둘을 잇는 조항이 원장에 없다. 반례가 이미 표 안에 있다 — `그룹 멤버 제거`·`가입 거절` 은 **L1** 인데 R84 열거에 있고, `ACL 항목 회수`(§5.3 인접 조작 표, L1)도 같다. 반대 방향으로, **이 표에서 가장 무거운 `보존 기간 축소`(L3)가 개정 전에는 무기록**이었다 — **R137-e** 가 그것을 기록 대상으로 넣었다(§2.12). **삭제(휴지통 이동)가 L1 이라는 사실도 기록 여부와 무관하다**(R137-d · §2.4 · EC36).

**넓히기의 취급 (R122 · R125 · R136)** — 이 표의 넓히기는 **셋**이다: `관리` 부여(§2.5) · **워크스페이스 생성 시점의 부여**(§2.11) · **설치 마법사의 초기 권한**(§4.5). 셋 다 **가역성 축에서 비가역으로 취급**한다 — ACL 항목을 지워도 이미 열람된 내용은 회수할 수 없기 때문이다. **등급은 두 축으로 갈린다 (R125)** — **주체 집합의 명시성**(R122-a)과 **대상 노드의 범위**다. 단건 주체 × **문서**면 L1, **어느 한쪽이라도** 집합이거나 **컨테이너 노드(디렉토리·워크스페이스)** 면 **L2** 이며, **L3 로는 올라가지 않는다**(R125-c).

> **R122-a 의 문언이 정정되었다 (2026-08-14)** — 초판의 `대상 집합` 이 **`주체 집합`** 으로 바뀌고 **"주체를 지목하지 않는 조작(복사 · 상속 되돌리기 · 부모 권한 가져오기)은 언제나 불특정 집합이다"** 가 추가됐다. **이 문서가 `워크스페이스 관리 부여 = L2` 의 근거를 노드 축으로 적어 `05` 와 갈렸던 것**(§9 경계면 ⑥)의 **진짜 원인이 이 문면 공백**이었고, R125 가 축을 나눈 뒤에도 조항 본문이 고쳐지지 않아 남아 있었다. 같은 공백이 `G17`(문서 단건 복사)이 갈린 원인이기도 했다 — **R133** 이 그것을 닫았다.

> **생성 시점 부여가 이 표에 새로 들어온 이유 (R136)** — 개정 전 이 문서는 *"R125 계열이 전부 기존 노드를 규정하고 생성 시점을 다루지 않는다"* 고 읽어 §2.11 을 미결(Q36)로 남겼다. **그 독해가 틀렸다** — **R125 계열에 "기존 노드" 한정 문언이 없고**, 예시의 범위를 조항의 범위로 오인한 것이다. 같은 부여가 **경로(생성 폼 / 공유 모달)에 따라 갈리던 상태**가 종결됐다.

> **이 두 축이 왜 필요했는가 (R125-a)** — 개정 전에는 R122-a 의 "대상 집합"이 주체 집합인지 영향 노드 집합인지 특정되지 않아, **워크스페이스에 개인 1명을 `보기` 로 부여하는 조작이 L1(무확인)** 이었다. `관리` 부여만 L2 로 잡혀 있어 **"전 문서를 볼 수 있게 한다"는 무확인이고 "전 문서를 보고 권한도 만질 수 있게 한다"만 확인을 받는** 상태였다 — R71-a 가 관리 권한의 열람 함의를 경고 대상으로 삼았으면서 **같은 열람 범위를 만드는 `보기` 부여는 통과**시킨 것이다. R122 가 막으려 한 사고 경로가 정확히 여기서 발생했다.

**삭제와 영구 삭제를 혼동하지 않는다 (R115-j)** — 이 표의 `휴지통 단건 영구 삭제`(L2)와 `휴지통 일괄 영구 삭제`(L3)는 **비가역**이다. 반면 **삭제(휴지통 이동)는 L1** 이다 — R52 로 파일이 `.trash` 로 이동할 뿐이고 R85 가 복구 경로를 보장하므로 가역이다. **두 조작은 이름이 비슷해 등급이 잘못 옮겨붙기 쉽다.** 삭제(휴지통 이동)의 진입점은 트리 컨텍스트 메뉴(R88)이므로 이 문서의 배정 대상이 아니지만, 이 표를 읽고 "삭제도 L2" 로 옮겨 적는 것을 막기 위해 명시한다.

**이 문서의 배정 대상이 아닌 인접 조작** — 아래는 요건상 등급이 정해져 있으나 진입점이 다른 문서에 있다. 혼선을 막기 위해 소재만 적는다.

│                                                          │

**R73 에 걸리는 조작 — 사전 비활성화 상태**

**R73 에 걸리는 조작 — 서버 거부 (UI 가 stale 했던 경우)**

**시스템 그룹 삭제 시도 — 사전 비활성화 상태**

```

**그룹 삭제 (L3)**

```
┌─ `기획팀` 그룹을 삭제한다 ───────────────────────────────┐
│  멤버 24명의 계정은 삭제되지 않는다.          (R101)     │

│                                                          │

`128건` 은 **이 다이얼로그를 열 때 재조회한 값**이다. 직전 화면에서 보여준 값과 다르면 `[삭제]` 를 잠그고 갱신된 값을 강조한다 (R116).

**보존 기간 축소 — 영향 건수 > 0 (L3, 타이핑 토큰은 건수 자체)**

```
┌─ 휴지통 보존 일수를 30 → 7 로 줄인다 ────────────────────┐
│  다음 정리 시점에 문서 342건이 영구 삭제된다.            │
│   · 지금은 아무 일도 일어나지 않는다. 다음 정리 시점에    │
│     한꺼번에 사라진다.                   (R86 · R115-f)  │
│   · 이 인스턴스의 모든 워크스페이스에 적용된다.          │
│                                                          │
│  계속하려면 삭제될 건수를 입력한다.                      │
│   [ 342                             ]                    │
│                              [ 취소 ]  [ 저장 ]          │
└──────────────────────────────────────────────────────────┘
```

- **타이핑 토큰이 건수 자체**이므로 사용자가 규모를 읽지 않고 통과할 수 없다 (R115-e). 대상 이름을 받는 다른 L3 과 다른 점이다.
- `342` 는 이 다이얼로그를 열 때 재조회한 값이다 (R116). 직전 화면과 다르면 실행을 잠그고 갱신값을 강조한다 — 잠금 해제 후 입력해야 하는 토큰도 갱신된 건수다.
- 감사 로그 보존 기간 축소도 같은 형태이며, "R84-a 가 수정·삭제 불가로 정한 기록을 없애는 유일한 경로"라는 문장이 추가된다.

**보존 기간 축소 — 영향 건수 = 0 (L2)**

```
┌─ 휴지통 보존 일수를 30 → 7 로 줄인다 ────────────────────┐
│  지금 삭제될 항목은 없다.                                │
│  앞으로 7일이 지난 항목이 다음 정리에서 사라진다.        │
│                                          (R86 · R115-f)  │
│                              [ 취소 ]  [ 저장 ]          │
└──────────────────────────────────────────────────────────┘
```

파괴되는 것이 없으므로 타이핑을 요구하지 않는다. 다만 **지연 효과 고지는 유지한다**(R115-f) — 정책이 바뀐 사실 자체는 알려야 한다.

**휴지통 단건 영구 삭제 (L2)**

```
┌─ `회의록.md` 를 영구 삭제한다 ───────────────────────────┐
│  파일이 디스크에서 사라지고 되돌릴 수 없다.              │
│  이 문서가 소유한 첨부도 함께 삭제된다.       (R50-c)    │
│                              [ 취소 ]  [ 영구 삭제 ]     │
└──────────────────────────────────────────────────────────┘
```

**오프보딩 4단계 — 확인 화면은 이 문서가 소유하지 않는다**

실행 확인은 **주체 일괄 회수 화면(R43-1)** 이 소유한다. 이 카드는 회수 대상 건수를 보여주고 그 화면으로 넘길 뿐이다. 넘길 때 함께 전달되어야 하는 맥락만 아래에 적는다 — 이 세 가지가 그 화면에 나타나지 않으면 사용자가 오프보딩 전체를 완료했다고 오해한다.

- 그룹을 통해 얻는 권한은 **3단계**에서 처리된다 (여기서는 직접 부여분만 사라진다).
- 계정과 감사 로그 이력은 그대로 남는다 (R101 — 계정은 삭제되지 않는다).
- 되돌릴 수 없다 (R110 으로 만료 기반 임시 부여가 없어 회수는 영구다).

**워크스페이스 마지막 `관리` 권한자 제거 (L2 — 차단하지 않는다, R109)**

```
┌─ 기술문서의 마지막 `관리` 권한자를 제거한다 ─────────────┐
│  제거하면 이 워크스페이스에 `관리` 권한자가 없어진다.    │
│   · 슈퍼유저는 계속 관리할 수 있다.           (R29)      │
│   · 이 워크스페이스의 모든 ACL 요청이 슈퍼유저에게 간다. │
│   · 목록에 `관리자 없음` 배지가 표시된다.     (R109-a)   │
│                              [ 취소 ]  [ 제거 ]          │
└──────────────────────────────────────────────────────────┘
```
