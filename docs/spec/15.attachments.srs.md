## 1. Scope Overview

이 scope 는 `.md` 가 아닌 것을 규정한다 — 업로드된 첨부 파일, 그리고 Phase 2 로 열려 있는 비-본문 축(PDF 뷰어 · `.task` 할 일 목록 · 문서 댓글). 파일이 시스템에 들어오는 경로, 디스크 위에 앉는 구조, 누가 그 파일에 도달하는지의 판정 근거, 화면에서 열리는 형태, 그리고 소유 문서가 사라질 때의 처분이 여기 모인다.

이 scope 를 관통하는 결정이 하나 있다 — 첨부의 권한을 **위치가 아니라 소유 문서**로 판정한다. 첨부를 문서와 같은 디렉토리에 두면 권한이 위치에 묶여 문서를 옮길 때마다 유출과 파손이 양방향으로 생기므로, 저장은 워크스페이스 루트 한 곳으로 모으고 권한은 소유 문서에서 파생시켜 위치와 권한을 분리했다. 이 scope 의 요구 여럿이 그 하나의 결정에서 따라 나온다.

## 2. Scope Boundaries

### In Scope

- 업로드 경로 두 가지와 각각의 권한 축 — 트리 드래그앤드롭(대상 디렉토리의 편집 권한)과 편집기 붙여넣기·드래그(소유 문서의 편집 권한) (`FR-ATTACH-001`·`SEC-ATTACH-001`·`FR-ATTACH-004`)
- 업로드 파일 형식을 제한하지 않는다는 결정과, 크기 제한을 설정에서 지정한다는 규정 (`CON-ATTACH-001`·`FR-ATTACH-006`)
- 첨부의 저장 구조 — 워크스페이스 루트 `.res` 와 해시 파일명, 소유 문서를 기록하는 `attachment` 테이블, 본문 첨부 링크의 경로 형식, 파일시스템만으로 재구성 가능한 `.res/index.json` 사이드카 (`DR-ATTACH-001`·`DR-ATTACH-002`·`DR-ATTACH-003`·`REL-ATTACH-001`)
- 첨부 권한 — 접근을 소유 문서의 보기 유효 권한으로 판정한다는 규정과, 그 검사를 매 요청 수행한다는 규정 (`SEC-ATTACH-002`·`SEC-ATTACH-003`)
- 소유 문서가 영구 삭제될 때의 첨부 동반 삭제 (`FR-ATTACH-005`)
- 비-md 파일의 표시 — 트리 목록에 나타난다는 규칙, 그리고 본문 영역에서 이미지는 미리보기·그 외는 다운로드 링크로 갈린다는 규칙 (`FR-ATTACH-002`·`FR-ATTACH-003`)
- Phase 2 비-본문 축 — PDF 뷰어, `.task` 할 일 목록, 문서 댓글과 그 허용 여부 설정·멘션·작성 권한 (`FR-ATTACH-007`~`FR-ATTACH-011`·`SEC-ATTACH-004`)

### Out of Scope

- 동명 파일 충돌 처리 — 가시 여부와 무관하게 항상 자동 접미사 + 동일한 안내이며 확인 단계를 두지 않는다는 규칙은 `SHELL` scope 가 소유한다 (`FR-ATTACH-001` Implementation Notes).
- 비-md 파일에서 모드 토글을 숨기는 규칙 — `EDITOR` scope 가 소유한다. `FR-ATTACH-003` 은 본문 영역에 무엇이 표시되는가만 정한다 (`FR-ATTACH-003` Implementation Notes).
- 보기·편집 유효 권한의 정의와 계산, 완전 숨김 규칙 — `ACL` scope 가 소유한다. `SEC-ATTACH-001`·`SEC-ATTACH-002` 는 어느 노드의 권한을 볼지만 정하고 그 값을 정의하지 않는다.
- 문서의 이동으로 첨부가 움직이지 않는다는 규정과 본문을 재작성하지 않는다는 규정 — `STORAGE` scope 가 소유한다. 이 scope 는 그 성질이 가능하게 만드는 저장 구조를 갖는다.
- 노드 ID 의 형식과 안정성, 그리고 휴지통 이동과 영구 삭제의 구분 — `STORAGE` scope 가 소유한다. `FR-ATTACH-005` 는 「영구 삭제」에만 발화하며 휴지통 이동만으로는 첨부를 지우지 않는다.
- 첨부 업로드·삭제가 감사 로그에 남는가 — `AUDIT` scope 가 소유한다. `FR-ATTACH-005` 의 동반 삭제가 감사 행을 만들지 않고 건수도 표시하지 않는다는 판정도 그쪽이 정본이며, 이 scope 는 그 결과를 인용한다.
- 첨부 다운로드가 무기록이라는 잔여 위험(R137-h)의 등재 자리 — `AUDIT` scope 가 소유한다. 이 scope 는 그 위험이 자기 경로에 있다는 사실을 요구 문면에 적어 두되, 읽기를 기록 대상으로 넓히는 판단은 하지 않는다.
- 컨테이너 권한 항목 회수 시 첨부 영향을 개수 대신 고정 문구로 알린다는 규칙 — `CONFIRM` scope 가 소유한다.
- 워크스페이스 루트의 물리 레이아웃 — `WORKSPACE` scope 가 소유한다. `.res` 가 그 아래 어디에 놓이는지는 이 scope 가, 워크스페이스 디렉토리 구조 전체는 그쪽이 갖는다.
- Phase 2 축의 파생 거동 — `.task` 의 버전 단위, 충돌 병합 화면, 감사 입도, 모드 토글, 색인 대상은 각각 `STORAGE`·`EDITOR`·`AUDIT` scope 의 조항에 걸리며 어느 쪽도 아직 답을 갖고 있지 않다. 열린 공백 `G34` 이며, `G34` 는 그 열거가 전량이 아니라고 스스로 밝힌다 (`FR-ATTACH-008` Implementation Notes).
- PAT `읽기 전용` 스코프로 댓글을 달 수 있는가 — `AUTH` scope 의 PAT 스코프 조항에 걸리는 미결 `G35`-④ 다. 댓글 허용 설정을 바꿀 권한은 `G35`-⑤ 로 여전히 열려 있으며 어느 scope 도 소유하지 않는다 (`SEC-ATTACH-004`·`FR-ATTACH-010` Implementation Notes).
- 해시의 산출 대상과 알고리즘, 중복 제거 여부, 크기 제한의 기본값·단위·`0` 의 의미, 거부 시점 — 원장이 정하지 않았고 어느 scope 도 소유하지 않는다. 구현 전에 이 축들을 먼저 정하라 (`DR-ATTACH-001`·`FR-ATTACH-006` Implementation Notes).

## 3. Assumptions and Constraints

- 파일시스템이 SSOT 다 — `STORAGE` scope 가 소유하는 전제이며, `REL-ATTACH-001` 의 사이드카가 존재하는 이유가 그것이다. `attachment` 테이블이 소유 관계의 단일 사본이 되면 그 전제가 무너진다.
- 메타데이터는 SQLite 단일 저장소에 있다 — `STORAGE` scope 가 소유한다. `.res/` 에 파일이 있어도 `attachment` 행이 없으면 권한을 판정할 수 없어 첨부는 접근 불가가 된다.
- 두 업로드 경로의 권한 축이 서로 다르다 (`SEC-ATTACH-001` 대 `FR-ATTACH-004`). 두 경로에 같은 권한 검사를 공유시키면 문서에만 편집 권한을 받은 사용자가 이미지를 붙여넣지 못하게 되어 편집기 경로가 깨진다.
- Phase 1 에서 이미지 미리보기와 다운로드 링크 외의 뷰어를 임의로 추가하지 않는다 (`FR-ATTACH-003`). Phase 2 의 PDF·`.task` 가 그 갈래에서 빠지지만 Phase 1 동안 PDF 는 여전히 다운로드 링크이며, 본문 슬롯을 md 전용으로 전제하지 않아야 그 확장이 같은 슬롯에 들어온다.
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가, Phase 라벨 판정 규칙도 `ARCH` scope 가 소유한다.
- 미결 둘이 이 scope 에 걸려 있다 — `G34`(`.task` 저장 형식이 JSON 이라 본문을 전제한 조항들이 그대로 적용되지 않는다) · `G35`(댓글 축의 PAT 스코프와 설정 변경 권한).

#### Requirement

사용자가 로컬 파일을 트리의 디렉토리 노드 위로 드래그앤드롭하면 시스템은 그 파일을 해당 디렉토리에 업로드한다. 업로드 전용 화면·모드는 두지 않으며 현재 화면에서 업로드가 완결된다.

#### Rationale

R2 가 1.0 의 「업로드 모드 / 뷰어 모드」 분리를 폐기했지만 폐기된 것은 업로드 **화면**이지 업로드 **기능**이 아니다. 원장이 두 조항이 모순되지 않음을 명시했다. 기각된 대안 — 업로드 전용 화면을 다시 두는 것.

#### Acceptance Criteria

- [x] AC-1: 로컬 파일을 트리의 디렉토리 노드 위로 드롭하면 그 디렉토리에 파일이 생성된다.
- [x] AC-2: 업로드가 끝나면 새 파일이 그 디렉토리의 자식 노드로 트리에 나타난다.
- [x] AC-3: 업로드를 위해 별도 화면·모드로 전환하지 않고 현재 화면에서 드롭만으로 업로드가 완료된다.

#### Acceptance Criteria

- [x] AC-1: 소유 문서에 보기 유효 권한이 있는 사용자의 첨부 요청은 허용된다.
