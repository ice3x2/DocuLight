## 1. Scope Overview

이 scope 는 제품 전체가 올라앉는 판을 규정한다 — 어떤 규모와 운영 형태를 전제하는가, 어떤 코드베이스 위에 짓는가, 어떤 프론트엔드 스택과 부품으로 짓는가, 1.0 에서 물려받는 AI·벡터검색·MCP 표면을 접근 제어 아래에 어떻게 다시 놓는가, 그리고 이 설계 문서 자체를 어떤 규약으로 쓰는가.

제품의 정의 자체 — 옵시디언의 편집·열람 경험을 웹으로 옮기고 여기에 문서/디렉토리 단위 접근 제어를 더한 사내 문서 시스템 — 는 원장 §1 이 정본으로 갖는다. 이 scope 가 담는 것은 그 제품을 실현하는 판의 제약이며, 판 위에서 벌어지는 기능은 각 기능 scope 가 갖는다.

## 2. Scope Boundaries

### In Scope

- 규모·운영 형태 전제 — 사내 단일 인스턴스, 수백~수천 명 (`CON-ARCH-001`)
- 코드베이스 전략 — 백엔드·프론트엔드 신규 작성, 1.0 에서는 코드가 아니라 기능을 물려받음, 1.0 동결 (`CON-ARCH-002`)
- 프론트엔드 스택과 부품 선택 — SPA 스택, UI 부품 패키지, 프레임워크 중립 에디터·머지·마크다운 패키지, 문서 본문의 정본 위치 (`CON-ARCH-003`·`CON-ARCH-004`·`CON-ARCH-005`·`CON-ARCH-006`)
- 빌드 산출물의 서빙 방식과 운영 프로세스 수 (`OPS-ARCH-001`)
- 1.0 의 AI 기능·벡터검색·MCP 서버를 도구 계약과 동작으로 물려받아 신규 작성 (`FR-ARCH-001`)
- MCP 표면의 인증·인가 — 호출 인증 필수화, 읽기 결과의 ACL 필터링, 쓰기 도구의 편집 권한 검사 (`SEC-ARCH-001`·`SEC-ARCH-002`·`SEC-ARCH-003`)
- 설계 문서 규약 — `docs/spec` 의 SpecKiwi SRS 정식화, 한 사실은 한 곳, Phase 라벨 판정 (`CON-ARCH-007`·`CON-ARCH-008`·`CON-ARCH-009`)

### Out of Scope

- MCP 호출자를 식별하는 인증 수단 자체 — PAT 의 발급·저장 형식·스코프·무효화는 `AUTH` scope 가 소유한다. 이 scope 는 MCP 호출에 인증이 필요하다는 사실만 정한다 (`SEC-ARCH-001` Implementation Notes).
- 완전 숨김 규칙의 정본, 그리고 거부 응답이 노드의 존재를 드러내도 되는지의 판정 — `ACL` scope 가 소유한다. 이 scope 는 그 규정이 MCP 표면에도 적용된다는 사실만 담는다 (`SEC-ARCH-002`·`SEC-ARCH-003` Implementation Notes).
- 유효 권한의 정의와 계산 방식 — `ACL` scope 가 소유한다. `SEC-ARCH-002`·`SEC-ARCH-003` 은 그 값을 쓰는 쪽의 계약만 고정한다.
- 벡터 인덱스의 갱신 시점과 삭제된 노드 엔트리의 배제 — `STORAGE` scope 가 소유한다. 이 scope 는 검색 *결과*의 필터링만 정한다.
- 앱 화면의 텍스트 검색 — 좌측 사이드바 검색 탭의 검색 대상·질의 문법·결과 표시는 `SHELL` scope 가 소유한다. 이 scope 는 AI·MCP 표면만 가지며, 두 축이 갈라지는 경계는 `CON-SHELL-002`(AI 검색은 MCP 로만 제공한다)가 못박는다. 그 경계를 여기서 다시 정하면 같은 사실이 두 자리에 놓인다.
- 플러그인 시스템을 범위에서 제외한다는 결정(R15) — 제품이 하지 않기로 한 것이며, 그 배제를 문면으로 담는 자리는 `EDITOR` scope 다.
- 멀티테넌트 SaaS 운영과 고객사 온프레미스 배포 — 제품이 대상으로 삼지 않는다(R19). 그 배제는 이 scope 안의 `CON-ARCH-001` 이 문면으로 담으므로 여기서 다시 열거하지 않는다.
- 성능 목표 — 응답 시간·처리량 수치는 원장에 없고 어느 scope 도 소유하지 않는다. `CON-ARCH-001` 은 규모만 전제하며 수치를 도출할 근거가 아니다. 필요해지면 새 조항으로 세워야 한다.

## 3. Assumptions and Constraints

- 이 scope 가 전 scope 공통 전제를 소유한다 — 규모(`CON-ARCH-001`) · 스택과 서빙(`CON-ARCH-003`·`OPS-ARCH-001`) · 문서 규약(`CON-ARCH-007`·`CON-ARCH-008`·`CON-ARCH-009`). 다른 scope 문서는 이 값들을 복제하지 않고 여기를 가리킨다.
- 1.0 이 동결된 채 계속 운영 가능하다는 것이 코드베이스 전략의 전제다 (`CON-ARCH-002`).
- 스택 선택은 런타임 성능과 번들 크기의 손해를 인지하고 감수한 결정이다 — 사내망 단일 인스턴스이고 구현 속도가 최우선 기준이라는 전제 위에서만 성립한다 (원장 §2.11).
- Phase 2 열거는 닫힌 목록이 아니다 (`CON-ARCH-009`). 이 문서를 포함해 어느 scope 문서도 Phase 2 를 전량으로 열거하지 않는다.
- 데스크탑 전용(R31)이라는 Phase 1 구속은 `EDITOR` scope 가 소유하며, 이 scope 의 스택·부품 선택은 그 전제 위에서 이뤄졌다.

#### Requirement

MCP 서버의 모든 도구 호출은 사용자 인증을 통과해야 실행된다. 인증되지 않은 호출은 도구 종류와 무관하게 거부하며, 인증 없이 호출할 수 있는 도구를 두지 않는다.

#### Rationale

1.0 에서는 MCP 의 read 계열 도구(`list_documents` · `read_document` · `search`)가 인증 없이 public 이었다. 문서에 권한 개념이 없었기에 성립한 전제이며, 문서별 ACL 이 핵심인 2.0 에서는 그 전제가 그대로 깨진다. 인증이 없으면 뒤따르는 ACL 필터링과 쓰기 권한 검사가 판정할 주체 자체를 갖지 못하므로, 이 조항은 두 인가 규칙의 선행 조건이다.

#### Acceptance Criteria

- [x] AC-1: 인증 자격을 싣지 않은 MCP 도구 호출은 도구 종류와 무관하게 거부된다.
- [x] AC-2: 인증 없이 호출할 수 있는 MCP 도구가 서버의 도구 목록에 존재하지 않는다.
- [x] AC-3: 유효한 사용자 자격으로 인증한 MCP 호출은 그 사용자를 호출 주체로 확정한다.

### SEC-ARCH-002 — MCP 읽기 도구와 벡터검색 결과를 호출자의 ACL 로 필터링한다

#### Requirement

MCP 읽기 도구가 돌려주는 결과와 벡터검색 결과는 호출자의 유효 권한으로 필터링한다. 호출자가 볼 수 없는 노드는 결과 목록에도, 요약·발췌 형태의 본문에도 나타나지 않는다.

#### Rationale

AI 벡터 인덱스는 전 문서를 담고 있으므로, 결과를 사용자별로 필터링하지 않으면 권한 없는 문서의 내용이 요약문 형태로 유출된다. 원장은 이것을 1.0 의 AI·MCP 기능을 그대로 물려받으면 안 되는 이유로 명시했다. 원장 §4 수용 기준 5 전단이 "같은 도구를 호출했을 때 결과가 각자의 ACL 로 다르게 나온다" 로 이 요구의 관문을 잡는다.

#### Acceptance Criteria

- [x] AC-1: 서로 다른 ACL 을 가진 두 사용자가 같은 MCP 읽기 도구를 같은 인자로 호출하면 각자의 유효 권한에 해당하는 결과만 돌려받는다.
- [x] AC-2: 벡터검색 호출의 결과 목록에 호출자가 볼 수 없는 노드의 항목이 포함되지 않는다.
- [x] AC-3: 벡터검색 결과의 요약·발췌 텍스트에 호출자가 볼 수 없는 노드의 본문이 포함되지 않는다.
- [x] AC-4: 권한 없는 노드가 걸러진 결과는 걸러졌다는 사실을 건수·순번·자리표시 어느 형태로도 노출하지 않는다.

### SEC-ARCH-003 — MCP 쓰기 도구는 대상 노드의 편집 유효 권한이 없으면 거부한다

#### Requirement

MCP 쓰기 도구는 실행 전에 대상 노드에 대한 호출자의 `편집` 유효 권한을 검사하고, 권한이 없으면 호출을 거부한다. 결과를 걸러내는 방식이 아니라 실행 자체를 막는다.

#### Rationale

감사 M9 해소. 원장 초판의 MCP 조항은 "ACL 로 필터링" 만 규정했는데, 필터링은 읽기 개념이라 쓰기 검사의 근거가 되지 못했다. 필터를 쓰기에 적용하면 "쓸 수 없는 대상을 결과에서 뺀다" 가 되어 실제 쓰기를 막지 못한다. 원장이 읽기와 쓰기를 갈라 명시한 이유가 이것이며, §4 수용 기준 5 후단이 "보기 권한만 있는 사용자의 쓰기 도구 호출은 거부된다" 로 이 요구의 관문을 잡는다.

#### Acceptance Criteria

- [x] AC-1: 대상 노드에 `보기` 유효 권한만 가진 사용자가 MCP 쓰기 도구를 호출하면 거부된다.
- [x] AC-2: 대상 노드에 `편집` 유효 권한을 가진 사용자가 같은 MCP 쓰기 도구를 호출하면 실행된다.
- [x] AC-3: 거부된 쓰기 호출은 대상 노드를 변경하지 않은 상태로 종료된다.

### FR-ARCH-001 — 1.0 의 AI·MCP 기능을 도구 계약과 동작으로 물려받아 신규 작성한다

| Field | Value |

| Tags | ai, mcp, migration |
| Risk | medium |
| Stability | stable |

| GitHub Issue | - |

#### Requirement

1.0 이 제공하던 AI 기능과 MCP 서버를 2.0 에서 신규 작성한다. 물려받는 것은 MCP 도구 계약 — 도구 이름 · 입력 인자와 기본값 · 출력 포맷 · 에러 코드 — 과 화면이 제공하던 동작이며, 1.0 의 소스·의존성·내부 구조는 물려받지 않는다. 의미 검색(A-RAG) 역시 1.0 의 `smart_search` 를 옮기지 않고 신규 작성한다. 신규 작성물은 MCP 인증·인가 제약을 적용한 형태여야 한다.

#### Rationale

사용자가 "당신이 기존보다 더 잘 만들 수 있다면 그렇게 하라" 는 조건을 달았고 실측이 그 조건을 충족했다 — 1.0 의 semantic 경로는 한 번도 실전 동작한 적이 없다. 그래서 인계 대상은 코드가 아니라 계약과 동작이다. 인계가 무조건적이지 않은 이유는 따로 있다 — 1.0 의 MCP read 계열 도구는 인증 없이 public 이었고 이는 문서에 권한 개념이 없었기에 성립한 전제다. 문서별 ACL 이 핵심인 2.0 에서는 그 전제가 그대로 깨지므로, 계약을 물려받되 인증·인가 제약을 얹은 형태여야 한다.

#### Acceptance Criteria

- [x] AC-1: 2.0 의 MCP 도구는 1.0 과 같은 도구 이름 · 입력 인자와 기본값 · 출력 포맷 · 에러 코드를 제공한다.
- [x] AC-2: 1.0 이 갖고 있던 AI 기능(LangChain 기반 파이프라인 · 벡터검색 · `smart_search`)은 2.0 에서 대응물을 갖되, 인계 대상은 그 도구 계약과 화면이 제공하던 동작이다. `smart_search` 의 semantic 경로는 1.0 에서 동작한 적이 없으므로(`R21-a`) 그 실행 결과는 재현 대상이 아니며 AC-4 가 그 자리를 받는다.
- [x] AC-3: 2.0 의 AI·MCP 코드에 1.0 의 소스를 옮겨 온 파일이 존재하지 않으며, 빌드·의존성 어느 것도 1.0 경로를 가리키지 않는다.
- [x] AC-4: 의미 검색(A-RAG)은 신규 작성물이며 1.0 의 `smart_search` 구현을 재사용하지 않는다.
- [x] AC-5: AI·MCP 표면 중 인증·ACL 제약을 적용하지 않은 호출 경로가 존재하지 않는다.

#### Requirement

DocuLight2.0 을 1.0 과 별도의 리포지토리로 두고, 백엔드와 프론트엔드를 모두 신규 작성한다. 1.0 에서 물려받는 것은 코드가 아니라 그것이 제공하던 기능이며, 2.0 의 어떤 빌드·의존성·설정도 1.0 의 소스 경로를 가리키지 않는다. 1.0 은 동결하여 계속 운영 가능한 상태로 남긴다.

#### Rationale

사용자 결정으로 「이식」의 범위를 닫았다 — 초판 문면은 "1.0 의 백엔드 자산을 이식한다" 였고 어디까지가 이식이고 어디부터가 신규인지 정하지 않아 읽는 사람마다 갈렸다. 가져오는 것은 기능 명세이지 소스가 아니다. 1.0 의 EJS SSR + vanilla JS 프론트로는 라이브 프리뷰·분할창·커맨드 팔레트·백링크 패널을 감당할 수 없다는 초판의 판단은 그대로 유효하며, 개정은 그 판단을 백엔드까지 넓힌 것이다. 1.0 동결은 2.0 이 완성되기 전까지 사내 이용을 끊지 않기 위한 조건이다.

#### Research / Analysis

- 원장 R21 근거 표의 자산별 처분 — (1) 그대로 이식: MCP 서버 · AI/벡터검색 · 로깅 · config · chokidar · Playwright. (2) 이식 후 그룹·ACL 로 확장: 인증 기반(bcrypt · 쿠키 · nodemailer). (3) 유지하되 모든 엔드포인트에 권한 필터가 침투: REST API(tree · raw · search). (4) 전면 교체: EJS SSR + vanilla JS 프론트 — 라이브 프리뷰·분할창·커맨드 팔레트·백링크 패널을 vanilla 로 감당할 수 없다는 것이 사유다. (5) 유지: CodeMirror 6 — 옵시디언도 CM6 기반이다.

#### Requirement

프론트엔드는 Vite + React + TypeScript 기반 SPA 로 작성한다. 서버 사이드 렌더링 프레임워크를 도입하지 않는다.

#### Rationale

SSR/SEO 요구가 0 이므로 Next.js 의 서버 계층은 순수 비용이다. 사내망 단일 인스턴스라 초기 로딩·SEO 압박이 없고 최우선 판단 기준은 구현 속도다. 기각된 대안 — Next.js: "정적 export 구성은 Next 의 서버 기능을 전부 봉인한다는 뜻이고, 'Next 서버를 절대 두지 않는다' 를 지킬 규율이 없다면 Vite SPA 가 더 정직한 선택" 이라는 것을 그 후보를 옹호하도록 배정된 담당자 본인이 인정했다. Svelte 5: `@tanstack/svelte-table` v8 이 `svelte/internal` 의존으로 Svelte 5 에서 동작하지 않고(v9 알파), runes 가 최근 파괴적 변경이라 웹·LLM 자료 다수가 Svelte 4 문법이어서 구현 속도 기준에서 실질 손해다 — 사용자·그룹 관리 테이블이 설정 모달의 중심에 놓이므로 이 공백이 정면으로 걸린다.

- [ ] AC-3: 서버 사이드 렌더링을 수행하는 프레임워크 런타임이 배포 구성에 존재하지 않는다.

#### Requirement

#### Acceptance Criteria

- [x] AC-1: 문서 본문 문자열을 정본으로 보유하는 React state 가 존재하지 않는다.
- [x] AC-2: CodeMirror 는 controlled `value` prop 으로 본문을 주입받지 않는다.
- [x] AC-3: 본문 값이 필요한 기능은 CodeMirror 인스턴스에서 값을 조회해 얻는다.

확정 요구사항은 Phase 명시가 없으면 전부 Phase 1 이다. Phase 2 목록은 닫힌 열거가 아니므로 이 목록이 전량이라고 가정하지 않는다. Phase 2 조항은 큰 축의 정의이며 화면 설계가 아니다.

#### Rationale

감사 H11 해소. 초판은 Phase 2 를 닫힌 열거로 적었다가 조항 하나가 그 열거에서 빠지는 사고가 났고, "닫힌 열거를 쓰는 것 자체가 결함이었으므로 열린 목록으로 바꾼다" 는 선례를 따라 열린 형태로 전환했다. 다만 근거 없이 열기만 하면 판정 근거가 0 이 되어 닫힌 열거보다 나쁘다는 경고가 원장에 이미 있었으므로 — 열 수 있었던 선례들은 뒤에 생성적 규칙이 따로 있었기 때문에 열 수 있었다 — 열거를 지우지 않고 판정 경로를 함께 실었다.

#### Implementation Notes

- 판정은 세 경로를 함께 써야 한다. ① 조항이 스스로 Phase 2 를 선언하는지 원장 전수로 훑는다. ② 자기 문면에 Phase 표기가 없는데 다른 조항의 비고가 미뤄 둔 것을 찾는다. ③ 하위 항목은 상위 조항의 Phase 를 따른다. ②가 없으면 이 목록 자신도 재도출되지 않는다 — R55·R55-a 는 Phase 토큰이 0건이고 R54 비고를 경유해야만 잡힌다. R148-a·R148-b·R148-c 는 Phase 토큰이 0건이고 이들을 미루는 비고도 없어 ①②만으로는 잡히지 않는다.
- ③에 단서가 필요한 이유는 반례가 둘 있기 때문이다. R55-b 는 R55 의 하위지만 fail-closed 서빙이 Phase 1 보안 규칙이고, R103-a 는 R103 의 하위지만 문면이 "Phase 2 에서도 요청 버튼을 두지 않는다" 여서 Phase 1·2 양쪽에 걸린다. 단서 없이 ③을 쓰면 이 둘을 잘못 판정한다.
- ①이 짚었다고 곧바로 항목이 되지 않는다 — 그 조항 자체가 미뤄졌는지 보라. ①은 목록 밖도 짚으며 전부 위양성이다: R89(이미 R17 에 흡수) · R23 · R33-b · R98 · R24-b(다른 조항의 Phase 2 를 가리키는 파생) · 취소선 조항. R48 도 ①에 걸리지만 비고 첫 문장이 "Phase 1 규정이다" 이고 뒤는 Phase 2 확장을 가리키는 역참조다.
- 이 목록은 2026-08-19 기준이며 조항이 신설되면 다시 판정해야 한다. 그것이 이 요구사항의 Stability 가 `evolving` 인 이유다.
- 인지된 제약 — 아카이브가 Phase 2 로 이관되면서 Phase 1 에는 워크스페이스를 없애는 수단이 없다.
- [2026-09-02] 유일한 증거 VE-1(`docs/spec/00.decision-log.md`)이 원장 문면을 사람이 대조한 `review` 라 자동 시험을 가리키지 않으며, 원장 머리표와 `R92` 가 `G30`·`G34`·`G35` 를 다르게 적은 불일치가 그 검토에 미해소로 남아 있으므로 승급하지 않는다.
