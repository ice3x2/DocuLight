## 1. Scope Overview

이 scope 는 제품 전체가 올라앉는 판을 규정한다 — 어떤 규모와 운영 형태를 전제하는가, 어떤 코드베이스 위에 짓는가, 어떤 프론트엔드 스택과 부품으로 짓는가, 1.0 에서 넘어오는 AI·벡터검색·MCP 표면을 접근 제어 아래에 어떻게 다시 놓는가, 그리고 이 설계 문서 자체를 어떤 규약으로 쓰는가.

제품의 정의 자체 — 옵시디언의 편집·열람 경험을 웹으로 옮기고 여기에 문서/디렉토리 단위 접근 제어를 더한 사내 문서 시스템 — 는 원장 §1 이 정본으로 갖는다. 이 scope 가 담는 것은 그 제품을 실현하는 판의 제약이며, 판 위에서 벌어지는 기능은 각 기능 scope 가 갖는다.

## 2. Scope Boundaries

### In Scope

- 규모·운영 형태 전제 — 사내 단일 인스턴스, 수백~수천 명 (`CON-ARCH-001`)
- 코드베이스 전략 — 1.0 백엔드 이식, 프론트엔드 신규 작성, 1.0 동결 (`CON-ARCH-002`)
- 프론트엔드 스택과 부품 선택 — SPA 스택, UI 부품 패키지, 프레임워크 중립 에디터·머지·마크다운 패키지, 문서 본문의 정본 위치 (`CON-ARCH-003`·`CON-ARCH-004`·`CON-ARCH-005`·`CON-ARCH-006`)
- 빌드 산출물의 서빙 방식과 운영 프로세스 수 (`OPS-ARCH-001`)
- 1.0 의 AI 기능·벡터검색·MCP 서버 이관 (`FR-ARCH-001`)
- MCP 표면의 인증·인가 — 호출 인증 필수화, 읽기 결과의 ACL 필터링, 쓰기 도구의 편집 권한 검사 (`SEC-ARCH-001`·`SEC-ARCH-002`·`SEC-ARCH-003`)
- 설계 문서 규약 — `docs/spec` 의 SpecKiwi SRS 정식화, 한 사실은 한 곳, Phase 라벨 판정 (`CON-ARCH-007`·`CON-ARCH-008`·`CON-ARCH-009`)

### Out of Scope

- MCP 호출자를 식별하는 인증 수단 자체 — PAT 의 발급·저장 형식·스코프·무효화는 `AUTH` scope 가 소유한다. 이 scope 는 MCP 호출에 인증이 필요하다는 사실만 정한다 (`SEC-ARCH-001` Implementation Notes).
- 완전 숨김 규칙의 정본, 그리고 거부 응답이 노드의 존재를 드러내도 되는지의 판정 — `ACL` scope 가 소유한다. 이 scope 는 그 규정이 MCP 표면에도 적용된다는 사실만 담는다 (`SEC-ARCH-002`·`SEC-ARCH-003` Implementation Notes).
- 유효 권한의 정의와 계산 방식 — `ACL` scope 가 소유한다. `SEC-ARCH-002`·`SEC-ARCH-003` 은 그 값을 쓰는 쪽의 계약만 고정한다.
- 벡터 인덱스의 갱신 시점과 삭제된 노드 엔트리의 배제 — `STORAGE` scope 가 소유한다. 이 scope 는 검색 *결과*의 필터링만 정한다.
- 플러그인 시스템을 범위에서 제외한다는 결정(R15) — 제품이 하지 않기로 한 것이며, 그 배제를 문면으로 담는 자리는 `EDITOR` scope 다.
- 멀티테넌트 SaaS 운영과 고객사 온프레미스 배포 — 제품이 대상으로 삼지 않는다(R19). 그 배제는 이 scope 안의 `CON-ARCH-001` 이 문면으로 담으므로 여기서 다시 열거하지 않는다.
- 성능 목표 — 응답 시간·처리량 수치는 원장에 없고 어느 scope 도 소유하지 않는다. `CON-ARCH-001` 은 규모만 전제하며 수치를 도출할 근거가 아니다. 필요해지면 새 조항으로 세워야 한다.

## 3. Assumptions and Constraints

- 이 scope 가 전 scope 공통 전제를 소유한다 — 규모(`CON-ARCH-001`) · 스택과 서빙(`CON-ARCH-003`·`OPS-ARCH-001`) · 문서 규약(`CON-ARCH-007`·`CON-ARCH-008`·`CON-ARCH-009`). 다른 scope 문서는 이 값들을 복제하지 않고 여기를 가리킨다.
- 1.0 이 동결된 채 계속 운영 가능하다는 것이 코드베이스 전략의 전제다 (`CON-ARCH-002`).
- 스택 선택은 런타임 성능과 번들 크기의 손해를 인지하고 감수한 결정이다 — 사내망 단일 인스턴스이고 구현 속도가 최우선 기준이라는 전제 위에서만 성립한다 (원장 §2.11).
- Phase 2 열거는 닫힌 목록이 아니다 (`CON-ARCH-009`). 이 문서를 포함해 어느 scope 문서도 Phase 2 를 전량으로 열거하지 않는다.
- 데스크탑 전용(R31)이라는 Phase 1 구속은 `EDITOR` scope 가 소유하며, 이 scope 의 스택·부품 선택은 그 전제 위에서 이뤄졌다.

### SEC-ARCH-001 — MCP 호출에 사용자 인증을 필수화한다

| Tags | mcp, authentication |
| Risk | medium |

| GitHub Issue | - |

#### Requirement

MCP 서버의 모든 도구 호출은 사용자 인증을 통과해야 실행된다. 인증되지 않은 호출은 도구 종류와 무관하게 거부하며, 인증 없이 호출할 수 있는 도구를 두지 않는다.

#### Rationale

1.0 에서는 MCP 의 read 계열 도구(`list_documents` · `read_document` · `search`)가 인증 없이 public 이었다. 문서에 권한 개념이 없었기에 성립한 전제이며, 문서별 ACL 이 핵심인 2.0 에서는 그 전제가 그대로 깨진다. 인증이 없으면 뒤따르는 ACL 필터링과 쓰기 권한 검사가 판정할 주체 자체를 갖지 못하므로, 이 조항은 두 인가 규칙의 선행 조건이다.

#### Acceptance Criteria

- [ ] AC-1: 인증 자격을 싣지 않은 MCP 도구 호출은 도구 종류와 무관하게 거부된다.
- [ ] AC-2: 인증 없이 호출할 수 있는 MCP 도구가 서버의 도구 목록에 존재하지 않는다.
- [ ] AC-3: 유효한 사용자 자격으로 인증한 MCP 호출은 그 사용자를 호출 주체로 확정한다.

### SEC-ARCH-002 — MCP 읽기 도구와 벡터검색 결과를 호출자의 ACL 로 필터링한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | mcp, acl, vector-search |
| Risk | medium |
| Stability | stable |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

MCP 읽기 도구가 돌려주는 결과와 벡터검색 결과는 호출자의 유효 권한으로 필터링한다. 호출자가 볼 수 없는 노드는 결과 목록에도, 요약·발췌 형태의 본문에도 나타나지 않는다.

#### Rationale

AI 벡터 인덱스는 전 문서를 담고 있으므로, 결과를 사용자별로 필터링하지 않으면 권한 없는 문서의 내용이 요약문 형태로 유출된다. 원장은 이것을 1.0 의 AI·MCP 기능을 문자 그대로 이관하면 안 되는 이유로 명시했다. 원장 §4 수용 기준 5 전단이 "같은 도구를 호출했을 때 결과가 각자의 ACL 로 다르게 나온다" 로 이 요구의 관문을 잡는다.

#### Acceptance Criteria

- [ ] AC-1: 서로 다른 ACL 을 가진 두 사용자가 같은 MCP 읽기 도구를 같은 인자로 호출하면 각자의 유효 권한에 해당하는 결과만 돌려받는다.
- [ ] AC-2: 벡터검색 호출의 결과 목록에 호출자가 볼 수 없는 노드의 항목이 포함되지 않는다.
- [ ] AC-3: 벡터검색 결과의 요약·발췌 텍스트에 호출자가 볼 수 없는 노드의 본문이 포함되지 않는다.
- [ ] AC-4: 권한 없는 노드가 걸러진 결과는 걸러졌다는 사실을 건수·순번·자리표시 어느 형태로도 노출하지 않는다.

#### Implementation Notes

- 필터를 어느 지점에 적용하는지가 정해져 있지 않다. 벡터 인덱스가 전 문서를 담고 있어 상위 N 건을 먼저 뽑은 뒤 거르면 권한 있는 결과가 통째로 사라져 빈 응답이 나온다. 정렬·상한 적용 지점과 필터 적용 지점의 순서를 구현 단계에서 정해야 하며, 원장은 이 축을 정하지 않았다.
- "필터링" 은 읽기 개념이다. 이 조항을 쓰기 도구의 인가 근거로 재사용하면 안 된다 — 쓰기 검사는 별도 요구사항이 소유한다.
- AC-4 는 완전 숨김 규칙과 만나는 자리다. 숨김의 정본 규정은 접근 제어 scope 가 소유하며, 이 조항은 그 규정이 MCP 표면에도 적용된다는 사실만 담는다.

### SEC-ARCH-003 — MCP 쓰기 도구는 대상 노드의 편집 유효 권한이 없으면 거부한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | mcp, acl, write-guard |
| Risk | medium |
| Stability | stable |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

MCP 쓰기 도구는 실행 전에 대상 노드에 대한 호출자의 `편집` 유효 권한을 검사하고, 권한이 없으면 호출을 거부한다. 결과를 걸러내는 방식이 아니라 실행 자체를 막는다.

#### Rationale

감사 M9 해소. 원장 초판의 MCP 조항은 "ACL 로 필터링" 만 규정했는데, 필터링은 읽기 개념이라 쓰기 검사의 근거가 되지 못했다. 필터를 쓰기에 적용하면 "쓸 수 없는 대상을 결과에서 뺀다" 가 되어 실제 쓰기를 막지 못한다. 원장이 읽기와 쓰기를 갈라 명시한 이유가 이것이며, §4 수용 기준 5 후단이 "보기 권한만 있는 사용자의 쓰기 도구 호출은 거부된다" 로 이 요구의 관문을 잡는다.

#### Acceptance Criteria

- [ ] AC-1: 대상 노드에 `보기` 유효 권한만 가진 사용자가 MCP 쓰기 도구를 호출하면 거부된다.
- [ ] AC-2: 대상 노드에 `편집` 유효 권한을 가진 사용자가 같은 MCP 쓰기 도구를 호출하면 실행된다.
- [ ] AC-3: 거부된 쓰기 호출은 대상 노드를 변경하지 않은 상태로 종료된다.

#### Implementation Notes

- 검사 대상은 요청 인자에 적힌 노드가 아니라 실제로 변경될 노드다. 한 호출이 여러 노드를 바꾸면 전부 검사해야 하며, 원장은 다중 노드 쓰기 도구의 검사 순서와 부분 실패 처리를 정하지 않았다.
- 거부 응답이 노드의 존재를 드러내도 되는지는 이 조항이 정하지 않는다. 완전 숨김 규칙과 만나는 자리이며 그 규정은 접근 제어 scope 가 소유한다.
- 읽기 필터 요구사항을 이 검사의 근거로 재사용하면 안 된다 — 원장이 두 갈래를 나눈 이유가 그 오용을 막기 위해서다.

### FR-ARCH-001 — 1.0 의 AI 기능과 MCP 서버를 이관한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | ai, mcp, migration |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

DocuLight 1.0 의 AI 기능(LangChain 기반 파이프라인 · 벡터검색 · `smart_search`)과 MCP 서버를 2.0 으로 이관한다. 이관은 원문 그대로가 아니라 MCP 인증·인가 제약을 적용한 형태여야 한다.

#### Rationale

1.0 이 이미 운용 중인 자산이라 재작성 이득이 없다. 다만 원장은 이 조항에 "단, 인증·ACL 제약을 반드시 적용" 이라는 단서를 함께 달았다 — 1.0 의 MCP read 계열 도구는 인증 없이 public 이었고, 문서에 권한 개념이 없었기에 성립한 전제다. 문서별 ACL 이 핵심인 2.0 에서는 그 전제가 그대로 깨지므로 이관은 무조건적이지 않다.

#### Acceptance Criteria

- [ ] AC-1: 1.0 의 LangChain 기반 AI 파이프라인·벡터검색·`smart_search` 가 2.0 에서 동작한다.
- [ ] AC-2: 1.0 의 MCP 서버가 2.0 에서 동작한다.
- [ ] AC-3: 이관된 AI·MCP 표면 중 인증·ACL 제약을 적용하지 않은 호출 경로가 존재하지 않는다.

- 인지된 제약 — 아카이브가 Phase 2 로 이관되면서 Phase 1 에는 워크스페이스를 없애는 수단이 없다.
