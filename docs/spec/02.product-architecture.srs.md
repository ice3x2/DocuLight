## 1. Scope Overview

이 scope 는 제품 전체가 올라앉는 판을 규정한다 — 어떤 규모와 운영 형태를 전제하는가, 어떤 코드베이스 위에 짓는가, 어떤 프론트엔드 스택과 부품으로 짓는가, 1.0 에서 물려받는 AI·벡터검색·MCP 표면을 접근 제어 아래에 어떻게 다시 놓는가, 그리고 이 설계 문서 자체를 어떤 규약으로 쓰는가.

제품의 정의 자체 — 옵시디언의 편집·열람 경험을 웹으로 옮기고 여기에 문서/디렉토리 단위 접근 제어를 더한 사내 문서 시스템 — 는 원장 §1 이 정본으로 갖는다. 이 scope 가 담는 것은 그 제품을 실현하는 판의 제약이며, 판 위에서 벌어지는 기능은 각 기능 scope 가 갖는다.

## 2. Scope Boundaries

### In Scope

- 규모·운영 형태 전제 — 사내 단일 인스턴스, 수백~수천 명 (`CON-ARCH-001`)
- 코드베이스 전략 — 백엔드·프론트엔드 신규 작성, 1.0 에서는 코드가 아니라 기능을 물려받음, 1.0 동결 (`CON-ARCH-002`)
- 프론트엔드 스택과 부품 선택 — SPA 스택, UI 부품 패키지, 프레임워크 중립 에디터·머지·마크다운 패키지, 문서 본문의 정본 위치 (`CON-ARCH-003`·`CON-ARCH-004`·`CON-ARCH-005`·`CON-ARCH-006`)
- 빌드 산출물의 서빙 방식과 운영 프로세스 수 (`OPS-ARCH-001`)
- 1.0 의 AI 기능·벡터검색·MCP 서버를 도구 계약과 동작으로 물려받아 신규 작성 (`FR-ARCH-001`)
- MCP 표면의 인증·인가 — 호출 인증 필수화, 읽기 결과의 ACL 필터링, 쓰기 도구의 편집 권한 검사 (`SEC-ARCH-001`·`SEC-ARCH-002`·`SEC-ARCH-003`)
- 설계 문서 규약 — `docs/spec` 의 SpecKiwi SRS 정식화, 한 사실은 한 곳, Phase 라벨 판정 (`CON-ARCH-007`·`CON-ARCH-008`·`CON-ARCH-009`)

### Out of Scope

- MCP 호출자를 식별하는 인증 수단 자체 — PAT 의 발급·저장 형식·스코프·무효화는 `AUTH` scope 가 소유한다. 이 scope 는 MCP 호출에 인증이 필요하다는 사실만 정한다 (`SEC-ARCH-001` Implementation Notes).
- 완전 숨김 규칙의 정본, 그리고 거부 응답이 노드의 존재를 드러내도 되는지의 판정 — `ACL` scope 가 소유한다. 이 scope 는 그 규정이 MCP 표면에도 적용된다는 사실만 담는다 (`SEC-ARCH-002`·`SEC-ARCH-003` Implementation Notes).
- 유효 권한의 정의와 계산 방식 — `ACL` scope 가 소유한다. `SEC-ARCH-002`·`SEC-ARCH-003` 은 그 값을 쓰는 쪽의 계약만 고정한다.
- 벡터 인덱스의 갱신 시점과 삭제된 노드 엔트리의 배제 — `STORAGE` scope 가 소유한다. 이 scope 는 검색 *결과*의 필터링만 정한다.
- 앱 화면의 텍스트 검색 — 좌측 사이드바 검색 탭의 검색 대상·질의 문법·결과 표시는 `SHELL` scope 가 소유한다. 이 scope 는 AI·MCP 표면만 가지며, 두 축이 갈라지는 경계는 `CON-SHELL-002`(AI 검색은 MCP 로만 제공한다)가 못박는다. 그 경계를 여기서 다시 정하면 같은 사실이 두 자리에 놓인다.
- 플러그인 시스템을 범위에서 제외한다는 결정(R15) — 제품이 하지 않기로 한 것이며, 그 배제를 문면으로 담는 자리는 `EDITOR` scope 다.
- 멀티테넌트 SaaS 운영과 고객사 온프레미스 배포 — 제품이 대상으로 삼지 않는다(R19). 그 배제는 이 scope 안의 `CON-ARCH-001` 이 문면으로 담으므로 여기서 다시 열거하지 않는다.
- 성능 목표 — 응답 시간·처리량 수치는 원장에 없고 어느 scope 도 소유하지 않는다. `CON-ARCH-001` 은 규모만 전제하며 수치를 도출할 근거가 아니다. 필요해지면 새 조항으로 세워야 한다.

## 3. Assumptions and Constraints

- 이 scope 가 전 scope 공통 전제를 소유한다 — 규모(`CON-ARCH-001`) · 스택과 서빙(`CON-ARCH-003`·`OPS-ARCH-001`) · 문서 규약(`CON-ARCH-007`·`CON-ARCH-008`·`CON-ARCH-009`). 다른 scope 문서는 이 값들을 복제하지 않고 여기를 가리킨다.
- 1.0 이 동결된 채 계속 운영 가능하다는 것이 코드베이스 전략의 전제다 (`CON-ARCH-002`).
- 스택 선택은 런타임 성능과 번들 크기의 손해를 인지하고 감수한 결정이다 — 사내망 단일 인스턴스이고 구현 속도가 최우선 기준이라는 전제 위에서만 성립한다 (원장 §2.11).
- Phase 2 열거는 닫힌 목록이 아니다 (`CON-ARCH-009`). 이 문서를 포함해 어느 scope 문서도 Phase 2 를 전량으로 열거하지 않는다.
- 데스크탑 전용(R31)이라는 Phase 1 구속은 `EDITOR` scope 가 소유하며, 이 scope 의 스택·부품 선택은 그 전제 위에서 이뤄졌다.

### SEC-ARCH-001 — MCP 호출에 사용자 인증을 필수화한다

| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | mcp, authentication |
| Risk | medium |
| Stability | stable |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

MCP 서버의 모든 도구 호출은 사용자 인증을 통과해야 실행된다. 인증되지 않은 호출은 도구 종류와 무관하게 거부하며, 인증 없이 호출할 수 있는 도구를 두지 않는다.

#### Rationale

1.0 에서는 MCP 의 read 계열 도구(`list_documents` · `read_document` · `search`)가 인증 없이 public 이었다. 문서에 권한 개념이 없었기에 성립한 전제이며, 문서별 ACL 이 핵심인 2.0 에서는 그 전제가 그대로 깨진다. 인증이 없으면 뒤따르는 ACL 필터링과 쓰기 권한 검사가 판정할 주체 자체를 갖지 못하므로, 이 조항은 두 인가 규칙의 선행 조건이다.

#### Acceptance Criteria

- [ ] AC-1: 인증 자격을 싣지 않은 MCP 도구 호출은 도구 종류와 무관하게 거부된다.
- [ ] AC-2: 인증 없이 호출할 수 있는 MCP 도구가 서버의 도구 목록에 존재하지 않는다.
- [ ] AC-3: 유효한 사용자 자격으로 인증한 MCP 호출은 그 사용자를 호출 주체로 확정한다.

#### Implementation Notes

- 1.0 의 read 계열 도구(`list_documents` · `read_document` · `search`)는 무인증으로 열려 있었다. 도구 계약을 그대로 물려받으면서(`R21-b`) 인증 요건을 얹지 않으면 같은 구멍이 신규 구현에 재현되는 것이 이 조항의 실패 모드다 — 계약을 옮길 때 도구 목록 전량을 훑어라.
- 인증 수단 자체는 이 조항이 정하지 않는다. 원장 §4 수용 기준 5 가 PAT 로 인증한 두 사용자를 시나리오로 쓰지만, PAT 규정은 인증 scope 가 소유한다.
- [2026-08-19] 무인증 표면은 read 게이트 하나가 아니다 — 1.0 은 `POST /context` 를 별도 표면으로 두고 도구 3개(`list_context_documents` · `read_document` · `search_documents`)를 인증 없이 연다(조사 원문 `arag-probe.md` §D-2 실측). AC-2 가 막아야 할 대상에 그 표면이 포함된다. 도구 목록을 훑을 때 주 표면 `POST /mcp` 만 보고 끝내지 마라 — 기능을 남기려면 주 표면으로 흡수하거나 인증을 붙여야 한다.

### SEC-ARCH-002 — MCP 읽기 도구와 벡터검색 결과를 호출자의 ACL 로 필터링한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | mcp, acl, vector-search |
| Risk | medium |
| Stability | stable |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

MCP 읽기 도구가 돌려주는 결과와 벡터검색 결과는 호출자의 유효 권한으로 필터링한다. 호출자가 볼 수 없는 노드는 결과 목록에도, 요약·발췌 형태의 본문에도 나타나지 않는다.

#### Rationale

AI 벡터 인덱스는 전 문서를 담고 있으므로, 결과를 사용자별로 필터링하지 않으면 권한 없는 문서의 내용이 요약문 형태로 유출된다. 원장은 이것을 1.0 의 AI·MCP 기능을 그대로 물려받으면 안 되는 이유로 명시했다. 원장 §4 수용 기준 5 전단이 "같은 도구를 호출했을 때 결과가 각자의 ACL 로 다르게 나온다" 로 이 요구의 관문을 잡는다.

#### Acceptance Criteria

- [ ] AC-1: 서로 다른 ACL 을 가진 두 사용자가 같은 MCP 읽기 도구를 같은 인자로 호출하면 각자의 유효 권한에 해당하는 결과만 돌려받는다.
- [ ] AC-2: 벡터검색 호출의 결과 목록에 호출자가 볼 수 없는 노드의 항목이 포함되지 않는다.
- [ ] AC-3: 벡터검색 결과의 요약·발췌 텍스트에 호출자가 볼 수 없는 노드의 본문이 포함되지 않는다.
- [ ] AC-4: 권한 없는 노드가 걸러진 결과는 걸러졌다는 사실을 건수·순번·자리표시 어느 형태로도 노출하지 않는다.

#### Implementation Notes

- 필터를 어느 지점에 적용하는지가 정해져 있지 않다. 벡터 인덱스가 전 문서를 담고 있어 상위 N 건을 먼저 뽑은 뒤 거르면 권한 있는 결과가 통째로 사라져 빈 응답이 나온다. 정렬·상한 적용 지점과 필터 적용 지점의 순서를 구현 단계에서 정해야 하며, 원장은 이 축을 정하지 않았다.
- "필터링" 은 읽기 개념이다. 이 조항을 쓰기 도구의 인가 근거로 재사용하면 안 된다 — 쓰기 검사는 별도 요구사항이 소유한다.
- AC-4 는 완전 숨김 규칙과 만나는 자리다. 숨김의 정본 규정은 접근 제어 scope 가 소유하며, 이 조항은 그 규정이 MCP 표면에도 적용된다는 사실만 담는다.
- [2026-08-19] 원장 `R21-b` 가 이 요구를 `R21` 개정의 스윕 대상 셋 중 하나로 지목했다. 필터의 규범은 바뀌지 않았다 — 바뀐 것은 그 필터가 걸리는 구현이 1.0 이식물이 아니라 신규 작성물이라는 사실이다. 따라서 "1.0 이 이미 그렇게 하고 있다" 를 이 요구의 충족 근거로 쓸 수 없다.
- [2026-08-19] 원장 `R21-a` 가 이 요구를 근거로 인용한다 — 텍스트 축을 SQLite FTS5 로 두면 여기서 요구하는 ACL 필터가 사후 필터가 아니라 `WHERE` 절로 성립해 위 첫 노트의 순서 문제와 `G36` ③(거른 뒤 N건인가 거르기 전 N건인가)이 텍스트 축에서는 생기지 않는다. 그것은 `R21-a` 의 근거이지 이 요구가 정한 규정이 아니다 — 저장 기술을 이 자리에서 규정하지 마라. 벡터 축에는 순서 문제가 그대로 남는다.

### SEC-ARCH-003 — MCP 쓰기 도구는 대상 노드의 편집 유효 권한이 없으면 거부한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | mcp, acl, write-guard |
| Risk | medium |
| Stability | stable |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

MCP 쓰기 도구는 실행 전에 대상 노드에 대한 호출자의 `편집` 유효 권한을 검사하고, 권한이 없으면 호출을 거부한다. 결과를 걸러내는 방식이 아니라 실행 자체를 막는다.

#### Rationale

감사 M9 해소. 원장 초판의 MCP 조항은 "ACL 로 필터링" 만 규정했는데, 필터링은 읽기 개념이라 쓰기 검사의 근거가 되지 못했다. 필터를 쓰기에 적용하면 "쓸 수 없는 대상을 결과에서 뺀다" 가 되어 실제 쓰기를 막지 못한다. 원장이 읽기와 쓰기를 갈라 명시한 이유가 이것이며, §4 수용 기준 5 후단이 "보기 권한만 있는 사용자의 쓰기 도구 호출은 거부된다" 로 이 요구의 관문을 잡는다.

#### Acceptance Criteria

- [ ] AC-1: 대상 노드에 `보기` 유효 권한만 가진 사용자가 MCP 쓰기 도구를 호출하면 거부된다.
- [ ] AC-2: 대상 노드에 `편집` 유효 권한을 가진 사용자가 같은 MCP 쓰기 도구를 호출하면 실행된다.
- [ ] AC-3: 거부된 쓰기 호출은 대상 노드를 변경하지 않은 상태로 종료된다.

### FR-ARCH-001 — 1.0 의 AI·MCP 기능을 도구 계약과 동작으로 물려받아 신규 작성한다

#### Requirement

1.0 이 제공하던 AI 기능과 MCP 서버를 2.0 에서 신규 작성한다. 물려받는 것은 MCP 도구 계약 — 도구 이름 · 입력 인자와 기본값 · 출력 포맷 · 에러 코드 — 과 화면이 제공하던 동작이며, 1.0 의 소스·의존성·내부 구조는 물려받지 않는다. 의미 검색(A-RAG) 역시 1.0 의 `smart_search` 를 옮기지 않고 신규 작성한다. 신규 작성물은 MCP 인증·인가 제약을 적용한 형태여야 한다.

#### Rationale

사용자가 "당신이 기존보다 더 잘 만들 수 있다면 그렇게 하라" 는 조건을 달았고 실측이 그 조건을 충족했다 — 1.0 의 semantic 경로는 한 번도 실전 동작한 적이 없다. 그래서 인계 대상은 코드가 아니라 계약과 동작이다. 인계가 무조건적이지 않은 이유는 따로 있다 — 1.0 의 MCP read 계열 도구는 인증 없이 public 이었고 이는 문서에 권한 개념이 없었기에 성립한 전제다. 문서별 ACL 이 핵심인 2.0 에서는 그 전제가 그대로 깨지므로, 계약을 물려받되 인증·인가 제약을 얹은 형태여야 한다.

#### Acceptance Criteria

- [ ] AC-1: 2.0 의 MCP 도구는 1.0 과 같은 도구 이름 · 입력 인자와 기본값 · 출력 포맷 · 에러 코드를 제공한다.
- [ ] AC-2: 1.0 이 갖고 있던 AI 기능(LangChain 기반 파이프라인 · 벡터검색 · `smart_search`)은 2.0 에서 대응물을 갖되, 인계 대상은 그 도구 계약과 화면이 제공하던 동작이다. `smart_search` 의 semantic 경로는 1.0 에서 동작한 적이 없으므로(`R21-a`) 그 실행 결과는 재현 대상이 아니며 AC-4 가 그 자리를 받는다.
- [ ] AC-3: 2.0 의 AI·MCP 코드에 1.0 의 소스를 옮겨 온 파일이 존재하지 않으며, 빌드·의존성 어느 것도 1.0 경로를 가리키지 않는다.
- [ ] AC-4: 의미 검색(A-RAG)은 신규 작성물이며 1.0 의 `smart_search` 구현을 재사용하지 않는다.
- [ ] AC-5: AI·MCP 표면 중 인증·ACL 제약을 적용하지 않은 호출 경로가 존재하지 않는다.

DocuLight2.0 을 1.0 과 별도의 리포지토리로 두고, 백엔드와 프론트엔드를 모두 신규 작성한다. 1.0 에서 물려받는 것은 코드가 아니라 그것이 제공하던 기능이며, 2.0 의 어떤 빌드·의존성·설정도 1.0 의 소스 경로를 가리키지 않는다. 1.0 은 동결하여 계속 운영 가능한 상태로 남긴다.

#### Acceptance Criteria

- [ ] AC-1: `DocuLight2.0` 은 1.0 과 별도의 리포지토리다.
- [ ] AC-2: 2.0 의 백엔드는 신규 작성물이며, 1.0 의 백엔드 소스를 옮겨 온 파일이 존재하지 않는다.
- [ ] AC-3: 2.0 의 프론트엔드는 신규 작성물이며, 1.0 의 EJS SSR·vanilla JS 프론트 코드를 옮겨 온 파일이 존재하지 않는다.

- [ ] AC-6: 로깅 · config · 파일 감시(chokidar) · E2E 도구(Playwright)는 `FR-ARCH-001` 의 인계 범위 밖이며, 1.0 에서 코드로 이식되지 않고 2.0 이 자기 조항(`R96` · `R77` 등) 위에서 새로 고르는 부품이다.

#### Research / Analysis

- 원장 R21 근거 표의 자산별 처분 — (1) 그대로 이식: MCP 서버 · AI/벡터검색 · 로깅 · config · chokidar · Playwright. (2) 이식 후 그룹·ACL 로 확장: 인증 기반(bcrypt · 쿠키 · nodemailer). (3) 유지하되 모든 엔드포인트에 권한 필터가 침투: REST API(tree · raw · search). (4) 전면 교체: EJS SSR + vanilla JS 프론트 — 라이브 프리뷰·분할창·커맨드 팔레트·백링크 패널을 vanilla 로 감당할 수 없다는 것이 사유다. (5) 유지: CodeMirror 6 — 옵시디언도 CM6 기반이다.
- 이 표가 `nodemailer` 를 이식 자산으로 열거한다는 사실은 잠긴 계정 복구 경로 공백(`G32`) 심의가 인용하는 자리다 — 메일 자기 서비스 후보의 인프라 전제가 부분 충족되어 있다는 근거가 여기서 나온다. 다만 그 심의는 이메일 필수 여부가 `G10` 미결이라 수신처가 보장되지 않는다는 점을 함께 든다. 이 요구사항은 `nodemailer` 를 이식한다는 사실만 담고, 그것으로 무엇을 하는지는 담지 않는다.
- [2026-08-19] 위 두 항목은 `R21` 개정 이전의 자산별 처분을 전사한 것이며 발견 경위의 기록으로만 남긴다. 개정 뒤의 처분은 하나다 — 백엔드·프론트엔드 전부 신규 작성이고, 물려받는 것은 MCP 도구 계약과 화면이 제공하던 동작이다(`R21-b`). 기각된 대안과 그 재개봉 조건은 `R21-c` 가 갖는다 — 검색 코어 3파일 이식은 사용자 결정으로 기각됐고, 벡터 저장소로 HNSWLib 을 택할 경우에 한해 다시 논의한다.

#### Implementation Notes

- 원장 §2.10 의 `R21 근거` 표는 처분 칸이 갱신되어 이 조항의 문면과 정합한다 — 그 표의 각주가 갱신 사실을 밝히면서 표 자체는 「무엇이 있었는가」의 기록으로 남긴다고 적는다. 취소선 아래의 옛 처분(그대로 이식 / 이식 후 확장 / 유지)을 이 조항의 근거로 인용하지 마라. 자산별 처분의 정본은 개정된 `R21` 과 `R21-b` 다.
- 1.0 동결의 운영 기간·해제 조건은 원장이 정하지 않았다. 두 리포가 동시에 살아 있는 동안 볼트를 공유하는지도 규정되지 않았다.
- [2026-08-19] 원장 `R21` 개정으로 이 조항의 제목·문면·AC 를 고쳤다. 개정의 근거는 언어 장벽이 아니다 — 개정 심의 브리프가 "1.0 은 JS·CommonJS 이고 2.0 은 TS·ESM 이라 언어 경계를 넘어야 한다" 를 이식 비용의 근거로 들었으나 원장이 그 전제를 틀린 것으로 정정했다. `TypeScript` 를 규정하는 것은 `CON-ARCH-003`(프론트엔드) 하나이고 백엔드 언어를 정한 요구사항은 `docs/spec` 어디에도 없다. 실제 근거는 `R21-a` 의 실측이다.
- [2026-08-19] `G32`(잠긴 계정 복구 경로) 심의는 이 조항의 근거 표가 `nodemailer` 를 이식 자산으로 열거한다는 사실을 메일 자기 서비스의 인프라 전제로 인용한다. `R21` 개정으로 그 자산은 이식 대상이 아니라 신규 작성 대상이 되었으므로 그 전제는 "1.0 이 이미 그 경로를 갖고 있다" 가 아니라 "같은 라이브러리를 새로 쓸 수 있다" 로 약해진다. `G32` 를 닫을 때 이 변화를 함께 판정하라 — 이 조항이 그 판정을 대신하지 않는다.
- [2026-08-19] AC-5·AC-6 은 재작성 전 AC-2 가 이름으로 들던 자산(MCP 서버 · AI/벡터검색 · 로깅 · config · chokidar · Playwright)의 처분을 되살린 것이다. 재작성 때는 AC-5 하나가 `FR-ARCH-001` 에 통째로 위임했으나 그 요구의 범위는 AI·MCP 이므로 로깅·config·chokidar·Playwright 가 어느 AC 도 다루지 않는 자리로 떨어졌다. 위임은 닿는 곳까지만 하고 나머지는 AC-6 이 직접 받는다.
- [2026-08-19] 위 첫 항목의 전제를 현재 사실로 고쳤다. 그 항목은 원장 §2.10 표가 개정 전 처분을 「그대로 담고 있어 이 조항의 문면과 어긋난다」고 적었으나, 그 표의 처분 칸은 이미 `옛 처분 → 새 처분` 형태로 갱신되어 이 조항과 정합하고 그 각주가 갱신 사실을 스스로 밝힌다. 표를 서술하는 문장이 표보다 낡아 있던 자리이며, 그대로 두면 다음 개정자가 이미 정합된 표를 어긋난 것으로 읽고 다시 고치려 든다.
- [2026-08-19] AC-4 와 `OPS-ARCH-001` AC-4 가 정면으로 충돌했다 — 후자가 「1.0 의 PM2 배포 구성을 그대로 쓴다」였다. 원장 `R21-b` 는 인계 대상을 MCP 도구 계약과 화면이 제공하던 동작으로 닫고 「2.0 의 어떤 설정도 1.0 경로를 가리키지 않으며」를 함께 세우므로, 배포 구성은 인계 대상에 들지 않는다. 그래서 이 AC 를 남기고 `OPS-ARCH-001` AC-4 를 그 문면에 맞췄다. 다만 원장 `R33-a` 비고는 「기존 PM2 배포 구성을 그대로 쓴다」로 개정 전 문면이 남아 있다 — `R124-a` 스윕이 닿지 않은 자리이고, 1.0 배포 구성 산출물 자체의 처분은 원장 미결이다.
- [2026-08-20] 위 항목의 현재형 주장 둘이 더는 참이 아니다. 원장 `R33-a` 가 이날 개정돼 비고의 「기존 PM2 배포 구성을 그대로 쓴다」가 실효됐으므로 「개정 전 문면이 남아 있다」는 해소됐고, 1.0 배포 구성 산출물의 처분도 사용자 결정으로 닫혔다 — 파일로 복사하지 않고 읽기 전용 참고에 그치며 구성은 2.0 용으로 신규 작성한다. AC-4(2.0 의 어떤 빌드·의존성·설정도 1.0 경로를 가리키지 않는다)와 같은 방향이며 AC 는 바꾸지 않았다.

#### Requirement

#### Rationale

SSR/SEO 요구가 0 이므로 Next.js 의 서버 계층은 순수 비용이다. 사내망 단일 인스턴스라 초기 로딩·SEO 압박이 없고 최우선 판단 기준은 구현 속도다. 기각된 대안 — Next.js: "정적 export 구성은 Next 의 서버 기능을 전부 봉인한다는 뜻이고, 'Next 서버를 절대 두지 않는다' 를 지킬 규율이 없다면 Vite SPA 가 더 정직한 선택" 이라는 것을 그 후보를 옹호하도록 배정된 담당자 본인이 인정했다. Svelte 5: `@tanstack/svelte-table` v8 이 `svelte/internal` 의존으로 Svelte 5 에서 동작하지 않고(v9 알파), runes 가 최근 파괴적 변경이라 웹·LLM 자료 다수가 Svelte 4 문법이어서 구현 속도 기준에서 실질 손해다 — 사용자·그룹 관리 테이블이 설정 모달의 중심에 놓이므로 이 공백이 정면으로 걸린다.

### OPS-ARCH-001 — 빌드 산출물을 2.0 의 Express 서버가 서빙하고 Node 프로세스를 1개로 유지한다

#### Requirement

프론트엔드 빌드 산출물(정적 파일)은 2.0 의 Express 서버가 서빙한다. 별도의 프론트엔드 서버를 두지 않으며 운영 배포의 Node 프로세스는 1개를 유지한다.

#### Rationale

프론트와 API 가 같은 오리진이 되어 CORS·CSRF 문제가 발생하지 않는다. PM2 로 단일 프로세스를 띄우므로 운영이 관리할 프로세스가 하나로 끝난다. 프로세스가 하나라는 사실은 사내 단일 인스턴스 규모 전제와 같은 방향이다 — 규모가 프로세스 분리를 요구하지 않으므로 분리는 순수 운영 비용이 된다.

#### Acceptance Criteria

- [ ] AC-1: 프론트엔드 정적 파일은 2.0 의 Express 서버 라우트로 서빙된다.
- [ ] AC-2: 운영 배포 구성에서 애플리케이션이 띄우는 Node 프로세스는 1개다.
- [ ] AC-3: 프론트엔드와 API 가 같은 오리진에서 제공되어 브라우저 요청에 CORS 설정이 필요하지 않다.
- [ ] AC-4: 운영 배포의 프로세스 관리는 PM2 로 한다. 그 배포 구성은 1.0 리포지토리의 경로를 가리키지 않는다.

#### Rationale

#### Requirement

확정 요구사항은 Phase 명시가 없으면 전부 Phase 1 이다. Phase 2 목록은 닫힌 열거가 아니므로 이 목록이 전량이라고 가정하지 않는다. Phase 2 조항은 큰 축의 정의이며 화면 설계가 아니다.

#### Rationale

감사 H11 해소. 초판은 Phase 2 를 닫힌 열거로 적었다가 조항 하나가 그 열거에서 빠지는 사고가 났고, "닫힌 열거를 쓰는 것 자체가 결함이었으므로 열린 목록으로 바꾼다" 는 선례를 따라 열린 형태로 전환했다. 다만 근거 없이 열기만 하면 판정 근거가 0 이 되어 닫힌 열거보다 나쁘다는 경고가 원장에 이미 있었으므로 — 열 수 있었던 선례들은 뒤에 생성적 규칙이 따로 있었기 때문에 열 수 있었다 — 열거를 지우지 않고 판정 경로를 함께 실었다.

#### Acceptance Criteria

- [ ] AC-1: 조항이 자기 문면에 Phase 를 명시하지 않으면 Phase 1 로 판정한다.
- [ ] AC-2: 하위 조항은 상위 조항의 Phase 를 따른다 — 단 하위가 스스로 다른 범위를 선언하거나 상위와 다른 축의 규칙이면 하위 자신의 판정이 이긴다.
- [ ] AC-3: 2026-08-19 기준 Phase 2 판정 목록은 R17 열거(그래프뷰·커맨드 팔레트·퀵스위처·분할 창·아웃라인·프론트매터 프로퍼티) · R31 · R54 · R55 · R55-a · R103 · R146 · R147 · R148 계열이다.
- [ ] AC-4: Phase 2 항목에 딸린 미결 공백(G34 · G35)은 Phase 1 착수를 막지 않는다.

#### Implementation Notes

- 판정은 세 경로를 함께 써야 한다. ① 조항이 스스로 Phase 2 를 선언하는지 원장 전수로 훑는다. ② 자기 문면에 Phase 표기가 없는데 다른 조항의 비고가 미뤄 둔 것을 찾는다. ③ 하위 항목은 상위 조항의 Phase 를 따른다. ②가 없으면 이 목록 자신도 재도출되지 않는다 — R55·R55-a 는 Phase 토큰이 0건이고 R54 비고를 경유해야만 잡힌다. R148-a·R148-b·R148-c 는 Phase 토큰이 0건이고 이들을 미루는 비고도 없어 ①②만으로는 잡히지 않는다.
- ③에 단서가 필요한 이유는 반례가 둘 있기 때문이다. R55-b 는 R55 의 하위지만 fail-closed 서빙이 Phase 1 보안 규칙이고, R103-a 는 R103 의 하위지만 문면이 "Phase 2 에서도 요청 버튼을 두지 않는다" 여서 Phase 1·2 양쪽에 걸린다. 단서 없이 ③을 쓰면 이 둘을 잘못 판정한다.
- ①이 짚었다고 곧바로 항목이 되지 않는다 — 그 조항 자체가 미뤄졌는지 보라. ①은 목록 밖도 짚으며 전부 위양성이다: R89(이미 R17 에 흡수) · R23 · R33-b · R98 · R24-b(다른 조항의 Phase 2 를 가리키는 파생) · 취소선 조항. R48 도 ①에 걸리지만 비고 첫 문장이 "Phase 1 규정이다" 이고 뒤는 Phase 2 확장을 가리키는 역참조다.
- 이 목록은 2026-08-19 기준이며 조항이 신설되면 다시 판정해야 한다. 그것이 이 요구사항의 Stability 가 `evolving` 인 이유다.
- 인지된 제약 — 아카이브가 Phase 2 로 이관되면서 Phase 1 에는 워크스페이스를 없애는 수단이 없다.
