## 1. 제품 정의

DocuLight 2.0 은 **옵시디언(Obsidian)의 편집·열람 경험을 웹으로 옮기고, 여기에 옵시디언에 없는 사용자·그룹 기반 문서 접근 제어를 더한** 사내 문서 시스템이다.

옵시디언 대비 차별점은 단 하나로 요약된다: **문서/디렉토리 단위 권한 관리.**

| R77-b | 잔여 위험 — 정지 중 이동된 문서가 재조정에서 신규 노드(상속)가 되면 **일시적으로 원래보다 넓은 권한으로 보일 수 있다.** 감사 목록 통지가 완화책이다 | 완전 차단(미등록 파일 격리)은 운영 마찰이 커서 채택하지 않음. 인지된 잔여 위험으로 기록 |
| R78 | **`.trash` 와 `.versions` 의 각 항목에 사이드카 메타 파일을 함께 기록한다** — 휴지통: 원본 노드 ID·원본 경로·삭제 시각·삭제자 / 버전: 문서 노드 ID·버전 순번·생성 시각. DB 인덱스는 이 메타의 캐시다 | 감사 C11 해소. R50-d(`.res/index.json`)·R40-b 와 동일 원칙 — DB 손상 시 파일시스템만으로 재구성 가능 |
| R79 | **벡터 인덱스는 노드 삭제·이동·아카이브 시 동기 갱신/제거한다.** 판정 대상 노드가 존재하지 않는 인덱스 엔트리는 검색 결과에서 **무조건 제외(fail-closed)** 한다 | 감사 C13 해소. 삭제된 문서의 요약이 검색으로 유출되는 경로 차단 |

**R20 근거 (JSON 을 채택하지 않은 이유)**

1. **읽기 빈도** — 트리 렌더링·검색·MCP 호출마다 권한 판정이 필요하다. 수천 명 × 수천 문서 규모에서 매 요청마다 전체 JSON 을 순회하는 구조는 성립하지 않는다.
2. **동시 쓰기** — 가입 승인·그룹 변경·ACL 변경이 겹치면 JSON 전체 rewrite 는 경합이 난다. 락으로 막는 것은 DB 를 손으로 다시 만드는 일이다.
3. **원자성** — "사용자 생성 + default 그룹 배정"은 한 트랜잭션이어야 한다.

### 2.4 접근 제어 (ACL)

| ID | 결정 | 비고 |
|---|---|---|
| R9 | ACL 대상은 **문서와 디렉토리 둘 다**이다 | |
| R10 | 대상마다 4종을 지정한다: 편집 사용자 / 보기 사용자 / 편집 그룹 / 보기 그룹 | |
| R11 | 편집 권한은 보기 권한을 포함한다 (편집 가능 ⇒ 보기 가능) | |
| R12 | 지정 UX 는 구글 독스 방식 — 사용자와 그룹을 **각각 검색**해서 추가한다 | |
| R14 | **상속 + 가산.** 노드마다 `상속` 플래그를 두고 기본값은 `상속 유지`다. ACL 항목은 **부여(가산)만** 하며, 권한을 좁히는 유일한 수단은 **`상속 끊기`로 명시 전환**하는 것이다 | Q2 확정 (D안) |
| R14-a | `상속 끊기` 전환 시 부모 ACL 을 **자동 복사하지 않는다.** "부모 권한 가져오기"를 별도 버튼으로 제공한다 | C안(SharePoint 방식)과의 유일한 차이. D 는 C 의 상위집합이다 |
| R14-b | **유효 권한 테이블(user×node) 비정규화를 하지 않는다.** 요청마다 계산한다 | 수천×수천 = 수백만 행이고 그룹 멤버 1명 추가에 전체 재계산이 필요하다. 매 요청 계산하면 **캐시 무효화 문제 자체가 사라진다**. 요청당 2쿼리 + 메모리 O(N) 순회로 충분 — **여기서 N 은 요청자가 접근 가능한 전 워크스페이스의 노드 수**이며(R25·R39·R41 조합), **트리 지연 로딩을 전제**로 성립한다 (감사 L6) |
| R14-c | **거부(deny) 규칙을 두지 않는다.** 허용 목록의 합집합만으로 판정한다 | 편집 ⊇ 보기 단조 구조라 유효 권한이 단조·가환이 되어 감사와 역질의가 쉽다. 계정 정지는 ACL 이 아니라 **principal 레벨 비활성화 게이트**로 별도 처리 |
| R25 | **권한이 없는 문서·디렉토리는 트리에서 완전히 숨긴다.** 존재 자체가 노출되어서는 안 된다 | 잠금 아이콘 등으로 표시하지 않음. 트리의 모든 노드에 권한 판정이 필요해짐. **단 R69 가 명시적 예외다** |
| R69 | **R25 의 예외 — pass-through 노드.** 사용자가 접근 가능한 자손을 가진 조상 디렉토리는 **이름만** 트리에 표시한다 | 감사 C1 해소. 이것이 없으면 자손에게만 권한을 준 문서에 도달할 경로가 화면에 존재하지 않는다 |
| R69-a | 트리에 표시되는 것은 **① 사용자가 유효 권한을 가진 노드**와 **② 그런 노드로 가는 경로상의 조상**뿐이다. 조상의 **형제 노드는 표시하지 않는다** | 경로 외의 구조는 여전히 숨겨진다 |
| R69-b | pass-through 노드는 **이름만 가지며 그 자체를 열람·편집·생성 대상으로 삼을 수 없다** | 클릭 시 펼치기만 동작. 새 문서 만들기 등 조작 불가 |
| R69-c | pass-through 여부는 **저장하지 않고 매 요청 계산**한다 | R14-b 와 일관. 자손 권한을 회수하면 조상이 자동으로 사라진다. `통과` 권한 레벨을 신설해 저장하는 방식은 **비정규화라 R14-b 위배**이므로 채택하지 않는다 |

**R70 채택 근거** — R14(D안)를 고른 논거 2번이 `이 문서만 한 명 더 보게 하기` 를 "가장 흔한 조작"이라고 못박았는데, 그 조작이 `관리` 레벨을 요구하면 일반 사용자에게는 불가능해져 **채택 근거 자체가 무너진다.** 넓히기를 `편집` 에 허용하면 그 논거가 성립하고, 좁히기를 `관리` 로 묶으면 R36 의 취지(관리 경계는 한 계층)도 유지된다. 편집자는 **경계를 만들 수 없고 넓히기만 한다.**

**Q2 결정 경위** — 보안·운영 관점은 C(상속 끊기 시 부모 ACL 자동 복사, SharePoint 방식)를 추천했으나 구현 관점이 D 로 뒤집었고 그 논거를 채택했다.

1. C 와 D 는 **스키마와 성능이 완전히 동일**하며 차이는 자동 복사 여부 하나뿐이다. **D 는 C 의 상위집합**이다.
2. C 는 `이 문서만 한 명 더 보게 하기` 라는 **가장 흔한 조작에서 상속을 영구히 끊는다.** D 는 이 조작이 순수 가산이라 부작용이 없다.
3. D 에서는 **좁히는 것만이 명시적 행위**이므로 "좁혔다고 착각하는" 상황이 원천 차단된다. A안이 탈락한 이유가 정확히 그것이었다.
4. 성능은 결정 근거가 아니었다 — A/B/C/D 모두 요청당 2쿼리 + O(N) 순회로 동일하다.

참고: 최초에 이 선택지를 "구글 드라이브 방식"이라고 불렀으나 이는 부정확했다. 구글 드라이브는 상속 유지 + 가산(= D)이고, 부모 ACL 복사 방식(= C)은 SharePoint 의 "Stop Inheriting Permissions" 다.

**Q11 해소** — R10 의 "4종 슬롯"은 다음으로 정리한다.

권한은 **`보기 < 편집 < 관리` 3단계 레벨**이고, 부여 주체는 **사용자 또는 그룹** 2종이다. 즉 슬롯을 늘리는 대신 레벨을 늘린다.

| 레벨 | 의미 | 부여 가능 대상 |
|---|---|---|
| `보기` | 열람 | 워크스페이스 · 디렉토리 · 문서 |
| `편집` | 열람 + 수정 (R11) | 워크스페이스 · 디렉토리 · 문서 |
| `관리` | 편집 + **ACL 부여·회수** | **워크스페이스에만** (R36) |

이 구조는 R28(생성자 자동 편집권)도 자연스럽게 흡수한다 — 별도 소유자 컬럼 없이 `(문서, 생성자, 편집)` 항목 1건으로 표현되고, 워크스페이스 관리자가 그 항목을 삭제하면 회수된다.

**R22 근거 (보안 결함 방지)**

1.0 에서는 MCP 의 read 계열 도구(`list_documents`, `read_document`, `search`)가 인증 없이 public 이었다. 문서에 권한 개념이 없었기에 성립한 전제다. 2.0 은 문서별 ACL 이 핵심이므로 이 전제가 그대로 깨진다.
