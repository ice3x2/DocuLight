## 1. Scope Overview

이 scope 는 인증 후 화면의 골격 — 좌·우 사이드바, 상단 문서 탭과 문서 헤더, 트리의 조작 진입점, 설정 모달의 구조 — 을 규정한다. **무엇이 어디에 놓이는가**가 축이다. 각 자리가 무엇을 보여주고 그 조작이 어떤 권한을 요구하는지는 그 사실을 소유하는 scope 가 갖고, 이 scope 는 진입점의 존부와 배치와 표시 조건만 갖는다.

같은 축 위에서 셸이 소유하는 규칙 몇 가지가 화면 밖에도 걸린다 — 노드 ID 기반 딥링크, 이름 충돌의 통일 처리, 런타임 설정의 단일 저장소, 그리고 전역 검색이 무엇을 대상으로 삼고 질의를 어떻게 해석하는가가 그것이다. 검색이 여기 있는 이유는 그 기능의 소재와 결과 표면이 좌측 사이드바 검색 탭이고 원장이 그 탭에 결과의 소유를 준 데 있다 — 자리를 소유한 scope 가 그 자리가 무엇을 하는지도 갖는다.

## 2. Scope Boundaries

### In Scope

- 좌측 사이드바의 뷰 전환 탭 구성과 우측 사이드바의 신설·세 탭 (`FR-SHELL-001`·`FR-SHELL-004`)
- 전역 검색 — 검색 대상 넷과 소재, 필터 팝오버, 결과 표시 형식, 질의 문법과 최소 질의 길이, 그리고 AI 검색과의 경계 (`FR-SHELL-013`·`FR-SHELL-014`·`CON-SHELL-002`)
- 우측 `태그` 탭의 집계 단위·클릭 동작·정렬 (`FR-SHELL-009`·`FR-SHELL-010`·`FR-SHELL-011`)
- 설정 모달의 구조 — 별도 페이지가 아닌 모달, 관리 기능 진입점의 단일화, 카테고리 전량 목록과 카테고리별 표시 권한 (`IR-SHELL-001`·`CON-SHELL-001`·`IR-SHELL-002`)
- 문서 단위 기능의 소재를 문서 헤더 메뉴로 두는 배치 규칙과 그 귀결인 새 버전 올리기 진입점 (`FR-SHELL-002`·`FR-SHELL-008`)
- 트리 컨텍스트 메뉴 항목의 존부와 노드 종류별 노출, 트리 상단 새 노트 버튼 (`FR-SHELL-003`)
- 상단 문서 탭 — 탭의 존재, 트리 클릭·Ctrl+클릭의 탭 거동, 탭 스트립과 문서 헤더의 2단 분리 (`FR-SHELL-005`·`FR-SHELL-012`·`IR-SHELL-003`)
- 노드 ID 기반 문서 딥링크와 브라우저 히스토리 동작 (`FR-SHELL-006`)
- 휴지통의 화면 표면 — 카테고리 표시 조건, 전 워크스페이스 통합 목록의 행 단위 판정, 영구 삭제 버튼의 미표시 (`FR-SHELL-007`·`SEC-SHELL-001`)
- 이름 충돌 처리의 통일(가시 여부와 무관하게 자동 접미사 + 동일 안내, 확인 단계 없음)과 덮어쓰기 경로의 단일화 (`SEC-SHELL-002`·`FR-SHELL-008`)
- 디렉토리 복사 시 요청자에게 보이는 노드만 복사한다는 규칙 (`SEC-SHELL-003`)
- 런타임에 바뀌는 설정의 단일 저장소를 DB 로 두는 결정 (`DR-SHELL-001`)

### Out of Scope

- 인증 전 화면 — 로그인 · 가입 신청 폼 · 설치 마법사의 구조는 `AUTH` scope 가 소유한다. 설정 모달 구조와 「관리 진입점은 하나」 원칙의 적용 범위는 인증 후 화면까지다. 모달 진입점인 좌하단 기어가 셸에 속하는데 인증 전에는 셸이 없으므로, 인증 전 화면은 이 구조를 *적용해서는 안 되는 것*이 아니라 *충족할 수 없다* (`IR-SHELL-001`·`CON-SHELL-001` Implementation Notes).
- 각 설정 카테고리의 **내부** 화면 — 권한 감사 3종은 `ACL`, 감사 로그는 `AUDIT`, 사용자·그룹 관리는 `PRINCIPAL` scope 가 소유한다. 이 scope 가 소유하는 것은 카테고리의 존부와 표시 권한이다. `IR-SHELL-002` Implementation Notes ④ 는 여기에 휴지통 목록과 인스턴스 설정 다섯 값도 넣지만 그 둘은 이 scope 가 갖는다 — 휴지통 화면은 In Scope 의 `FR-SHELL-007`·`SEC-SHELL-001` 이고 `14.storage` §2 도 `SHELL` 소유로 적으며(위임되는 것은 그 데이터 범위 규칙이고 아래 항목이 적는다), 인스턴스 설정 화면은 `09.auth`·`12.audit-log`·`14.storage` §2 가 셋 다 `SHELL` 소유로 적는다. 그 노트의 열거를 고치는 판정은 `IR-SHELL-002` 가 소유한다.
- 트리 컨텍스트 메뉴 항목의 활성/비활성 판정 근거 — 파일 조작별 필요 권한 표와, 숨은 하위가 있는 디렉토리의 이동·삭제에 걸리는 추가 게이트는 `ACL` scope 가 소유한다. 이 scope 는 그 표를 복제하지 않으며, 여기에 권한 값을 하드코딩하면 두 곳이 조용히 어긋난다 (`FR-SHELL-003` Implementation Notes).
- 트리의 **내용** 규칙 — md 가 아닌 파일도 목록에 표시된다는 규칙은 `ATTACH` scope 가, 접근 가능한 워크스페이스들을 나란히 표시한다는 규칙은 `WORKSPACE` scope 가 소유한다. `FR-SHELL-001` 의 동형 요구는 탭 전환 구조와 배치로 한정된다 (`FR-SHELL-001` Implementation Notes).
- 휴지통의 열람 범위 규칙(본인 삭제분 + 워크스페이스 관리자는 전체), 영구 삭제의 필요 권한 값, 보존 기간 경과 시의 자동 영구 삭제 — `STORAGE` scope 가 소유한다. 이 scope 는 그 값들이 화면에 나타나는 방식만 갖는다 (`FR-SHELL-007`·`SEC-SHELL-001` Implementation Notes).
- 권한 없는 노드에 대한 404 통일 규칙 — `ACL` scope 의 `SEC-ACL-006` 이 소유하고 그 AC 가 딥링크 화면 표면까지 덮는다. `FR-SHELL-006` 은 참조만 하고 복제하지 않는다.
- 노드 ID 가 추측 불가한 랜덤 값이어야 한다는 규정 — `STORAGE` scope 가 소유한다. 딥링크가 URL 에 노드 ID 를 노출하므로 그 성질에 의존하지만, 값의 형식을 이 scope 가 정하지는 않는다.
- 버전 생성의 단위와 보관 상한 — `STORAGE` scope 가 소유한다. `FR-SHELL-008` 은 새 버전 올리기의 진입점만 갖는다 (`FR-SHELL-008` Implementation Notes).
- 새 버전 올리기의 확인 등급이 대상 파일 형식으로 갈린다는 규칙, 그리고 이 scope 의 조작 일반에 붙는 확인 등급 — `CONFIRM` scope 가 소유한다.
- 검색 결과에 걸리는 표시 필터의 **규범**과 검색 인덱스가 워크스페이스 경계를 넘는다는 규칙 — `WORKSPACE` scope 가 소유한다. `FR-SHELL-013` 은 무엇을 검색하고 결과를 어떤 형식으로 보이는지만 갖고 그 필터를 복제하지 않는다. 텍스트 색인의 **갱신 시점**은 어느 요구도 소유하지 않는다 — `G36` ⑤ 이며, 벡터 인덱스의 동기 갱신 규정(`STORAGE` scope)은 그 축을 덮지 않는다.
- 의미 검색(A-RAG)과 MCP 표면의 인증·인가 — `ARCH` scope 가 소유한다. `CON-SHELL-002` 는 그 표면과 좌측 검색 탭 사이의 경계만 갖고, 의미 검색이 어떻게 구현되는지는 정하지 않는다.
- 태그 집계의 원천에 걸리는 표시 필터의 **규범** — `WORKSPACE` scope 의 `SEC-WORKSPACE-004` 가 정본으로 소유하며 그 AC-4·AC-5 가 목록 미노출과 수치 미가산을 갖는다. `FR-SHELL-009` 는 집계 단위(출현 문서 수)를 소유하고 — 정본이 그 단위의 소유를 명시적으로 부인한다 — 그 필터가 이 탭에 걸린 결과를 AC-3·AC-4 로 적어 Phase 1 수용 기준 3 의 E2E 표적을 고정한다. 필터 규범 자체를 개정할 때 갱신 지점은 정본 한 곳이다.
- 휴지통 일괄 영구 삭제를 Phase 1 에 도입하지 않는다는 결정(R142) — `CONFIRM` scope 가 소유한다. 휴지통 표면에 그 진입점을 만들기 전에 그 조항을 확인하라.
- 존재가 구별되지 않는 표면에 권한 요청 버튼을 두지 않는다는 결정(R103-a) — `ACL` scope 가 소유하며 딥링크 404 표면을 함께 지배한다. 그 자리에 요청 버튼을 붙이면 버튼의 존재가 404 통일의 취지를 무너뜨린다.

## 3. Assumptions and Constraints

- 이 scope 의 규정은 인증 후 화면을 전제한다. 인증 전에는 셸 자체가 없다.
- Phase 1 은 데스크탑 전용이다 — 그 구속은 `EDITOR` scope 가 소유하며, 이 scope 는 좁은 화면에서의 모달·사이드바 거동을 정하지 않는다.
- UI 부품 선택(가상 스크롤 트리 · 모달·탭·팝오버 · 관리 테이블 패키지)은 `ARCH` scope 가 소유한다. 이 scope 의 배치 규정은 그 부품 위에서 실현된다.
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가 소유한다.
- 이 scope 에 걸린 미결 — ~~`G8`~~(2026-08-22 종결 · `R152` — 항목 셋이 전량이고 `IR-SHELL-004` 가 받았다) · ~~`G10`~~(2026-08-22 종결 · `R153` — 본인 개명 불가로 확정돼 `계정` 의 표시 이름 자리는 비워 두는 것이 아니라 **없애는 것**으로 닫혔다) · `G14`·`G14-a`(화면 최신성 규정과 태그 축·검색 결과의 갱신 계기) · `G31`(본문 `#태그` 의 렌더·클릭 수단 — `FR-SHELL-009` 가 태그 진입점을 우측 패널 하나로 줄이면서 드러났다) · `G36`(전역 검색이 남긴 값들 — 필터 팝오버의 기본값 · 결과 상한과 발췌 길이 · 첨부 이름 검색의 권한 판정 · 텍스트 색인 시점. **② 우선순위·혼용 해석은 2026-08-22 에 `R149-f` 로 닫혔고 `FR-SHELL-014` 의 차단이 풀렸다** — `FR-SHELL-013` 은 나머지 넷으로 여전히 `blocked` 다) · `G38`(한국어 질의의 일치 단위가 `R149-c` 의 최소 2자와 충돌한다 — `G36` ② 를 닫으면서 실측으로 드러났다). 등재의 정본은 `00.index.md` §9 의 `Impact` 열이며, 그 열이 바뀌면 이 목록도 함께 훑는다.

#### Requirement

좌측 사이드바 상단에 뷰 전환 탭 세 개(문서 트리 · 검색 · 즐겨찾기)를 두고, 옵시디언 좌측 사이드바의 탭 전환 구조와 배치를 따른다. 즐겨찾기의 대상에는 문서와 디렉토리 자체가 모두 포함된다.

#### Rationale

제품 초기 질의 Q1 을 닫으며 확정된 조항이다. 이 상단 탭은 "열린 문서 탭"이 아니라 사이드바 뷰 전환 탭이다 — 열린 문서의 탭은 중앙 본문 상단에 따로 있으므로 둘을 같은 것으로 읽으면 화면이 어긋난다. 즐겨찾기 대상에 디렉토리 자체를 포함시킨 것은 트리 비대화에 대한 대응이다.

#### Acceptance Criteria

- [ ] AC-1: 좌측 사이드바 상단에 `문서 트리` · `검색` · `즐겨찾기` 세 개의 뷰 전환 탭이 표시된다.
- [ ] AC-2: 뷰 전환 탭 하나를 선택하면 좌측 사이드바 본문이 그 뷰로 교체된다.
- [ ] AC-3: 문서 노드를 즐겨찾기에 추가하면 즐겨찾기 뷰 목록에 그 문서가 나타난다.
- [ ] AC-4: 디렉토리 노드를 즐겨찾기에 추가하면 즐겨찾기 뷰 목록에 그 디렉토리가 나타난다.

#### Requirement

모든 설정 화면은 별도 페이지가 아니라 모달 팝업으로 제공하며, 모달의 내부 구조는 좌측 카테고리 리스트와 우측 설정 패널의 2단이다.

#### Rationale

#### Acceptance Criteria

- [ ] AC-1: 관리 기능만을 위한 별도 관리자 화면이나 별도 라우트가 존재하지 않는다.
- [ ] AC-2: 관리 기능에 도달하는 경로는 설정 모달의 좌측 카테고리다.
- [ ] AC-3: 문서별 ACL 지정은 설정 모달이 아니라 별도의 공유 모달에서 수행한다.

앞 문장(문서 단위 기능은 헤더 메뉴에 둔다)이 생성적 규칙이므로 뒤의 열거는 규범이 아니라 현재 목록이다. 규칙과 목록을 구분하지 않으면 목록이 닫힌 열거로 오독되어, 새 문서 단위 기능이 생길 때마다 배치가 다투어지거나 조항 개정이 필요해진다. 인스턴스·워크스페이스 단위 기능이 설정 모달 하나로 모이는 것과 대칭이며, 나누는 축은 "이 조작의 대상이 문서 하나인가"다.

#### Acceptance Criteria

- [ ] AC-1: 문서 단위로 작용하는 기능의 진입점은 설정 모달이 아니라 문서 헤더 메뉴에 배치된다.
- [ ] AC-2: 문서 헤더 메뉴에서 그 문서의 공유 모달을 열 수 있다.
- [ ] AC-3: 문서 헤더 메뉴에서 그 문서의 버전 기록을 열 수 있다.

### FR-SHELL-003 — 트리 컨텍스트 메뉴와 트리 상단 새 노트 버튼

| Field | Value |

| Stability | stable |

#### Requirement

좌측 트리에 컨텍스트 메뉴와 트리 상단 `새 노트` 버튼을 둔다. 컨텍스트 메뉴 항목은 새 문서 · 새 디렉토리 · 이름 변경 · 이동 · 복사 · 삭제 · 공유 · 즐겨찾기 · 새 버전 올리기이며, 각 항목의 활성 여부는 파일 조작별 필요 권한 표를 따른다. `새 버전 올리기` 는 파일 노드 전용이고, `복사` 는 원본 `보기` 만으로 활성된다.

#### Rationale

감사 H1 을 해소한 조항이다 — 이것이 없으면 Phase 1 사용자는 업로드로만 문서를 만들 수 있다. 초판 열거에는 `복사` 와 `새 버전 올리기` 가 빠져 있었고 뒤에 추가됐다. 복사는 워크스페이스 경계를 넘는 유일한 수단이고 새 버전 올리기는 덮어쓰기의 유일한 합법 경로이므로, 진입점이 없으면 두 기능에 도달할 수 없는 상태였다. `복사` 가 `보기` 만으로 활성되는 이유는 복사가 원본을 건드리지 않는 비파괴 동작이기 때문이다 — 읽을 수 있으면 복사할 수 있다. 이동·삭제가 `편집` 을 요구하는 것과 이 지점에서 갈린다.

#### Acceptance Criteria

- [ ] AC-1: 트리 상단에 `새 노트` 버튼이 있고, 누르면 새 문서를 만들 수 있다.
- [ ] AC-2: 트리 노드에서 컨텍스트 메뉴를 열면 새 문서 · 새 디렉토리 · 이름 변경 · 이동 · 복사 · 삭제 · 공유 · 즐겨찾기 · 새 버전 올리기 항목이 나타난다.
- [ ] AC-3: 요청자가 그 조작에 필요한 권한을 갖지 않은 항목은 비활성으로 표시된다.
- [ ] AC-4: `새 버전 올리기` 항목은 파일 노드의 컨텍스트 메뉴에만 나타난다.
- [ ] AC-5: 디렉토리 노드와 pass-through 노드의 컨텍스트 메뉴에는 `새 버전 올리기` 항목이 없다.
- [ ] AC-6: `복사` 항목은 원본에 대한 `보기` 권한만 있으면 활성되며 `편집` 권한을 요구하지 않는다.

감사 M12 를 해소한 조항이다. 같은 사실이 config 파일과 DB 두 곳에 있으면 재기동 시 config 값으로 조용히 원복되어, 관리자가 화면에서 바꾼 값이 사라진다. 보관 버전 개수의 저장 소재가 미결로 표기돼 있던 것도 이 조항으로 닫혔다.

#### Acceptance Criteria

- [x] AC-1: 런타임에 변경 가능한 설정 값은 DB 에서 읽고 DB 에 쓴다.
- [x] AC-2: config 파일은 포트 · docsRoot · DB 경로 · 프록시 홉 수만 담고 런타임 변경 가능한 설정을 담지 않는다.
- [x] AC-3: 설정 모달에서 런타임 설정을 변경한 뒤 서버를 재기동해도 그 값이 유지된다.
- [x] AC-4: 부트스트랩 열거에 칸을 더하려는 값은 「DB 에 둘 수 없는 기동 값인가」를 통과해야 하며, 그렇지 않은 값은 config 에 두지 않는다.

#### Requirement

문서 딥링크(URL 라우팅)를 제공한다. URL 에는 경로가 아니라 노드 ID 를 사용하고 브라우저 뒤로·앞으로가 동작한다. 권한 없는 노드에 대한 404 통일 규칙은 `SEC-ACL-006` 이 소유하며 이 요구가 정하지 않는다.

#### Rationale

사내 메신저로 문서 링크를 공유하는 것은 사내 문서 도구의 핵심 수요다. 경로 독립 노드 ID 와 404 통일이라는 재료가 이미 갖춰져 있어 결정만 하면 되는 상태였다. 경로가 아니라 노드 ID 를 URL 에 쓰는 이유는 문서를 개명·이동해도 링크가 깨지지 않게 하기 위해서다 — 경로 기반 URL 이었다면 노드 ID 를 도입해 얻은 이점이 URL 계층에서 사라진다.

#### Acceptance Criteria

- [ ] AC-1: 문서를 열면 그 문서의 노드 ID 를 담은 URL 이 주소창에 반영된다.
- [ ] AC-2: 그 URL 로 접근한 다른 사용자에게 권한이 있으면 같은 문서가 열린다.
- [ ] AC-3: 문서를 개명하거나 이동한 뒤에도 기존 딥링크가 같은 문서를 연다.
- [ ] AC-4: 브라우저 뒤로·앞으로 버튼이 문서 이동 이력을 따라 동작한다.

### FR-SHELL-007 — 휴지통 카테고리의 표시 조건과 전 워크스페이스 통합 목록

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | verified |
| Priority | medium |
| Tags | trash, settings-modal |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md) |

#### Requirement

휴지통 카테고리는 접근 가능한 워크스페이스가 1개 이상인 사용자 전원에게 표시한다. 휴지통은 접근 가능한 전 워크스페이스의 통합 목록이며 `워크스페이스` 열과 필터를 제공한다. 열람 범위 판정과 영구 삭제 가능 여부는 행마다 그 행의 워크스페이스를 기준으로 적용하므로, 그 워크스페이스의 관리자는 전체/본인분 범위 토글을 갖고 그 밖의 사용자는 본인 삭제분으로 고정된다.

#### Rationale

삭제 권한은 `편집` 에게 열려 있는데 휴지통이 `관리` 전용 구역에 있어 편집자가 자기 문서를 지우고도 복구할 수 없는 상태였다. 표시 조건만 넓히고 데이터 범위는 기존 휴지통 규칙으로 분기시켜 그 모순을 닫았으며, 관리 기능 단일 진입점 원칙은 유지된다 — 휴지통은 여전히 설정 모달 안에 있고 구역만 개인으로 옮겼다. 통합 목록으로 만든 이유는 삭제 격리 디렉토리가 워크스페이스마다 있는데 휴지통이 개인 구역으로 이동해 워크스페이스 스코프 선택기를 쓸 수 없게 됐기 때문이다. 통합 목록 + 워크스페이스 열·필터라는 형태는 검색 탭의 범위 선택기와 같은 선례를 따른다.

#### Acceptance Criteria

- [x] AC-1: 접근 가능한 워크스페이스가 1개 이상인 사용자에게 휴지통 카테고리가 표시된다.
- [x] AC-2: 접근 가능한 워크스페이스가 하나도 없는 사용자에게는 휴지통 카테고리가 표시되지 않는다.
- [x] AC-3: 휴지통 목록은 접근 가능한 전 워크스페이스의 항목을 하나의 목록으로 보여주고 `워크스페이스` 열을 갖는다.
- [x] AC-4: `워크스페이스` 필터로 목록을 특정 워크스페이스의 항목으로 좁힐 수 있다.
- [x] AC-5: 어떤 워크스페이스에 `관리` 권한을 가진 사용자는 그 워크스페이스 항목에 대해 전체/본인분 범위 토글을 쓸 수 있다.
- [x] AC-6: `관리` 권한이 없는 워크스페이스의 항목은 요청자 본인이 삭제한 것만 목록에 나타난다.

### SEC-SHELL-002 — 이름 충돌 처리는 가시 여부와 무관하게 하나로 통일한다

| Field | Value |
| --- | --- |
| Type | security |

| Priority | medium |
| Tags | name-collision, oracle |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

이름 충돌은 대상이 요청자에게 보이든 보이지 않든 항상 같은 방식으로 처리한다 — 자동 접미사를 붙이고 동일한 안내를 표시한다. 확인 단계를 두지 않는다.

#### Rationale

개정 전에는 보이는 충돌은 거부하고 대안을 제안했고, 보이지 않는 충돌은 조용히 자동 리네임했다. 흐름의 차이 자체가 "거기에 무언가 있다"를 알려주는 존재 오라클이었다 — 완전 숨김 원칙 아래에서는 두 경로가 관측상 구별되지 않아야 한다. 확인 단계를 없앤 것도 같은 이유다: 확인이 뜨는지 안 뜨는지가 그대로 오라클이 된다.

#### Acceptance Criteria

- [ ] AC-1: 요청자에게 보이는 파일과 이름이 충돌하면 자동 접미사가 붙은 이름으로 생성된다.
- [ ] AC-2: 요청자에게 보이지 않는 파일과 이름이 충돌해도 자동 접미사가 붙은 이름으로 생성된다.
- [ ] AC-3: 두 경우의 안내 문구가 동일하다.
- [ ] AC-4: 이름 충돌 시 사용자에게 확인을 묻는 단계가 없다.

### FR-SHELL-008 — 덮어쓰기의 유일한 경로는 파일 노드 전용 새 버전 올리기다

| Field | Value |
| --- | --- |
| Type | functional |

| Risk | medium |
| Stability | stable |

| GitHub Issue | - |
| Related Docs | [셸 화면 설계](./03.screen-design-shell.md) |

#### Requirement

기존 파일 덮어쓰기는 "기존 파일을 선택해 새 버전 올리기"라는 별도 경로로만 제공한다. 그 진입점은 트리 컨텍스트 메뉴의 파일 노드 전용 항목 `새 버전 올리기…` 이며 디렉토리·pass-through 노드에는 나타나지 않는다. 필요 권한은 대상 파일 `편집` 이다.

#### Rationale

덮어쓰기 경로를 이 하나로 좁히면 존재 오라클이 생기지 않는다 — 이 경로는 요청자에게 보이는 파일에만 존재하므로 "덮어쓸 수 있는가"라는 물음이 보이지 않는 파일에 대해 제기되지 않는다. 이름 충돌을 항상 자동 접미사로 통일한 결정과 짝을 이루며, 둘을 합치면 덮어쓰기 의도는 명시적 경로로만 표현된다. 진입점을 문서 헤더 메뉴가 아니라 트리 컨텍스트 메뉴에 둔 이유는 Phase 1 헤더 메뉴가 공유·버전 기록 둘로 한정되어 자리가 없기 때문이다. md 와 바이너리를 다르게 다루는 것은 md 만 버전 보관 대상이어서 되돌릴 수 있고 바이너리는 그렇지 않기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 업로드·생성 흐름에는 기존 파일을 덮어쓰는 선택지가 없다.
- [ ] AC-2: 파일 노드의 컨텍스트 메뉴에서 `새 버전 올리기…` 를 실행해 그 파일을 덮어쓸 수 있다.
- [ ] AC-3: 대상 파일에 `편집` 권한이 없으면 `새 버전 올리기…` 를 실행할 수 없다.
- [ ] AC-4: md 문서에 새 버전을 올리면 이전 본문이 버전으로 보관된다.
- [ ] AC-5: 바이너리 파일에 새 버전을 올리면 복구할 수 없다는 경고를 표시한다.

#### Requirement

디렉토리를 복사할 때는 요청자에게 보이는 노드만 복사하고 누락된 노드가 있다는 사실을 알리지 않는다. 복사 다이얼로그에는 숨은 노드의 유무와 무관하게 항상 동일한 문구를 표시한다. 복사가 끝나면 복사된 항목 수를 토스트로 알린다.

#### Rationale

UX 패널 4:0. 남은 두 선택지가 모두 깨진다 — 전부 복사하면 복사본이 대상 부모에서 상속해 권한 상승이 되고, 숨은 노드가 있다고 거부하면 그 거부 자체가 존재 오라클이 된다. 보이는 것만 복사하는 쪽이 성립하는 이유는 복사가 원본을 건드리지 않는 비파괴 동작이기 때문이다. 안내 문구를 조건 없이 항상 같게 두는 이유는 조건부 표시가 그 자체로 오라클이기 때문이다. 복사된 항목 수를 알리는 것은 노출이 되지 않는다 — 복사된 것은 언제나 요청자가 이미 보던 것뿐이라 새로 알려주는 사실이 없고, 대량 이관 시 사후 대조점이 된다.

#### Acceptance Criteria

- [ ] AC-1: 요청자가 볼 수 없는 하위 노드는 복사 결과에 포함되지 않는다.
- [ ] AC-2: 복사 결과에 누락된 노드가 있어도 그 사실을 알리는 표시가 나타나지 않는다.
- [ ] AC-3: 복사 다이얼로그는 숨은 노드의 유무와 관계없이 "권한에 따라 일부 항목이 제외될 수 있습니다"라는 동일한 문구를 표시한다.
- [ ] AC-4: 복사가 끝나면 복사된 항목 수를 담은 토스트가 표시된다.

### FR-SHELL-009 — 태그 탭은 전 워크스페이스 태그를 출현 문서 수로 집계한다

#### Requirement

우측 사이드바 `태그` 탭은 접근 가능한 전 워크스페이스의 태그 목록과 각 태그의 출현 문서 수를 보여주며 범위 선택기를 제공한다. 집계 원천에 요청자의 유효 권한 필터를 적용한다 — 개수만 거르는 것이 아니라 태그의 등장 자체가 필터를 거치므로, 요청자가 볼 수 있는 문서에 한 번도 나타나지 않는 태그는 목록에 없다. 개수의 단위는 `출현 문서 수` 이며 `출현 횟수` 가 아니다. 개수 옆에는 조건 없이 항상 같은 기준 문구를 상시 표기한다.

#### Rationale

심의 3인 만장일치. 초판 규정은 "현재 열린 문서의 태그"였고 UX 패널 3:1 로 통과했으나, 2026-08-18 옵시디언 실측 앞에서 그 다수 의견의 근거 두 개가 모두 무너져 전복됐다. 뒤집기의 근거는 셋이다 — ① 우측 사이드바 조항의 문면이 "옵시디언과 동일 위치·구조"를 요구하고, 그 탭 묶음이 옵시디언 우측 세트의 전사임이 실측으로 확인됐다 ② 그 조항 근거 칸의 "권한 필터 적용"이 초판 아래에서 무대상이었다 — 현재 문서의 태그는 이미 볼 수 있는 문서의 것이라 걸러질 대상이 원리적으로 0 이며, 조항이 자기 화면에 대해 공허해지는 것은 그 조항이 다른 화면을 상정했다는 흔적이다 ③ 태그 어휘를 열거하는 자리가 Phase 1 제품 전체에 없어, 태그 탐색의 유일한 시작점이 "이미 열어 둔 문서에 그 태그가 달려 있는 경우"라 태그 체계가 자기 자신을 통해서만 발견되는 닫힌 고리였다. **전복의 근거로 "옵시디언과 동일한 UI"라는 제품 정의를 인용하지 않았다** — 심의 3인이 각자 그 동형 요구는 `에디터와 렌더링 결과` 둘로 한정되어 사이드바 패널의 내용 범위에 미치지 않는다고 판정했다. 개수의 단위를 `출현 문서 수` 로 정하고 옵시디언 문구(`number of occurrences`)를 그대로 옮기지 않은 것은 의도적이다 — 권한 필터가 문서 단위로 걸리므로 출현 횟수는 이 필터 위에서 정의되지 않는다. 개수 옆 문구를 조건 없이 상시 표기하는 것은 조건부 표시가 그 자체로 오라클이기 때문이며, 개수가 사람마다 달라지는 것은 권한 필터의 정상 동작이지 결함이 아니다. 범위 선택기의 선례는 휴지통 통합 목록과 검색 탭이다.

#### Acceptance Criteria

- [ ] AC-1: `태그` 탭은 접근 가능한 전 워크스페이스의 태그를 하나의 목록으로 보여준다.
- [ ] AC-2: 범위 선택기로 목록을 특정 워크스페이스로 좁힐 수 있다.
- [ ] AC-3: 요청자가 볼 수 있는 문서에 한 번도 나타나지 않는 태그는 목록에 나타나지 않는다.
- [ ] AC-4: 각 태그 옆의 수치는 그 태그가 달린 문서 중 요청자가 볼 수 있는 문서의 개수다.
- [ ] AC-5: 한 문서에 같은 태그가 여러 번 나타나도 그 문서는 수치에 1 로 계산된다.
- [ ] AC-6: 개수 옆의 기준 문구는 숨은 항목의 유무와 관계없이 항상 같은 문구로 표시된다.

#### Research / Analysis

- 옵시디언 1.8.9 설치본의 `app.js` · `app.css` · `i18n/en.json` 과 실제 볼트 설정을 원자료로 직접 읽어 실측했고, 독립 검증자가 10개 주장 전건을 원자료에서 재현했다. 확인된 사실 둘 — **위치는 우측**이다(패널 초기화가 `right` 를 기본값으로 쓰고 모바일에서만 `left` 로 바뀌며, 기본 활성 상태다). **범위는 전역**이다(en.json 의 설명 문구가 *"Displays all your tags along with their number of occurrences"* 이고, 구현이 메타데이터 캐시의 태그 조회로 파일 캐시 전체를 순회하며 활성 파일 필터가 없다. 초기 정렬값은 `frequency` 다). 즉 위치는 초판과 일치했고 범위는 불일치했다.

#### Implementation Notes

- ① **집계 원천에 필터를 적용해야 한다.** 전체를 집계한 뒤 개수만 깎으면, 요청자가 볼 수 없는 문서에만 있는 태그가 0 건으로 목록에 남아 그 태그의 존재가 드러난다. 목록에서 태그 자체가 빠져야 한다. ② 본문의 `#태그` 가 어떻게 렌더되고 클릭 가능한지가 어느 조항에도 없다(`G31`) — 라이브 프리뷰 대상 정본 목록에 태그가 없어 의도적 배제인지 누락인지 먼저 판정해야 한다. 이 탭의 집계 자체는 그 판정과 독립으로 성립하지만, 태그 진입점이 이 패널 하나로 줄어드는 상태가 그 공백의 증상이다. ③ 이 탭의 갱신 계기는 같은 사이드바의 백링크·아웃고잉과 다르다 — 그 둘은 활성 문서를 추종하고 이 탭은 문서와 독립인 전역 색인이다(`G14-a`). ④ 검증 방법이 `Playwright E2E` 이고 우선순위가 `high` 인 근거는 Phase 1 수용 기준 3 이다 — 그 기준이 권한 필터 표면 전부를 시험하되 표면 목록을 필터 정본 조항에 위임하고, 그 조항의 열거가 이 태그 집계를 명시적으로 지목하며, 기준 문면이 *"집계형 표면은 목록 미노출과 수치 미가산을 각각 단언한다"* 로 이 요구의 AC-3·AC-4 를 직접 겨냥한다.
- [2026-08-19] ⑤ AC-3·AC-4 는 `SEC-WORKSPACE-004` AC-4·AC-5 와 문면이 겹치지만 삭제하지 않는다 — 이 요구가 소유하는 것은 R106 이 정한 집계 단위(출현 문서 수)이고 정본은 그 단위의 소유를 명시적으로 부인한다. 필터 규범 자체를 개정할 때 갱신 지점은 정본 한 곳이며, 이 두 AC 는 그 필터가 이 탭에 걸린 결과를 Phase 1 수용 기준 3 의 E2E 표적으로 고정하는 자리다.

#### Requirement

우측 `태그` 탭에서 태그를 클릭하면 좌측 사이드바의 검색 탭이 활성되고 그 태그가 질의로 채워진다. 우측은 색인(어떤 태그가 얼마나 있는가)을 소유하고 좌측 검색 탭은 결과(그 태그가 달린 문서는 무엇인가)를 소유한다.

#### Rationale

2026-08-18 개정으로 규범의 실질은 유지되고 문면 둘이 고쳐졌다. ① 초판의 "흡수"는 "우측에 그 수요를 받을 것이 없다"는 초판 전제의 어휘였고, 이제는 역할 분담이다. ② 초판 근거였던 "탐색 축은 좌측이 소유한다"는 좌측 사이드바 조항 문면에 없는 일반화였다(심의 2인이 독립으로 지적) — 그 조항의 규범은 좌측 3탭의 구조·배치일 뿐이다. 좌측 3탭 구조는 이 동선으로 깨지지 않는다 — 결과 목록은 여전히 좌측 하나이고 우측은 질의어를 건넬 뿐이며, 옵시디언도 좌측에 파일 탐색기·검색·북마크를 두고 우측에 태그를 둔다. 태그 탭이 전역 집계로 개정된 뒤 이 동선은 오히려 더 하중을 받는다 — 이것이 없으면 우측 패널이 자체 결과 목록을 길러 결과 표면이 두 벌이 된다.

#### Acceptance Criteria

- [ ] AC-1: 우측 `태그` 탭에서 태그를 클릭하면 좌측 사이드바가 검색 탭으로 전환된다.
- [ ] AC-2: 전환된 검색 탭의 질의 입력에 클릭한 태그가 채워진다.
- [ ] AC-3: 우측 `태그` 탭은 자체 문서 결과 목록을 갖지 않는다.

#### Requirement

우측 `태그` 탭의 목록은 이름순으로 정렬한다. 비교 규칙은 자연 정렬(숫자 인식) · 대소문자와 악센트 무시 · 로케일 `ko` 고정이며, 그 비교 함수는 공용 한 자리에 둔다.

#### Rationale

초판은 옵시디언 실측(초기 정렬값 `frequency`) 하나를 근거로 빈도순을 기본으로 두었고, 원장이 그 조항에 〔판단 — 원장 근거 없음〕 을 스스로 달아 두었다. `R159` 가 이름순으로 뒤집었다. 비교 규칙의 세부는 1.0 파일 트리 정렬의 실측에서 왔다 — 1.0 에는 태그 패널이 존재하지 않으므로 따를 대상이 그것뿐이었다. 로케일을 `ko` 로 고정하는 것만이 1.0 을 그대로 베끼지 않는 지점이며, 1.0 은 로케일을 넘기지 않아 서버 호스트에 따라 한글과 영문의 선후가 뒤집힌다.

#### Acceptance Criteria

- [ ] AC-1: `태그` 탭을 처음 열면 목록이 이름순으로 정렬되어 있다.
- [ ] AC-2: 이름순 비교는 숫자를 인식해 `2` 가 `10` 보다 앞에 온다.
- [ ] AC-3: 이름순 비교는 대소문자와 악센트를 무시한다.
- [ ] AC-4: 이름순 비교의 로케일은 `ko` 로 고정되어 서버 호스트 로케일이 달라도 한글과 영문의 선후가 바뀌지 않는다.
- [ ] AC-5: 비교 함수는 공용 한 자리에 있으며 목록마다 자체 비교식을 두지 않는다.

좌측 트리에서 문서를 클릭하면 활성 탭을 그 문서로 교체하고, `Ctrl`+클릭은 새 탭으로 연다. 다만 충돌로 자동 저장이 중단된 탭과 저장이 거부된 탭은 자동 교체 대상에서 제외하고 사용자 확인을 요구한다.

#### Acceptance Criteria

- [ ] AC-1: 좌측 트리에서 문서를 클릭하면 새 탭이 생기지 않고 활성 탭의 내용이 그 문서로 바뀐다.
- [ ] AC-2: 좌측 트리에서 `Ctrl`+클릭하면 새 탭이 생기고 그 문서가 열린다.
- [ ] AC-3: 활성 탭이 충돌로 자동 저장 중단 상태이면 트리 클릭이 그 탭을 즉시 교체하지 않고 확인을 요구한다.

#### Requirement

문서 탭 스트립과 문서 헤더를 하나로 합치지 않고 2단으로 분리한다.

#### Rationale

UX 패널 3:1. 탭 스트립은 문서 *간* 이동이고 헤더는 문서 *내* 상태·조작이라 계층이 다르다. 통합하면 두 가지가 깨진다 — ① 탭이 늘 때 브레드크럼과 저장 상태 표시가 먼저 잘린다 ② 헤더 `⋯` 의 공유·버전 조작이 "어느 문서에 대한 것인가"를 흔들어 엉뚱한 문서를 공유하는 경로가 생긴다. 두 번째가 결정적이다 — 되돌릴 수 없는 권한 사고의 경로이기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 문서 탭 스트립과 문서 헤더가 서로 다른 행에 표시된다.
- [ ] AC-2: 문서 헤더에 그 문서의 브레드크럼과 저장 상태가 표시된다.
- [ ] AC-3: 탭이 늘어나도 문서 헤더의 브레드크럼과 저장 상태가 탭 스트립에 밀려 잘리지 않는다.
- [ ] AC-4: 문서 헤더의 `⋯` 메뉴는 현재 활성 문서를 대상으로 동작한다.

### FR-SHELL-013 — 전역 검색의 대상 넷과 소재, 필터 팝오버, 결과 표시 형식

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | implemented |
| Priority | high |
| Tags | search, global-search, left-sidebar |
| Risk | medium |
| Stability | evolving |
| Verification Method | Playwright E2E |
| GitHub Issue | - |
| Related Docs | [셸 화면 설계](./03.screen-design-shell.md) |

#### Requirement

전역 검색의 대상은 문서 제목 · 본문 · 태그 · 첨부파일 이름 넷이다. 검색의 소재는 좌측 사이드바의 검색 탭이며 결과도 그 탭이 소유한다. 검색창 오른쪽의 필터 버튼이 여는 팝오버에서 체크박스로 네 대상 각각의 포함 여부를 정한다. 결과는 문서 제목을 머리로 두고 그 아래에 일치 지점의 발췌를 쌓는 형식으로 표시하며, 목록은 스크롤한다.

#### Rationale

원장이 검색 조항 없이 검색의 주변만 정하고 있던 요구 공백을 메운 조항이다 — 좌측에 검색 탭을 두는 조항, 결과를 요청자 권한으로 거르는 조항, 태그 클릭이 질의를 채우는 조항, 인덱스가 워크스페이스 경계를 넘는 조항이 모두 "검색이 이미 있다" 를 전제하고 주변만 정했고 무엇을 검색하는지 정한 조항이 없었다. 원장 §4 Phase 1 수용 기준 3 이 권한 필터의 표면 중 하나로 검색 결과를 지목하므로 이 요구 없이는 Phase 1 종료를 판정할 수 없다. 결과 소재를 좌측으로 확정한 근거는 원장 R106-a 와 1.0 실측 화면이다.

#### Acceptance Criteria

- [x] AC-1: 좌측 사이드바 검색 탭에서 질의를 입력하면 결과가 그 탭 안에 표시되며, 결과 목록을 소유하는 다른 표면이 존재하지 않는다.
- [x] AC-2: 이름에서만 일치하는 노드, 본문에서만 일치하는 문서, 태그에서만 일치하는 문서, 첨부파일 이름에서만 일치하는 문서가 각각 검색 결과에 나타난다.
- [x] AC-3: `이름` 축은 md 문서뿐 아니라 트리에 서는 비-md 노드의 이름도 덮는다.
- [x] AC-4: PDF 노드는 본문 축으로도 검색되며, 그 본문의 색인 항목에는 페이지 번호가 함께 실린다.
- [x] AC-5: 검색창 오른쪽 필터 버튼을 누르면 팝오버가 열리고, 네 대상(이름·본문·태그·첨부 이름) 각각에 대한 체크박스가 표시된다.
- [x] AC-6: 필터를 처음 열면 `이름` 만 켜져 있고 나머지 셋은 꺼져 있다.
- [x] AC-7: 마지막으로 고른 조합이 다음 방문에 되살아나며, 그 값이 없거나 깨졌으면 기본값으로 돌아간다.
- [x] AC-8: 필터 팝오버에서 어떤 대상의 체크를 해제하면 그 대상에서만 일치하는 문서가 결과에 나타나지 않는다.
- [x] AC-9: 결과는 문서 제목 머리행 아래에 그 문서에서 찾은 일치 지점의 발췌를 쌓는 형식으로 표시된다.
- [x] AC-10: 한 문서에서 일치 지점이 여럿이면 그 문서의 제목 머리행은 하나이고 발췌가 그 아래에 여러 줄로 쌓인다.
- [x] AC-11: 결과 건수를 표시할 때 거르기 전 개수나 분모를 함께 보이지 않는다.
- [x] AC-12: 결과 목록이 표시 영역을 넘으면 목록이 스크롤된다.

### FR-SHELL-014 — 검색 질의 문법은 공백이 AND 이고 파이프가 OR 이며 최소 질의 길이는 2자다

| Field | Value |

| Status | implemented |
| Priority | medium |
| Tags | search, query-syntax, global-search |
| Risk | medium |
| Stability | evolving |
| Verification Method | 단위 테스트 |
| GitHub Issue | - |

#### Requirement

검색 질의에서 낱말 사이의 공백은 AND 로 해석한다. 다만 검색어 사이에 `|` 가 있으면 그 자리는 OR 로 해석한다. 최소 질의 길이는 2자다 — AND 는 2자 이상인 항이 하나라도 있으면 나머지 항이 1자여도 수용하고, OR 는 모든 항이 2자 이상이어야 수용한다.

#### Rationale

비대칭의 근거는 비용이다 — AND 는 2자 이상인 항이 색인을 먼저 좁히지만 OR 는 각 항이 독립으로 전수를 훑으므로 1자를 허용하면 결과가 폭발한다. 주체 검색의 최소 질의 길이 2자와 값은 같으나 다른 조항이다 — 그쪽은 공용 주체 선택 컴포넌트가 소유하고 결과 상한 20건이 함께 붙는다. 이 요구에는 상한이 붙지 않는다(그 값은 미결이다).

#### Acceptance Criteria

- [x] AC-1: 공백으로 나뉜 두 낱말 질의는 두 낱말이 모두 일치하는 문서만 돌려준다.
- [x] AC-2: 두 낱말 사이에 파이프 문자를 둔 질의는 어느 한 낱말이라도 일치하는 문서를 돌려준다.
- [x] AC-3: 항이 하나뿐인 질의는 그 항이 2자 이상일 때만 수용된다.
- [x] AC-4: AND 질의는 2자 이상인 항이 하나라도 있으면 1자인 항을 함께 담아도 수용된다.
- [x] AC-5: 모든 항이 1자인 AND 질의는 수용되지 않는다.
- [x] AC-6: OR 질의는 항 하나라도 1자이면 수용되지 않는다.
- [x] AC-7: 혼용 질의는 AND 가 파이프보다 강하게 묶인 것으로 해석된다 — 두 낱말을 공백으로 잇고 그 뒤에 파이프와 셋째 낱말을 둔 질의는, 앞 두 낱말을 모두 가진 문서와 셋째 낱말을 가진 문서를 돌려주고 첫 낱말만 가진 문서는 돌려주지 않는다.
- [x] AC-8: 혼용 질의의 최소 길이는 파이프로 나뉜 묶음마다 독립으로 판정된다 — 묶음마다 2자 이상인 항이 하나라도 있어야 수용된다.
- [x] AC-9: 괄호는 연산자가 아니다 — 괄호가 든 질의는 그 괄호를 포함한 문자열로 찾는다.

#### Requirement

AI 검색은 MCP 표면으로만 제공한다. 좌측 사이드바의 검색 탭은 텍스트 검색이며 여기에 AI·벡터 검색을 섞지 않는다. 이 제약이 좌측 검색 탭의 범위를 텍스트로 한정한다.

#### Rationale

둘은 다른 기능이다 — 텍스트 검색은 글자를 찾고 AI 검색은 뜻이 가까운 것을 찾는다. 원장은 1.0 의 AI·벡터검색을 물려받는 조항과 MCP 결과를 요청자 ACL 로 거르는 조항을 각각 두었는데, 좌측 검색 탭이 그 둘과 갈라지는 자리가 못박혀 있지 않았다. 못박지 않으면 좌측 탭의 범위가 열려 구현자가 임의로 AI 를 얹게 되고, 한 표면에서 텍스트 검색의 필터와 벡터검색의 필터가 만나 어느 규범이 걸리는지가 갈린다.

#### Acceptance Criteria

- [x] AC-1: 좌측 검색 탭의 질의는 텍스트 검색 경로로만 처리되며 벡터·의미 검색 경로를 호출하지 않는다.
- [x] AC-2: 좌측 검색 탭에 AI 검색으로 전환하는 토글·버튼·모드가 존재하지 않는다.
- [x] AC-3: 의미 검색 도구는 MCP 표면에서만 호출할 수 있다.

#### Requirement

개인 설정은 (사용자, 항목) 쌍을 키로 하는 DB 행에 저장한다. 인스턴스 설정 저장소와 같은 표를 쓰지 않으며, 브라우저 로컬 저장소를 정본으로 쓰지 않는다. 쓴 적 없는 항목은 그 설정의 기본값으로 읽힌다.

#### Rationale

`DR-SHELL-001` 이 런타임 설정의 단일 저장소를 DB 로 정했으나 그 열거는 인스턴스 설정 다섯뿐이고, 개인 설정의 소재는 어느 조항도 정하지 않았다. 인스턴스 설정 표는 전역 평면 맵이라 거기에 개인 키를 얹으면 전 사용자가 한 값을 공유한다. 브라우저 로컬만 두면 같은 사람이 기기마다 다른 값을 갖고, 그것이 `R96` 이 막으려던 「같은 사실이 두 곳」 형태를 재현한다. 테마처럼 첫 페인트 전에 필요한 값은 클라이언트가 캐시할 수 있으나 그 캐시는 정본이 아니다 — 정본이 둘이 되면 어긋난 뒤 어느 쪽이 옳은지 판정할 수단이 없다.

#### Acceptance Criteria

- [ ] AC-1: 개인 설정을 쓰면 DB 에 들어가고 같은 사용자로 읽으면 그 값이 나온다.
- [ ] AC-2: 한 사용자가 바꾼 값이 다른 사용자의 읽기에 나타나지 않는다.
- [ ] AC-3: 쓴 적 없는 항목은 그 설정의 기본값으로 읽힌다.
- [ ] AC-4: DB 를 닫았다 다시 열어도 개인 설정이 남는다.
- [ ] AC-5: 인스턴스 설정 저장소와 개인 설정 저장소가 서로의 값을 읽거나 덮어쓰지 않는다.
- [ ] AC-6: 열거에 없는 개인 설정 키는 쓸 수 없다.

#### Requirement

사용자는 트리의 한 노드에서 새 문서와 새 디렉토리를 만들 수 있다. 새 노드가 서는 자리는 고른 노드가 담긴 자리이며, 그 자리는 메뉴 항목의 활성 판정이 보는 자리와 같다. 이름이 겹치면 서버가 접미사를 붙이고 그 사실을 사용자에게 알린다.

#### Rationale

`FR-SHELL-003` 은 진입점의 존부와 노출만 소유하고 각 항목의 조작은 각자의 요구가 소유한다고 위임했는데, 그 Implementation Notes ④ 가 2026-08-29 에 「그 위임에 받는 쪽이 없다」고 적고 「생성 조작을 소유하는 요구가 나중에 서면 이 문단과 함께 다시 판정하라」고 지시했다. `IR-SHELL-005` 가 그 구멍의 절반을, `FR-SHELL-015` 가 나머지 절반 중 이름 변경·이동·복사를 받았고, 남은 것이 생성이다. 그래서 트리 컨텍스트 메뉴 아홉 항목 중 `새 문서` 와 `새 디렉토리` 둘만 아직 아무 일도 하지 않는다. 화면에서 자리를 골라 만들 수 없으면 사용자가 문서를 놓을 수 있는 자리는 첫 워크스페이스의 루트 하나뿐이다.

#### Acceptance Criteria

- [x] AC-1: 파일 노드에서 `새 문서` 를 고르면 그 파일이 담긴 자리에 문서가 서고, 디렉토리 노드에서 고르면 그 디렉토리 아래에 선다 — 메뉴 항목의 활성 판정도 같은 자리의 권한을 보아야 한다. 두 곳이 갈리면 열려 보이던 항목이 서버에서 거절된다.
- [x] AC-2: `새 디렉토리` 도 같은 자리 규칙을 따르며, 만든 디렉토리 아래에 다시 문서를 만들 수 있다.
- [x] AC-3: 두 항목을 고르면 **트리 안 담길 자리 아래에** 이름을 정하는 줄이 서고 기본 이름이 골라진 채 초점을 받는다. `Enter` 가 확정이고 `Esc` 가 취소이며, 그만두면 아무것도 서버로 나가지 않는다.
- [x] AC-4: 이름 규칙은 화면이 판정하지 않는다 — 금지 문자와 길이 상한과 이름 충돌은 서버가 소유하며, 화면이 막는 것은 입력이 비어 있는 경우 하나뿐이다.
- [x] AC-5: 만든 노드가 트리에 나타난다 — 화면이 지어 넣지 않고 서버가 준 것을 다시 받아 그린다.
- [x] AC-6: 이름이 겹쳐 서버가 접미사를 붙이면 그 사실이 사용자에게 안내된다 — 알리지 않으면 사용자가 자기 문서를 찾지 못한다.
- [x] AC-7: 트리 상단 `새 노트` 버튼과 이 조작이 **같은 함수**를 지난다. 다만 그 버튼은 이름을 묻지 않고 곧바로 만든다 — 곧바로 쓰기 시작하는 자리이기 때문이며, 그 차이는 자리와 이름을 인자로 받는 한 함수의 두 호출로 표현된다.

#### Implementation Notes

- 담을 자리를 고르는 규칙은 `tree-contract.ts` 가 소유한다 — `destinationsFor` 와 같은 자리다. 화면 부품 안에 두면 같은 메뉴를 다른 자리에서 그릴 때 규칙이 갈린다.
- 활성 판정과 결과가 같은 자리를 가리켜야 한다. `enabledMenuItems` 가 `parent: edit` 으로 **부모**의 권한을 보므로, 파일 노드에서 고른 만들기는 그 파일의 부모에 만들어야 한다. 노드 자신 아래에 만들려 하면 파일 아래에 노드를 두는 셈이 되고, 열려 보이던 항목이 서버에서 거절된다.
- 트리 상단 `새 노트` 버튼과 이 조작은 한 함수를 쓴다. 그 버튼은 이 요구가 서기 전부터 있었고 자리를 고를 수 없다는 점만 다르다 — 자리를 인자로 받으면 두 진입점이 같은 함수의 두 호출이 된다.
- 이 요구가 닫히면 `IR-SHELL-005` 의 명시 목록에서 `new-file` 과 `new-directory` 두 줄이 지워진다. 그 두 줄이 지워지는 것이 이 요구의 완료 신호다.
