## 1. Scope Overview

이 scope 는 파괴적이거나 되돌리기 어려운 조작 앞에 놓이는 **마찰**을 규정한다 — 무엇을 확인 없이 실행하고, 무엇에 다이얼로그를 세우고, 무엇에 타이핑을 요구하는가. 등급 체계(L1·L2·L3), 등급을 배정하는 기준, 조작별 배정, 확인 화면이 보여주는 수치의 규칙, 그리고 확인 흐름이 완전 숨김을 우회하는 정보 통로가 되지 않도록 막는 제약이 여기 모인다.

조작 **자체**는 이 scope 가 정의하지 않는다. `ACL`·`STORAGE`·`PRINCIPAL`·`WORKSPACE` scope 가 각자 자기 조작을 정의하고, 이 scope 는 그 위에 등급만 얹는다. 등급이 한 곳에 모여 있는 이유는 배정 기준이 조작마다 다시 발명되면 같은 파괴력의 조작이 화면마다 다른 마찰을 갖게 되기 때문이다.

## 2. Scope Boundaries

### In Scope

- 등급 체계 — L1·L2·L3 세 단계로의 통일과 각 단계의 형태 (`FR-CONFIRM-001`)
- 배정 기준과 그 우선순위 — 가역성과 효과의 즉시성, 요구사항의 직접 지정이 기준보다 앞선다는 규칙 (`FR-CONFIRM-002`·`FR-CONFIRM-003`)
- 확인 화면의 규칙 — 열 때의 수치 재조회와 불일치 시 실행 잠금, 조작 입력 폼은 확인 관문이 아니라는 판정, 지연 효과 조작의 문구 (`FR-CONFIRM-004`·`FR-CONFIRM-005`·`FR-CONFIRM-008`)
- 확인 흐름이 정보를 새게 하지 않도록 하는 제약 — 보이지 않는 대상의 존재 판정에 쓰지 않기, 분모와 미도달 건수 미표시, 도달하지 못하는 하위가 있어도 거부·열거하지 않기, 상속 끊김 고지의 무조건 표시, 컨테이너 회수의 첨부 영향을 고정 문구로 (`SEC-CONFIRM-001`·`SEC-CONFIRM-003`·`SEC-CONFIRM-005`·`SEC-CONFIRM-004`·`SEC-CONFIRM-006`)
- 접근자 인원 수에 시점을 표기하지 않는 표기 규칙 (`IR-CONFIRM-001`)
- 조작별 등급 배정 — 휴지통·계정·그룹·토큰·권한 항목 배정표, 보존 기간 축소, 오프보딩 그룹 멤버십 제거, 새 버전 올리기, 넓히기의 두 축, 상속 끊기, 이동, 복사, 컨테이너 권한 항목 회수, 부모 권한 가져오기, 워크스페이스 생성·설치 시점의 부여 (`FR-CONFIRM-006`·`FR-CONFIRM-007`·`FR-CONFIRM-009`~`FR-CONFIRM-019`·`SEC-CONFIRM-002`·`SEC-CONFIRM-007`)
- 컨테이너 부여 확인의 적용 하위 노드 수 표시와 상속 고지의 단일 템플릿 (`FR-CONFIRM-012`·`FR-CONFIRM-013`)
- 넓히기 L1 토스트의 버튼을 실행취소가 아니라 회수로 표기하는 예외 (`FR-CONFIRM-014`)
- 다건·일괄의 확인 — 주체 다건 일괄 회수의 허용, 묶음 1회 확인, L3 토큰이 영향 건수이고 0건은 실행을 막는다는 규칙, 오프보딩 앞 세 단계를 다건화하지 않는다는 결정 (`FR-CONFIRM-020`~`FR-CONFIRM-023`)
- 휴지통 일괄 영구 삭제를 Phase 1 에 도입하지 않는다는 결정과, 그 배정을 「미도입 · 도입 시 발효」로 조건부 보존한다는 처분 (`CON-CONFIRM-001`)
- 부모 권한 가져오기로 만들어진 권한 항목의 부여자를 실행자로 기록한다는 저장 규칙 (`DR-CONFIRM-001`)

### Out of Scope

- 등급이 적용되는 조작 **자체**의 정의 — 부여·회수·이동·복사·상속 끊기의 정의와 필요 권한, 그리고 권한 항목의 스키마는 `ACL` scope 가 소유한다. 이 scope 는 등급만 정한다 (`FR-CONFIRM-011`·`DR-CONFIRM-001` Implementation Notes).
- 휴지통의 보존 기간 기본값, 영구 삭제의 필요 권한, 경과분의 자동 영구 삭제 — `STORAGE` scope 가 소유한다. `FR-CONFIRM-007` 은 보존 기간 *축소 조작*의 확인 절차만 정하고 기본값을 정하지 않는다 (`FR-CONFIRM-007` Implementation Notes).
- 감사 로그의 보존 기간 기본값 — `AUDIT` scope 가 소유한다.
- 오프보딩 단계의 정의 — `PRINCIPAL` scope 가 소유하며, 2단계가 1단계의 자동 결과라는 사실도 그쪽이 갖는다. `FR-CONFIRM-009`·`FR-CONFIRM-023` 은 그 단계들에 붙는 등급과 다건화 여부만 정한다 (`FR-CONFIRM-023` Trace Links).
- 설치 마법사 자체의 토큰·차단 규칙 — `AUTH` scope 가 소유한다. `FR-CONFIRM-019` 는 그 경로에서 이뤄지는 부여의 확인만 정한다 (`FR-CONFIRM-019` Implementation Notes).
- 워크스페이스 생성 폼 자체, 그리고 그 폼 안의 관리자 지정과 `default` 그룹 초기 권한 — `WORKSPACE`·`PRINCIPAL` scope 가 소유한다. `FR-CONFIRM-005`·`FR-CONFIRM-019` 는 생성 버튼이 확인 관문이 아니라는 것과 생성 시점 부여가 확인 1개를 받는다는 것만 정한다.
- 새 버전 올리기의 진입점과 버전 생성의 단위·보관 상한 — `SHELL`·`STORAGE` scope 가 소유한다. `FR-CONFIRM-010` 은 대상 파일 형식으로 등급이 갈린다는 규칙만 갖는다.
- 첨부의 저장 구조와 소유 판정 — `ATTACH` scope 가 소유한다. `SEC-CONFIRM-006` 은 회수 다이얼로그에 그 개수를 표시하지 않는다는 규칙만 갖는다.
- 접근자 지표 두 종류의 정의와 명단·수치의 권한 차등 — `ACL` scope 가 소유한다. `IR-CONFIRM-001` 은 그 수치에 시점을 붙이지 않는다는 표기 규칙만 갖는다 (`IR-CONFIRM-001` Implementation Notes).
- 휴지통 통합 목록 화면과 행마다 권한이 갈리는 표시 — `SHELL` scope 가 소유한다. `SEC-CONFIRM-001` 은 그 목록의 일괄 선택이 존재 오라클이 되지 않아야 한다는 제약만 건다 (`SEC-CONFIRM-001` Implementation Notes).
- 확인을 거친 조작이 감사 로그에 남는 형식과 다건의 감사 입도 — `AUDIT` scope 가 소유한다.
- 넓히기의 결과를 편집 레벨 사용자가 사후에 관측할 수단 — 제품에 없다. 시뮬레이션·상속 끊김 목록·접근자 명단이 모두 관리 전용이고 권한 요청 워크플로가 Phase 2 라 에스컬레이션 경로도 없다. 열린 공백 `G16` 이며 아직 어느 scope 도 소유하지 않는다 (`SEC-CONFIRM-007` Implementation Notes).

## 3. Assumptions and Constraints

- ACL 에 시간 축이 없다 — `PRINCIPAL` scope 의 만료일 부재 조항이 소유하는 전제이며, `IR-CONFIRM-001` 이 시점 표기를 금지하는 근거가 그것이다.
- 완전 숨김 규칙이 이 scope 의 여러 제약의 전제다 — `ACL` scope 가 소유한다. 확인 흐름이 그 규칙의 우회 경로가 되어서는 안 된다는 것이 `SEC-CONFIRM-001` 의 축이고, 분모·미도달 건수·첨부 개수를 감추는 규칙들이 모두 여기서 파생한다.
- 배정 기준이 가역성과 효과의 즉시성이므로(`FR-CONFIRM-002`), 어느 조작의 가역성 판정이 바뀌면 그 조작의 등급도 함께 바뀐다. 넓히기는 가역성 축에서 비가역으로 취급된다 (`SEC-CONFIRM-002`).
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가 소유한다.
- 미결 둘이 이 scope 에 걸려 있다 — `G16`(넓히기 결과의 사후 관측 수단 부재) · `G27`(감사 로그 보존 기간과 휴지통 보존 기간의 대소 관계).
- 이 scope 의 요구 다수에서 Priority 값은 원장이 배정한 것이 아니라 도구 기본값이다. 원장 §4 수용 기준 13개가 이 scope 의 조항을 지목하지 않는다.

#### Requirement

시스템은 조작의 확인 절차를 L1·L2·L3 세 등급 하나의 체계로 통일한다. L1 은 확인 없이 즉시 실행하고 되돌릴 수 있는 토스트를 띄운다. L2 는 실행 전에 확인 다이얼로그를 받는다. L3 은 실행 전에 타이핑 확인을 받는다. 화면이나 문서에 따라 같은 등급 이름에 다른 확인 절차를 부여하지 않는다. 이름 충돌로 자동 접미사가 붙었다는 통지는 이 체계의 대상이 아니며 어떤 등급도 배정하지 않는다.

#### Rationale

두 설계서가 같은 등급 이름에 다른 의미를 부여해, 두 문서를 오가며 구현하면 확인 단계가 통째로 사라지는 사고가 가능했다. 기각된 대안 — L1 부터 다이얼로그를 두는 체계. 가역 조작에도 마찰을 붙이므로 채택하지 않았다. 자동 접미사 통지를 대상에서 뺀 이유는 요청한 생성·업로드가 그대로 수행되고 이름만 달라진 결과 통지여서 되돌릴 조작이 없기 때문이다 — L1 의 실행취소 토스트에도 해당하지 않는다.

#### Acceptance Criteria

- [ ] AC-1: L1 로 배정된 조작은 확인 절차 없이 즉시 실행되고 실행 직후 되돌리기 토스트가 나타난다.
- [ ] AC-2: L2 로 배정된 조작은 실행 전에 확인 다이얼로그를 표시하고 사용자가 승인해야 실행된다.
- [ ] AC-3: L3 으로 배정된 조작은 실행 전에 지정된 토큰을 타이핑해야 실행된다.
- [ ] AC-4: 같은 등급 이름이 화면이나 설계 문서에 따라 서로 다른 확인 절차를 뜻하지 않는다.
- [ ] AC-5: 이름 충돌로 자동 접미사가 붙었다는 통지에는 확인 다이얼로그도 타이핑 확인도 되돌리기 토스트도 붙지 않는다.

### FR-CONFIRM-002 — 확인 등급 배정 기준 — 가역성과 효과의 즉시성

| Field | Value |
| --- | --- |
| Type | functional |

| Priority | medium |
| Tags | confirmation-grade, grading-rule |
| Risk | medium |
| Stability | stable |
| Verification Method | review |
| GitHub Issue | - |
| Related Docs | [권한 화면 설계](./05.screen-design-permission.md) |

#### Requirement

조작의 확인 등급은 가역성과 효과의 즉시성 두 축으로 배정한다. 가역이면서 효과가 즉시 드러나는 조작은 L1 이다. 비가역이거나 효과가 잠재·지연되는 조작은 L2 다. L2 조건을 충족하면서 영향이 광범위한(다건·서브트리·인스턴스 전역) 조작은 L3 이다. 등급을 확인 절차의 유무로 되짚는 순환 정의로 규정하지 않고 조작의 성질로 규정한다.

#### Rationale

되돌릴 수 있어도 지금 아무 일도 일어나지 않는 조작은 사용자가 결과를 확인할 수 없으므로 확인이 필요하다. 그래서 가역성만으로 가르지 않고 효과의 즉시성을 둘째 축으로 세웠다. 성질로 규정해야 "L2 = 확인이 필요한 조작" 같은 순환 정의를 피할 수 있다.

#### Acceptance Criteria

- [ ] AC-1: 가역이고 효과가 즉시 드러나는 조작에는 L1 이 배정된다.
- [ ] AC-2: 비가역인 조작에는 최소 L2 가 배정된다.
- [ ] AC-3: 가역이더라도 효과가 잠재되거나 지연되는 조작에는 최소 L2 가 배정된다.
- [ ] AC-4: L2 조건을 충족하면서 영향이 다건·서브트리·인스턴스 전역 중 하나에 해당하는 조작에는 L3 이 배정된다.
- [ ] AC-5: 등급의 정의가 확인 절차의 유무를 다시 참조하는 순환 정의로 기술되지 않는다.

- [ ] AC-1: 이동·복사 다이얼로그에서 목적지를 고르고 입력을 마친 뒤에 등급이 요구하는 확인 단계가 한 번 더 표시된다.

- [ ] AC-3: 드래그앤드롭으로 목적지가 미리 채워진 상태에서 조작을 실행해도 확인 단계가 표시된다.
- [ ] AC-4: L2 조작이 확인 단계 없이 클릭 1회로 실행되는 경로가 존재하지 않는다.

시스템은 다음 조작에 지정된 확인 등급을 적용한다 — 삭제(휴지통 이동) L1, 휴지통 단건 영구 삭제 L2, 휴지통 일괄 영구 삭제 L3, 비활성 계정에 대한 권한 부여 L2, `default` 그룹을 주체로 하는 일괄 회수 L3, 그룹 삭제 L3, 개인 액세스 토큰 폐기 L2, 문서 노드의 권한 항목 회수 L1, 그룹 멤버 제거와 가입 거절 L1. 휴지통 일괄 영구 삭제는 Phase 1 에 도입하지 않으므로 그 L3 배정은 조작을 도입하는 시점에 발효한다. 이 표가 열거한 조작의 등급값 정본은 이 요구다.

#### Rationale

### FR-CONFIRM-007 — 보존 기간 축소의 등급은 실제 영향 건수로 정한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | implemented |
| Priority | medium |
| Tags | confirmation-grade, retention, typing-token |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md) |

#### Requirement

휴지통 보존 기간과 감사 로그 보존 기간을 축소하는 조작의 확인 등급은 확인 시점의 실제 영향 건수로 정한다. 영향 건수가 0 보다 크면 L3, 0 이면 L2 다. L3 의 타이핑 토큰은 영향 건수 자체로 한다.

#### Rationale

저장 시점에는 아무 일도 일어나지 않고 다음 정리 시점에 한꺼번에 삭제되는 지연 효과이며 범위가 인스턴스 전역이라 L3 조건을 충족한다. 건수를 타이핑하게 하면 사용자가 규모를 읽지 않을 수 없다. 파괴가 없는 정책 변경(0건)에는 타이핑을 요구하지 않는다. 실제 영향으로 등급을 가르는 이 방식은 이후 이동의 등급 판정(R123-a)이 인용하는 선례가 되었다.

#### Acceptance Criteria

- [ ] AC-1: 보존 기간을 축소할 때 영향 건수가 1 이상이면 타이핑 확인을 받는다.
- [ ] AC-2: 보존 기간을 축소할 때 영향 건수가 0 이면 확인 다이얼로그만 받고 타이핑을 요구하지 않는다.
- [ ] AC-3: 타이핑 확인의 토큰은 영향 건수를 그대로 입력하는 것이다.
- [ ] AC-4: 영향 건수는 확인 다이얼로그를 여는 시점에 재조회한 값이다.

### FR-CONFIRM-011 — 넓히기의 등급은 주체 명시성과 대상 노드 범위로 정한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | implemented |
| Priority | medium |
| Tags | confirmation-grade, grant, container-node |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [권한 화면 설계](./05.screen-design-permission.md), [폴더 권한 패널](./06.folder-permission-panel.md) |

#### Requirement

넓히기의 확인 등급은 두 축으로 정한다 — 주체 집합의 명시성과 대상 노드의 범위. 주체가 명시적으로 지목된 단건이고 대상이 문서 노드면 L1 이다. 두 축 중 어느 한쪽이라도 집합이거나 대상이 컨테이너 노드(디렉토리·워크스페이스)면 L2 다. 주체를 지목하지 않는 조작(복사·상속 되돌리기·부모 권한 가져오기)은 언제나 불특정 집합으로 판정한다. 넓히기에는 L3 을 배정하지 않는다.

#### Rationale

주체 축의 판정 기준은 "개별 숙고가 조작에 내재하는가" 다 — 검색해 고르고 레벨을 선택하는 다단계 행위 자체가 확인 역할을 하므로 명시적 단건은 L1 이 된다. "단건이라 예외" 가 아니다. 노드 축이 필요한 이유는 개정 전 실제 구멍이 증명한다 — 워크스페이스에 개인 1명을 보기 로 부여하는 조작이 L1(무확인)이었고, 관리 부여만 L2 로 잡혀 있어 "전 문서를 볼 수 있게 한다" 는 무확인이고 "전 문서를 보고 권한도 만질 수 있게 한다" 만 확인을 받았다. 패널 4인이 각자 독립적으로 이 구멍을 지적했다. 넓히기에 L3 을 두지 않는 이유는 패널 4:0 — 배정된 L3 은 전부 실제 데이터 파괴인데 넓히기의 비가역은 파괴가 아니고, 운영상으로도 폴더 부여에 타이핑을 걸면 회피 경로가 "상위 폴더나 워크스페이스에 더 넓게 한 번 부여" 가 되어 안전을 늘리는 대신 실제 부여 범위를 넓힌다. 워크스페이스 관리 부여가 L2 인 근거도 이 조항이며 등급 직접 지정 경로로 못박는다 — 개정 전에는 이 배정이 어느 규칙으로도 도출되지 않아 두 설계서가 각자 다른 근거를 창작했고 그 두 근거가 서로 달랐다.

#### Acceptance Criteria

- [ ] AC-1: 검색해 고른 단건 주체에게 문서 노드의 권한을 부여하면 확인 다이얼로그 없이 실행된다.
- [ ] AC-2: 주체가 그룹이거나 불특정 집합이면 대상이 문서 노드여도 확인 다이얼로그를 받는다.
- [ ] AC-3: 대상이 디렉토리나 워크스페이스면 주체가 명시적 단건이어도 확인 다이얼로그를 받는다.
- [ ] AC-4: 복사·상속 되돌리기·부모 권한 가져오기는 주체 축에서 불특정 집합으로 판정된다.
- [ ] AC-5: 워크스페이스에 관리 레벨을 부여하는 조작은 확인 다이얼로그를 받는다.
- [ ] AC-6: 어느 넓히기 조작에도 타이핑 확인이 배정되지 않는다.

### FR-CONFIRM-012 — 컨테이너 부여 확인에 적용 하위 노드 수를 표시한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | implemented |
| Priority | medium |
| Tags | confirmation-grade, container-node, impact-count |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [폴더 권한 패널](./06.folder-permission-panel.md), [권한 화면 설계](./05.screen-design-permission.md) |

#### Requirement

컨테이너 노드(디렉토리·워크스페이스)에 대한 권한 부여의 확인 다이얼로그에 적용 하위 노드 수를 표시한다. 이 수치는 요청자에게 보이는 하위 노드 중 그 부여가 상속으로 실제 도달하는 것의 수이며, 요청자가 볼 수 없는 노드를 포함하지 않는다. 소재는 확인 다이얼로그이고 모달 본문에 상시 표시하지 않으며, 다이얼로그를 열 때 재조회하는 수치에 포함된다. 사람 수를 세는 접근 가능 지표와 라벨을 공유하지 않는다.

#### Rationale

접근 가능 인원의 델타만으로는 서브트리 규모를 알 수 없다 — 1명을 추가하면 하위가 3건이든 3,000건이든 화면에 똑같이 +1명 이 뜬다. 이동에서 막으려 한 것과 같은 종류의 무지가 부여에서 발생한다(R43-5). 패널 4인 중 3인. 라벨을 공유하지 않는 이유는 한쪽이 사람 수이고 이것은 노드 수여서 축이 다르기 때문이다 — 섞으면 혼합형 라벨 사고가 재발한다. 소재를 확인 다이얼로그로 한정한 이유는 상시 표시하면 재조회의 스테일 보호를 받지 못하는데 다이얼로그를 띄운 사이 하위에서 상속이 끊기면 값이 달라지기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 디렉토리나 워크스페이스에 권한을 부여하는 확인 다이얼로그에 적용 하위 노드 수가 표시된다.
- [ ] AC-2: 표시되는 수치는 그 부여가 상속으로 도달하는 하위 노드만 센 값이다.
- [ ] AC-3: 상속이 끊긴 하위 노드는 이 수치에 가산되지 않는다.
- [ ] AC-4: 이 수치에 요청자가 볼 수 없는 노드가 포함되지 않는다.
- [ ] AC-5: 적용 하위 노드 수는 모달 본문에 상시 표시되지 않는다.
- [ ] AC-6: 확인 다이얼로그를 여는 시점에 이 수치를 재조회하고 달라졌으면 실행을 잠근다.
- [ ] AC-7: 이 수치의 라벨이 사람 수를 세는 접근 가능 지표의 라벨과 같지 않다.

#### Implementation Notes

- 위 논증의 ① 단계는 하방 deny 예외가 없다는 전제(R14-c)에 의존한다 — 하방 예외를 도입하면 상속이 이어져도 요청자가 차단될 수 있어 논증이 깨진다. 인지된 비용 — 상위 순회의 비용 근거(R14-b)와 달리 이 카운트는 하향이라 성질이 다르다. 트리 구조 카운트는 권한 판정이 아니라 노드 경로 인덱스로 단일 쿼리 집계가 가능하고, 재조회는 다이얼로그를 열 때 1회다. 분모·미도달 건수·하위 집계형 접근자 수치는 별도 요구가 금지한다(R126-b). 워크스페이스 생성 시점에는 이 수치가 항상 0 이라 표시하지 않는다(R136-a). 편집 권한자가 부여 결과를 사후 관측할 수단은 G16 으로 미결이며 이 수치는 부분적 완화일 뿐 사후 검증이 아니다. 우선순위는 원장이 배정한 바 없다 — 표의 medium 은 도구 기본값이다.

### FR-CONFIRM-015 — 상속 끊기의 확인 등급은 대상 노드 유형으로 갈린다

| Field | Value |
| --- | --- |
| Type | functional |

| Status | implemented |
| Priority | medium |
| Tags | confirmation-grade, inheritance, typing-token |
| Risk | medium |
| Stability | stable |

| GitHub Issue | - |
| Related Docs | [폴더 권한 패널](./06.folder-permission-panel.md), [권한 화면 설계](./05.screen-design-permission.md) |

#### Requirement

상속 끊기의 확인 등급은 대상 노드 유형으로 갈린다. 디렉토리에 대한 상속 끊기는 L3 이며 타이핑 토큰은 영향 건수로 한다. 디렉토리가 아닌 노드에 대한 상속 끊기는 L2 다. 워크스페이스는 상속의 시작점이라 끊을 상위가 없으므로 대상이 아니며 토글 자체를 렌더하지 않는다.

#### Rationale

상속 플래그 자체는 가역·즉시라 두 축만 보면 L1 이지만, 끊긴 동안 편집 중이던 사용자의 저장이 거부되어(R91-②) 본문이 유실될 수 있다 — 그 부수 효과가 비가역이라 L2 가 된다. 디렉토리에서는 그 본문 유실이 서브트리 규모로 확대되므로 실제 본문 유실(진짜 비가역) + 서브트리 라는 L3 조건을 정직하게 충족한다. 넓히기에서 서브트리 축을 배제한 것과 방향이 반대여도 근거는 일관된다 — 좁히기·파괴에는 서브트리 축이 살아 있다. 관리 권한자만 수행하는 저빈도 조작이라 마찰 비용이 낮다.

#### Acceptance Criteria

- [ ] AC-1: 디렉토리에서 상속 끊기를 실행하면 타이핑 확인을 받는다.
- [ ] AC-2: 디렉토리 상속 끊기의 타이핑 토큰은 영향 건수를 그대로 입력하는 것이다.
- [ ] AC-3: 그 건수에 분모가 붙지 않는다.
- [ ] AC-4: 디렉토리가 아닌 노드에서 상속 끊기를 실행하면 확인 다이얼로그를 받는다.
- [ ] AC-5: 워크스페이스 권한 화면에 상속 끊기 토글이 렌더되지 않는다.

| Field | Value |

#### Requirement

이동의 확인 등급은 이동 전후의 접근 가능 수치 변화로 정한다. 수치가 변하면 L2 로 확인 다이얼로그를 받고, 수치가 같으면 L1 이다. 같은 상속 구조 안에서의 폴더 정리처럼 변화가 없는 이동은 L1 이다.

#### Rationale

이동은 목적지 상속을 새로 받아 넓어질 수도 좁아질 수도 있다. 넓어지면 노출의 비가역성(R122)이, 좁아지면 상속 끊기와 같은 부작용(권한을 잃은 사용자의 저장이 R91-② 로 거부되어 본문 유실)이 걸린다. 양방향 모두 확인이 필요하다. 변화가 없는 이동은 가장 흔한 파일 조작이므로 마찰을 남기지 않는다. 실제 영향으로 등급을 가르는 선례는 보존 기간 축소(R115-e)다.

#### Acceptance Criteria

- [ ] AC-1: 이동으로 접근 가능 수치가 늘어나면 확인 다이얼로그를 받는다.
- [ ] AC-2: 이동으로 접근 가능 수치가 줄어들면 확인 다이얼로그를 받는다.
- [ ] AC-3: 이동 전후의 접근 가능 수치가 같으면 확인 다이얼로그 없이 실행된다.

### FR-CONFIRM-017 — 복사의 확인 등급은 대상 유형과 무관하게 언제나 L2 다

| Field | Value |
| --- | --- |

#### Requirement

복사의 확인 등급은 대상 유형과 무관하게 언제나 L2 다. 문서 단건 복사도 L2 이며, 이동처럼 수치 변화로 등급을 가르는 조건부 판정을 두지 않는다.

#### Rationale

복사는 주체를 지목하지 않는다 — 수혜자가 목적지의 상속에서 파생되므로(R97-a) 요청자가 고른 적이 없다. 따라서 L1 조건(단건 주체 × 문서 노드의 논리곱)에서 주체 축이 탈락하고 불특정 집합 = L2 분기에 떨어진다. 노드 축 미해당은 L2 사유의 부재일 뿐 L1 자격 부여가 아니다. 보강 셋 — ① 편집 권한자는 수혜자를 열거할 수 없다(R118) ② 복사는 이동을 모든 축에서 지배하는데(원본 잔존 · 워크스페이스 경계 통과 R97 · 첨부 복제 R97-a · 회수 수단 부재) 이동은 이미 조건부 L2 다 ③ L1 이면 회수 토스트를 인스턴스화할 수 없다 — 회수할 권한 항목이 없어 거짓 버튼이 된다. 패널 3인 중 2인이며, 소수 의견은 빈도와 복사 프리뷰의 사전 방어를 들어 L1 을 주장했다. 조건부로 두지 않는 이유는 워크스페이스 경계를 넘는 유일한 수단의 관문을 계산 결과에 의존시키지 않기 위해서다 — 복사 프리뷰 수치는 항상 표시되므로(R120) 확인 단계에 얹을 정보는 이미 있다.

#### Acceptance Criteria

- [ ] AC-1: 문서 단건을 복사하면 확인 다이얼로그를 받는다.
- [ ] AC-2: 디렉토리를 복사하면 확인 다이얼로그를 받는다.
- [ ] AC-3: 복사 전후의 접근 가능 수치가 같아도 확인 다이얼로그를 받는다.
- [ ] AC-4: 복사에 확인 없이 실행되는 경로가 존재하지 않는다.

#### Requirement

컨테이너 노드(디렉토리·워크스페이스)에 대한 권한 항목 회수는 L2 로 확인 다이얼로그를 받는다. 문서 노드를 대상으로 하는 회수는 L1 을 유지한다.

#### Rationale

원장은 같은 부작용(권한을 잃은 편집자의 저장이 R91-② 로 거부되어 본문 유실)을 근거로 상속 끊기(R122-b)와 좁아지는 이동(R123)을 L2 로 올려놓고, 세 번째 경로인 컨테이너 항목 회수만 L1 로 남겨두었다. 컨테이너 회수는 서브트리 전체에서 접근이 사라지므로 그 부작용이 가장 크다.

#### Acceptance Criteria

- [ ] AC-1: 디렉토리의 권한 항목을 회수하면 확인 다이얼로그를 받는다.
- [ ] AC-2: 워크스페이스의 권한 항목을 회수하면 확인 다이얼로그를 받는다.
- [ ] AC-3: 문서 노드의 권한 항목을 회수하면 확인 다이얼로그 없이 실행된다.

#### Rationale

#### Acceptance Criteria

- [ ] AC-1: 컨테이너 회수의 확인 다이얼로그에 첨부 개수가 표시되지 않는다.
- [ ] AC-2: 컨테이너 회수의 확인 다이얼로그에 첨부도 함께 접근할 수 없게 된다는 문구가 한 줄 표시된다.
- [ ] AC-3: 그 문구는 하위 첨부의 유무와 무관하게 항상 같은 문구로 표시된다.

#### Requirement

부모 권한 가져오기의 필요 레벨은 관리다. 편집 레벨 사용자에게는 이 버튼을 노출하지 않는다. 확인 등급은 L2 다.

#### Rationale

넓히기를 편집에 허용하는 일반 규칙(R70-a)대로면 이것은 편집이므로 신규 결정이다(패널 3인 중 2인). 근거 둘 — ① 요청자가 열거할 수 없는 집합(R118 로 명단은 관리 전용)을 통째로 실행하는 조작이라 "개별 숙고가 조작에 내재하는가" 를 0% 만족하고, 편집에 열면 "누구인지 알 수 없는 11명에게 부여하시겠습니까" 라는 성립 불가능한 확인이 된다 ② 관리에 유보된 제품의 유일한 좁히기 수단(R14·R70-c)을 클릭 1회로 무효화한다. "개별 부여로 같은 종착 상태에 갈 수 있다" 는 반론은 성립하지 않는다 — 식별·숙고·부여자 기록 셋이 사라진다. 넓히기를 편집에 여는 채택 근거(R70)는 훼손되지 않는다 — 이 버튼은 가장 흔한 조작이 아니고 상속 끊김 상태에서만 나타나며(그 상태를 만드는 것도 관리 전용) 일상 수요인 1명 추가는 L1 로 열려 있다.

### FR-CONFIRM-019 — 워크스페이스 생성과 설치 시점의 부여도 확인 1개를 받는다

| Field | Value |

| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |

#### Requirement

워크스페이스 생성 시점의 부여도 L2 다. 관리자 지정과 기본 그룹 초기 권한 둘을 합쳐 확인 다이얼로그 1개를 둔다. 생성 버튼은 확인 관문이 아니다. 이 확인에는 적용 하위 노드 수를 표시하지 않고 지연 효과 고지로 대체한다. 같은 규칙을 설치 마법사의 초기 권한 설정에도 적용한다.

#### Rationale

패널 3인 중 2인. 넓히기 등급 규칙에 "기존 노드" 한정 문언이 없다 — 예시의 범위를 조항의 범위로 오인한 것이다. 노드 축으로도 두 경로가 같은 답을 낸다 — 관리자 지정은 워크스페이스 관리 부여이고 기본 그룹 초기 권한은 컨테이너 × 그룹이다. 확인을 둘로 나누지 않는 이유는 연속 다이얼로그가 확인 피로를 학습시키기 때문이다. 적용 하위 수를 빼는 이유는 생성 시점에 항상 0 이라 공허하기 때문이며, 이것은 워크스페이스를 상속 끊기 대상에서 뺀 것과 같은 유형이다. 다만 적용 하위 = 0 은 등급을 낮추는 근거가 아니라 오히려 효과의 잠재·지연 축의 독립 근거다 — 보존 기간 축소 규칙(R115-e)이 영향 건수 0 을 L3 에서 L2 로 낮추는 근거로만 썼지 L1 근거로 쓰지 않았다. 그 워크스페이스는 곧 문서로 채워지고 수혜자에 아직 계정도 없는 사람들이 포함되는(R8·R60-a) 무한 휴면 부여라 비활성 계정 부여(L2)보다 강하다. 기존 장치는 확인을 대체하지 못한다 — 기본값 없음(R111-a)은 부주의를 막고 확인은 오판을 막아 층이 다르다. 자유 가입 + 편집 경고(R111-c)는 ① 승인 모드(사실상 전사)를 놓치고 ② 보기 를 포함하지 않아 워크스페이스 보기 부여 구멍이 그대로 남으며 ③ 소재가 폼 안이라 관문 자격이 없다. 소수 의견은 생성 버튼을 관문으로 삼자고 했으나, 그것을 인정하면 이동·복사의 실행 버튼도 관문이 되어 입력 폼 규칙이 무력화된다. 설치 마법사까지 확장하는 이유는 기본 그룹 앞으로 부여된 권한이 나중에 재생성되지 않는데(R119) 그 유일한 출생지가 생성 폼과 설치 마법사이고 둘 다 무확인이었기 때문이며, 설치 마법사는 범위가 인스턴스 전원이라 더 넓다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스 생성 폼을 제출하면 부여 내용을 담은 확인 다이얼로그가 표시된다.
- [ ] AC-2: 관리자 지정과 기본 그룹 초기 권한이 하나의 확인 다이얼로그에 함께 표시된다.
- [ ] AC-3: 생성 버튼을 누르는 것만으로 부여가 실행되지 않는다.
- [ ] AC-4: 이 확인 다이얼로그에 적용 하위 노드 수가 표시되지 않는다.
- [ ] AC-5: 이 확인 다이얼로그에 지연 효과 고지 문구가 표시된다.
- [ ] AC-6: 설치 마법사의 초기 권한 설정도 확인 다이얼로그를 받는다.

### FR-CONFIRM-020 — 주체 다건 일괄 회수를 허용한다

| Field | Value |
| --- | --- |

#### Requirement

여러 주체를 한 번에 선택해 그 주체들의 권한 항목을 일괄 회수할 수 있다. 적용 범위는 단건 주체 회수와 같다. 시스템 그룹이 선택에 섞이면 그에 대한 안내를 주체별로 각각 표시하고 묶음 확인으로 접지 않는다. 임의 노드를 다중 선택해 회수하는 조작은 제공하지 않는다.

#### Rationale

심의 3:0. 이것은 새 조작 종류가 아니라 기존 주체 일괄 회수(R43-1)의 술어를 여러 주체로 넓히는 것이다. 방향이 fail-closed 다 — 회수는 fail-closed 방향이고 재부여로 복구된다는 판정이 이미 있다(R134-b). 잃는 것은 가용성이지 기밀성이 아니고, 복구 재료가 남는다(R84-a 불변성 + 부여 이벤트는 권한 항목이 지워져도 살아남는다). 부분 실패 논거(R73)는 이 조작에 적용되지 않는다 — 주체 일괄 회수는 권한 항목만 제거하므로 그 조건을 발동시킬 수 없다고 원장이 두 곳에 명시한다. 규모는 이미 그 화면에 있다 — 기본 그룹 단일 주체가 이미 수천 건이다. 노드 축 다건을 열지 않는 이유는 근거 조항이 없고 주체 단위 정의를 벗어나기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 여러 주체를 선택해 한 번에 회수하는 조작이 존재한다.
- [ ] AC-2: 일괄 회수의 적용 범위가 단건 주체 회수와 같다.
- [ ] AC-3: 선택에 시스템 그룹이 포함되면 그 안내가 주체마다 각각 표시된다.
- [ ] AC-4: 임의 노드를 다중 선택해 회수하는 조작은 제공되지 않는다.

#### Requirement

일괄 조작의 확인은 묶음 전체에 대해 1회 받는다. 선택된 항목마다 따로 확인을 받지 않는다.

#### Rationale

심의 3:0. 배정 기준의 문면이 강제한다 — L3 조건이 "L2 조건 + 광범위(다건·서브트리·인스턴스 전역)" 인데 다건 은 묶음의 속성이다. 항목 단위로 확인하면 각 항목은 단건이라 일괄 L3 라는 배정이 애초에 도출되지 않는다. 토큰 규정도 묶음을 전제한다 — 항목 단위면 토큰이 언제나 1 이라 "사용자가 규모를 읽지 않을 수 없다" 는 목적이 정확히 0 이 된다. 반대편은 이미 판정되었다 — 워크스페이스 생성 확인을 둘로 나누지 않은 이유가 연속 다이얼로그가 확인 피로를 학습시키기 때문이고, L3 타이핑 20연속은 그 병리의 극단이며 학습된 피로는 뒤에 오는 진짜 위험한 확인까지 무력화한다.

#### Acceptance Criteria

- [ ] AC-1: 주체 N 명을 선택해 일괄 회수하면 확인 단계가 1회만 표시된다.
- [ ] AC-2: 선택 항목 수가 늘어나도 확인 단계의 횟수가 늘어나지 않는다.

### FR-CONFIRM-022 — 일괄 회수 L3 의 토큰은 영향 건수이고 0건은 실행을 막는다

| Field | Value |

| Stability | stable |

| GitHub Issue | - |

#### Requirement

일괄 회수 L3 의 타이핑 토큰은 영향 건수, 즉 회수될 권한 항목의 수로 한다. 건수는 확인 다이얼로그를 열 때 재조회하고 값이 달라져 실행이 잠기면 토큰도 갱신된 값으로 바뀐다. 다이얼로그에는 주체 수와 항목 수를 함께 보이고 건수에 분모를 붙이지 않는다. 영향 건수가 0 이면 등급을 낮추지 않고 실행 자체를 막는다.

#### Rationale

심의 3:0. 신규 규칙이 아니라 세 번째 적용이다 — 보존 기간 축소(R115-e)가 원칙을 세웠고 디렉토리 상속 끊기(R131)가 이미 재사용했다. 재조회의 적용 대상에 일괄 회수가 이미 명시되어 있어 확인 기반은 원장에 깔려 있다. 대안이 없다 — L3 의 기본 토큰인 대상 이름 입력은 20명이면 이름 20개가 되어 성립하지 않는다. 0 건의 처분이 보존 기간 축소와 갈리는 이유는 보존 기간 축소가 0 건에도 조작으로 성립하는 자리이기 때문이다(정책은 바뀐다). 회수는 0 건이면 바꿀 것이 없어 조작 자체가 성립하지 않으므로 등급을 낮추는 것이 아니라 진행을 막는다.

#### Acceptance Criteria

- [ ] AC-1: 일괄 회수의 타이핑 토큰은 회수될 권한 항목의 수를 그대로 입력하는 것이다.
- [ ] AC-2: 확인 다이얼로그에 주체 수와 항목 수가 함께 표시된다.
- [ ] AC-3: 항목 수에 분모가 붙지 않는다.
- [ ] AC-4: 재조회로 건수가 바뀌어 실행이 잠기면 토큰도 갱신된 건수로 바뀐다.
- [ ] AC-5: 영향 건수가 0 이면 확인 다이얼로그로 강등되지 않고 실행이 차단된다.
- [ ] AC-6: 선택된 주체 중 일부만 0 건인 경우는 총합으로 판정한다.

### FR-CONFIRM-023 — 오프보딩 앞 세 단계는 다건화하지 않는다

| Field | Value |

| Type | functional |

#### Requirement

오프보딩 절차의 1·2·3 단계는 다건화하지 않는다. 다건 회수는 4 단계에만 적용한다. 사용자 20명을 오프보딩하면 앞 세 단계는 사람당 1회씩 20회 진행하고 4 단계만 일괄 1회로 처리한다. 이 중 확인을 사람당 받는 단계는 1·3 단계다 — 2 단계(PAT 무효화)는 1 단계의 자동 결과여서 별도 조작이 없고 따라서 확인 대상도 아니다. 오프보딩 단계 정의의 정본은 FR-PRINCIPAL-003 이다.

#### Rationale

심의 3:0. 3 단계 확인이 제거될 그룹 이름을 모두 나열하도록 요구하고(R115-h) 그 근거가 "실행 전에 보여주는 것이 유일한 기회" 인데, 그 나열은 사람마다 다른 정보라 20명분을 한 다이얼로그에 넣으면 조항의 목적이 무너진다. 3 단계에 L2 를 배정한 조항(R115-g)도 오프보딩 3 단계에 한정해 그룹 상세의 단건 멤버 제거 L1 과 갈라 두었으므로 그 한정어를 떼고 일반화하지 않는다. 1·3 단계는 부분 실패 결과 조건(R73)에 걸려 부분 실패가 필연이다. 오프보딩 카드가 진행 상태를 저장하지 않고 조회 시점의 실제 상태에서 파생하므로(R101-d) 4 단계를 다른 화면에서 일괄 처리해도 각 카드의 완료 표시는 자동으로 맞는다.

- [ ] AC-2: 다건 회수 조작은 오프보딩 4 단계에만 제공된다.
- [ ] AC-3: 사용자 20명을 오프보딩하는 흐름에서 1·3 단계의 확인은 사람당 각각 발생한다.
- [ ] AC-4: 2 단계는 사람마다 1 단계의 자동 결과로 진행되며 별도 조작도 확인 다이얼로그도 갖지 않는다.
