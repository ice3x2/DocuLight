# Workspace

| Field | Value |
|---|---|
| Document Type | scope_srs |
| Scope | WORKSPACE |
| Scope Name | Workspace |

## 1. Scope Overview

이 scope 는 노드 계층의 최상위 단위인 **워크스페이스**를 규정한다 — 계층에서의 자리와 그 계층을 더 늘리지 않는다는 제약, 워크스페이스가 권한 경계이자 상속 체인의 루트라는 성질, 디스크 위의 물리 저장 레이아웃과 식별 권위, 노드 이름의 검증, 그리고 워크스페이스가 사라지는 수단.

축은 **경계**다. 무엇이 한 워크스페이스에 속하는가, 그리고 무엇이 그 경계를 넘고 무엇이 넘지 못하는가. 이 scope 의 요구 여럿이 그 하나의 물음을 서로 다른 표면에서 답한다 — 인덱싱은 경계를 넘지만 표시는 요청자 권한으로 걸러지고, 노드 이동은 경계를 넘지 못하며, 트리는 접근 가능한 워크스페이스들을 나란히 보여준다.

## 2. Scope Boundaries

### In Scope

- 노드 계층에서 워크스페이스가 갖는 자리와, 계층을 `루트 → 워크스페이스 → 디렉토리 → 문서` 밖으로 늘리지 않는다는 제약 (`FR-WORKSPACE-001`·`CON-WORKSPACE-001`)
- 워크스페이스가 권한 경계라는 성질 — 상속 체인의 루트, `관리` 레벨을 워크스페이스에만 부여하고 생성 시 관리자를 지정한다는 규정, 워크스페이스 관리자의 관장 범위 (`SEC-WORKSPACE-001`·`SEC-WORKSPACE-002`·`SEC-WORKSPACE-003`)
- 인덱싱 경계와 표시 경계의 분리 — 링크·검색 인덱스는 워크스페이스 경계를 넘고, 그 결과 표면은 표시 직전에 요청자 권한으로 필터링된다 (`FR-WORKSPACE-002`·`SEC-WORKSPACE-004`)
- 그 필터의 예외와 귀결 — 아웃고잉 링크 패널, 권한 없는 문서를 가리키는 위키링크의 깨진 링크 표시, 권한 없는 문서명으로 수동 위키링크를 쓰는 것을 막지 않는다는 결정 (`SEC-WORKSPACE-005`·`SEC-WORKSPACE-006`·`FR-WORKSPACE-009`)
- 좌측 트리에 접근 가능한 워크스페이스를 나란히 표시한다는 규칙 (`FR-WORKSPACE-003`)
- 물리 저장 레이아웃과 사이드카 파일의 식별 권위 (`DR-WORKSPACE-001`·`DR-WORKSPACE-002`)
- 노드 이름 검증 규칙과, 대소문자만 다른 동명을 이름 충돌로 처리한다는 규칙 (`FR-WORKSPACE-004`·`FR-WORKSPACE-005`)
- 최초 기동 시의 기본 워크스페이스 생성 (`FR-WORKSPACE-006`)
- 워크스페이스의 제거 수단이 휴지통이 아니라 아카이브라는 결정과, 아카이브·복원 자체 (`FR-WORKSPACE-007`·`FR-WORKSPACE-008`)

### Out of Scope

- 워크스페이스 생성·삭제·아카이브·복원을 실행할 수 있는 주체의 판정 — 슈퍼유저 권능은 `PRINCIPAL` scope 가 소유한다 (`FR-WORKSPACE-007` Implementation Notes).
- 워크스페이스 생성 폼 안의 `default` 그룹 초기 권한 — 신규 생성 폼의 기본값 `없음` 은 `PRINCIPAL` scope 가, 설치 마법사에서 고르는 기본 워크스페이스의 초기 권한(기본값 `편집`)은 `AUTH` scope 가 소유한다. 두 기본값이 다르다는 점에 주의하라 — 후자는 부여할 사람이 아직 없는 부트스트랩 순간의 예외다 (`FR-WORKSPACE-001`·`FR-WORKSPACE-006` Implementation Notes).
- 생성 시점 부여의 확인 등급과 `[생성]` 버튼이 확인 관문이 아니라는 판정 — `CONFIRM` scope 가 소유한다 (`FR-WORKSPACE-001` Implementation Notes).
- ACL 부여·회수의 확인 등급, 감사 기록, 유효 권한 시뮬레이션 화면 — 각각 `CONFIRM`·`AUDIT`·`ACL` scope 가 소유한다. `SEC-WORKSPACE-003` 은 관장 권능만 정한다 (`SEC-WORKSPACE-003` Implementation Notes).
- 우측 `태그` 탭의 내용과 집계 단위 — `SHELL` scope 가 소유한다. `SEC-WORKSPACE-004` 의 필터가 그 집계 원천에 적용되지만, 태그 표면 자체를 이 scope 가 갖지 않는다 (`SEC-WORKSPACE-004` Implementation Notes).
- 존재가 구별되지 않는 표면에 권한 요청 버튼을 두지 않는다는 결정(R103-a) — `ACL` scope 가 소유하며, `SEC-WORKSPACE-005` 의 패널과 `SEC-WORKSPACE-006` 의 깨진 위키링크를 함께 지배한다. 그 자리에 요청 버튼을 붙이면 버튼의 존재 자체가 그 이름의 문서가 있다는 사실을 드러낸다 (해당 두 요구의 Implementation Notes).
- 이름 충돌 시의 자동 접미사 규칙(항상 자동 접미사 + 동일한 안내, 확인 단계 없음) — `SHELL` scope 가 정본으로 소유한다. 접미사의 **구체 형식과 번호 증가 방식**은 원장이 정하지 않았고 어느 scope 도 소유하지 않는다 — `SEC-SHELL-002` Implementation Notes 가 그 축을 구현 판단으로 남겼고 `10.access-control` §2 도 같게 적는다. `FR-WORKSPACE-005` 는 대소문자만 다른 동명이 충돌로 판정된다는 것까지만 정한다 (`FR-WORKSPACE-005` Implementation Notes).
- 재조정 대기열의 정체·스키마·소재·권한 — `AUDIT` scope 가 소유한다. `DR-WORKSPACE-002` 는 그 대기열에 기재한다는 사실만 요구한다 (`DR-WORKSPACE-002` Implementation Notes).
- `.archive` 를 서빙 루트에서 제외하고 DB 에 대응 레코드가 없는 파일시스템 경로 요청을 전부 거부하는 fail-closed 서빙 규칙 — `STORAGE` scope 가 소유한다. **그 규칙은 이 scope 의 아카이브 조항의 하위이면서도 Phase 1 이다** — 아카이브가 아니라 서빙 보안 축이므로 상위의 Phase 를 따르지 않는다. 아카이브를 Phase 2 로 미룬 것을 그 규칙까지 미루는 것으로 읽으면 「레코드 없음 → 무제한 허용」 이 되살아난다 (`FR-WORKSPACE-008` Implementation Notes).
- 파일시스템과 DB 의 재조정, 노드 ID, 휴지통, 백업 — `STORAGE` scope 가 소유한다. 이 scope 는 워크스페이스 단위의 물리 레이아웃과 식별만 갖는다.
- 자동완성 후보·백링크 패널·검색 탭이 놓이는 화면 자리 — `SHELL` scope 가, 위키링크의 해석 규칙과 삽입 형식은 `STORAGE` scope 가 소유한다. 이 scope 는 인덱싱이 경계를 넘는다는 사실과 표시 직전 필터만 갖는다.

## 3. Assumptions and Constraints

- 볼트에 해당하는 별도 계층을 두지 않는다 (`CON-WORKSPACE-001`). 링크 경계와 권한 경계를 분리하는 3계층 안은 폐기됐으므로, 이 scope 의 「경계」는 언제나 워크스페이스 하나를 뜻한다.
- 모든 `.md` 문서는 서버 로컬 파일시스템이 SSOT 다 — `STORAGE` scope 가 소유하는 전제이며, 이 scope 의 물리 레이아웃과 사이드카 조항이 그 위에 선다.
- ACL 판정 모델(상속·가산·거부 없음)은 `ACL` scope 가 소유한다. 워크스페이스가 상속 체인의 루트라는 규정은 그 모델의 시작점을 정하는 것이지 모델 자체를 정하는 것이 아니다.
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가 소유한다.
- 아카이브 계열 두 요구는 Phase 2 다. Phase 2 열거가 닫힌 목록이 아니라는 판정 규칙은 `ARCH` scope 가 소유한다.
- 미결 `G16` 이 이 scope 에 걸린다 — `편집` 보유자의 넓히기 전파는 `SEC-WORKSPACE-003` 의 부여 권능과 별개 경로인데, 그 결과를 관측할 화면이 모두 `관리` 전용이라는 비대칭이 열려 있다.

#### Requirement

루트 아래에 워크스페이스 계층을 두고, 노드 계층을 `루트 → 워크스페이스 → 디렉토리 → 문서` 4단계로 구성한다. 이 계층의 명칭은 제품 전반에서 `워크스페이스` 다.

#### Rationale

옵시디언의 볼트(vault)에 해당하는 개념을 도입하되 명칭은 `워크스페이스`로 확정했다. 이 계층이 제품의 차별점인 권한 관리의 경계를 담는 자리다 — 관리 권한은 이 한 계층에만 부여되고(별도 조항), 상속 체인도 여기서 시작한다. 원장 Q11 을 해소한 결정이며, 이 계층이 서면서 폐기된 대안(임의 디렉토리 관리자)의 자리가 사라졌다.

#### Acceptance Criteria

- [ ] AC-1: 모든 문서와 디렉토리는 정확히 하나의 워크스페이스에 속한다.
- [ ] AC-2: 워크스페이스의 부모는 루트뿐이며, 워크스페이스 안에 다른 워크스페이스를 만들 수 없다.
- [ ] AC-3: 문서·디렉토리 노드는 루트를 직접 부모로 가질 수 없다.
- [ ] AC-4: 사용자에게 보이는 화면·문구·API 응답에서 이 계층을 `볼트`(vault)가 아니라 `워크스페이스`로 표기한다.

### CON-WORKSPACE-001 — 노드 계층을 4단계 밖으로 늘리지 않는다

| Field | Value |
| --- | --- |
| Type | constraint |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | hierarchy, scope-boundary |
| Risk | medium |
| Stability | stable |
| Verification Method | review |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

옵시디언의 볼트에 해당하는 별도 계층을 두지 않는다. 노드 계층은 `루트 → 워크스페이스 → 디렉토리 → 문서` 로 끝나며 그 사이에 중간 계층을 추가하지 않는다.

#### Rationale

기각된 대안을 명시적으로 닫는 조항이다 — 링크 경계와 권한 경계를 분리하는 3계층 안(볼트 계층을 따로 두는 안)은 복잡도 대비 이득이 없어 폐기했다. 원장 Q12 를 해소했다. 이 안이 불필요해진 이유는 두 경계를 굳이 분리할 필요가 없었기 때문이다 — 워크스페이스가 권한 경계를 맡고, 링크·검색은 그 경계를 넘도록 별도 조항이 정했으므로 링크 경계라는 개념 자체가 제품에 없다.

#### Acceptance Criteria

- [ ] AC-1: 루트와 워크스페이스 사이에 어떤 중간 계층도 존재하지 않는다.
- [ ] AC-2: 워크스페이스와 디렉토리 사이에 어떤 중간 계층도 존재하지 않는다.
- [ ] AC-3: 링크 경계와 권한 경계를 서로 다른 계층에 배치하는 구조를 도입하지 않는다 — 둘은 모두 워크스페이스 계층에서 결정된다.
- [ ] AC-4: 노드 경로·ID 체계·권한 모델은 4단계를 넘는 조상 체인을 전제하지 않는다.

### SEC-WORKSPACE-001 — 워크스페이스는 상속 체인의 루트다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | acl-inheritance, workspace-create |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md), [권한 화면 설계](./05.screen-design-permission.md) |

#### Requirement

워크스페이스는 ACL 상속 체인의 루트이며 상위로부터 권한을 물려받지 않는다. 상속 플래그와 `부모 권한 가져오기` 버튼을 워크스페이스에 노출하지 않고, 대신 워크스페이스 생성 절차에 관리자 지정 단계를 포함한다.

#### Rationale

감사 M10 해소. 슈퍼유저 권한을 정한 조항이 개정되면서 "루트 ACL" 개념이 사라졌고, 그 결과 워크스페이스에는 물려받을 상속 원천이 아예 없어졌다. 상속 플래그를 그대로 노출하면 원천 없는 상속을 켜는 조작이 화면에 남아 사용자가 아무 효과 없는 스위치를 만지게 된다. 상속으로 권한이 들어오지 않으므로 관리자는 생성 시점에 명시적으로 지정되어야 하며, 이 단계를 빼면 생성 직후 아무도 그 워크스페이스의 ACL 을 다룰 수 없는 상태가 만들어진다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스의 유효 권한 계산 결과에 상위 노드로부터 상속된 항목이 포함되지 않는다.
- [ ] AC-2: 워크스페이스를 대상으로 하는 권한 화면에 상속 플래그가 나타나지 않는다.
- [ ] AC-3: 워크스페이스를 대상으로 하는 권한 화면에 `부모 권한 가져오기` 버튼이 나타나지 않는다.
- [ ] AC-4: 워크스페이스 생성 절차는 관리자 지정 단계를 포함한다.
- [ ] AC-5: 관리자를 지정하지 않은 상태로는 워크스페이스 생성이 완료되지 않는다.

#### Requirement

`관리` 레벨은 워크스페이스 노드에만 부여할 수 있다. 디렉토리·문서 노드에는 부여할 수 없으며 임의 디렉토리 관리자를 두지 않는다.

#### Rationale

폐기된 조항(임의 디렉토리 관리자)을 대체한 결정이다. 관리 경계를 한 계층에 묶으면 "이 노드를 누가 관장하는가"의 답이 트리 전체에 흩어지지 않고 항상 그 노드가 속한 워크스페이스 하나로 정해진다. 원장 Q11 의 레벨 표가 `관리` 의 부여 가능 대상을 워크스페이스로 한정한 것이 이 조항의 표 형태다 — `보기`·`편집` 은 워크스페이스·디렉토리·문서 세 계층 모두에 부여 가능하지만 `관리` 만 다르다.

#### Acceptance Criteria

- [ ] AC-1: 디렉토리 노드에 `관리` 레벨을 부여하는 요청은 거부된다.
- [ ] AC-2: 문서 노드에 `관리` 레벨을 부여하는 요청은 거부된다.
- [ ] AC-3: 디렉토리·문서를 대상으로 하는 권한 부여 UI 의 레벨 선택지에 `관리` 가 나타나지 않는다.
- [ ] AC-4: 워크스페이스 노드에 대해서는 `보기`·`편집`·`관리` 세 레벨을 모두 부여할 수 있다.
- [ ] AC-5: 상속·가산으로 계산된 디렉토리·문서의 유효 권한이 `관리` 가 되는 경로는 그 노드가 속한 워크스페이스의 `관리` 항목 하나뿐이다.

#### Requirement

워크스페이스에 `관리` 레벨을 보유한 주체는 그 워크스페이스에 속한 모든 노드의 ACL 을 부여하고 회수한다. 그 권능은 해당 워크스페이스 밖으로 미치지 않는다.

### FR-WORKSPACE-002 — 링크·검색 인덱스는 워크스페이스 경계를 넘는다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | link-family, search, indexing |
| Risk | medium |
| Stability | stable |
| Verification Method | Playwright E2E |
| GitHub Issue | - |
| Related Docs | [셸 화면 설계](./03.screen-design-shell.md) |

#### Requirement

위키링크·백링크·그래프뷰·검색의 인덱스는 워크스페이스 단위로 분할하지 않고 전 워크스페이스를 하나의 인덱스로 다룬다. 워크스페이스는 권한 경계이지 링크 경계가 아니다. 이 조항은 인덱싱 경계만 규정하며 표시 경계는 별도 조항이 정한다.

#### Rationale

옵시디언과 명시적으로 다른 지점이다 — 옵시디언에서 볼트는 닫힌 링크 세계라 볼트를 넘는 링크가 성립하지 않지만, 이 제품에서 워크스페이스는 권한 경계일 뿐이므로 링크가 경계를 넘어야 한다. 원장 §4 수용 기준 3 이 이 조항을 직접 지목한다(*"위키링크 `[[` 자동완성이 워크스페이스를 넘어(R39) 동작하고"*). 인덱싱 경계와 표시 경계를 분리한 것이 이 조항의 핵심이며, 그 분리는 원장이 조항 문면에 직접 적어 두었다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스 A 의 문서에서 `[[` 를 입력하면 워크스페이스 B 의 문서가 자동완성 후보로 나타난다(요청자가 그 문서에 유효 권한을 가진 경우).
- [ ] AC-2: 워크스페이스 A 의 문서가 워크스페이스 B 의 문서를 가리키면 B 문서의 백링크 패널에 A 문서가 나타난다(권한 조건 동일).
- [ ] AC-3: 검색은 단일 워크스페이스가 아니라 전 워크스페이스를 대상으로 수행된다.
- [ ] AC-4: 워크스페이스를 넘는 위키링크를 클릭하면 볼트 전환에 해당하는 별도 조작 없이 대상 문서가 열린다.
- [ ] AC-5: 인덱스 자체는 요청자와 무관하게 구축되며, 워크스페이스별로 분리된 인덱스를 두지 않는다.
- [ ] AC-6: 링크 수집 결과에 워크스페이스명을 부기해 어느 워크스페이스의 문서인지 구분할 수 있다.

### SEC-WORKSPACE-004 — 링크·검색 결과 표면은 표시 직전 요청자 권한으로 필터링한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | acl-filter, link-family, search |
| Risk | medium |
| Stability | evolving |
| Verification Method | Playwright E2E |
| GitHub Issue | - |
| Related Docs | [셸 화면 설계](./03.screen-design-shell.md) |

#### Requirement

인덱스가 워크스페이스 경계를 넘는 것은 인덱싱 경계에 대한 규정이지 표시 경계가 아니다. 링크 계열과 검색의 모든 결과 표면 — 백링크 · 아웃고잉 링크 · `[[` 자동완성 후보 · 검색 결과 · 그래프뷰 노드 · 태그 목록과 그 집계 — 는 표시 직전 요청자의 유효 권한으로 필터링한다. 이 여섯 표면 열거가 필터 적용 대상의 정본이며, 아웃고잉 링크 패널만 별도 조항이 정한 명시적 예외다.

#### Rationale

감사 H3·H4 를 해소한 조항이다. MCP 도구와 벡터검색 결과를 요청자 ACL 로 필터링하도록 정한 원칙(R22)을 앱 내 기능 전체로 확장한 것이다. **이 조항이 표면 목록의 정본이다** — 원장 §4 수용 기준 3 이 *"표면 목록은 R80 을 정본으로 두고 여기 열거하지 않는다"* 고 못박아 열거의 이중 관리를 금지했다(R124: 한 사실은 한 곳에). 따라서 새 결과 표면이 생기면 이 조항의 열거를 늘리는 것이 유일한 갱신 지점이고, 수용 기준의 E2E 는 판정 시점의 이 열거를 읽는다. 인덱싱 경계와 표시 경계를 분리한 이유는 둘이다 — 인덱스를 권한으로 분할하면 회수 즉시성(R59)이 인덱스 재구축 지연에 종속되고, 워크스페이스를 넘는 링크라는 제품의 결정이 성립하지 않는다. 개수 힌트를 금지한 것은 존재 자체의 노출이 완전 숨김(R25) 위반이기 때문이다 — 숨긴 것을 세어 보여주면 숨긴 의미가 없다.

#### Acceptance Criteria

- [ ] AC-1: 백링크 패널은 요청자가 유효 권한을 갖지 않는 문서에서 유래한 역참조를 표시하지 않는다.
- [ ] AC-2: `[[` 자동완성 후보 목록에 요청자가 유효 권한을 갖지 않는 문서가 나타나지 않는다.
- [ ] AC-3: 검색 결과에 요청자가 유효 권한을 갖지 않는 문서가 나타나지 않는다.
- [ ] AC-4: 태그 목록에서, 요청자가 볼 수 있는 문서에 한 번도 나타나지 않는 태그는 표시되지 않는다.
- [ ] AC-5: 태그의 출현 문서 수 집계에 요청자가 유효 권한을 갖지 않는 문서가 가산되지 않는다.
- [ ] AC-6: 필터는 인덱스 조회 결과에 대해 표시 직전에 적용되며, 권한 회수 후 그 표면을 다시 조회하면 첫 조회부터 결과에 반영된다.
- [ ] AC-7: 권한 없는 문서발 역참조는 통째로 생략되며 `비공개 N건` 같은 개수 힌트를 표시하지 않는다.
- [ ] AC-8: 결과 목록에 건수를 표기할 때 그 값은 필터를 통과한 항목만 센다.

- 집계 원천에 필터를 걸면 태그 개수가 요청자별 산출물이 되어 인스턴스 단위 캐시를 공유할 수 없다. 옵시디언에는 없던 비용이며 인지된 대가다.

- 〔미결〕 필터 결과가 화면에 **언제 다시 적용되는지**는 이 조항이 정하지 않는다. `G14-a` 가 갱신 시점 규정이 필요한 네 자리로 트리·검색 결과·즐겨찾기·우측 사이드바를 지목하고, 우측 사이드바는 백링크·아웃고잉(활성 문서 추종)과 태그(문서 독립 전역 색인)로 갱신 축이 둘로 갈린다 — 넷으로 세고 규정을 넷만 쓰면 태그 축이 빠진다. `G14-b` 는 권한 변경 사실이 화면에 도달하는 경로가 규정되지 않았다고 적는다. 이 조항의 *"표시 직전"* 은 매 렌더에서 성립하므로 규범 자체는 완결이나, 렌더가 언제 일어나는지는 열려 있다. 이 열린 축 때문에 stability 를 evolving 으로 둔다.
- 필터는 서버에서 걸어야 한다. 인덱스 조회 결과를 클라이언트로 보낸 뒤 감추면 응답 본문에 존재가 남는다.
- [2026-08-19] 수용 기준 판정 E2E 는 판정 시점의 이 조항 열거를 읽어 표면마다 단언을 만들고, 집계형 표면(태그)에 대해서는 목록 미노출(AC-4)과 수치 미가산(AC-5)을 각각 단언하며, Phase 1 에 존재하지 않는 표면(그래프뷰 — R17 로 Phase 2)은 제외 사유와 함께 명시한다. 원장 §4 수용 기준 3 이 이 문면을 그대로 적는다 — 검증 방법 지시이므로 수용 기준이 아니라 여기에 둔다.

### SEC-WORKSPACE-005 — 아웃고잉 링크 패널은 권한 필터의 예외다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | acl-filter, outgoing-links |
| Risk | medium |
| Stability | stable |
| Verification Method | Playwright E2E |
| GitHub Issue | - |
| Related Docs | [셸 화면 설계](./03.screen-design-shell.md) |

#### Requirement

아웃고잉 링크 패널에는 표시 직전 권한 필터를 적용하지 않는다. 현재 문서 본문에 있는 링크를 그대로 나열하고 미해결 링크도 표시하되, `존재하지 않음` 과 `권한 없음` 을 구분하지 않는다.

#### Rationale

두 패널의 규칙이 정반대인 이유는 **링크 텍스트가 누구의 본문에서 왔는가** 하나다. 아웃고잉 링크 텍스트는 요청자 자신의 본문에서 유래하므로 *"본문을 볼 수 있는 사람은 그 본문 안의 링크 텍스트도 본다"* 는 원칙(R42)이 그대로 적용된다 — 필터해도 지킬 것이 없고 본문과 패널의 불일치만 생긴다. 백링크는 남의 본문에서 유래하므로 필터를 그대로 유지한다. 감출 것이 없으므로 개수 힌트 금지 규칙(R80-a)도 이 패널에는 대상이 없다.

#### Acceptance Criteria

- [ ] AC-1: 아웃고잉 링크 패널은 현재 문서 본문의 위키링크를 하나도 생략하지 않고 나열한다.
- [ ] AC-2: 패널의 항목 수는 본문의 위키링크 수와 항상 같다.
- [ ] AC-3: 대상 문서가 존재하지 않는 링크와 요청자에게 권한이 없는 링크는 동일한 `미해결` 스타일로 렌더된다.
- [ ] AC-4: 두 경우의 툴팁·사유 문구·아이콘이 동일하다.
- [ ] AC-5: 두 경우의 응답 본문에도 구분 가능한 값(사유 코드·플래그)이 담기지 않는다.
- [ ] AC-6: 패널의 미해결 표시와 본문의 깨진 링크 렌더가 같은 링크 집합에 대해 일치한다.
- [ ] AC-7: 백링크 패널에는 이 예외를 적용하지 않고 필터를 그대로 유지한다.

### SEC-WORKSPACE-006 — 권한 없는 문서를 가리키는 위키링크는 깨진 링크로 표시한다

| Field | Value |
| --- | --- |

| Risk | medium |
| Stability | stable |

#### Requirement

요청자에게 유효 권한이 없는 문서를 가리키는 위키링크는 존재하지 않는 문서를 가리키는 링크와 동일한 깨진 링크로 렌더한다. 링크 텍스트 자체는 본문 그대로 보인다.

#### Rationale

원칙은 *"본문을 볼 수 있는 사람은 그 본문 안의 링크 텍스트도 본다"* 이다. 문서 본문은 통째로 보이거나 통째로 안 보이거나 둘 중 하나이므로, 이미 본문을 읽을 수 있는 사람에게 그 안의 링크 텍스트를 보이는 것은 완전 숨김(R25) 위반이 아니다. 표시 방식은 옵시디언이 존재하지 않는 문서를 표시하는 방식과 같게 두어, 사용자가 이미 아는 관용을 그대로 쓴다.

#### Acceptance Criteria

- [ ] AC-1: 본문 렌더에서 권한 없는 대상 문서를 가리키는 위키링크는 깨진 링크 스타일로 표시된다.
- [ ] AC-2: 존재하지 않는 문서를 가리키는 위키링크와 스타일·툴팁이 동일하다.
- [ ] AC-3: 두 경우의 클릭 동작과 그 결과 화면이 동일하다.
- [ ] AC-4: 링크 텍스트는 본문에 적힌 대로 보이며 마스킹하거나 생략하지 않는다.
- [ ] AC-5: 깨진 링크 렌더에 권한 없음과 존재하지 않음을 구분할 수 있는 표시·응답 값이 들어가지 않는다.

#### Requirement

좌측 문서 트리는 요청자가 접근 가능한 모든 워크스페이스를 동시에 최상위 항목으로 표시한다. 한 번에 하나만 여는 워크스페이스 전환 방식을 두지 않는다.

#### Rationale

링크가 워크스페이스 경계를 넘는다는 결정과 일관된 화면이다. 옵시디언의 볼트 전환과 다른 지점이며, 전환식으로 두면 경계를 넘는 백링크를 클릭할 때마다 워크스페이스를 바꿔야 해 경계를 넘게 만든 이유 자체가 사라진다. 트리가 곧 접근 가능 범위의 표현이므로 권한 없는 워크스페이스는 완전 숨김(R25) 대로 나타나지 않는다.

#### Acceptance Criteria

- [ ] AC-1: 요청자가 둘 이상의 워크스페이스에 유효 권한을 가지면 좌측 트리에 그 워크스페이스들이 동시에 최상위 항목으로 나타난다.
- [ ] AC-2: 두 워크스페이스의 하위 노드를 전환·선택 조작 없이 각각 펼칠 수 있다.
- [ ] AC-3: 현재 워크스페이스를 고르는 전환 UI 를 제공하지 않는다.
- [ ] AC-4: 요청자가 유효 권한을 갖지 않는 워크스페이스는 트리에 나타나지 않는다.
- [ ] AC-5: 워크스페이스를 넘는 링크를 타고 다른 워크스페이스의 문서를 열면 그 문서가 속한 워크스페이스가 트리에서 이미 보이는 상태다.

### DR-WORKSPACE-001 — 워크스페이스 물리 저장 레이아웃

| Field | Value |
| --- | --- |
| Type | data |

| Risk | medium |
| Stability | stable |

#### Requirement

워크스페이스의 물리 저장 구조는 `docsRoot/<워크스페이스ID(해시)>/…` 단일 루트 하위 폴더다. 해시 디렉토리명은 워크스페이스 한 계층에만 적용하고 표시 이름은 DB 에 둔다. 문서와 디렉토리는 실제 이름을 그대로 유지한다.

#### Rationale

해시 디렉토리명을 쓰면 이름 변경 시 물리 경로가 불변이라 첨부·백업·링크가 깨지지 않는다. 또한 한글·공백·특수문자, Windows 예약어(`CON`·`PRN`·`AUX`·`NUL`), 경로 260자 제한을 **워크스페이스 계층에 한하여** 회피한다. 그 회피를 문서·디렉토리 계층까지 확대하지 않은 이유는 두 가지다 — 옵시디언 호환성(볼트를 그대로 넣어 열 수 있어야 하고 §4 수용 기준 1 이 그것을 시험한다)과 파일시스템이 문서의 SSOT 라는 원칙(R4)이다. 파일 이름이 해시가 되면 서버에서 파일을 직접 열어 본 사람이 무엇이 무엇인지 알 수 없어 SSOT 가 실질적으로 무너진다. 워크스페이스별 독립 파일시스템 경로는 두지 않는다 — 백업과 재조정 스캔의 대상이 여러 루트로 흩어지면 두 조작 모두 루트 목록에 종속된다.

#### Requirement

각 워크스페이스 디렉토리 안에 `{id, name, createdAt}` 을 기록한 `.workspace.json` 을 둔다. 워크스페이스 이름·식별의 권위는 DB 이고 이 파일은 재구성용 사본이다 — 재조정 시 DB 기준으로 재작성하며, DB 에 해당 워크스페이스가 없을 때에만 파일에서 복원한다. `id` 중복이 발견되면 나중 것을 격리하고 재조정 대기열에 기재한다.

#### Rationale

DB 가 손상돼도 파일시스템만으로 전체 재구성이 가능해야 한다 — 이 사이드카가 없으면 워크스페이스 디렉토리명이 해시라는 결정이 파일시스템을 SSOT 로 둔 원칙(R4)을 무너뜨린다. 해시 폴더만 남으면 어느 것이 무엇인지 알 방법이 사라지기 때문이다. 권위를 DB 로 못박은 것은 감사 M20 해소이며, `cp -r` 백업 사본이 같은 `id` 로 이중 등록되는 경로를 차단한다. 격리를 삭제가 아니라 대기열 기재로 처리하는 이유는 사본과 원본을 자동으로 판별할 수 없기 때문이다 — 사람이 판단할 때까지 둘 다 남긴다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스 생성 시 그 디렉토리 안에 `.workspace.json` 이 만들어지고 `id`·`name`·`createdAt` 세 필드를 담는다.
- [ ] AC-2: 재조정 시 `.workspace.json` 은 DB 값을 기준으로 재작성된다.
- [ ] AC-3: 사이드카의 `name` 과 DB 의 표시 이름이 어긋나면 DB 값이 이기고 파일이 갱신된다.
- [ ] AC-4: DB 에 해당 워크스페이스 레코드가 없을 때에만 `.workspace.json` 에서 워크스페이스를 복원한다.
- [ ] AC-5: 스캔 중 이미 등록된 `id` 를 가진 `.workspace.json` 을 또 발견하면 나중 것을 격리하고 DB 에 이중 등록하지 않는다.
- [ ] AC-6: 그 격리 사실이 재조정 대기열에 기재된다.
- [ ] AC-7: DB 를 비운 상태로 `docsRoot` 만 남기고 기동하면 모든 워크스페이스가 `.workspace.json` 으로부터 재구성된다.

#### Requirement

워크스페이스 삭제는 휴지통에 들어가지 않는다. 워크스페이스를 제거하는 수단은 아카이브 하나뿐이다.

#### Rationale

워크스페이스는 단위가 커서 문서·디렉토리와 별도로 취급한다. 휴지통(R52·R85)은 `.trash/<노드ID>/원본이름` 형태의 노드 단위 격리 구조라 워크스페이스 전체를 담는 단위가 아니고, 보존 기간 경과 시 자동 영구 삭제(R86)가 걸리면 워크스페이스 하나가 통째로 조용히 사라진다. 아카이브는 자동 정리가 없어(R86) 그 위험이 없다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스를 대상으로 하는 휴지통 삭제 조작을 제공하지 않는다.
- [ ] AC-2: 워크스페이스 제거 요청은 아카이브 조작으로만 수행된다.
- [ ] AC-3: 아카이브된 워크스페이스는 휴지통 목록에 나타나지 않는다.
- [ ] AC-4: 휴지통 보존 기간 경과에 따른 자동 영구 삭제가 아카이브에는 적용되지 않는다 — 아카이브의 정리는 슈퍼유저의 명시적 조작만으로 일어난다.

#### Requirement

아카이브된 워크스페이스는 아카이브 디렉토리로 이동하고 DB 에서는 `archived` 플래그로 관리한다 — ACL 행과 인덱스 행은 유지된다. 아카이브 해제(복원)는 플래그 해제와 디렉토리 원위치다. 아카이브·복원·`.archive` 영구 삭제의 행위자는 슈퍼유저다.

#### Rationale

초판 기록의 *"DB 에서 분리"* 는 오기였고 원 지시는 *"DB 에서 관리"* 였다 — 감사 C12(CRITICAL)가 바로 그 오기에서 파생된 결함이었다. 행이 유지되므로 아카이브로 ACL 이 소실되지 않고, 복원이 권한을 다시 구성하지 않아도 아카이브 이전 상태가 그대로 돌아온다. 행위자를 슈퍼유저로 둔 것은 워크스페이스 생성·삭제·아카이브·복원 권한을 슈퍼유저에 묶은 R29 와 같은 계열이다 — 워크스페이스 관리자에게 열면 자기 워크스페이스를 통째로 치울 수 있게 되어 관리 경계가 존속 결정까지 삼킨다.

#### Acceptance Criteria

- [ ] AC-1: 아카이브 시 워크스페이스 디렉토리가 아카이브 디렉토리로 이동한다.
- [ ] AC-2: 아카이브 시 DB 의 워크스페이스 레코드는 삭제되지 않고 `archived` 플래그가 설정된다.
- [ ] AC-3: 아카이브 후에도 그 워크스페이스와 하위 노드의 ACL 행이 유지된다.
- [ ] AC-4: 아카이브 후에도 그 워크스페이스의 인덱스 행이 유지된다.
- [ ] AC-5: 복원 시 `archived` 플래그가 해제되고 디렉토리가 원위치로 돌아간다.
- [ ] AC-6: 복원된 워크스페이스의 ACL 이 아카이브 이전과 동일하다.
- [ ] AC-7: 슈퍼유저가 아닌 주체의 아카이브 요청은 거부된다.
- [ ] AC-8: 슈퍼유저가 아닌 주체의 복원 요청과 `.archive` 영구 삭제 요청은 거부된다.

#### Requirement

요청자가 유효 권한을 갖지 않는 문서명을 수동으로 타이핑해 위키링크를 작성하는 것은 차단하지 않는다. 그렇게 작성된 링크는 깨진 링크로 렌더된다. 권한 필터는 자동완성 후보 목록에만 걸리고 입력 자체를 막지 않는다.

#### Rationale

원장 R80-b 가 정한 규범이며, 같은 표면에 걸리지만 방향이 반대다 — SEC-WORKSPACE-004 는 결과 표면에서 권한 밖 문서를 걸러내라고 정하고, 이 요구는 입력을 막지 말라고 정한다. 한 블록에 두면 무엇을 막고 무엇을 막지 않는지가 같은 수용 기준 목록 안에서 뒤섞인다. 막지 않아도 안전한 근거는 R42 다 — 권한 없는 문서를 가리키는 링크와 아예 없는 문서를 가리키는 링크가 같은 깨진 링크로 보이므로 링크 작성으로는 존재가 드러나지 않고 R25 완전 숨김이 유지된다.

#### Acceptance Criteria

- [ ] AC-1: 요청자가 유효 권한을 갖지 않는 문서명을 수동으로 타이핑해 위키링크를 작성하는 것이 차단되지 않는다.
- [ ] AC-2: 그렇게 작성된 링크가 깨진 링크로 렌더된다.
