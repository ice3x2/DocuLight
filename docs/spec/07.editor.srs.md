## 1. Scope Overview

이 scope 는 문서 본문을 사람이 직접 다루는 표면 — 편집기와 렌더러 — 을 규정한다. "옵시디언의 편집·열람 경험을 웹으로 옮긴다" 는 약속이 무엇으로 성립하는지(보기 · 라이브 편집 · 소스 편집 세 모드와 제목 줄 모드 아이콘 · 라이브 프리뷰 · 렌더 대상 요소), 그 표면이 권한·저장과 만나는 자리에서 어떻게 거동하는지(읽기 전용 눈 아이콘 · 저장 거부 뒤의 본문 보존 · 충돌 병합 화면), 그리고 이 경험의 Phase 경계가 어디인지를 담는다.

축은 **본문 영역 안**이다. 본문 영역 밖의 배치·패널·탭은 `SHELL` scope 가, 본문이 디스크에 앉는 방식은 `STORAGE` scope 가 갖는다.

## 2. Scope Boundaries

### In Scope

- 편집·렌더링 경험의 동형 요구 — 무엇을 옵시디언과 같게 만드는가 (`FR-EDITOR-001`)
- 단일 화면과 보기 · 라이브 편집 · 소스 편집 세 모드 — 제목 줄 모드 아이콘의 순환, 본문 우클릭 · 「더 보기(⋯)」의 모드 직접 선택, 권한과 개인 설정에 따른 기본 모드 (`FR-EDITOR-011`), 소스 편집의 원문 편집과 모드 전환의 본문 불변 (`FR-EDITOR-012`). 옛 상단 보기·편집 토글과 라이브 프리뷰·소스 하위 토글(`FR-EDITOR-002`·`FR-EDITOR-003`)은 2026-09-23 디자인 v2 로 폐기돼 이 두 요구로 대체됐다
- 라이브 프리뷰 대상 요소 아홉 가지의 정본 목록 (`FR-EDITOR-007`)
- 권한·저장 상태가 편집 표면에 나타나는 방식 — 보기 권한만 있을 때의 읽기 전용 눈 아이콘과 흐린 편집 항목, 저장 거부 뒤의 본문 보존과 로컬 내보내기, 비-md 파일에서의 모드 아이콘과 md 전용 메뉴 항목(모드 항목 · 편집 조작 · 버전 기록 보기) 숨김 (`FR-EDITOR-004`·`FR-EDITOR-005`·`FR-EDITOR-006`)
- 낙관적 저장이 충돌했을 때의 병합 화면과 그 진입·해소 (`FR-EDITOR-008`)
- 이 경험의 Phase 범위 선언 — Phase 1 범위와 링크 계열 네 항목, Phase 2 여섯 축, 데스크탑 전용과 모바일·태블릿 이관, 플러그인 시스템 제외 (`CON-EDITOR-001`~`CON-EDITOR-005`)

### Out of Scope

- 링크 계열 네 항목의 화면과 권한 필터 — 자동완성 후보를 포함한 표시 필터와 워크스페이스 경계를 넘는 인덱싱은 `WORKSPACE` scope 가, 백링크·아웃고잉 링크 패널과 태그 탭의 소재는 `SHELL` scope 가 소유한다. 이 scope 는 그 네 항목이 Phase 1 에 든다는 선언만 갖는다 (`CON-EDITOR-002` Implementation Notes).
- 위키링크의 해석 규칙과 본문에 삽입되는 링크 형식 — `STORAGE` scope 가 소유한다.
- 자동 저장의 트리거와 디바운스, 충돌 판정의 근거(읽은 시점의 내용 해시), 충돌 감지 시 자동 저장의 중단과 재개, 그리고 저장 거부 판정 자체 — `STORAGE` scope 가 소유한다. 이 scope 는 병합 화면과 거부 *이후*의 화면만 규정한다 (`FR-EDITOR-005`·`FR-EDITOR-008` Implementation Notes).
- 문서 탭의 거동 — 트리 클릭에 의한 활성 탭 자동 교체와 그 예외, 병합 해소 전 이탈 처리, 분할 창 도입 시 탭의 창별 귀속은 `SHELL` scope 의 탭 조항이 소유한다 (`FR-EDITOR-005`·`FR-EDITOR-008` Implementation Notes).
- 비-md 파일이 본문 영역에서 어떤 형태로 표시되는가 — 이미지 미리보기와 그 외 다운로드 링크의 갈래는 `ATTACH` scope 가 소유한다. 이 scope 는 모드 아이콘과 md 전용 메뉴 항목(모드 항목 · 편집 조작 · 버전 기록 보기)의 숨김만 규정한다 — 2026-09-23 모호성 해소 #29 로 모드 항목에서 넓어졌다 (`FR-EDITOR-006` Implementation Notes).
- 편집 유효 권한의 정의와 계산 — `ACL` scope 가 소유한다. `FR-EDITOR-004` 는 그 값을 화면에 반영하는 규칙만 갖고, 이 화면 규칙을 권한 강제의 수단으로 삼지 않는다.
- Phase 2 열거가 열린 목록이라는 판정 규칙 — `ARCH` scope 가 소유한다. `CON-EDITOR-003` 의 여섯 축은 그 목록의 한 부분이며 Phase 2 전량이 아니다 (`CON-EDITOR-003` Implementation Notes).
- `docs/spec/00.index.md` §3 Target Map 의 `phase-1` 기술 — 인덱스 문서가 소유한다. 원장이 아니다 (`CON-EDITOR-004` Implementation Notes).
- 제품이 하지 않기로 한 것 중 이 축에 걸리는 셋 — 플러그인 시스템 제외(R15) · Phase 2 여섯 축(R17) · 모바일·태블릿 이관(R31) — 은 다른 scope 로 위임되지 않는다. 이 scope 가 직접 소유하므로 In Scope 에 있다.

## 3. Assumptions and Constraints

- 문서 본문의 정본은 CodeMirror 이고 React state 로 올리지 않는다 — `ARCH` scope 가 소유하는 제약이다. 저장 거부와 병합 요구가 "편집 중이던 본문이 유실되지 않는다" 를 지킬 수 있는 근거가 그 구조이므로, 이 scope 의 요구를 구현하면서 그 구조를 깨면 요구가 함께 깨진다.
- 에디터·머지·마크다운 파이프라인의 패키지 선택은 `ARCH` scope 가 소유한다. `FR-EDITOR-008` 의 병합 화면은 그 목록에 든 `@codemirror/merge` 재활용을 전제한다.
- Phase 1 은 데스크탑 전용이다 (`CON-EDITOR-004`). 이 scope 의 화면 규정은 좁은 화면에서의 거동을 정하지 않는다.
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가 소유한다.
- 미결 두 건이 이 scope 에 걸려 있다 — `G30`(분할 창 pane 최소 폭) · `G31`(본문 `#태그` 의 렌더·클릭 수단과 프론트매터 태그의 노출 수단).

#### Requirement

플러그인 시스템은 제품 범위에서 제외한다. 서드파티 플러그인을 설치하거나 실행하는 수단을 제공하지 않으며, 옵시디언 동일성 판정에서도 플러그인으로만 제공되는 기능은 판정 대상이 아니다.

#### Rationale

웹 환경에서 서드파티 코드를 실행하려면 샌드박스와 보안 격리가 필요하고, 원장은 그 난이도를 검토 항목 중 최상위로 평가했다. 옵시디언과 동일한 경험을 요구하는 조항의 범위 경계를 이 조항이 위에서 닫는다 — 동일성 요구가 무한히 넓어지지 않도록 하는 세 경계(플러그인 제외 · Phase 1 범위 · Phase 2 범위) 중 첫 번째다.

#### Acceptance Criteria

- [ ] AC-1: 사용자 또는 관리자가 서드파티 플러그인을 설치·활성화할 수 있는 화면·API·설정 항목이 제품에 존재하지 않는다.
- [ ] AC-2: 옵시디언 동일성 판정에서 플러그인으로만 제공되는 기능은 판정 대상에서 제외된다.

#### Requirement

Phase 1 의 범위는 편집·렌더링 경험과 링크 계열로 한다. 링크 계열은 위키링크 `[[ ]]` 입력·자동완성, 백링크 패널, 아웃고잉 링크, 태그 네 가지다.

#### Rationale

#### Acceptance Criteria

- [x] AC-1: 위키링크 `[[ ]]` 입력과 자동완성이 Phase 1 산출물에 포함된다.

#### Implementation Notes

### FR-EDITOR-004 — 보기 권한만 있으면 모드 아이콘을 읽기 전용 눈 아이콘으로 노출한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | in_progress |
| Priority | medium |
| Tags | mode-toggle, permission-ui, design-v2 |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [셸 화면 설계](./03.screen-design-shell.md) |

#### Requirement

요청자가 그 md 문서에 보기 권한만 가진 경우, 모드 아이콘(`FR-EDITOR-011`)을 숨기지 않고 보기 모드의 눈 아이콘으로 노출한다(존재는 표시). 그 아이콘은 눌러도, `Ctrl+E` 를 눌러도 모드를 바꾸지 않으며 편집 모드로 진입할 수 없다. 아이콘에 마우스를 올리면 말풍선 「읽기 전용 문서입니다」를 보이고, 비활성 상태는 aria-disabled · 말풍선 문구 · 커서 모양으로 구별한다. 문서 헤더의 저장 상태 표시는 편집 권한이 있으면 모드와 관계없이 나타나고 보기 권한만 있으면 나타나지 않는다. 본문 위와 상태 바에는 권한 안내 문구를 두지 않는다. 비-md 파일에는 모드 아이콘과 md 전용 메뉴 항목이 없다(`FR-EDITOR-006`).

#### Rationale

감사 M3·M4 해소. 이 조항이 고르는 것은 "숨김"이 아니라 "비활성 노출"이다 — 그 문서가 보인다는 사실은 이미 요청자에게 드러나 있으므로 편집 토글을 지워도 감출 것이 없고, 지우면 편집이 애초에 불가능한 문서인지 내 권한이 모자란 것인지 구별되지 않는다.
- [2026-09-23] 디자인 v2 — 토글이 모드 아이콘으로 바뀌어도 「숨김이 아니라 비활성 노출」의 취지는 그대로다. 권한 때문에 편집할 수 없는 문서는 눈 아이콘과 「읽기 전용 문서입니다」를, 형식 때문에 편집할 수 없는 비-md 파일은 아이콘 없음(FR-EDITOR-006)을 보여 두 경우가 구별된다. 기각된 대안: 비활성 아이콘을 따로 그리는 것 — 사용자가 편집 가능한 보기 아이콘과 같은 모양·색을 지정했고, 비활성 구분은 aria-disabled·말풍선·커서로 한다(qna #4, IR-SHELL-006 AC-7).

#### Acceptance Criteria

- [ ] AC-1: 보기 권한만 있는 사용자에게 md 문서의 모드 아이콘이 보기 모드의 눈 아이콘으로 표시된다 — 비-md 파일에는 모드 아이콘이 없다(`FR-EDITOR-006` AC-2).
- [ ] AC-2: 그 사용자가 모드 아이콘을 누르거나 `Ctrl+E`(macOS 는 `Cmd+E`)를 눌러도 모드가 바뀌지 않고 편집 모드로 진입하지 않는다.
- [ ] AC-3: 그 아이콘에 마우스를 올리면 말풍선에 「읽기 전용 문서입니다」가 표시된다.
- [ ] AC-4: 그 아이콘은 `aria-disabled` 상태이고 보조 기술에 읽기 전용임을 알리는 이름을 가지며, 커서 모양과 마우스를 올렸을 때 배경이 생기지 않는 것으로 편집 가능한 보기 아이콘과 구별된다.
- [ ] AC-5: 보기 권한만 있는 문서에서는 저장 상태 표시가 나타나지 않는다.
- [ ] AC-6: 본문 위와 상태 바에 권한 안내 문구가 나타나지 않는다.
- [ ] AC-7: 보기 권한만 있는 md 문서의 본문 우클릭 메뉴와 「더 보기(⋯)」 메뉴에서 라이브 편집 · 소스 편집 항목과 잘라내기 · 붙여넣기 · 링크 삽입 항목은 숨겨지지 않고 흐리게 표시되며 「권한 없음」이 붙고, 눌러도 실행되지 않는다. 공유 항목은 요청자가 그 문서에 공유(권한 넓히기)를 실행할 수 없을 때 같은 방식으로 흐리게 표시되고 「권한 없음」이 붙으며 눌러도 실행되지 않는다 — 공유를 실행할 수 있는 권한의 판정은 `SEC-ACL-009` AC-1(원장 R70-a)이 소유하며 이 요구가 다시 정하지 않는다. 비-md 파일의 두 메뉴에서 빠지는 항목은 `FR-EDITOR-006` 이 정한다.
- [ ] AC-8: 편집 권한이 있는 md 문서에서는 모드와 관계없이(보기 모드 포함) 문서 헤더에 저장 상태 표시가 나타난다 — 읽기 전용 눈 아이콘(AC-1)과 편집 권한자의 보기 모드 눈 아이콘은 이 표시의 유무로도 구별된다.

#### Requirement

편집 중 권한 상실이나 충돌로 저장이 거부되면, 편집 중이던 본문을 되돌리거나 비우지 않고 화면에 그대로 보존하고, 그 본문을 로컬로 복사하거나 내려받을 수단을 함께 제공한다. 저장이 거부된 사실은 사용자에게 알린다.

#### Rationale

감사 M3·M4 해소. 저장이 거부된 순간 본문을 되돌리면 사용자가 방금 쓴 내용이 복구 불가능하게 사라진다 — 서버에 없고 화면에도 없기 때문이다. 이 부작용은 원장에서 다른 조항들의 확인 등급을 올리는 근거로 반복 인용된다(상속 끊기 · 접근 범위가 좁아지는 이동 · 컨테이너 항목 회수는 모두 "권한을 잃은 편집자의 저장이 거부되어 본문이 유실된다"는 이유로 등급이 올라갔다). 그래서 이 요구가 무너지면 그 등급 배정들의 근거도 함께 무너진다.

#### Acceptance Criteria

- [x] AC-1: 저장이 거부된 뒤에도 편집 중이던 본문이 화면에 그대로 남아 있다.
- [x] AC-2: 저장이 거부된 상태에서 편집 중이던 본문을 로컬 파일로 내려받을 수 있다.
- [x] AC-3: 저장이 거부된 사실이 사용자에게 표시된다.

#### Requirement

비-md 파일은 본문 영역에서 열리되, 모드 아이콘(`FR-EDITOR-011`)은 md 문서에서만 노출하고 비-md 파일에서는 숨긴다. 비-md 파일의 「더 보기(⋯)」 메뉴와 본문 우클릭 메뉴에는 보기 · 라이브 편집 · 소스 편집 항목, 편집 조작(잘라내기 · 붙여넣기 · 링크 삽입), 버전 기록 보기가 나타나지 않는다.

#### Rationale

감사 M3·M4 해소. 보기 권한만 있는 md 문서에서 토글을 비활성으로 남겨 두는 것과 갈린다 — 거기서는 권한만 얻으면 켜지지만, 비-md 파일에는 켜질 편집 모드 자체가 없다. 비활성으로 남기면 언젠가 켜질 수 있는 것처럼 읽힌다.
- [2026-09-23] 디자인 v2 — 숨길 대상이 모드 아이콘으로 바뀌었다. 권한 때문에 편집할 수 없는 문서(눈 아이콘과 「읽기 전용 문서입니다」, FR-EDITOR-004)와 형식 때문에 편집할 수 없는 비-md 파일(아이콘 없음)이 화면에서 구별된다. 이 구별은 사용자 결정이 아니라 기존 요구에서 끌어낸 것이다(결정 기록 편집 모드 절). ⋯·우클릭 메뉴의 모드 항목도 같은 이유로 숨긴다(qna #5) — 흐리게 남기면 언젠가 켜질 수 있는 것처럼 읽힌다.
- [2026-09-23] 2차 검증 반영(qna #29): 비-md 파일의 두 메뉴에서 모드 항목 말고도 편집 조작(잘라내기 · 붙여넣기 · 링크 삽입)과 버전 기록 보기가 빠진다(AC-4 · AC-5). 편집 조작은 v2 에서 새로 든 항목이라 「나머지는 기존 규칙」(qna #5)으로는 판정이 서지 않았다. 비-md 파일에는 편집할 본문이 없고, 버전 기록은 원장 R24-b 비고 · R63 과 설계서 03 §3.3 이 이미 md 로 한정한다. 이 요구가 비-md 메뉴 규칙을 한 곳에 갖고, FR-EDITOR-011 의 메뉴 AC 는 md 문서로 한정한다.

#### Requirement

라이브 프리뷰의 대상 요소는 헤딩 · 강조 · 목록 · 링크 · 인용 · 코드블록 · 표 · 수식 · Mermaid · 태그 열 가지다. 커서가 없는 줄에서는 각 요소의 마크다운 기호를 숨기고, 그 줄에 커서를 올리면 원문을 드러낸다. 태그는 `G31` 판정으로 열 번째로 들어왔다 — Phase 1 범위 선언이 태그를 링크 계열에 넣었고 우측 태그 탭이 전역 색인으로 확정되면서 본문 쪽 진입점이 비었으므로, 태그의 부재는 의도적 배제가 아니라 누락이었다. 프론트매터의 태그는 이 목록에 들어오지 않는다 — 프로퍼티 패널이 Phase 2 이고, 본문 문법이 아닌 것을 본문 데코레이션이 건드리면 그 자리의 소유가 두 곳으로 갈린다.

#### Rationale

이 목록이 라이브 프리뷰 대상의 정본이다. 2026-08-11 에 이 항목이 신설되면서 §4 Phase 1 수용 기준 2 의 목록과 일원화됐고(감사 L2 해소), 이중 관리를 피하기 위해 정본을 여기 두고 수용 기준은 이 항목을 참조한다 — 수용 기준이 목록을 스스로 열거하지 않는 이유가 그것이다. 정본을 한 곳에 두는 이유는 원장이 겪은 정합성 결함의 대다수가 "본문은 개정했는데 파생 표만 옛 문언으로 남는" 유형이었기 때문이다. 따라서 이 목록을 바꾸는 개정은 여기서 시작해야 하고, 수용 기준 2 를 고쳐서 시작해서는 안 된다.

#### Requirement

자동 저장과 명시 저장은 편집기의 포커스와 커서 위치를 그대로 둔다. 저장이 끝난 직후에 이어 친 글자는 문서에 들어가며, 사용자가 편집기를 다시 눌러야 입력이 이어지는 일이 없다. 저장이 거절되거나 충돌한 경우도 같다.

#### Rationale

2026-08-24 실제 볼트 검증에서 관측된 결함이 이 요구의 근거다. 자동 저장이 성공한 직후 `document.activeElement` 가 편집기에서 빠졌고, 그 뒤에 친 글자는 문서에도 디스크에도 들어가지 않은 채 사라졌다. 사용자는 글자가 사라진 것을 뒤늦게 알아차리며 그 사이의 입력을 되찾을 수 없다. 자동 저장은 사용자가 부르지 않은 조작이므로 그 부작용이 입력 유실이면 자동이라는 성질 자체가 해가 된다. 이 축을 금지하는 조항이 지금까지 없었다 — `FR-EDITOR-001` AC-2 는 「편집이 저장된다」까지만 요구하고 그 저장이 무엇을 건드리는지는 정하지 않아, 그 회차도 AC-2 는 통과로 판정했다. `CON-ARCH-006` 이 본문 정본을 CodeMirror 에 두는 이유로 든 것이 「매 입력마다 React 렌더가 개입해 커서가 튄다」인데, 저장 뒤 포커스 유실은 같은 계열의 남은 자리다.

#### Acceptance Criteria

- [x] AC-1: 자동 저장이 끝난 뒤에도 포커스가 편집기에 남는다.
- [x] AC-2: 저장 직후에 이어 친 글자가 문서에 들어간다.
- [x] AC-3: 저장이 커서 위치를 바꾸지 않는다.
- [x] AC-4: 저장이 거절되거나 충돌해도 포커스와 커서가 그대로다.

### IR-EDITOR-001 — 편집기 스타일시트는 데모가 아니라 제품 화면에 닿는다

| Field | Value |

#### Requirement

편집기가 만드는 데코레이션과 위젯의 스타일시트는 편집기를 쓰는 제품 화면에서 실제로 적용된다. 데모가 자기 진입점에서 그 스타일을 얹는 것으로는 이 요구가 성립하지 않는다 — 데모와 제품이 서로 다른 진입점을 갖는 한, 데모에서 통과한 화면 판정이 제품에서 참이라는 보장이 없다.

#### Rationale

부품이 있는 것과 제품에 붙은 것은 다르다. 이 저장소는 같은 부류를 이미 한 번 겪었다 — 설치 서비스와 관문이 모두 있었으나 어느 것도 운영 조립에 들어가 있지 않아 새 인스턴스가 최초 슈퍼유저를 만들 수 없었다. 그때 세운 대책이 진입점 도달 가능성을 재는 조립 방벽이며, 스타일시트도 같은 축의 조립물이다.

#### Acceptance Criteria

- [x] AC-1: 제품 화면에서 본문 태그가 칩으로 보인다 — 계산된 배경과 테두리 반경이 기본값이 아니다.
- [x] AC-2: 제품 화면에 편집기가 내보내는 스타일시트의 규칙이 실제로 실려 있다 — 데코레이션 클래스를 받는 규칙이 0건인 상태를 두지 않는다.
- [x] AC-3: 데모와 제품이 같은 스타일 진입점을 쓴다 — 한쪽에만 얹혀 다른 쪽이 조용히 어긋나는 구조를 두지 않는다.
- [x] AC-4: 이 축이 제품 화면을 재는 브라우저 검사로 확인된다 — 데모를 재는 검사만으로는 이 요구가 닫히지 않는다.

#### Requirement

제품과 데모는 공통 편집기 스타일 진입점을 사용하고, 보기 · 라이브 편집 · 소스 편집 · 비교 화면은 앱 테마(테마와 사용자별 기본 색상)를 따른다. 편집기의 서체는 제품 화면의 서체 규칙(`IR-SHELL-006`)을 따른다. 테마 변경은 편집 동작과 위젯 좌표를 보존한다.

#### Rationale

디자인 v2 결정(2026-09-23)의 서체 절이 신문지 테마의 명조체 제목을 버리고 화면 전체를 나눔고딕 하나로 통일했으며, 고정폭이 필요한 값에만 나눔고딕코딩을 쓰고 크기 단계를 12 · 13 · 14 · 16 · 21 · 30px 로 정했다. 본문은 16px · 행간 1.75, 제목은 36 → 30px, H2 는 24 → 21px 로 바뀌었다. 결정 기록이 SRS 반영 때 정하라고 남긴 H3 · 인용의 크기는 qna #1 이 그 단계 안에서 닫았다(H3 16px ExtraBold, 인용은 본문과 같은 16px) — 시안에서 14px 로 그려지는 인용은 시안의 결함으로 본다. 읽기 폭은 시안의 700px(좌우 40px 포함, 본문 620px)로 바꿨다.

이 요구는 편집기 콘텐츠에만 적용되는 치수를 갖고, 서체 자체의 규칙(나눔고딕 · 나눔고딕코딩 · 크기 단계)은 제품 화면 전체의 시각 계약 `IR-SHELL-006` 이 소유한다 — 두 곳에 같은 서체 규칙을 적으면 한쪽만 고쳐진다.

#### Acceptance Criteria

- [ ] AC-1: 보기와 라이브 편집의 본문은 16px · 행간 1.75 이고, 제목(H1) 30px, H2 21px, H3 16px ExtraBold, 인용 16px 이다. 소스 편집 · 코드 · PAT 는 14px 이고 소스 편집의 행간은 1.8 이며, 서체는 `IR-SHELL-006` AC-12 를 따른다. 읽기 최대 폭은 좌우 여백 40px 를 포함한 700px(본문 620px)이고 좁은 데스크탑의 좌우 여백은 24px 이며, 긴 한글 제목을 자르지 않는다.
- [ ] AC-2: 앱 의미 토큰을 editor integration 계층에서 편집기 변수와 CodeMirror 테마에 연결한다. 보기 · 라이브 편집 · 소스 편집 · 본문 검색 · 선택 · 커서 · 열린 비교 화면의 실제 계산 스타일이 테마(밝게 · 어둡게) 변경과 기본 색상 변경을 따른다.
- [ ] AC-3: 코드·표는 자기 영역 안에서 가로 스크롤하고 앱 폭을 밀지 않는다. 기존 라이브 프리뷰 10요소와 KaTeX 스타일을 유지하며 구문 강조·태그·인용·링크·Mermaid도 테마별 읽을 수 있는 색을 쓴다.
- [ ] AC-4: Mermaid 테마 변경은 렌더 캐시를 구분하거나 갱신해 기존 다이어그램에 적용한다. 수식·다이어그램 오류에는 원문을 확인할 경로가 있다. 비교·병합 추가/삭제는 색 외에도 기호 또는 라벨로 구분한다.

### FR-EDITOR-011 — 제목 줄 모드 아이콘의 세 모드 순환과 권한에 따른 기본 모드

#### Requirement

문서 화면은 하나이며 보기 · 라이브 편집 · 소스 편집 세 모드를 갖는다. 이 요구의 모드 규칙은 md 문서에 적용하며, 비-md 파일의 모드 아이콘과 두 메뉴의 항목은 `FR-EDITOR-006` 이 정한다. 문서는 요청자에게 편집 권한이 있으면 편집 모드로, 없으면 보기로 열고, 이 규칙은 트리 클릭 · 새 탭으로 열기 · 백링크 · 딥링크 등 이미 있는 문서를 여는 모든 경로에 같게 적용한다. 편집 모드로 열 때 어느 모드로 여는지와 권한과 무관하게 보기로 열지는 개인 설정(`IR-SHELL-004`)이 정하며, 두 설정이 기본값이면 편집 권한이 있는 문서는 라이브 편집으로 열린다. 편집 권한이 있는 사용자가 새로 만든 노트는 기본 열람 모드와 관계없이 편집 모드로 열며, 라이브 편집과 소스 편집 중 어느 쪽인지는 개인 설정 「편집으로 열 때의 모드」가 정한다. 모드는 문서 제목 줄 오른쪽의 모드 아이콘 하나로 바꾼다 — 아이콘은 지금 모드를 눈(보기) · 연필(라이브 편집) · `</>`(소스 편집) 모양으로 나타내고, 아이콘을 누르거나 `Ctrl+E`(macOS 는 `Cmd+E`)를 누르면 보기 → 라이브 편집 → 소스 편집 → 보기 순서로 바뀐다. 문서 본문 우클릭과 제목 줄의 「더 보기(⋯)」는 세 모드 중 하나를 바로 고르는 메뉴를 열며, 그 메뉴로 모드를 바꾸는 것도 편집 권한이 있을 때뿐이다(편집 권한이 없을 때의 메뉴 표시는 `FR-EDITOR-004`). 머지 뷰(`FR-EDITOR-008`)를 보는 동안에는 모드 아이콘 · `Ctrl+E` · 메뉴의 모드 항목이 모두 꺼진다. 상단 보기·편집 토글과 라이브·소스 하위 토글은 두지 않으며, 1.0 의 「업로드 모드 / 뷰어 모드」 분리도 두지 않는다.

#### Rationale

디자인 v2 결정(2026-09-23, `docs/decision/design-v2.md` 편집 모드 절)이 확정한 편집 모드 규칙이다. 기본 모드는 사용자 결정 1(개인 설정 「기본 열람 모드」를 남기고 기본값을 「권한에 따라」로)과 결정 5(「권한이 있으면 라이브 편집, 없으면 보기」를 문서를 여는 모든 경로에 같게)에서 왔고, 전환 수단(모드 아이콘 순환 · `Ctrl+E` · 우클릭과 ⋯ 메뉴의 직접 선택)은 결정 기록의 편집 모드 절이 정했다. 설정 두 항목의 값 집합(`권한에 따라` · `항상 보기`, `라이브 편집` · `소스 편집`)은 qna #3 이 닫았다.

이 요구는 `FR-EDITOR-002`(단일 화면과 상단 보기·편집 토글)와 `FR-EDITOR-003`(라이브 프리뷰·소스 하위 토글)의 전환 메커니즘을 대체한다 — 두 요구의 Requirement 문장이 명시한 전환 수단 자체가 없어지므로 같은 요구의 문면 수정이 아니다(규칙 §11.4 · §29.3). v2 가 바꾸지 않은 사실 중 단일 화면과 1.0 모드 분리 폐기는 이 요구의 Requirement 문장과 AC-13 으로 옮겼고, 소스 모드의 원문 편집과 전환의 본문 보존은 `FR-EDITOR-012` 가 잇는다. 전환 UI 와 본문 보존은 재는 대상이 달라 한 요구에 모으지 않았다.

기각된 대안 — 모든 경로에서 보기로 여는 기존 설계(`03.screen-design-shell.md` §3.2.3 · §11-11). 그 근거는 틀렸을 때의 대가 비대칭(편집으로 잘못 열면 무버튼 자동 저장이 켜진 화면이다 — 원장 `R152`)이었다. 사용자가 결정 1 로 기본값을 뒤집었고, 그 수요는 「항상 보기」 설정값(AC-4)으로 남았다. 이 판단을 다시 열려면 사용자 결정 1 · 5 를 먼저 다시 열어야 한다.
- [2026-09-23] 보충: 대체된 FR-EDITOR-002 의 옛 AC-1(같은 화면에서 전환)은 AC-14 가, 옛 AC-2(1.0 모드 분리 폐기)는 AC-13 이 잇는다. AC-15 는 결정 기록 편집 모드 절이 읽기 전용일 때 흐리게 둔다고 한 편집 항목이 편집 권한과 편집 모드에서는 활성이라는 반대쪽을 적은 것이다 — 보기 모드에서의 활성 여부는 결정 기록이 정하지 않았다.

#### Implementation Notes

- ① 문서를 여는 경로(트리 클릭 · 딥링크 · 충돌 뒤 재개 등)는 `packages/web/src/App.tsx` 의 `toTab(node)` 한 지점을 지나고 그 결과에 이미 `node.level` 이 실려 있다(2026-09-23 조사 — 정의 139-145행, 호출 385 · 1197 · 1386행). 기본 모드는 그 한 지점에서 정하라. 경로마다 따로 정하면 AC-3 이 깨진다.
- ② 지금 「언제나 보기로 연다」가 성립하는 원인은 `DocumentSurface.tsx` 의 `initialMode` 기본값 `'read'` 와, `DocumentArea.tsx` 가 `<DocumentSurface>` 에 `initialMode` 를 넘기지 않는 것이다(2026-09-23 조사).
- ③ `packages/web/src/document/surface-contract.ts` 의 `nextMode(from, to, { canEdit })` 는 `to` 를 받아 되돌릴 뿐 순환 순서를 갖지 않는다. 순환 순서는 그 계약 파일 한 곳에 두고 아이콘 클릭과 `Ctrl+E` 가 같은 함수를 부르게 하라 — 두 진입점이 각자 순서를 가지면 한쪽만 고쳐진다.
- ④ `Ctrl+E` 전역 키 처리기는 저장소에 없다(`App.tsx` 에 keydown 처리기가 없고, `DocumentSurface.tsx` 의 전역 keydown 은 `Ctrl+S` 하나다). 브라우저가 이 조합에 기본 동작을 두는지는 이 조사에서 재지 않았다 — 실제 브라우저에서 기본 동작이 막히는지 확인하라.
- ⑤ 본문 영역(`DocumentSurface.tsx` 의 `[role='region']`)에 `onContextMenu` 처리기가 없다. 우클릭 메뉴와 ⋯ 메뉴는 같은 항목 배열(`document-menu.ts` 의 `DOCUMENT_MENU_ITEMS`)을 그려야 한다 — 두 메뉴가 각자 목록을 가지면 한쪽에만 항목이 생긴다.
- ⑥ 없앨 UI 는 `DocumentSurface.tsx` 의 `ModeToggle`(상단 2단 토글과 하위 토글)이다. 그 안의 `aria-disabled` 관례는 읽기 전용 눈 아이콘(`FR-EDITOR-004`)이 그대로 잇는다.
- ⑦ `packages/web/test/document-surface.test.tsx` 와 `surface-gaps.test.tsx` 는 대체된 두 요구의 토글 구조를 고정 단언한다. TDD 로 이 요구의 시험을 먼저 세운 뒤 그 단언을 옮겨라 — 옛 단언을 지워 green 을 만들지 마라.
- ⑧ 기본 모드가 소비하는 편집 유효 권한의 정의와 계산은 `ACL` scope 가 소유한다(이 문서 §2 Out of Scope). 이 요구는 그 값을 읽기만 하며, 화면의 모드 판정을 권한 강제의 수단으로 삼지 않는다 — 저장 거부는 서버가 판정한다.
- ⑨ 설계서 `03.screen-design-shell.md` §3.4 의 두 조항(머지 뷰가 열린 동안 토글 비활성, 편집 진입 때 스냅샷 1회)은 이 요구에 넣지 않았다. 결정 기록이 두 조항의 v2 형태를 정하지 않았다.
- [2026-09-23] ⑨ 정정: ⑨ 가 넣지 않았다고 적은 두 조항 가운데 스냅샷 시점은 qna #20 이 닫았다 — 편집 세션의 버전 스냅샷은 문서를 연 때가 아니라 그 세션의 첫 저장 때 한 번 찍는다. 편집 권한자가 문서를 라이브 편집으로 열기만 하고 저장하지 않으면 스냅샷이 생기지 않는다. 그 규칙은 FR-STORAGE-003 이 소유하며(AC-6) 이 요구는 참조만 한다. 현재 구현(useAutosave)도 첫 저장에서 세션을 연다. 머지 뷰가 열린 동안의 모드 전환 비활성은 여전히 결정 기록 밖이다.
- [2026-09-23] ⑨ 재정정: 남아 있던 머지 뷰 조항은 qna #30 이 닫았다 — 머지 뷰(FR-EDITOR-008)를 보는 동안 모드 아이콘 · Ctrl+E · 두 메뉴의 모드 항목을 모두 끈다(AC-17). 세 수단이 ③ · ⑤ 의 한 순환 함수와 한 항목 배열을 지나므로 끄는 판정도 그 한 곳에 두라. ⑩ 새로 만든 노트(AC-18)도 ① 의 한 지점에서 판정하되 「새로 만든 노트인가」를 입력으로 받아라 — 새 노트 경로만 따로 모드를 정하면 판정이 두 곳이 된다. qna #36 은 라이브 편집만 적었고 편집으로 열 때의 모드가 소스 편집인 사용자는 따로 말하지 않았다.
- [2026-09-23] ⑩ 정정(qna #39): ⑩ 끝의 「qna #36 은 라이브 편집만 적었고 … 따로 말하지 않았다」는 qna #39 로 닫혔다 — 새 노트는 기본 열람 모드만 건너뛰고, 어느 편집 모드인지는 AC-5 와 같은 「편집으로 열 때의 모드」 판정을 그대로 쓴다. ① 의 한 지점이 「새로 만든 노트인가」를 받으면 기본 열람 모드 판정만 건너뛰고 편집 하위 모드 판정은 이미 있는 문서와 같은 코드를 지나게 하라 — 새 노트용 모드 값을 따로 두면 설정과 갈린다.

### FR-EDITOR-012 — 소스 편집 모드는 원문을 그대로 편집하고 모드 전환은 본문을 바꾸지 않는다

#### Requirement

보기 · 라이브 편집 · 소스 편집 세 모드(`FR-EDITOR-011`) 가운데 소스 편집은 Phase 1 에 포함하며, 라이브 편집에서 화면에서 사라지는 원문(표 구분선 · 각주 정의 등)을 그대로 보이고 편집하게 한다. 모드 사이의 전환은 문서 본문을 바꾸지 않으며, 전환 직전까지 입력한 글자를 잃지 않는다.

#### Rationale

감사 M1 해소에서 온 조항이다(원래 `FR-EDITOR-003`). 라이브 편집에서는 표 구분선 · 각주 정의 같은 원문이 화면에서 사라지는데, 소스 모드가 없으면 그 원문을 고칠 수단이 제품에 없다. 비용도 근거였다 — CodeMirror 6 데코레이션을 끄는 것으로 족해 추가 비용이 미미하다.

디자인 v2 결정(2026-09-23)이 라이브 프리뷰↔소스 하위 토글을 없애고 세 모드 순환(`FR-EDITOR-011`)에 합치면서 `FR-EDITOR-003` 의 전환 수단이 사라졌다. 전환 수단은 `FR-EDITOR-011` 이 갖고, 이 요구는 v2 가 바꾸지 않은 두 사실 — 소스 모드의 Phase 1 포함과 원문 편집(옛 AC-2), 전환의 본문 보존(옛 AC-3) — 만 잇는다. 전환 UI(아이콘 · 단축키 · 메뉴 · 기본 모드)와 본문 보존은 재는 대상이 달라 `FR-EDITOR-011` 과 나눴다.

#### Acceptance Criteria

- [ ] AC-1: 소스 편집 모드에서 표 구분선과 각주 정의가 원문 그대로 보이고 편집할 수 있다.
- [ ] AC-2: 모드 전환은 문서 본문을 바꾸지 않는다.
- [ ] AC-3: 모드 전환 직전까지 입력한 글자가 전환 뒤에도 남아 있다 — 전환이 편집기를 다시 세워 입력을 잃지 않는다.
