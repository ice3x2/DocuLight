### CON-EDITOR-001 — 플러그인 시스템을 범위에서 제외한다

#### Requirement

플러그인 시스템은 제품 범위에서 제외한다. 서드파티 플러그인을 설치하거나 실행하는 수단을 제공하지 않으며, 옵시디언 동일성 판정에서도 플러그인으로만 제공되는 기능은 판정 대상이 아니다.

#### Rationale

웹 환경에서 서드파티 코드를 실행하려면 샌드박스와 보안 격리가 필요하고, 원장은 그 난이도를 검토 항목 중 최상위로 평가했다. 옵시디언과 동일한 경험을 요구하는 조항의 범위 경계를 이 조항이 위에서 닫는다 — 동일성 요구가 무한히 넓어지지 않도록 하는 세 경계(플러그인 제외 · Phase 1 범위 · Phase 2 범위) 중 첫 번째다.

#### Acceptance Criteria

- [ ] AC-1: 사용자 또는 관리자가 서드파티 플러그인을 설치·활성화할 수 있는 화면·API·설정 항목이 제품에 존재하지 않는다.
- [ ] AC-2: 옵시디언 동일성 판정에서 플러그인으로만 제공되는 기능은 판정 대상에서 제외된다.

### CON-EDITOR-002 — Phase 1 범위는 편집·렌더링 경험과 링크 계열이다

#### Requirement

Phase 1 의 범위는 편집·렌더링 경험과 링크 계열로 한다. 링크 계열은 위키링크 `[[ ]]` 입력·자동완성, 백링크 패널, 아웃고잉 링크, 태그 네 가지다.

#### Rationale

제품의 차별점(문서/디렉토리 단위 권한 관리)을 얹기 전에, "옵시디언을 웹으로 옮긴다"는 약속이 성립하는 최소 표면을 Phase 1 으로 고정한다. 라이브 프리뷰의 대상 요소 목록은 이 조항에서 분리해 별도 조항이 정본으로 보유한다 — 목록이 두 곳에 있으면 한쪽만 개정되기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 위키링크 `[[ ]]` 입력과 자동완성이 Phase 1 산출물에 포함된다.
- [ ] AC-2: 백링크 패널이 Phase 1 산출물에 포함된다.
- [ ] AC-3: 아웃고잉 링크 표시가 Phase 1 산출물에 포함된다.
- [ ] AC-4: 태그가 Phase 1 산출물에 포함된다.

#### Requirement

그래프뷰, 커맨드 팔레트, 퀵스위처, 분할 창, 아웃라인, 프론트매터 프로퍼티 여섯 축은 Phase 2 에 둔다. Phase 1 산출물에는 포함하지 않는다.

#### Rationale

Phase 2 조항은 「큰 축」의 정의이며 화면 설계가 아니다. 여섯 축의 설계는 Phase 1 이 끝난 뒤 시작하므로, 이 요구는 축의 존재와 Phase 1 제외만 확정하고 각 축의 동작을 규정하지 않는다.

#### Acceptance Criteria

- [ ] AC-1: Phase 1 종료 판정 시 이 여섯 축의 기능이 산출물에 포함되어 있지 않다.
- [ ] AC-2: Phase 1 화면에 이 여섯 축의 진입점(메뉴·버튼·단축키 배정)이 존재하지 않는다.

- 두 축에 미결이 붙어 있다. ① 분할 창 — pane 최소 폭이 규정되어 있지 않다(`G30`). 중앙 본문 최소가 480px 인데 분할하면 pane 이 240px 이 되고, 편집 모드 헤더의 축약 불가 블록이 좌우 패딩 포함 247px 이라 7px 부족하다. 또한 분할 창을 도입할 때 문서 탭이 창별로 귀속되도록 설계해야 한다(셸 scope 의 탭 조항). ② 프론트매터 프로퍼티 — 이 축이 Phase 2 로 미뤄졌고 라이브 프리뷰 대상 목록에도 프론트매터가 없어, Phase 1 에서 프론트매터 태그의 노출 수단이 규정되지 않았다(`G31` 후단). 이 열거는 Phase 2 의 전량이 아니다 — Phase 2 열거는 열린 목록이며 그 규칙은 아키텍처 scope 가 소유한다.

#### Requirement

UI 는 옵시디언을 웹으로 옮긴 형태로 만든다. 에디터의 동작과 마크다운 렌더링 결과가 옵시디언과 동일해야 한다.

#### Rationale

제품 정의가 "옵시디언의 편집·열람 경험을 웹으로 옮기고 문서/디렉토리 단위 권한 관리를 더한다"이므로, 편집·렌더링의 동일성은 제품이 성립하기 위한 전제다. 옵시디언 대비 차별점은 권한 관리 하나로 요약되며 나머지는 같아야 한다는 것이 이 조항의 취지다.

#### Acceptance Criteria

- [ ] AC-1: 실제 옵시디언 볼트를 기본 워크스페이스에 그대로 넣었을 때 브라우저에서 그 볼트의 문서를 읽을 수 있다.
- [ ] AC-2: 같은 볼트의 문서를 브라우저에서 편집할 수 있다.

#### Implementation Notes

- ① 동일성의 판정 축(픽셀 단위인지 기능 단위인지)을 원장이 정하지 않았다. §4 수용 기준 1 이 이 요구의 유일한 관문이고 그 문면은 "읽기와 편집이 모두 동작한다"이므로, 판정 범위를 그것으로 한정한다. ② 이 요구를 개별 화면 결정을 뒤집는 만능 근거로 쓰지 마라 — 2026-08-18 실측 심의에서, 이 조항을 겨눈 전복 조건이 "이 조항이 그 자리를 지배하지 않는다"는 이유로 무효 판정을 받았다. 화면의 개별 배치는 그 화면을 소유한 조항이 정한다. ③ 동일성 요구의 상한은 세 범위 경계(플러그인 제외 · Phase 1 범위 · Phase 2 축)가 닫는다.

#### Requirement

문서 편집에 잠금을 두지 않는다. 편집 권한이 있는 사용자는 누구나 같은 문서를 동시에 편집할 수 있고, 저장 시점에 원본이 변경되어 있으면 병합 화면을 띄워 사용자가 해소하게 한다.

#### Rationale

낙관적 방식이라 편집을 시작하는 데 조율이 필요 없고 실제로 부딪힌 경우에만 비용을 낸다. 기각된 대안 — 실시간 협업(WebSocket · CRDT). 서버는 REST 를 유지한다. 병합 UI 는 `@codemirror/merge` 이식 자산을 재활용하며 버전 비교·복원 UI 와 같은 컴포넌트다 — 새 자산을 들이지 않는 것이 이 선택의 비용 근거다.

#### Acceptance Criteria

- [ ] AC-1: 두 사용자가 같은 문서를 동시에 편집 모드로 열 수 있고, 어느 쪽도 잠금으로 차단되지 않는다.
- [ ] AC-2: 두 세션이 같은 문서를 편집·저장하면 나중에 저장하는 세션에 병합 화면이 뜬다.
- [ ] AC-3: 병합 화면에서 서버의 현재 내용과 사용자의 편집 내용을 나란히 대조할 수 있다.
- [ ] AC-4: 사용자가 병합을 해소하고 저장하면 그 결과가 문서에 반영된다.
