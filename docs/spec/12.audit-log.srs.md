#### Requirement

제품은 관리 조작의 이력을 남기는 감사 로그 audit_log 를 둔다. 감사 행의 칸 구성 정본은 R140 이 정의하며 이 요구사항은 다시 적지 않는다. 기록 대상 판정의 정본은 R137 의 기준이고, R84 가 열거한 8개 조작(ACL 부여·회수 · 상속 끊기·되돌리기 · 그룹 멤버십 변경 · PAT 발급·폐기 · 계정 상태 전환 · 영구 삭제 · 아카이브·복원 · 관리 권한에 의한 열람)은 규범이 아니라 그 기준의 예시다.

#### Rationale

감사 H8 해소. R14-c 의 감사·역질의 근거와 R70-d·R71-b 가 전제하는 이력의 실체다. 개정 전에는 열거가 곧 규범이라 조작이 늘 때마다 낡았다. R137-b 의 자기 검증으로 기존 열거와 기존 제외(일반 문서 열람)가 새 기준에서 그대로 재도출되었으므로, 이 개정은 열거 교체가 아니라 지위 강등 + 누락분 추가로 끝난다.

#### Acceptance Criteria

- [ ] AC-1: 감사 로그 저장소 audit_log 가 존재하고 기록된 행을 조회할 수 있다.
- [ ] AC-2: R84 가 열거한 8개 조작이 각각 감사 행을 1건 이상 남긴다.
- [ ] AC-3: 8개 조작 각각이 R137 기준 ①②③ 중 최소 하나에 걸린다는 판정이 남고, 어느 기준에도 걸리지 않는 항목이 0개다.
- [ ] AC-4: 기록 대상 여부를 판정하는 코드·화면·필터가 그 8개 열거를 고정 목록으로 참조하지 않는다.
- [ ] AC-5: 감사 행의 칸 구성이 R140 이 정의한 것과 일치하고 이 요구사항이 별도의 칸을 정의하지 않는다.

### OBS-AUDIT-002 — 감사 로그의 불변성과 보존 기간

| Field | Value |

| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md) |

#### Requirement

감사 로그의 행은 기록된 뒤 수정할 수 없고 삭제할 수 없다. 감사 로그의 보존 기간은 인스턴스 설정에서 지정한다. 보존 기간의 기본값, 휴지통 보존 기간(R86)과의 대소 관계, 값 0 의 의미는 원장이 정하지 않았으므로 그 축이 닫히기 전까지 이 요구사항은 진행할 수 없다.

#### Rationale

불변성은 다른 조항 여럿이 딛고 선 전제다 — R137-g 가 든 복구 재료(R43-1 이 그 ACL 을 지워도 부여 이벤트는 살아남는다)와 R142-a 가 다건 회수를 허용하며 든 재부여로 복구된다(R134-b)가 모두 이 불변성 위에 있다. 보존 기간을 설정으로 여는 것은 R115-e 가 보존 기간 축소에 확인 등급 L3 를 배정하면서 이미 전제한 것이다.

#### Acceptance Criteria

- [ ] AC-1: 기록된 감사 행의 값을 바꾸는 경로가 화면·API·내보내기·관리 도구 어느 곳에도 없다.
- [ ] AC-2: 기록된 감사 행을 개별로 삭제하는 경로가 화면·API·관리 도구 어느 곳에도 없다.
- [ ] AC-3: 감사 로그 보존 기간을 인스턴스 설정 화면에서 지정할 수 있다.

#### Implementation Notes

- 보존 기간의 세 축이 G27 로 미결이다 — ① 기본값이 없다. R86 은 휴지통 기본 30일을 명시하는데 대응 문장이 없다 ② 휴지통 보존과의 대소 관계가 없다. 감사 보존이 더 짧으면 삭제 기록이 휴지통보다 먼저 사라지는 역전이 생기고, R137-d 로 삭제를 기록 대상에 넣었으므로 실제 문제가 된다 ③ 값 0 의 의미(무제한인지 즉시인지)가 없다. R86 은 휴지통에 대해 0 은 무제한이라고 명시했다. 역질의 자체가 이 보존 기간에 종속된다 — 이 사용자가 이 노드의 권한을 언제 잃었나 의 답은 부여 행과 회수 행의 생존에 달려 있고, 오프보딩 조사는 수개월 뒤 시작된다. 그러므로 이 공백이 열려 있는 동안 R141·R142-a 의 근거는 조건부다. 보존 기간 만료에 따른 자동 소멸은 이 조항의 수정·삭제 금지에 걸리지 않는다 — 금지 대상은 개별 행에 대한 조작이다. 불변성 축 자체는 미결에 걸리지 않으므로 blocked 는 보존 기간 축에서만 발생한다. 우선순위는 원장이 배정한 바 없다.

### OBS-AUDIT-003 — 감사 로그의 기록 대상은 열거가 아니라 기준으로 정한다

| Field | Value |
| --- | --- |
| Type | observability |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | audit-log, recording-criteria |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md) |

#### Requirement

감사 로그의 기록 대상은 조작 열거가 아니라 다음 기준으로 판정한다. 다음 중 하나라도 참이면 기록한다 — ① 노드의 존재·위치·본문이 바뀐다 ② 누가 그 노드에 도달하는가가 바뀐다 ③ R71 상방 게이트로 판정을 우회해 접근한다. 순수 읽기는 기록하지 않는다.

#### Rationale

패널 2:0. 개정 전 R84 는 열거가 곧 규범이라 조작이 늘 때마다 낡았다. 다만 R115-d 의 열린 목록 전환을 그대로 이식하면 안 된다 — R115-d 가 열 수 있었던 이유는 뒤에 생성적 규칙(R115-a)이 따로 있어서 열거를 지워도 남는 것이 있었기 때문이다. R84 는 규칙이 한 줄도 없어, 규칙 없이 열린 목록으로 선언하면 판정 근거가 0 이 되어 닫힌 열거보다 나쁘다. 그래서 순서가 있다 — ① 기준 신설 ② 열거를 예시로 강등. 두 패널이 각자 독립적으로 같은 교정에 도달했다. 순수 읽기를 제외하는 근거는 R84 의 볼륨 과다다.

#### Acceptance Criteria

- [ ] AC-1: 노드의 존재·위치·본문을 바꾸는 조작이 기준 ① 에 걸려 감사 행을 남긴다.
- [ ] AC-2: 그 노드에 누가 도달하는가를 바꾸는 조작이 기준 ② 에 걸려 감사 행을 남긴다.
- [ ] AC-3: R71 상방 게이트로 판정을 우회한 접근이 기준 ③ 에 걸려 감사 행을 남긴다.
- [ ] AC-4: 세 기준 어느 것에도 걸리지 않는 순수 읽기(일반 문서 열람)는 감사 행을 남기지 않는다.
- [ ] AC-5: 새 조작을 추가할 때 기록 여부가 이 세 기준으로 판정되며 별도의 열거 갱신을 요구하지 않는다.

### OBS-AUDIT-004 — 다른 화면이 행위자와 시각을 영구히 재현하면 기록하지 않는다

#### Requirement

R137 기준에 걸리는 조작이라도 제품의 다른 화면이 그 조작의 행위자와 시각까지 영구히 재현하면 감사 로그에 기록하지 않는다. 기간 한정 재현은 재현이 아니다. 이 제외축으로 md 문서의 새 버전 올리기는 기록 대상에서 빠지고, 바이너리 파일의 새 버전은 기록한다.

#### Rationale

원장이 이미 세 번 쓴 판별자다(R101-d · R115-g · R115-i). md 새 버전이 제외되는 근거는 R61·R63-a 가 버전 이력으로 행위자·시각을 영구 보관한다는 것이고, 바이너리가 기록되는 근거는 R63 이 버전 대상을 md 로 한정해 재현 수단이 없다는 것이다.

#### Acceptance Criteria

- [ ] AC-1: md 문서의 새 버전 저장이 감사 행을 남기지 않는다.
- [ ] AC-2: 바이너리 파일의 새 버전 올리기가 감사 행을 남긴다.
- [ ] AC-3: 제외 판정이 재현처가 영구 보관일 때만 성립하고, 보존 기간이 있는 재현처는 제외 근거가 되지 않는다.
- [ ] AC-4: 제외된 조작마다 그 재현처가 무엇이며 그곳이 행위자와 시각을 모두 보이는지가 판정된다.

### OBS-AUDIT-005 — 기준으로 재도출된 누락 조작을 기록 대상에 추가한다

| Field | Value |
| --- | --- |
| Type | observability |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | audit-log, recording-criteria |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

다음 조작은 R137 기준에 걸리므로 감사 행을 남긴다 — 생성 · 복사 · 이동 · 삭제(휴지통 이동) · 휴지통 복구 · 업로드 · 바이너리 새 버전 · 워크스페이스 생성. 삭제(휴지통 이동)는 휴지통 복구와 짝으로 기록한다.

#### Rationale

워크스페이스 생성은 R136 이 그 폼 안의 관리자 지정(R35-a)과 default 초기 권한(R111)을 부여로 확정했는데 열거에 없었고, R136-d 로 설치 마법사도 같다. 업로드는 생성에 흡수된다(R45). 삭제가 의도가 아니라 누락인 근거 — L1(가역)이라 기록하지 않는다 는 규칙은 원장에 없고 반례가 이미 있다. ACL 항목 회수는 R115-b 상 L1 인데 R84 열거에 있다(그룹 멤버 제거·가입 거절도 같다). R115 는 마찰의 축, R84 는 조회 가능성의 축이고 둘을 잇는 조항이 없다. 결정적 근거는 R110-a 의 자기모순이다 — 원장은 만료를 배제하며 R25 완전 숨김 하에서 문서가 설명 없이 사라지고 감사 로그에 회수 이벤트도 남지 않는다 는 추적 불가능한 사고 라고 썼는데 삭제가 정확히 그 상태를 만든다. 패널 2:0. 이 자리의 등재 사유도 정정되었다(R137-g) — 복제된 콘텐츠는 추적 대상도 아니다 는 부분적으로 거짓이었다. R97-a 는 복사 시 R28 로 생성자에게 편집권을 주고 그것이 acl_entry 1건으로 못박혔으며 R84 는 ACL 부여를 이미 기록하므로, 생성·복사는 이미 감사 행을 1건 남기고 있었고 R84-a 불변성 때문에 R43-1 이 그 ACL 을 지워도 부여 이벤트는 살아남는다. 개정 전 문면으로 불가능했던 것은 셋이다 — ① 신규인지 복사인지 라벨 ② 원본이 무엇이었는지 출처 ③ 자기가 만들지 않은 노드에 대한 이동·개명·삭제. 공백의 실체는 복사가 무기록 이 아니라 출처를 표현할 수 없고 타인 소유 노드 조작이 전부 무기록 이었다. 패널 2인이 각자 독립적으로 이 오류를 지적했다.

#### Acceptance Criteria

- [ ] AC-1: 노드 생성이 감사 행을 남긴다.
- [ ] AC-2: 복사가 감사 행을 남기며 행 수는 R140-d 를 따른다.
- [ ] AC-3: 이동이 감사 행을 남긴다.
- [ ] AC-4: 삭제(휴지통 이동)가 감사 행을 남긴다.
- [ ] AC-5: 휴지통 복구가 감사 행을 남긴다.
- [ ] AC-6: 업로드가 생성에 흡수되어 생성 감사 행을 남기고 별도의 업로드 조작명을 만들지 않는다.

### SEC-AUDIT-001 — 경계를 넘는 복사의 유출 감사와 행위자 기록

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |

| Priority | medium |
| Tags | audit-log, workspace-boundary, exfiltration |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |

#### Requirement

경계를 넘는 복사에서 원본 노드 자리의 감사 행은 원본 노드가 속한 워크스페이스의 감사 로그에 속하고, 사본 노드 자리의 감사 행은 사본이 속한 워크스페이스의 감사 로그에 속한다. 각 행은 그 워크스페이스의 관리 보유자와 R71 상방 게이트 보유자가 읽으며, 한 감사 행을 두 워크스페이스가 공유하지 않는다. 복사의 행위자는 두 행 모두에 기록하고, 행위자가 원본 워크스페이스에 보기 만 가진 경우와 R71 로 도달한 경우에도 예외를 두지 않는다.

#### Rationale

심의 2:0. 목적지에만 남기면 내 워크스페이스에서 무엇이 나갔는가 라는 유출 감사의 1차 수요가 죽고, 한 행을 양쪽이 공유하면 그 행의 열람 자격이 두 워크스페이스에 걸쳐 R36(워크스페이스가 권한 경계)을 깬다. 행위자를 두 행 모두에 적어도 새 노출이 아닌 근거 — 행위자는 열람자가 이미 아는 것의 부분집합이다. 복사가 성립하려면 그가 원본에 도달했어야 하고, 그 사실은 원본 워크스페이스 관리자가 이미 볼 수 있는 것이다(R126-a 형태의 논증).

#### Acceptance Criteria

- [ ] AC-1: 경계를 넘는 복사 뒤 원본 워크스페이스의 관리 보유자가 자기 감사 로그에서 반출 사실을 조회할 수 있다.
- [ ] AC-2: 경계를 넘는 복사 뒤 사본 워크스페이스의 관리 보유자가 자기 감사 로그에서 유입 사실을 조회할 수 있다.
- [ ] AC-3: 한 감사 행이 두 워크스페이스의 감사 로그에 동시에 나타나지 않는다.
- [ ] AC-4: 원본 자리 행의 행위자에 복사 실행자가 기록된다.
- [ ] AC-5: 사본 자리 행의 행위자에 복사 실행자가 기록된다.
- [ ] AC-6: 행위자가 원본 워크스페이스에 보기 권한만 가진 경우에도 원본 자리 행의 행위자가 비지 않는다.
- [ ] AC-7: 행위자가 R71 상방 게이트로 원본에 도달한 경우에도 원본 자리 행의 행위자가 비지 않는다.

#### Requirement

감사 행의 노드 참조는 노드 ID(R76)로 저장한다. 열람 시점에 그 노드가 그 행을 조회하는 워크스페이스에 속할 때만 경로로 해석해 표시하고, 그렇지 않으면 모든 외부 노드에 대해 동일한 고정 문구로 표시한다.

#### Acceptance Criteria

- [ ] AC-1: 감사 행에 저장되는 노드 참조 값이 노드 ID 이고 경로 문자열이 아니다.
- [ ] AC-2: 조회하는 워크스페이스에 속한 노드가 경로로 해석되어 표시된다.
- [ ] AC-3: 조회하는 워크스페이스에 속하지 않는 노드가 고정 문구로 표시된다.
- [ ] AC-4: 서로 다른 두 외부 워크스페이스의 노드가 같은 고정 문구로 표시된다.
- [ ] AC-5: 열람자에게 나중에 그 워크스페이스의 권한이 생기면 같은 감사 행이 경로로 해석되어 보인다.
- [ ] AC-6: 외부 노드임을 이유로 감사 행 자체를 삭제하거나 저장하지 않는 처리를 하지 않는다.

### REL-AUDIT-001 — 재조정 대기열은 감사 로그와 별개 저장소다

| Field | Value |
| --- | --- |
| Type | reliability |
| Target | phase-1 |
| Status | planned |
| Priority | high |
| Tags | reconciliation, audit-log, queue |
| Risk | medium |
| Stability | stable |
| Verification Method | 통합 테스트 |
| GitHub Issue | - |

#### Requirement

재조정(R77 계열·R40-d)이 지목하는 감사 목록 은 audit_log 와 별개인 재조정 대기열 이며 reconciliation_finding(유형, 참조 감사 행 1..N, 해소 감사 행) 로 구성한다. 일어난 일의 기록은 audit_log 에만 두고 대기열은 유형과 감사 행 참조만 갖는다 — 시각·대상 노드·행위자·해소 시각·해소자를 자기 칸으로 갖지 않고 전부 참조 감사 행에서 읽으며, 미해소 는 해소 감사 행 이 비어 있는 상태이지 별도 칸이 아니다. R77 이 만든 신규 노드는 audit_log 에 생성 1행, 대기열에 그 행을 가리키는 항목 1건이다.

#### Rationale

심의 2:0. 성질이 세 축에서 반대다 — audit_log 는 불변(R84-a)인데 대기열 항목은 사후에 처리되고(R77-a 수동 연결), 로그는 보존 기간 만료로 사라지는데 대기열은 해소될 때까지 남아야 하며(사라지면 R77-b 완화책이 무너진다), 로그는 무엇이 일어났나 이고 대기열은 무엇이 아직 처리되지 않았나 이다. 가변성 하나만으로도 병합은 불가능하다 — R84-a 에 resolved_at 한 칸을 뚫으면 전부 불변 이라는 성질에서 나오는 증거력이 무너진다. 재조정 신규 노드를 사람이 만든 노드와 다르게 취급하면 R137 이 없앤 결함이 출처별 예외 로 되살아난다 — 재조정 신규 노드는 R137 기준 ①(존재가 바뀐다)에 정면으로 걸린다. 참조 감사 행이 복수인 것은 R77-a 의 상관 실패가 신규 노드와 tombstone 두 행을 한 항목으로 묶기 때문이고, 그래서 대상 노드를 단수 칸으로 둘 수 없다 — 두면 쌍 중 한쪽만 가리키게 된다.

#### Acceptance Criteria

- [ ] AC-1: 재조정 대기열이 audit_log 와 별개의 저장소로 존재한다.
- [ ] AC-2: 대기열 항목이 유형·참조 감사 행·해소 감사 행 세 축만 갖는다.
- [ ] AC-3: 대기열 항목이 시각·대상 노드·행위자·해소 시각·해소자를 자기 칸으로 갖지 않는다.
- [ ] AC-4: 대기열 항목의 미해소 상태가 해소 감사 행 이 비어 있는 것으로 판정되며 별도 칸이 아니다.
- [ ] AC-5: 대기열 항목의 참조 감사 행 이 복수를 담을 수 있고, R77-a 상관 실패의 신규 노드와 tombstone 두 행이 한 항목으로 묶인다.
- [ ] AC-6: 서버 정지 중 파일을 이동한 뒤 기동하면 재조정이 만든 신규 노드가 audit_log 에 생성 1행을 남기고 대기열에 그 행을 가리키는 항목 1건이 생긴다.
- [ ] AC-7: 같은 사실이 audit_log 와 대기열에 두 번 적히지 않는다.
- [ ] AC-8: 대기열 항목이 보존 기간 만료로 사라지지 않고 해소될 때까지 남는다.

### DR-AUDIT-001 — 사람이 아닌 주체의 행위자는 하위체계별 예약 주체 행이다

| Field | Value |
| --- | --- |
| Type | data |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | audit-log, system-principal, reconciliation |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md) |

#### Requirement

사람이 아닌 주체의 행위자 는 하위체계별 예약 주체 행이다 — system:reconciler · system:retention 등. 예약 주체는 로그인·상태 전환·삭제가 불가능하며, is_system 판정은 단일 지점에 두고 주체를 열거하는 모든 화면이 그것을 경유한다.

#### Rationale

심의 2:1(결선 포함). 행위자 는 자유 입력 필터이고 조작 은 단일 선택 드롭다운이므로(04 §2.7), 하위체계를 조작 값에 밀어 넣으면 재조정이 한 일 전부 를 한 번에 고를 수 없다. 더 나쁜 것은 조작 의 distinct 집합이 하위체계 × 조작의 곱집합으로 부풀어 R137-f 가 막으려던 축이 되는 것이고, 조작=생성 필터가 재조정이 만든 노드를 조용히 놓친다. 선례는 R30-a 의 시스템 그룹(삭제·개명이 금지된 예약 주체)이다. 폴백을 두지 않는 이유는 두면 이 조항의 이점이 조용히 무너지기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 재조정이 남기는 감사 행의 행위자가 system:reconciler 다.
- [ ] AC-2: 보존 기간 만료로 발생한 영구 삭제 감사 행의 행위자가 system:retention 다.
- [ ] AC-3: 예약 주체로 로그인할 수 없다.
- [ ] AC-4: 예약 주체의 상태를 전환할 수 없다.
- [ ] AC-5: 예약 주체를 삭제할 수 없다.
- [ ] AC-6: is_system 판정이 단일 지점에 있고 주체를 열거하는 모든 화면이 그 지점을 경유한다.
- [ ] AC-7: 하위체계 구분이 조작 값에 섞이지 않아 조작 의 distinct 집합이 하위체계 × 조작의 곱집합으로 부풀지 않는다.
- [ ] AC-8: 조작=생성 필터가 재조정이 만든 노드를 놓치지 않는다.
- [ ] AC-9: 행위자를 지정하지 않은 감사 행을 system 으로 채우는 폴백이 없다.

### REL-AUDIT-002 — 대기열 항목의 해소는 새 감사 행 추가로만 수행한다

| Field | Value |
| --- | --- |
| Type | reliability |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | reconciliation, audit-log, immutability |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

대기열 항목의 해소(R77-a 수동 연결 포함)는 기존 감사 행을 수정하지 않고 해소 행위를 새 감사 행으로 추가하는 방식으로만 수행한다. 원 감사 행은 R84-a 대로 불변이다. 그 해소 감사 행이 곧 대기열 항목의 해소 감사 행 이므로 해소 시각과 해소자를 대기열이 따로 갖지 않는다.

#### Rationale

원장이 이미 두 번 쓴 형태다 — R137-a(다른 화면이 영구히 재현하면) · R110-a(회수 이벤트가 남지 않으면 추적 불가능한 사고). 재조정이 그 시점에 상관 판정을 못 했다는 것은 사후 정정으로 거짓이 되지 않는 사실이고, R77-a 가 fail-closed 를 택한 이유를 나중에 검증하려면 판정 실패 자체가 보존돼야 한다. 수동 연결이 기록 대상인 것은 R137 기준 ②로 이미 걸린다 — 이식으로 도달이 바뀐다.

#### Acceptance Criteria

- [ ] AC-1: 대기열 항목을 해소해도 그 항목이 참조하던 감사 행의 값이 바뀌지 않는다.
- [ ] AC-2: 해소 행위가 새 감사 행을 1건 남긴다.
- [ ] AC-3: 대기열 항목의 해소 감사 행 이 그 새 감사 행을 가리킨다.
- [ ] AC-4: R77-a 수동 연결이 해소 경로에 포함되고 같은 규칙을 따른다.
- [ ] AC-5: 대기열이 해소 시각과 해소자를 자기 칸으로 갖지 않고 해소 감사 행에서 읽는다.
- [ ] AC-6: 해소 뒤에도 재조정이 그 시점에 상관 판정을 하지 못했다는 사실이 원 감사 행으로 보존된다.

### IR-AUDIT-002 — 재조정 대기열 화면의 소재와 미해소 건수 배지

| Field | Value |
| --- | --- |
| Type | interface |

| Status | planned |
| Priority | medium |
| Tags | reconciliation, queue, settings-screen |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [설정 화면 설계](./04.screen-design-settings.md) |

#### Requirement

재조정 대기열 화면은 워크스페이스 관리 › 감사 로그 카테고리 안의 두 번째 화면(패널 내부 전환)이며, R24-a 의 구역·카테고리 구성과 표시 권한을 바꾸지 않는다. 대기열 항목을 감사 로그 표에 섞지 않는다. R77-b 가 완화책으로 든 통지는 좌측 카테고리에 붙는 미해소 건수 배지로 구현하며, 배지는 그 사용자가 볼 수 있는 스코프의 미해소 건수만 센다.

#### Rationale

결선 판정. 인스턴스 구역에 두는 안은 열람 자격에서 탈락한다 — 04 §1.4 상 인스턴스 구역의 표시 조건은 슈퍼유저 소속이고 예외가 없는데, 발견의 다수는 워크스페이스 스코프이고 처리 주체는 워크스페이스 관리 보유자다. 그 화면을 슈퍼유저 방에 두면 R77-b 의 완화책이 그것을 필요로 하는 사람에게 배달되지 않아 위험 수용 판단이 근거를 잃는다. 게다가 04 §2.7 이 같은 축의 같은 문제를 이미 화면 안 스코프 선택기로 풀고 인스턴스 구역에 카테고리를 하나 더 만들지 않는다 고 명시했다 — 정반대 처방을 낼 이유가 없다. 배지가 통지 수단인 이유는 Phase 1 에 알림 체계가 없기 때문이고(R110-a), 선례가 이미 둘이다 — 04 §1.3 전체 와이어프레임의 가입 승인 (3) 배지와 R109-a 의 관리자 없음 상시 배지.

#### Acceptance Criteria

- [ ] AC-1: 재조정 대기열이 워크스페이스 관리 › 감사 로그 카테고리 안에서 패널 내부 전환으로 열린다.
- [ ] AC-2: 재조정 대기열 항목이 감사 로그 표의 행으로 섞여 나타나지 않는다.
- [ ] AC-3: R24-a 의 구역·카테고리 구성과 표시 권한이 이 화면 때문에 바뀌지 않는다.
- [ ] AC-4: 재조정 대기열이 인스턴스 구역의 별도 카테고리로 만들어지지 않는다.
- [ ] AC-5: 좌측 카테고리에 미해소 건수 배지가 상시 표시된다.
- [ ] AC-6: 배지의 수가 그 사용자가 볼 수 있는 스코프의 미해소 항목 수와 일치한다.
- [ ] AC-7: 배지가 전역 총계나 분모를 표시하지 않는다.

### SEC-AUDIT-007 — 재조정 대기열 항목의 스코프는 참조 감사 행에서 파생한다

| Field | Value |
| --- | --- |
| Type | security |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | reconciliation, queue, workspace-boundary |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

대기열 항목의 스코프는 감사 행과 같은 기준으로 정하며 그 기준의 정본은 R141 이다. 스코프는 항목이 참조하는 감사 행들의 대상 노드에서 파생하고, 대기열에 워크스페이스 칸을 두지 않는다. 어느 워크스페이스에도 귀속되지 않는 항목과 워크스페이스 경계를 넘는 항목은 인스턴스 스코프로 격상해 슈퍼유저에게만 보인다.

#### Rationale

새 접근 규칙을 만들지 않고 기존 선택기를 그대로 쓴다(R124). 참조 감사 행이 둘 이상이고 서로 다른 워크스페이스에 속하면 그것이 곧 경계를 넘는 항목 이므로 격상 조건이 별도 판정 없이 도출된다. 경계를 넘는 것으로 보이는 쌍은 R138 계열과 같은 문제이므로 그 결론을 따르고, 불확실하면 좁은 쪽이다 — R77-a 가 상관 판정에서 택한 fail-closed 와 같은 방향이다.

#### Acceptance Criteria

- [ ] AC-1: 대기열 항목의 스코프가 그 항목이 참조하는 감사 행들의 대상 노드에서 파생한다.
- [ ] AC-2: 대기열에 워크스페이스를 담는 칸이 없다.
- [ ] AC-3: 참조 감사 행이 둘 이상이고 서로 다른 워크스페이스에 속하면 그 항목이 인스턴스 스코프로 격상된다.
- [ ] AC-4: 어느 워크스페이스에도 귀속되지 않는 항목이 인스턴스 스코프로 격상된다.
- [ ] AC-5: 인스턴스 스코프로 격상된 항목이 워크스페이스 관리 보유자에게 보이지 않는다.
- [ ] AC-6: 대기열 조회가 기존 스코프 선택기를 그대로 쓰고 새 접근 규칙을 두지 않는다.

### OBS-AUDIT-007 — 복사의 감사 행 수는 내부 1행 경계 2행이다

| Field | Value |
| --- | --- |
| Type | observability |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | audit-log, workspace-boundary, exfiltration |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

사본 노드 자리의 감사 행은 언제나 생긴다(R137 기준 ①). 원본 노드 자리의 감사 행은 경계를 넘을 때만 생긴다(R138 의 유출 감사 사유). 따라서 워크스페이스 내부 복사는 1행, 경계를 넘는 복사는 2행이다. 이것이 복사의 감사 행 수의 정본이다.

#### Rationale

심의 2:1. 원본 노드는 R137 의 세 기준 어디에도 걸리지 않는다 — 존재·위치·본문이 바뀌지 않고(R105 — 복사는 원본을 건드리지 않아 비파괴적), 원본에 도달하는 사람도 바뀌지 않는다. 경계에서 원본 자리 행이 생기는 근거는 R137 이 아니라 R138 이다 — 목적지에만 남기면 내 워크스페이스에서 무엇이 나갔는가 라는 유출 감사의 1차 수요가 죽는다는 사유이고, 그 사유가 내부 복사에는 존재하지 않는다. 따라서 행 수는 경계 판정에 분기하는 것이 아니라 근거가 다른 두 규칙의 합이다. 어느 워크스페이스의 열람자도 복사 1건당 정확히 1행을 보므로 행 수 자체는 오라클이 아니다. 소수 의견을 기록한다 — 심의 1인은 저장 형태가 경계에 분기하면 쓰기 경로가 경계 판정에 의존하게 되고 그 자리가 R134 가 지목한 구현 위반 지점 이라며 내부도 2행을 주장했다. 그 경우 같은 로그에 같은 사실이 두 번 적혀 R124·R139-a(사실은 두 번 적히지 않는다)에 걸리는 것이 채택하지 않은 이유다.

#### Acceptance Criteria

- [ ] AC-1: 워크스페이스 내부 복사가 감사 행 1건을 남긴다.
- [ ] AC-2: 내부 복사가 남기는 1행의 대상 역할이 사본 이다.
- [ ] AC-3: 경계를 넘는 복사가 감사 행 2건을 남긴다.
- [ ] AC-4: 경계를 넘는 복사의 두 행 중 하나의 대상 역할이 원본, 다른 하나가 사본 이다.
- [ ] AC-5: 어느 워크스페이스의 열람자도 복사 1건당 정확히 1행을 본다.
- [ ] AC-6: 내부 복사가 같은 사실을 두 번 적는 행을 만들지 않는다.

### OBS-AUDIT-008 — 다건 조작의 감사는 실제로 바꾼 것마다 1행이다

| Field | Value |
| --- | --- |
| Type | observability |

| Priority | medium |
| Tags | audit-log, granularity, bulk-operation |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

다건 조작의 감사는 그 조작이 실제로 바꾼 것마다 1행이다 — 노드를 바꾸는 조작(삭제·복사·이동)은 노드마다 1행, acl_entry 를 바꾸는 조작(부여·회수)은 항목마다 1행이다. 1행 + 영향 건수 를 쓰지 않는다. 복사의 행 수는 이 요구사항이 아니라 R140-d 가 정본이며, 원본 노드는 아무것도 바뀌지 않으므로 이 규칙만으로는 원본 자리에 행이 생기지 않는다.

#### Rationale

심의 3:0. 입도 단위를 노드 가 아니라 바꾼 것 으로 쓰는 이유 — 원장에 acl_entry 의 (주체, 노드) 유일성 제약이 없고 R70-a(편집자도 부여)·R70-d(granted_by 기록)를 함께 읽으면 같은 주체·같은 노드에 부여자가 다른 항목이 둘 있을 여지가 문면상 닫혀 있지 않다. 그때 노드마다 1행 이면 두 항목 중 하나의 granted_by 가 기록되지 않아 R70-d 의 역질의가 깨진다. 이 정정으로 R142-c 의 토큰과 감사 행 수가 정의상 같아진다. 결정적인 것은 배달 실패다 — 집계 1행의 대상 은 노드도 acl_entry 도 아닌 주체이므로 어느 워크스페이스에도 귀속되지 않아 인스턴스 스코프로 격상되고 슈퍼유저 전용이 된다. 그러면 자기 워크스페이스에서 128건의 ACL 이 사라진 사실을 그 워크스페이스 관리자가 볼 수 없다. R101-f 로 슈퍼유저의 일괄 회수는 여러 워크스페이스를 건드리는데 1행은 여러 로그에 동시에 귀속될 수 없다 — R138 이 경계를 넘는 복사에서 2행을 강제한 것과 같은 논리(R36 이 권한 경계)가 다건에서 N행으로 나타난다. 그 밖에 R110-a 가 만료 ACL 을 배제하며 지목한 추적 불가능한 사고 를 제품 자신의 조작이 만들게 된다. G26 ③ 종결.

#### Acceptance Criteria

- [ ] AC-1: 노드 N개를 바꾸는 다건 조작이 감사 행 N건을 남긴다.
- [ ] AC-2: acl_entry M건을 바꾸는 다건 조작이 감사 행 M건을 남긴다.
- [ ] AC-3: 같은 주체·같은 노드에 부여자가 다른 acl_entry 항목이 둘 있으면 회수가 감사 행 2건을 남기고 각 행이 서로 다른 granted_by 를 담는다.
- [ ] AC-4: 다건 조작이 1행 + 영향 건수 형태의 집계 행을 남기지 않는다.
- [ ] AC-5: 일괄 회수의 감사 행 수가 R142-c 의 타이핑 토큰(회수될 acl_entry 항목 수)과 같다.
- [ ] AC-6: 이 사용자가 이 노드의 권한을 언제 누구에 의해 잃었나 라는 역질의가 낱행으로 답해진다.

#### Requirement

R139-e 는 이제 이 조항을 참조하는 쪽이다. 스코프를 대상 에서만 파생시키는 이유는 R140 이 같은 축에서 이미 판정했다 — 상대편에 의존시키면 경계를 넘는 행이 귀속처를 잃고 슈퍼유저 전용으로 격상되어 R138 이 자멸한다.

#### Requirement

감사 행의 저장은 낱행이고 표시는 묶음 접기다. 뷰어는 한 번의 조작에서 나온 행들을 접힌 1줄로 보이고 펼치면 낱행을 보인다. 묶음은 표시 산물이지 기록이 아니므로 조작 distinct 필터(R137-f)의 원천이 되지 않는다. 묶음 키를 화면·API·필터에 노출하지 않는다.

R50-c 로 동반 삭제되는 첨부는 감사 행을 만들지 않고 건수도 표시하지 않는다. 소유 문서의 영구 삭제 1행이 전부다.

#### Rationale

심의 3:0. R137 기준 어디에도 걸리지 않는다 — 기준 ①②는 노드를 말하는데 첨부는 노드가 아니고(R50-a 의 attachment 별도 테이블), 첨부 도달은 R66 으로 소유 문서의 보기 권한에서 파생된다. R137-a 제외축을 자기 자신으로 충족한다 — 첨부 소멸은 R50-c 로 소유 문서의 영구 삭제에서 결정론적으로 따라오고 그 행은 R84-a 로 영구하며 행위자·시각이 같다. 기간 한정 재현은 재현이 아니다 라는 단서도 통과한다 — 재현원이 같은 로그의 같은 행이다. 대상 에 넣을 값도 없다 — 해시를 넣으면 대상 이 두 타입을 갖게 되어 R140-b 의 마스킹이 일부 행에 적용 불가가 된다. 건수를 싣지 않는 이유는 R134 다 — 사람 수(R121)·노드 수(R126)에 이은 세 번째 지표 축인데 대응 조작이 없다.

#### Acceptance Criteria

- [ ] AC-1: 첨부 N건을 가진 문서를 영구 삭제하면 감사 행이 영구 삭제 1건만 생긴다.
- [ ] AC-2: 동반 삭제된 첨부마다 별도의 감사 행이 생기지 않는다.
- [ ] AC-3: 영구 삭제 행이 동반 삭제된 첨부의 건수를 담지 않는다.
- [ ] AC-4: 감사 화면이 동반 삭제된 첨부의 건수를 표시하지 않는다.
- [ ] AC-5: 감사 행의 대상 이 첨부 해시 같은 노드 아닌 값을 담지 않는다.

#### Requirement

디렉토리 삭제·복사의 서브트리는 하위 노드마다 1행이다.

#### Rationale

심의 3:0. 삭제 — 서브트리 1행으로 접으면 이 문서가 언제·누구에 의해 지워졌나 의 답이 그 시점의 서브트리 구성원을 담은 유일한 곳(휴지통 행·R78 사이드카)에 의존하는데 그것은 R86 경과 시 함께 사라진다. R137-a 의 기간 한정 재현은 재현이 아니다 가 정면으로 요구한다. 복사 — R137-g 가 확인한 대로 노드당 행은 이미 발생하고 있었다(R97-a → R28·R132 로 하위 노드마다 acl_entry 1건이 생기고 R84 가 ACL 부여로 이미 기록한다). 여기서 복사 만 접으면 같은 사건의 두 축이 서로 다른 입도로 기록되어 R124 위반이고, R137-g 가 남은 문제로 지목한 출처(원본이 무엇이었나)를 노드 단위로 답할 수 없게 된다 — 출처는 노드마다 다르다.

#### Acceptance Criteria

- [ ] AC-1: 하위 노드 N개를 가진 디렉토리를 삭제하면 감사 행이 노드마다 1건씩 생긴다.
- [ ] AC-2: 하위 노드 N개를 가진 디렉토리를 복사하면 감사 행이 노드마다 생기며 행 수는 R140-d 를 따른다.
- [ ] AC-3: 서브트리 조작이 1행으로 접혀 저장되지 않는다.
- [ ] AC-4: 서브트리 복사의 각 행이 그 노드의 출처를 상대 노드 로 담아 출처를 노드 단위로 답할 수 있다.
- [ ] AC-5: 서브트리 조작의 낱행과 ACL 부여 행이 같은 입도(노드 단위)로 기록된다.
- [ ] AC-6: 서브트리 삭제 뒤 휴지통 행과 R78 사이드카가 사라져도 개별 문서가 언제 누구에 의해 지워졌는지를 감사 로그로 답할 수 있다.
