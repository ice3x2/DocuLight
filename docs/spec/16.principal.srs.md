## 1. Scope Overview

이 scope 는 시스템이 **주체**로 인식하는 것 — 사용자와 그룹 — 의 정의, 그 주체의 수명주기, 그리고 주체를 고르는 화면을 규정한다. 권한 계층이 몇 단인가, 슈퍼유저를 무엇으로 판정하는가, 그룹이 무엇을 멤버로 갖는가, 계정과 그룹이 어떻게 사라지는가(또는 사라지지 않는가), 어떤 화면에서든 주체를 고를 때 지켜야 하는 규칙이 여기 모인다.

주체가 **무엇을 할 수 있는가**는 `ACL` scope 가 갖는다. 이 scope 는 ACL 항목이 가리키는 대상을 정의하고, 그 대상이 사라지거나 바뀔 때 ACL 항목에 무슨 일이 벌어지는지를 정한다.

## 2. Scope Boundaries

### In Scope

- 권한 계층을 슈퍼유저와 일반 유저 2단계로 두는 제약과 「관리자」 표기 규약 (`CON-PRINCIPAL-001`·`CON-PRINCIPAL-007`)
- 슈퍼유저 판정 — 슈퍼유저 그룹 소속 하나로만 판정하며, 그 소속이 갖는 권능 (`DR-PRINCIPAL-001`·`SEC-PRINCIPAL-001`)
- 그룹의 성질 — 사용자만을 멤버로 갖고 중첩되지 않는다, 시스템 그룹은 삭제·개명할 수 없다 (`DR-PRINCIPAL-002`·`CON-PRINCIPAL-002`)
- 사용자 관리·그룹 관리 기능의 존재와 사용자 관리 화면의 계정 4상태 표시 (`FR-PRINCIPAL-001`·`FR-PRINCIPAL-009`)
- 계정 수명주기 — 계정을 삭제하지 않고 `suspended` 로만 관리한다 (`CON-PRINCIPAL-003`)
- 오프보딩 — 네 단계의 안내된 흐름, 카드의 단일 컴포넌트화와 진행 상태 미저장, 일괄 회수 화면의 적용 범위 문구 (`FR-PRINCIPAL-003`·`CON-PRINCIPAL-004`·`FR-PRINCIPAL-004`)
- 주체가 사라질 때 ACL 에 벌어지는 일 — 그룹 삭제가 그 그룹 앞 ACL 제거를 같은 트랜잭션에 포함한다, 시스템 그룹도 주체 단위 일괄 회수의 대상이다 (`FR-PRINCIPAL-002`·`FR-PRINCIPAL-010`·`FR-PRINCIPAL-011`)
- 관리 권한자가 없어지는 상황의 처분 — 마지막 관리 권한자 제거는 차단이 아니라 경고, 관리자 없는 워크스페이스의 상시 배지 (`FR-PRINCIPAL-005`·`FR-PRINCIPAL-006`)
- ACL 항목에 만료일을 두지 않는다는 결정 (`CON-PRINCIPAL-005`)
- 주체 선택 UI — 검색 결과의 계정 노출 범위와 중립어 배지, 최소 질의 길이와 결과 상한, 단일 공용 컴포넌트 제약, 비활성 계정에 부여할 때의 확인 1단계 (`SEC-PRINCIPAL-002`·`SEC-PRINCIPAL-003`·`CON-PRINCIPAL-006`·`FR-PRINCIPAL-008`)
- 새 워크스페이스 생성 폼의 `default` 그룹 초기 권한 기본값 (`FR-PRINCIPAL-007`)

### Out of Scope

- ACL 의 판정 규칙 — 상속과 가산, 부여의 종류, 유효 권한의 계산, 워크스페이스 `관리` 레벨의 성질, 슈퍼유저와 관리 레벨이 ACL 판정을 우회한다는 규정은 `ACL` scope 가 소유한다. `CON-PRINCIPAL-001` 이 금지한 「등급」은 계정 레코드에 저장되는 값을 말하며, 워크스페이스 `관리` 레벨은 그 금지의 대상이 아니다 (`CON-PRINCIPAL-001` Implementation Notes).
- 주체 단위 ACL 일괄 회수 화면 자체 — 영향 범위 표의 열 구성과 실행 규칙은 `ACL` scope 가 소유한다. 이 scope 는 그 대상에 시스템 그룹이 포함되는가와 오프보딩 흐름에서의 진입 방식만 갖는다.
- 확인 등급의 **배정 규칙** — `CONFIRM` scope 가 소유한다. 그룹 삭제·일괄 회수·비활성 계정 부여·워크스페이스 생성 시점 부여의 등급을 이 scope 의 요구가 인용할 때도 그 규칙을 다시 정의하지 않는다 (`FR-PRINCIPAL-002`·`FR-PRINCIPAL-007`·`FR-PRINCIPAL-011` Implementation Notes).
- 계정 상태를 인증 단계에서 차단하는 게이트, 상태별 로그인 안내 문구, PAT 무효화 조건 — `AUTH` scope 가 소유한다. `CON-PRINCIPAL-003` 이 계정 삭제를 없앤 결과 PAT 무효 사유 중 「삭제」가 사문이 되었으나, 그 조항의 처분은 `AUTH` scope 에 있다 (`CON-PRINCIPAL-003` Implementation Notes).
- 워크스페이스의 생성·삭제·아카이브와 그 폼 자체 — `WORKSPACE` scope 가 소유한다. `FR-PRINCIPAL-007` 은 그 폼 안의 `default` 초기 권한 기본값만 갖는다.
- 사용자·그룹 관리 화면이 놓이는 자리(설정 모달 카테고리)와 그 카테고리의 표시 권한 — `SHELL` scope 가 소유한다.
- 그룹 삭제·일괄 회수가 감사 로그에 남는 형식과 다건 회수의 감사 입도 — `AUDIT` scope 가 소유한다.
- 거부(deny) 규칙을 두지 않는다는 결정(R14-c) — `ACL` scope 가 소유한다. 그 조항이 계정 정지를 ACL 이 아니라 principal 레벨 비활성화 게이트로 처리하도록 두 축을 갈라 놓았으므로, 정지를 ACL 항목으로 표현하려는 설계는 이 scope 가 아니라 그 조항과 충돌한다.
- 사용자 스키마 — 이메일 필수 여부, 표시 이름 규칙, 본인이 자기 표시 이름을 바꿀 수 있는가는 미결 `G10` 이며 아직 어느 요구도 소유하지 않는다. 주체 검색 결과 행에 동명이인을 구별할 보조 열을 둘 수 있는지가 이 축에 걸려 있다 (`SEC-PRINCIPAL-002` Implementation Notes).

## 3. Assumptions and Constraints

- 사용자·그룹·ACL 메타데이터는 SQLite 단일 저장소에 있다 — `STORAGE` scope 가 소유하는 전제이며, `FR-PRINCIPAL-002` 의 「같은 트랜잭션」이 그 저장소 위에서 성립한다.
- 감사 로그의 행위자 참조가 깨지지 않는다는 것이 계정을 삭제하지 않는 결정의 근거다(R101). 그 참조의 형식은 `AUDIT` scope 가 소유한다.
- `default` 그룹과 슈퍼유저 그룹은 시스템 그룹이라 삭제될 수 없다 (`CON-PRINCIPAL-002`). 따라서 `default` 앞 ACL 이 대량으로 사라지는 경로는 그룹 삭제가 아니라 주체 단위 일괄 회수다 — 2026-08-16 에 반대 서술이 거짓으로 판정됐다.
- ACL 에 시간 축이 없다 (`CON-PRINCIPAL-005`). 접근자 인원 수에 시점을 표기하지 않는 규칙이 여기서 따라오며, 그 규칙 자체는 `CONFIRM` scope 가 소유한다.
- 인스턴스 규모와 프론트엔드 스택 전제는 `ARCH` scope 가 소유한다.
- 미결 `G10`(사용자 스키마)이 이 scope 에 걸려 있고 `SEC-PRINCIPAL-002` 의 결과 행 구성을 미확정으로 남긴다.
- `G23`(`관리자 없음` 상태의 운영 종착점 부재)도 이 scope 에 걸려 있다 — 배지(`R109-a`)를 본 사람이 취할 조치 동선이 화면에 없고 `R103` 권한 요청 큐는 Phase 2 다. 이 scope 에 걸린 미결의 등재 정본은 `00.index.md` §9 의 `Impact` 열이며, 그 열이 바뀌면 이 목록도 함께 훑는다.

#### Requirement

사용자 권한 계층은 슈퍼유저와 일반 유저 2단계로만 구성한다. 일반 유저와 사용자 그룹의 권한은 전부 대상별 스코프(ACL)로만 관리하며, 그 사이에 중간 관리자 등급을 두지 않는다.

#### Rationale

중간 관리자 등급을 만들면 권한의 원천이 「등급」과 「ACL」 둘이 되어, 같은 사용자에 대해 두 값이 갈릴 수 있고 어느 쪽이 정본인지 판정할 규칙이 따로 필요해진다. 등급을 두지 않으면 그 판정 문제 자체가 생기지 않는다. 기각된 대안은 중간 관리자 등급이며, 관리 경계를 나누려는 수요는 등급이 아니라 워크스페이스 계층으로 받는다.

#### Acceptance Criteria

- [x] AC-1: 인스턴스 전역 권한을 부여하는 수단은 슈퍼유저 하나뿐이며, 그 밖의 전역 등급은 존재하지 않는다.
- [x] AC-2: 일반 유저의 모든 권한은 대상 노드에 걸린 ACL 항목으로 판정된다.
- [x] AC-3: 사용자 그룹의 권한도 사용자와 동일하게 대상 노드에 걸린 ACL 항목으로 판정되며, 그룹 전용의 별도 권한 축이 존재하지 않는다.

#### Requirement

슈퍼유저 여부는 슈퍼유저 그룹의 멤버십 하나로만 판정한다. 사용자 레코드에 등급 필드나 슈퍼유저 플래그 필드를 두지 않는다.

#### Rationale

감사 지적 H6 해소. 판정 근거를 둘로 두면(그룹 멤버십과 계정 플래그) 두 값이 갈릴 수 있고, 갈린 뒤에는 어느 쪽이 정본인지 아무도 눈치채지 못한다. 슈퍼유저 그룹의 삭제 잠금, `active` 멤버 수 0 가드, `default` 그룹이 모두 그룹 메커니즘 위에 서 있으므로 판정도 같은 메커니즘으로 일원화한다. 기각된 대안은 사용자 레코드의 등급·플래그 필드다.

#### Acceptance Criteria

- [x] AC-1: 슈퍼유저 판정은 슈퍼유저 그룹의 멤버십 조회 결과 하나로 이뤄진다.
- [x] AC-2: 사용자 레코드에 등급 필드나 슈퍼유저 플래그 필드가 존재하지 않는다.
- [x] AC-3: 슈퍼유저 그룹에서 멤버십이 제거된 계정은 더 이상 슈퍼유저로 판정되지 않으며, 그를 위해 별도로 갱신해야 하는 계정 측 값이 없다.

#### Requirement

사용자 그룹의 멤버는 사용자만이 될 수 있다. 그룹이 다른 그룹을 멤버로 갖는 중첩 구조를 허용하지 않는다.

#### Rationale

#### Acceptance Criteria

- [ ] AC-1: 그룹의 멤버로 다른 그룹을 지정하는 요청은 거부된다.
- [ ] AC-2: 그룹 멤버십 저장 구조가 그룹을 멤버로 표현할 수 있는 칸을 갖지 않는다.
- [ ] AC-3: 유효 권한 계산은 사용자가 직접 속한 그룹까지만 따라가며, 그룹에서 그룹으로 이어지는 참조를 순회하지 않는다.

#### Acceptance Criteria

- [ ] AC-1: 계정을 영구 삭제하는 조작이 화면에도 API 에도 존재하지 않는다.
- [ ] AC-2: 계정 비활성화 요청은 그 계정을 `suspended` 로 전환하며 계정 레코드를 지우지 않는다.
- [ ] AC-3: `suspended` 로 전환된 계정을 행위자로 가리키는 감사 로그 행이 그대로 보존되고 참조가 깨지지 않는다.

#### Requirement

시스템은 오프보딩을 ① 계정 `suspended` 전환 ② PAT 무효화 ③ 그룹 멤버십 제거 ④ ACL 일괄 회수의 네 단계로 이뤄진 하나의 안내된 흐름으로 제공한다. 각 단계는 마지막 슈퍼유저 가드를 개별적으로 통과해야 한다.

#### Rationale

네 단계를 각각 따로 하면 담당자가 하나를 빠뜨리고, 빠뜨린 자리에 잔존 권한이 남는다. 하나의 안내된 흐름으로 묶는 이유가 그것이다. 중간에 거부되어도 이전 단계를 되돌리지 않는 이유는 1단계만 적용된 계정도 이미 로그인과 토큰 인증이 차단되어 부분 진행 상태가 그 자체로 유효하기 때문이다 — 롤백하면 오히려 접근이 되살아난다. 4단계를 주체 일괄 회수 화면으로 위임하는 이유는 영향 범위 표와 타이핑 확인이 이미 그 화면에 있어서이며, 카드 안에 다시 그리면 중복 구현이 된다. 용어는 「퇴사 처리」가 아니라 「오프보딩」으로 통일한다.

#### Acceptance Criteria

- [ ] AC-1: 오프보딩 흐름은 계정 `suspended` 전환 · PAT 무효화 · 그룹 멤버십 제거 · ACL 일괄 회수 네 단계를 한 화면에서 순서대로 안내한다.
- [ ] AC-2: PAT 무효화 단계는 별도 조작 없이 계정이 `active` 가 아니게 된 결과로 자동 수행된다.
- [ ] AC-3: 각 단계는 슈퍼유저 그룹의 `active` 멤버 수 가드를 개별로 통과해야 하며, 한 단계의 통과가 다른 단계의 통과를 대신하지 않는다.
- [ ] AC-4: 어느 단계가 가드로 거부되면 흐름은 그 자리에서 멈추고, 이미 적용된 이전 단계의 결과는 되돌리지 않는다.
- [ ] AC-5: ACL 일괄 회수 단계는 주체 일괄 회수 화면으로 위임되며, 카드는 그 화면으로 가는 진입 버튼과 완료 표시만 갖는다.
- [ ] AC-6: 카드는 영향 범위 표(워크스페이스·경로·레벨·부여자·부여 시각)를 자체적으로 그리지 않는다.
- [ ] AC-7: 화면 문구는 「오프보딩」으로 표기하며 「퇴사 처리」를 쓰지 않는다.

#### Implementation Notes

#### Acceptance Criteria

- [ ] AC-1: ACL 부여 화면에 만료일을 입력하거나 선택하는 자리가 존재하지 않는다.
- [ ] AC-2: `acl_entry` 스키마에 만료 시각 칸이 존재하지 않는다.
- [ ] AC-3: 시간 경과만으로 `acl_entry` 가 제거되거나 무효화되는 경로가 존재하지 않는다.
- [ ] AC-4: 권한이 등장하는 화면(권한 시뮬레이션·상속 끊김 목록·이동 프리뷰)은 기준 시점을 표기하지 않는다.

### FR-PRINCIPAL-007 — 새 워크스페이스 생성 폼에서 default 그룹 초기 권한을 고르며 기본값은 없음이다

- [ ] AC-4: 초기 권한을 `없음` 으로 두고 생성한 워크스페이스는 생성 직후 지정된 워크스페이스 관리자와 슈퍼유저가 접근할 수 있다.
- [ ] AC-5: 가입 모드가 자유 가입인 인스턴스에서 초기 권한으로 `편집` 을 선택하면 경고가 표시된다.

- [ ] AC-4: 사용자 관리 화면은 네 상태를 `비활성` 하나로 묶어 표시하지 않는다.

#### Requirement

제품의 화면 문구와 문서는 `관리자` 를 단독으로 쓰지 않는다. 항상 `워크스페이스 관리자` 또는 `슈퍼유저` 로 범위를 명시한다.

#### Rationale

두 주체는 서로 다르다 — 슈퍼유저는 그룹 멤버십으로 판정되는 인스턴스 전역 권한자이고, 워크스페이스 관리자는 그 워크스페이스에 대한 `관리` 레벨 보유자다. 범위 없이 `관리자` 만 쓰면 어느 범위의 권한자를 가리키는지 모호해지고, 그 모호함이 화면 문구에서 권한 판정 오해로 이어진다. `관리자 없음` 배지가 예외인 이유는 그 배지가 워크스페이스 행에 붙어 문맥이 자명하기 때문이다.

#### Acceptance Criteria

- [ ] AC-1: 사용자에게 보이는 문구에 범위 수식어 없는 `관리자` 가 나타나지 않는다.
- [ ] AC-2: 워크스페이스 단위 권한자를 가리킬 때는 `워크스페이스 관리자` 로 표기한다.
- [ ] AC-3: 인스턴스 전역 권한자를 가리킬 때는 `슈퍼유저` 로 표기한다.
- [ ] AC-4: 이 규칙의 예외는 `관리자 없음` 배지 하나뿐이다.

### FR-PRINCIPAL-010 — 시스템 그룹도 주체 단위 일괄 회수의 대상이다

| Field | Value |
| --- | --- |

| Tags | bulk-revocation, system-group, acl |

| Stability | stable |

| GitHub Issue | - |

#### Requirement

슈퍼유저 그룹과 `default` 그룹도 주체 단위 일괄 회수의 대상이며 주체 선택에서 제외하지 않는다.

#### Rationale

시스템 그룹 잠금은 삭제와 개명만 금지하며 ACL 회수를 다루지 않는다. 특히 `default` 그룹 앞으로 부여된 ACL 은 설치 마법사나 워크스페이스 생성 시점에 만들어진 일반 `acl_entry` 이므로 회수하면 영구히 사라진다 — 가입 시 자동 소속과 활성화 시점 소속은 멤버십 규정이지 ACL 재생성 규정이 아니다. 따라서 이 조작은 실제 효과가 있는 의미 있는 조작이며 막을 근거가 없다.

#### Acceptance Criteria

- [ ] AC-1: 주체 일괄 회수의 주체 선택에서 슈퍼유저 그룹과 `default` 그룹이 후보에서 제외되지 않는다.
- [ ] AC-2: `default` 그룹을 주체로 일괄 회수를 실행하면 그 그룹 앞으로 부여된 `acl_entry` 가 제거된다.
- [ ] AC-3: 회수된 `acl_entry` 는 이후 사용자 가입이나 계정 활성화 절차로 재생성되지 않는다.

### FR-PRINCIPAL-011 — 시스템 그룹 일괄 회수의 확인 등급과 슈퍼유저 그룹 무효 안내

| Field | Value |
| --- | --- |
| Type | functional |
| Target | phase-1 |
| Status | planned |
| Priority | medium |
| Tags | bulk-revocation, system-group |
| Risk | medium |
| Stability | stable |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [권한 화면 설계](./05.screen-design-permission.md) |

#### Requirement

`default` 그룹을 주체로 하는 일괄 회수는 확인 등급 배정표(FR-CONFIRM-006)가 그 조작에 배정한 등급의 확인을 요구한다 — 등급값의 정본은 그 배정표이고 이 요구는 값을 다시 적지 않는다. 슈퍼유저 그룹을 주체로 선택하면 그 회수가 접근을 줄이지 못한다는 사실을 화면에 안내한다.

#### Rationale

`default` 그룹 회수가 최고 등급인 이유는 그 조작이 광범위하고 비가역이기 때문이다 — 등급의 배정 규칙 자체는 확인 등급 요구가 소유하며 여기서 다시 정의하지 않는다. 슈퍼유저 그룹 회수에 안내가 필요한 이유는 슈퍼유저가 ACL 판정을 우회하므로 항목을 지워도 접근이 그대로 유지되기 때문이다. 안내가 없으면 실행한 사람은 접근을 끊었다고 믿는데 실제로는 아무것도 달라지지 않는다.

#### Acceptance Criteria

- [ ] AC-1: `default` 그룹을 주체로 한 일괄 회수는 실행 전에 확인 등급 배정표(FR-CONFIRM-006)가 그 조작에 배정한 등급의 확인을 요구한다.
- [ ] AC-2: 슈퍼유저 그룹을 주체로 선택하면 그 회수가 접근을 줄이지 못한다는 안내가 화면에 표시된다.
- [ ] AC-3: 슈퍼유저 그룹을 주체로 한 회수를 실행한 뒤에도 그 그룹의 멤버는 대상 노드에 계속 도달한다.
