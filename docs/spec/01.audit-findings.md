# CRITICAL

## C1 ★ 자손에게만 권한을 주면 그 문서에 도달할 경로가 화면에서 사라진다

**관련**: R14, R25, R12, R9 · **발견**: UI 축 (권한 축이 Q2 검토 시 유사 지적)

R14 는 하향 상속 + 가산이므로 자식 노드에 권한을 부여해도 **조상 디렉토리에는 아무 권한도 생기지 않는다.** 그런데 R25 는 권한 없는 디렉토리를 트리에서 완전히 숨긴다.

```
워크스페이스 W / 기획 / 2026 / 로드맵.md
관리자가 공유 모달(R12)로 사용자 B 에게 로드맵.md 만 '보기' 부여
→ B 의 트리: W 는 보이나 /기획 은 권한 없어 숨김 → /2026 도 숨김
→ 로드맵.md 를 표시할 자리가 없다
반대로 조상을 표시하면 B 는 기획·2026 의 존재와 이름을 알게 됨 → R25 위반
```

**이것은 예외 케이스가 아니다.** Q2 결정 경위 2번이 `이 문서만 한 명 더 보게 하기` 를 **"가장 흔한 조작"** 이라고 명시했고, 그 논거로 D안을 채택했다. 검색 탭(R3)으로 우회해도 결과 목록에 경로가 나오는 순간 같은 위반이다.

**선택지**
- (a) "부여된 노드의 **조상은 이름만 노출하는 pass-through 노드**로 표시(내용·형제는 비노출)"를 R25 의 명시적 예외로 확정
- (b) 자손 부여 시 조상에 **암묵 `통과` 권한을 자동 생성**
- (c) 권한 축이 제안한 **가상 루트("나에게 공유된 문서") 평면 목록** — 실제 경로는 숨김

## C2 ★★★ `.res` 위치가 R50 과 §2.17 레이아웃에서 서로 다르다

**관련**: R50, R65, R66, §2.17 · **발견**: 3개 축 전부

- **R50** — "**문서와 같은 디렉토리**의 `.res`" (디렉토리마다)
- **§2.17 확정 레이아웃** — `.res/` 를 **워크스페이스 루트에 하나만**

레이아웃대로 구현하면 R66 의 "부모 디렉토리 보기 권한"이 곧 **워크스페이스 보기 권한**으로 붕괴하여, 워크스페이스 보기 권한만 있으면 **그 안 모든 비공개 문서의 첨부를 다운로드**할 수 있다. R66 이 막으려던 유출이 워크스페이스 전체 규모로 열린다.

R50 이 정본으로 보인다 — R65 의 "이동 시 링크 절대경로 갱신"은 `.res` 가 디렉토리마다 있을 때만 필요한 조치이기 때문이다. **`.versions` 도 동일한 미정의를 안고 있다** (워크스페이스 평면 저장이면 서로 다른 디렉토리의 동명 문서 버전이 충돌).

## C3 ★★★ R65 와 R66 이 이동 후 서로를 양방향으로 깨뜨린다

**관련**: R65, R66, R50, R42 · **발견**: 3개 축 전부

R65 는 이동 시 첨부를 남기고, R66 은 첨부의 **물리 부모 디렉토리** 권한으로 판정한다. 이동 순간 본문과 첨부의 권한 경계가 영구히 어긋난다.

| 방향 | 시나리오 |
|---|---|
| **유출** | `/공개/초안.md`(첨부 `/공개/.res/`)를 `/임원/` 으로 이동 → 첨부는 `/공개/.res/` 잔류 → 전 직원이 R66 검사를 통과해 매출 그래프 등을 계속 다운로드 |
| **파손** | `/공개/보고서.md` 를 `/팀A/` 로 이동 → `/팀A` 권한만 있는 사용자는 본문은 읽지만 이미지가 전부 깨져 보임 |

**유출 방향은 R42 가 세운 원칙("본문은 통째로 보이거나 통째로 안 보이거나")의 정면 위반이다.**

추가로 R65 근거 문단이 스스로 인정하듯 **여러 문서가 같은 첨부를 참조**할 수 있어 "부모 하나"라는 전제 자체가 성립하지 않는다.

**선택지** — (a) R66 을 "그 첨부를 참조하는 문서 중 하나 이상에 보기 권한" 으로 재정의(역참조 인덱스 필요) (b) R65 를 뒤집어 첨부를 함께 이동 + 참조 카운트 도입

## C4 `상속 끊기` 가 관리자·슈퍼유저까지 배제하는지 미정의 — 되돌릴 수 없는 lockout

**관련**: R14, R25, R29, R37, R43-3 · **발견**: 권한 축

관리 권한(Q11 표)과 슈퍼유저 전권(R29)이 **ACL 판정을 우회하는 별도 게이트인지, 워크스페이스 노드에 붙은 ACL 항목으로서 상속되는 것인지**가 어디에도 없다. 후자라면 상속 끊기가 관리 권한도 함께 끊는다.

```
U 가 편집 권한을 가진 디렉토리 D 에서 상속을 끊고 ACL 을 자기 하나만 남김
→ 워크스페이스 관리자·슈퍼유저의 권한도 D 에 도달하지 않음
→ R25 에 의해 D 가 관리자·슈퍼유저의 트리에서 사라짐
→ R43-3(상속 끊김 감사 목록)은 그 노드를 나열할 권한을 어디서 얻는지 미정의
→ 아무도 되돌릴 수 없는 노드가 생긴다
```

**제안**: "슈퍼유저와 해당 워크스페이스의 `관리` 레벨은 ACL·상속 판정을 우회한다"를 명시적 요건으로 추가 (R14-c 가 deny 를 배제한 것과 대칭되는 상방 게이트). **이것 없이는 R43-2·R43-3 이 동작 근거를 갖지 못한다.**

## C5 최초 슈퍼유저를 어떻게 만드는지 정의되지 않았다

**관련**: R56, R7, R29, R30 · **발견**: 권한 축

R7 의 가입 모드 ②·③ 과 R29·R30 은 모두 슈퍼유저의 **선행 존재를 전제**하는데 최초 슈퍼유저의 출처가 없다.

- 가입 모드 ② 로 신규 설치 → 승인할 슈퍼유저가 없어 **부팅 직후 영구 잠금**
- "첫 가입자를 자동 승격"으로 구현 → 자유 가입(①) 모드에서 **사내망 접근 가능한 아무나 먼저 가입해 인스턴스 장악**

**제안**: 설치 시 환경변수/CLI 로 슈퍼유저 1명 생성, 그 계정 존재 전까지 웹 가입 경로 전체 차단.

## C6 마지막 슈퍼유저의 정지·삭제를 막는 규칙이 없다

**관련**: R30, R60, R29, R43-1 · **발견**: 권한 축 (UI 축도 R43-1 경로로 지적)

R30 은 슈퍼유저 **그룹**의 삭제와 마지막 **멤버 제거**만 금지한다. R60 이 도입한 `suspended` 전환과 계정 삭제, R43-1 의 주체 단위 일괄 회수는 R30 의 사정거리 밖이다.

슈퍼유저 1명뿐인 상태에서 그 계정을 `suspended` 로 전환 → 멤버 제거가 아니므로 R30 미발동 → R60 이 로그인·PAT 를 차단 → **본인도 되돌릴 수 없음.** 가입 모드 ② 면 신규 가입 승인도 불가.

**제안**: R30 을 "슈퍼유저 그룹의 **인증 가능한(`active`) 멤버 수가 0 이 되는 모든 조작을 거부**"로 확장.

## C7 생성·삭제·이동·개명의 필요 권한이 통째로 정의되지 않았다 — 이동으로 R36 이 우회된다

**관련**: R10, Q11 표, R45, R52, R65, R28 · **발견**: 권한 축 (UI 축은 진입점 부재로 별도 지적 → H1)

Q11 표는 `편집` 을 **"열람 + 수정"** 으로만 정의한다. 문서·디렉토리의 **생성·삭제·이동·개명**이 `편집` 에 포함되는지 어디에도 없다. R45(업로드)만 유일하게 명시했다.

| 해석 | 결과 |
|---|---|
| `편집` ⊅ `삭제` | 편집 권한자가 자기 문서를 삭제할 수 없어 **R52(휴지통)의 주체가 아무도 없다** |
| `편집` ⊇ `이동` | `D1`(비공개) 편집자가 문서를 `D2`(전사 공개)로 이동 → **관리 권한 없이 전사 공개.** R36("ACL 부여는 워크스페이스 관리자만")이 이동을 통해 우회된다. R43-5 프리뷰는 경고일 뿐 차단이 아니다 |

**제안**: Q11 레벨 표에 **조작 목록 열**을 추가해 전수 열거. 특히 **이동은 목적지의 유효 권한이 출발지보다 넓어질 때 `관리` 레벨을 요구**해야 R36 이 실효를 갖는다.

## C8 저장 트리거가 정의되지 않았다 — R1 과 R18·R61 의 충돌

**관련**: R1, R18, R61, R62, 수용기준 6 · **발견**: UI 축

옵시디언은 명시적 저장 없이 지속 자동 저장한다. R1 은 "에디터가 옵시디언과 동일"을 요구한다. 그런데 R18("**저장 시점에** 원본이 변경되었으면 병합")과 R61("**저장 시** 이전 본문을 `.versions` 에 보관")은 둘 다 **이산적 저장 이벤트**를 전제한다.

자동 저장이면 → A 가 한 글자 칠 때마다 B 화면에 머지 뷰가 반복 팝업되고, 타건마다 버전이 쌓여 R62 의 보관 개수를 몇 분 만에 순환 소모한다.
명시적 저장 버튼이면 → R1 의 "옵시디언과 동일"이 깨진다.

**제안**: "명시적 저장(Ctrl+S) + 이탈 시 확인"을 채택하고 R1 의 예외로 명문화. 자동 저장을 유지하려면 저장과 버전 스냅샷을 분리(디바운스·세션 단위 버전)해야 하며 별도 요구사항이 필요하다.

## C9 서버 정지 중 발생한 파일시스템 변경을 재조정하는 절차가 없다

**관련**: R4, R20-a, R14, R25 · **발견**: 저장 축

ACL 추종을 chokidar 실시간 감지(R20-a) **하나에만** 의존하는데 **기동 시 전체 재스캔 요구사항이 없다.** R20-a 는 "이동/개명"만 다루고 직접 생성·삭제의 DB 처리도 없다.

```
서비스 중지 중 운영자가 /임원전용/급여.md → /공지/ 로 이동 → 기동
→ ACL 행은 옛 경로에 잔존, 새 경로는 ACL 없음
→ R14(상속+가산)로 /공지/ 권한 상속 → 전 사원 열람
→ R25(완전 숨김) 때문에 관리자가 트리로 확인조차 불가
```

## C10 rename 판정 기준이 없어 ACL 이 엉뚱한 파일로 이식된다

**관련**: R20-a · **발견**: 저장 축

"chokidar 로 rename 을 감지"라고만 적혀 있고 **무엇을 근거로 unlink/add 쌍을 동일 노드로 판정하는지**(내용 해시·크기·inode·시간 창)가 없다. 판정 실패는 ACL 고아를, **오탐은 ACL 이식(권한 상승)** 을 낳는다.

보강 근거: Q2 구현 관점 분석에서 이미 "chokidar 는 rename 이벤트를 주지 않고 `unlink`+`add` 로 온다. **Windows 에서 `ino` 신뢰성은 불확실**"이 지적된 바 있다.

## C11 R40-b 가 세운 "파일시스템만으로 재구성" 원칙이 대부분의 데이터에 적용되지 않는다

**관련**: R40-b, R4, R52, R61, R20 · **발견**: 저장 축 (권한 축도 아카이브 경로로 지적)

`.workspace.json` 이 담는 것은 `{id, name, createdAt}` 뿐. **휴지통 원위치 인덱스(R52) · 버전 인덱스(R61) · ACL 전체(R20) · 사용자·그룹 · PAT** 는 전부 DB 단독이다. 선언한 원칙이 워크스페이스 식별자 하나에만 적용되는데 그 비대칭의 사유가 없다.

DB 손상 시 `.trash/` 는 **원래 어느 경로였는지 알 방법이 전혀 없고**, `.versions/` 는 어느 문서의 몇 번째 버전인지 알 수 없다. 두 디렉토리가 식별 불가능한 블롭 더미가 된다.

## C12 ★ 아카이브의 "DB 에서 분리"로 ACL 이 소실되고, 복구 절차·행위자가 없다

**관련**: R54, R55, R68, R29, R53 · **발견**: 3개 축 전부

- "DB 에서 분리"가 행 **삭제**인지 **플래그 비활성화**인지 **export** 인지 미정의
- **복구(un-archive) 요구사항 자체가 없다** (R53 의 복구는 휴지통 전용)
- R29 는 워크스페이스 **생성·삭제** 권한만 주고 R54 는 아카이브가 삭제와 다르다고 하여 **아카이브 행위자가 미정의**
- 아카이브 후 복구 시 ACL 이 비어 있으면 R14(가산만) 규칙상 아무도 접근 불가이거나, 구현에 따라 전원 공개 — **어느 쪽인지 결정 불가**
- 다른 워크스페이스에서 넘어오던 위키링크(R39)·즐겨찾기(R3-a)·벡터 인덱스(R13) 항목의 처리도 전부 없음

## C13 벡터 인덱스 수명주기가 없어 R22 필터가 우회된다

## H17 문서 이동·개명 시 `.versions` 추종이 미정의 — 남의 히스토리가 붙을 수 있다

**관련**: R61, R62, R65, R52, R20-a · **발견**: 저장 축 + 권한 축

R65 는 **`.res` 에 대해서만** 이동 처리를 규정한다. `/A/문서.md` → `/B/문서.md` 이동 후 나중에 `/A/문서.md` 라는 새 문서가 생기면 **남의 버전 히스토리가 붙는다.** 버전 열람·복원 권한도 §2.16 전체에 한 줄도 없다 — 문서를 공개로 전환하는 순간 **과거 비공개 버전 전체가 함께 열리는지** 알 수 없다.

## H18 휴지통·아카이브·미참조 첨부의 보존 정책이 전혀 없다

**관련**: R52, R67, R68, R65 · **발견**: 저장 축

버전에는 개수 상한(R62)이 있으나 **휴지통·아카이브에는 보존 기간·개수·용량 어느 정책도 없다.** 미참조 `.res` 정리는 R65 근거 문단에 "별도 정리 도구로 대응"이라고 **언급만 되고 요구사항으로 확정되지 않았다.** 대용량 바이너리(R46: 모든 형식 허용) 반복 업로드·삭제로 디스크가 차면 R61 의 버전 복사까지 실패한다.

## H19 1.0 → 2.0 이행이 R56 한 줄 외에 정의되지 않았다

**관련**: R56, R21, R50, R58, R13, R65 · **발견**: 저장 축
