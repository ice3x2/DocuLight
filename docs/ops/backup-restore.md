# 백업과 복원 런북

대상 요구사항 — `OPS-STORAGE-001` (원장 `R87`)

DocuLight 2.0 은 **두 저장소**에 상태를 나눠 둔다.

| 저장소 | 무엇이 있나 | 정본 근거 |
|---|---|---|
| `docsRoot` (파일시스템) | 문서 본문·첨부·`.workspace.json` 사이드카 | `DR-STORAGE-001` — 본문의 SSOT 는 파일시스템이다 |
| SQLite DB 파일 | 노드 ID·워크스페이스·사용자·그룹·ACL·감사 로그·재조정 대기열 | `DR-STORAGE-002` — 메타데이터의 단일 저장소 |

**둘을 같은 시점으로 묶어야 한다.** 시점이 갈리면 ACL 없는 파일이나 파일 없는
노드가 생긴다.

두 경로는 서버 설정이 정한다. 기본값은 `cwd` 아래 `.doculight-data/` 이고,
배포 환경이 `DOCULIGHT_DATA_DIR` · `DOCULIGHT_DOCS_ROOT` · `DOCULIGHT_DB_FILE`
로 바꾼다. 어느 자리를 쓰는지 먼저 확인하라.

---

## 1. 백업

### 1.1 절차

```
1) 서비스를 멈춘다
   pm2 stop doculight

2) 두 대상을 함께 스냅샷한다  ← 이 둘 사이에 아무 일도 일어나지 않아야 한다
   <docsRoot>          디렉토리 전체
   <databaseFile>      그리고 같은 이름의 -wal · -shm 파일이 있으면 함께

3) 서비스를 다시 띄운다
   pm2 start doculight
```

### 1.2 왜 멈추고 뜨는가

서비스가 도는 동안 두 대상을 각각 복사하면 그 사이에 일어난 쓰기가 한쪽에만
들어간다. **멈추는 것이 두 시점을 하나로 만드는 가장 단순한 방법**이고,
사내 단일 인스턴스 규모에서는 그 정지 시간이 문제가 되지 않는다
(`CON-ARCH-001`).

`-wal` 파일을 함께 담는 이유 — DB 를 WAL 모드로 열기 때문에(`database.ts`)
가장 최근 쓰기가 아직 본 파일에 병합되지 않았을 수 있다. 본 파일만 담으면
그 쓰기가 사라진다. 정상 종료된 뒤라면 WAL 은 비어 있지만, 프로세스가
비정상 종료된 경우를 위해 있으면 함께 담는다.

### 1.3 배포 환경이 정할 자리

원장이 정하지 않았으므로 여기서 지어내지 않는다. 배포할 때 정하라.

- **백업 도구** — `tar`·`robocopy`·스토리지 스냅샷 중 무엇을 쓸지
- **주기** — 하루 1회인지 그보다 잦은지
- **보관 위치와 보관 기간** — 어디에 몇 벌을 남길지

## 2. 복원

### 2.1 절차

```
1) 서비스를 멈춘다
   pm2 stop doculight

2) 백업의 두 대상을 제자리에 되돌린다
   <docsRoot>          디렉토리 전체
   <databaseFile>      (있으면 -wal · -shm 포함)

3) 서비스를 띄운다
   pm2 start doculight

4) 재조정 대기열을 확인한다   ← 건너뛰지 마라
```

### 2.2 4단계를 건너뛰면 안 되는 이유

**복원 직후의 스캔은 자동이다.** 기동이 다음 순서를 밟는다.

1. `.workspace.json` 사이드카로 워크스페이스를 재구성한다 (`DR-WORKSPACE-002`)
2. 워크스페이스가 하나도 없으면 기본 워크스페이스를 만든다 (`FR-WORKSPACE-006`)
3. `docsRoot` 와 DB 를 전체 재조정한다 (`REL-STORAGE-001`)

운영자가 스캔을 따로 실행할 필요는 없다 (`OPS-STORAGE-001` AC-2). 그러나
**스캔이 찾아낸 것을 처분하는 일은 자동이 아니다.**

시점이 어긋난 백업으로 복원하면 재조정이 두 방향의 차이를 발견하고, 각각을
재조정 대기열에 **미해소** 항목으로 남긴다 (`AC-3`).

값의 정본은 코드다 — 유형명은 `packages/server/src/domain/reconciliation/vocabulary.ts`,
격리 자리는 `packages/server/src/domain/workspace/quarantine.ts` 다. 아래 표는 그것을
읽는 사람을 위한 안내이지 정의가 아니다.

| 상황 | 재조정이 하는 일 | 대기열 항목 |
|---|---|---|
| 파일은 있는데 DB 에 노드가 없다 | 노드를 새로 만든다. **부모에서 권한을 상속하므로 원래보다 넓게 보일 수 있다** | `unregistered-file` |
| DB 에 노드가 있는데 파일이 없다 | 노드를 지우지 않고 tombstone 으로 표시한다 | `missing-file` |
| 같은 `id` 를 가진 `.workspace.json` 이 둘이다 | 자기 자리에 있지 않은 쪽을 `docsRoot/.quarantine/` 로 옮긴다 | `duplicate-workspace-sidecar` |

이 목록을 아무도 보지 않으면 안전망이 작동하지 않는다. 특히 첫 행은 **권한이
일시적으로 넓어질 수 있는 자리**라 사람이 확인해야 한다.

### 2.3 `cp -r` 로 만든 사본을 `docsRoot` 안에 두지 마라

워크스페이스 디렉토리를 `docsRoot` 안에 복사해 두면 같은 `id` 를 가진
사이드카가 둘이 된다. 기동 시 재조정이 **자기 `id` 로 이름 붙은 디렉토리에
있지 않은 쪽**을 `docsRoot/.quarantine/` 으로 옮기고 대기열에 남긴다
(`DR-WORKSPACE-002` AC-5).

옮기기만 하고 지우지 않는다 — 사본과 원본을 자동으로 판별할 수 없으므로
사람이 판단할 때까지 둘 다 남긴다. 확인한 뒤 `.quarantine/` 을 비우는 것은
운영자의 몫이다.

백업 사본은 `docsRoot` **밖**에 둬라.

## 3. 확인 목록

복원 뒤 이 넷을 확인한다.

- [ ] `pm2 list` 에 `doculight` 프로세스가 **1개** 떠 있다 (`OPS-ARCH-001` AC-2)
- [ ] 브라우저에서 서버 포트로 접속이 열린다 — 기본값의 정본은
      `packages/server/src/config/config.ts` 의 `DEFAULT_PORT` 이고, 배포가
      `PORT` 로 덮었다면 그 값이다
- [ ] 워크스페이스 목록이 복원 전과 같다
- [ ] 재조정 대기열의 미해소 항목을 전부 확인했다 (§2.2)
