# 1.0 동결과 읽기 전용 컷오버 런북

대상 요구사항 — `MIG-AUTH-001` · `MIG-AUTH-002` · `CON-ARCH-002` AC-8 (원장 `R93` · `R21`)

1.0 에서 2.0 으로 넘어가는 것은 **읽기 전용 컷오버**다. 두 인스턴스를 모두 쓰기
가능한 상태로 병행 운영하지 않는다 — 같은 문서의 두 사본이 각자 편집되면 어느
쪽이 정본인지 정할 방법이 없어진다(감사 `H19`).

이 문서는 그 컷오버의 **운영 절차**이며, 아래 「동결의 성격」이 밝히는 대로
동결 자체가 코드가 아니라 이 문서로 성립한다.

---

## 0. 동결의 성격 — 무엇으로 동결하는가

**1.0 의 동결은 기술적 강제가 아니라 운영 규약이다.** 그렇게 정한 근거가 셋 있다.

1. **1.0 저장소를 고칠 수 없다.** `C:\Work\git\DocuLight\DocLight` 는 읽기
   전용으로 다루기로 한 것이 이 이행의 전제다. 그 안에 편집을 막는 코드를 넣는
   것은 곧 그 저장소를 고치는 것이다.
2. **서비스를 멈추거나 프록시로 막지 않는다** (2026-08-25 사용자 결정 3-A).
   그렇게 하면 `MIG-AUTH-001` AC-2(이행 뒤에도 읽기 전용 참조로 열람할 수
   있다)와 `CON-ARCH-002` AC-8(동결된 상태로 운영 가능하게 유지된다)이 함께
   깨진다. 동결은 **끄는 것이 아니라 쓰기를 그만두는 것**이다.
3. **2.0 은 1.0 의 편집 경로에 개입할 위치에 없다.** 두 리포는 별개 프로세스이며
   `CON-ARCH-002` AC-4 가 2.0 의 어떤 설정도 1.0 경로를 가리키지 못하게 한다.

그래서 `MIG-AUTH-001` AC-1(「이행 시점부터 1.0 에서 문서를 편집하려는 시도가
거부된다」)의 성립 근거는 이 문서의 §2 이고, 그 성격은 **조직 규약**이다.
이것을 코드로 재려 하지 마라 — 잴 자리가 없다.

## 1. 이행 절차

### 1.1 준비

이행 전에 2.0 이 한 번은 기동해 있어야 한다. 기본 워크스페이스 `workspace` 가
최초 기동에 만들어지고(`FR-WORKSPACE-006` · `R56`) 이행이 그 자리를 대상으로
삼기 때문이다.

1.0 쪽에서 확인할 두 경로:

| 무엇 | 어디 | 확인 방법 |
|---|---|---|
| 계정 파일 | `<1.0>/data/users.json` | `{ version, users[], updatedAt }` 형태다 |
| 문서 루트 | `<1.0>/config.json5` 의 `docsRoot` | 상대 경로면 1.0 저장소 기준이다 |

1.0 의 벡터 인덱스(`<1.0>/data/vector/`)는 **경로를 확인할 필요조차 없다** —
이행이 그것을 인자로 받지 않는다. 아래 §1.3 이 그 이유를 적는다.

### 1.2 계정 이행

```
cd <2.0>/packages/server
npm run migrate -- --legacy-users <1.0>/data/users.json
```

이행이 하는 일과 하지 않는 일:

| 하는 일 | 근거 |
|---|---|
| 1.0 계정을 원래 상태와 무관하게 전원 `active` 로 세운다 | `MIG-AUTH-002` AC-1 |
| 그 계정이 `default` 그룹 앞으로 부여된 권한을 받게 한다 | `MIG-AUTH-002` AC-2 · `R60-a` |
| 1.0 의 bcrypt 해시(`$2b$`)를 **그대로** 옮긴다 | `MIG-AUTH-002` AC-3 · `R57` |

| 하지 않는 일 | 근거 |
|---|---|
| 1.0 의 전역 API Key(`userKey` · `userKeyHash`)를 옮기지 않는다 | `MIG-AUTH-002` AC-4 · `R58` |
| 사용자에게 비밀번호 변경을 요구하지 않는다 | `MIG-AUTH-002` AC-3 |

**사용자는 기존 비밀번호로 그대로 로그인한다.** 계정 이름은 1.0 의 이메일 주소다.

### 1.3 콘텐츠 이행

```
cd <2.0>/packages/server
npm run migrate -- --legacy-docs <1.0 docsRoot>
```

| 하는 일 | 근거 |
|---|---|
| `docsRoot` 아래 **전부**를 기본 워크스페이스로 복사한다 | `MIG-AUTH-001` AC-3 |
| 마크다운이 아닌 파일도 바이트 그대로 복사한다 | `MIG-AUTH-001` AC-4 |
| 복사한 파일에서 노드 트리를 세운다 | `REL-STORAGE-001` 재조정 경로 |
| 벡터 인덱스를 2.0 에서 새로 세운다 | `MIG-AUTH-001` AC-5 |

**1.0 의 벡터 인덱스는 옮기지 않는다.** 2.0 의 임베딩은 신규 작성물이라(`R21-a`)
1.0 이 HNSWLib 으로 만든 벡터는 이 공간의 값이 아니다 — 옮기면 좌표계가 다른
수를 같은 축에서 재게 된다.

이행은 **두 번 돌려도 안전하다.** 계정은 같은 이름을 건너뛰고, 콘텐츠는 이미 있는
파일을 덮지 않는다. 도중에 끊겼을 때 다시 부르는 것이 정상 복구 경로다.

### 1.4 이행 확인

| 확인할 것 | 방법 |
|---|---|
| 계정이 다 왔나 | 1.0 `users.json` 의 사용자 수와 2.0 설정 모달의 사용자 목록 수를 대조 |
| 기존 비밀번호로 들어가지나 | 이행된 계정 하나로 실제 로그인 |
| 문서가 다 왔나 | 1.0 `docsRoot` 의 파일 수와 2.0 기본 워크스페이스의 트리를 대조 |
| 비-md 가 왔나 | 이미지가 있는 문서를 열어 그림이 보이는지 확인 |

## 2. 동결 선언 — 이행 시점부터 지키는 것

이행이 끝난 시점부터 다음을 지킨다. **이것이 `MIG-AUTH-001` AC-1 의 내용이다.**

1. **1.0 에서 문서를 편집하지 않는다.** 새 문서 작성·기존 문서 수정·삭제·이동
   전부 2.0 에서 한다.
2. **1.0 은 계속 띄워 둔다.** 멈추지 않는다 — 읽기 전용 참조로 남기는 것이
   `R21` 의 「1.0 계속 운영」이고 `CON-ARCH-002` AC-8 이 요구하는 상태다.
3. **1.0 에서 편집을 시도한 사람에게는 2.0 을 안내한다.** 1.0 은 그 시도를
   기술적으로 막지 못하므로, 막는 것은 사람이다. 이행 공지에 그 사실을 적는다.
4. **1.0 에 새로 들어온 편집이 발견되면 손으로 2.0 에 옮긴다.** 이행을 다시
   돌리면 안 된다 — 이행은 이미 있는 파일을 덮지 않으므로 그 편집이 반영되지
   않고, 반영하려고 덮게 만들면 2.0 에서 한 편집이 1.0 판으로 되돌아간다.

### 2.1 전역 API Key 클라이언트

1.0 의 전역 API Key 는 **유예 없이** 폐기된다(`MIG-AUTH-002` AC-4 · `R58`).
그 키를 쓰던 클라이언트가 2.0 에 요청하면 거부되며, 거부 응답이 갈아탈 곳을
함께 알려 준다(`MIG-AUTH-002` AC-5):

> 1.0 전역 API Key 는 이행 시점부터 인정되지 않습니다. 유예 기간은 없습니다.
> 개인 액세스 토큰(PAT)을 발급받아 Authorization: Bearer 헤더로 보내십시오.

**발급 화면은 아직 서지 않았다.** PAT 발급·폐기의 사용자 표면은 `SEC-AUTH-005`
의 축이며 이 이행의 범위 밖이다 — 그 화면이 설 때까지 토큰이 필요한 클라이언트는
운영자가 개별로 처리한다. 이 사실을 이행 공지에 함께 적어라. 없는 화면을
가리키는 안내는 안내가 아니다.

## 3. 해제 조건

**원장은 1.0 동결의 운영 기간과 해제 조건을 정하지 않았다**(`CON-ARCH-002`
Implementation Notes). 두 리포가 동시에 살아 있는 동안 볼트를 공유하는지도
규정되지 않았다.

그러므로 이 문서는 해제 절차를 담지 않는다. 1.0 을 내리기로 결정하는 시점에
그 결정을 원장 조항으로 세운 뒤 이 문서에 절차를 더하라.
