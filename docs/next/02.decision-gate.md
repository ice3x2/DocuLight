# 결정 1 — 옛 버전(1.0) 코드를 어디까지 가져다 쓸 것인가

## 배경부터

이 제품에는 **이전 버전이 있다.** 그것을 1.0 이라 부르고, 지금 만드는 것이 2.0 이다.

원장에 이런 조항이 있다:

> **`R21`** — DocuLight2.0 을 새 리포로 두고, **1.0 의 백엔드 자산을 이식한다.** 프론트엔드는 신규 작성한다. 1.0 은 동결하여 계속 운영한다.

「이식한다」는 곧 **옛 코드를 가져다 쓴다**는 뜻이다. 처음부터 다 새로 만들지 않겠다는 결정이다.

## 그래서 문제가 뭔가

**두 가지다.**

### ① 가져올 코드가 이 저장소 안에 없다

1.0 은 여기 있다:

```
C:\Work\git\DocuLight\DocLight
```

지금 우리가 작업하는 곳은:

```
C:\Work\git\DocuLight2.0
```

**서로 다른 폴더다.** 그리고 2.0 의 어떤 설정 파일도 1.0 이 어디 있는지 적어 두지 않았다. `package.json` 에도, 문서에도 없다.

이게 왜 문제냐 — **새로 합류한 사람이 "1.0 자산을 이식하라"는 요구사항을 읽고, 그 1.0 이 어디 있는지 찾을 방법이 없다.** 지금은 이 문서가 유일한 단서다.

> 참고로 1.0 은 실재한다. 확인해 보니 JavaScript 파일 **129개**가 있고, 로그인 처리(`auth.js`)·설치 가드(`setup-guard.js`)·사용자 저장소(`user-store.js`)·그룹 저장소(`group-store.js`)·MCP 서버(`mcp.js`) 같은 것들이 들어 있다. 없는 것을 가정한 게 아니다.

### ② 「이식」이 복사-붙여넣기가 아니다

이게 더 중요하다. 조사해 보니 **1.0 과 2.0 의 구조가 세 군데에서 근본적으로 다르다.**

#### 다름 ① — 데이터를 어디 저장하는가

| | 1.0 | 2.0 요구사항 |
|---|---|---|
| 사용자·그룹 저장 | **JSON 파일** (`user-store.js` 가 파일에 씀) | **SQLite 데이터베이스** (`DR-STORAGE-002`) |

JSON 파일에 저장하던 것을 데이터베이스로 옮기는 것은 **저장 방식 자체를 바꾸는 일**이다. 코드를 그대로 가져다 쓸 수 없다.

#### 다름 ② — 권한을 어떻게 표현하는가

이것이 가장 크다.

| | 1.0 | 2.0 요구사항 |
|---|---|---|
| 시스템 그룹 | `Superuser` / `Editor` / `Viewer` **셋** | `슈퍼유저` / `default` **둘** |
| 권한이 붙는 곳 | **그룹에** 붙는다 (그룹이 `permissions` 목록을 가짐) | **문서·폴더에** 붙는다 (노드마다 ACL 항목) |

말로 풀면 이렇다.

- **1.0 방식**: *"너는 Editor 그룹이야. Editor 는 편집할 수 있어."* → 권한이 **사람 쪽**에 붙어 있다.
- **2.0 방식**: *"이 폴더는 김대리에게 편집 권한을 줬어."* → 권한이 **문서 쪽**에 붙어 있다.

**이건 완전히 다른 사고방식이다.** 그리고 2.0 의 유일한 차별점이 바로 이 문서/폴더 단위 권한 관리다. 즉 **제품의 핵심이 되는 부분은 1.0 에서 가져올 게 없다.**

#### 다름 ③ — 프로그래밍 언어와 모듈 방식

| | 1.0 | 2.0 |
|---|---|---|
| 언어 | JavaScript | **TypeScript** |
| 모듈 | CommonJS (`require`) | **ESM** (`import`) |

이것도 그대로 복사되지 않는다. 그리고 **이 경계를 어떻게 넘을지 정한 요구사항이 없다.**

## 그래서 실제로 「이식」할 수 있는 건 뭔가

조사 결과를 정리하면 이렇다.

| 가져다 쓸 수 있는 것 | 새로 만들어야 하는 것 |
|---|---|
| 로그인 처리 (`bcrypt` 로 비밀번호 암호화) | **사용자·그룹 데이터 모델** |
| 로그인 시도 횟수 제한 (rate limit) | **권한(ACL) 계층 전체** |
| 설치 마법사의 차단 로직 | 저장소를 파일에서 DB 로 |
| MCP 도구 목록·LangChain 파이프라인 | 언어·모듈 방식 전환 |

**한 줄 요약**: 로그인 같은 *주변 장치*는 가져올 수 있지만, **사용자·그룹·권한이라는 *핵심*은 신규 작성**이다.

## 무엇을 정해야 하나

### 정할 것 A — 1.0 저장소를 공식 참조 대상으로 등록할 것인가

| 선택지 | 뜻 | 대가 |
|---|---|---|
| **ⓐ 등록한다** | 2.0 문서 어딘가에 1.0 경로를 적고, 이식할 파일 목록을 만든다 | 두 저장소가 묶인다. 1.0 이 옮겨지거나 지워지면 2.0 문서가 거짓이 된다 |
| **ⓑ 등록하지 않는다** | 필요할 때 사람이 찾아서 본다 | 새로 합류한 사람이 못 찾는다. 지금 상태 |
| **ⓒ 필요한 것만 복사해 온다** | 이식할 파일을 2.0 안으로 미리 옮겨 놓는다 | 1.0 이 나중에 고쳐져도 따라오지 않는다 |

### 정할 것 B — 「이식」의 범위를 요구사항에 적을 것인가

지금 원장 `R21` 은 *"백엔드 자산을 이식한다"* 라고만 적혀 있어서, **어디까지가 이식이고 어디부터가 신규인지 읽는 사람마다 다르게 판단한다.**

위의 표(가져다 쓸 것 / 새로 만들 것)를 **조항으로 못박을지** 결정해야 한다. 안 그러면 개발자 A 는 1.0 권한 코드를 가져다 고치려 하고, 개발자 B 는 새로 짜서, 나중에 합쳐지지 않는다.

## 언제까지 정해야 하나

**서버 개발을 시작하기 전**이다. 구현 계획상 wave 1(서버·DB 만들기)이 시작되는 시점이고, 그 전 단계인 wave 0(테스트 환경 정비)은 이 결정 없이도 진행할 수 있다.

# 결정 2 — 문서 검색 기능을 누가 정의할 것인가

## 배경부터

옵시디언에는 왼쪽에 **검색 탭**이 있다. 문서 전체에서 단어를 찾는 기능이다. DocuLight 2.0 도 그것을 따라 하기로 했다.

## 문제 — 검색이 "있다"고 다들 전제만 하고, 아무도 정의하지 않았다

원장을 전부 뒤져 봤다. 검색을 언급하는 조항은 이렇게 있다:

| 조항 | 뭐라고 하나 | 실제로 정하는 것 |
|---|---|---|
| `R3` | 좌측 사이드바에 `문서 트리 / 검색 / 즐겨찾기` 탭을 둔다 | **탭이 있다**는 것만 |
| `R80` | 검색 **결과**에서 권한 없는 문서를 걸러 낸다 | 결과를 거르는 방법 |
| `R106-a` | 태그를 클릭하면 검색 탭이 열리고 **질의가 채워진다** | 검색창에 글자가 들어간다는 것 |
| `R39` | 검색은 워크스페이스 **경계를 넘는다** | 검색 범위 |
| `R13`·`R22` | 1.0 의 **벡터검색**을 가져오고 권한으로 거른다 | AI 검색 이야기 |

**보이는가?** 전부 *"검색이 이미 있다"* 를 전제하고 그 **주변**을 정하고 있다.

정작 이런 게 없다:

- **무엇을 검색하나?** 문서 제목만? 본문도? 태그도? 첨부파일 이름도?
- **어떻게 입력하나?** 그냥 단어만? `AND`/`OR` 같은 게 되나? 따옴표로 정확히 일치는?
- **결과를 어떻게 보여주나?** 문서 목록만? 본문 일부를 미리보기로?
- **범위를 고를 수 있나?** 전체 검색? 이 워크스페이스만?

## 이게 왜 지금 문제가 되나

Phase 1 이 끝났는지 판정하는 **수용 기준 13개**가 원장에 있다. 그중 3번이 이렇게 적혀 있다:

> **`R80` 이 정한 표면 전부에서 권한 밖 문서가 걸러진다**

그리고 `R80` 이 말하는 「표면」 목록에 **검색 결과**가 들어 있다.

즉 — **검색 결과에서 권한 필터가 제대로 도는지 시험해야 Phase 1 을 끝낼 수 있는데, 검색 자체가 정의되지 않아 시험할 대상이 없다.**

## 이건 「미결 공백」과 다르다

원장에는 이미 **미결 공백**이라는 개념이 있다. `G8`·`G10` 처럼 *"결정을 안 한 것"* 을 번호로 적어 두는 것이다.

그런데 검색은 성격이 다르다.

| | 미결 공백 (`G{n}`) | 이번 경우 |
|---|---|---|
| 상태 | 무엇을 정해야 할지는 안다. 답만 안 정했다 | **정해야 한다는 사실 자체가 기록된 적 없다** |
| 예 | *"감사 로그 보존 기간의 기본값을 며칠로 할까?"* | *"검색이라는 기능이 통째로 없다"* |

그래서 이걸 **요구 공백**이라 부른다. 빠뜨린 게 *답*이 아니라 *질문*이다.

## 무엇을 정해야 하나

| 선택지 | 뜻 | 대가 |
|---|---|---|
| **ⓐ 조항으로 세운다** | 원장에 `R149` 같은 새 조항을 만들어 검색을 정의한다 | 지금 설계 시간이 든다. 대신 Phase 1 판정이 가능해진다 |
| **ⓑ 공백으로 연다** (`G36`) | *"검색이 정의되지 않았다"* 를 미결로 등록만 하고 나중에 정한다 | 지금은 편하다. 대신 Phase 1 완료 선언을 그때까지 못 한다 |
| **ⓒ 1.0 것을 쓴다고 정한다** | `R13` 의 벡터검색을 그대로 검색 탭에 연결한다 | 옵시디언식 텍스트 검색과 AI 벡터검색은 **다른 기능**이다. 사용자 기대와 어긋날 수 있다 |
| **ⓓ Phase 2 로 미룬다** | Phase 1 에서는 검색 탭을 비활성으로 둔다 | 수용 기준 3 에서 검색을 빼야 한다. `R3`·`R80`·`R106-a` 도 함께 손봐야 한다 |

> **참고 — ⓒ 를 고른다면 확인할 것**: `R3` 이 말하는 검색 탭은 옵시디언을 따라 한 것이고, 옵시디언의 검색은 **글자 그대로 찾는 텍스트 검색**이다. `R13` 의 벡터검색은 *"뜻이 비슷한 문서를 찾는"* AI 기능이라 성격이 다르다. 둘 다 필요할 수도 있다.

## 언제까지 정해야 하나

**Phase 1 을 끝냈다고 선언하기 전**이다. 구현 순서상으로는 wave 6(링크·검색) 이전이므로 시간 여유는 있다.

## 정하고 나면

두 결정 모두 **원장(`docs/spec/00.decision-log.md`)에 반영**하면 된다.

- 조항을 세우면 → `§2.x` 에 `R{n}` 추가 + `§5 변경 이력` 에 한 줄
- 공백을 열면 → `§3.2` 에 `G{n}` 추가

그리고 원장을 고치면 **그 조항을 인용하는 모든 자리를 함께 훑어야 한다**(`R124-a`). 이제는 SRS 요구사항(`docs/spec/*.srs.md`)도 원장을 가리키므로 거기까지 닿는다.
