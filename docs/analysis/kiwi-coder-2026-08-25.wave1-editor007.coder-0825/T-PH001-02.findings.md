## 2. 판정 ② 가 막힌 원인 — 범위 밖 heightmap drift

CM6 의 `posAtCoords` 는 non-Text 블록을 이렇게 처리한다
(`@codemirror/view/dist/index.js`, `posAtCoords`):

```js
if (block.type != BlockType.Text)
    return yOffset < (block.top + block.bottom) / 2 ? PosAssoc(block.from, 1)
                                                    : PosAssoc(block.to, -1);
```

둘 다 표 범위 **안**이므로 경계 포함 겹침 판정이면 드러나야 한다. 그런데 실제로는
`elementAtHeight(yOffset)` 이 표 블록을 **집지 못한다** — CM6 의 heightmap 이 표를
DOM 보다 **37.7px 위**에 놓고 있기 때문이다.

```
표의 DOM rect        : 351.7 – 453.3
CM6 heightmap block  : 314.0 – 415.6   (drift -37.7)
```

drift 는 문서를 내려가며 **mermaid/코드 블록마다 누적**된다(문서 처음 -2 → 표 앞
-39.7). 원인은 `packages/editor/src/styles/editor.css` 의 `.dl-mermaid { margin: 0.6em 0 }`
이다 — CM6 는 블록 위젯 높이를 `getBoundingClientRect` 로 재고 그 값은 **margin 을
빼고 padding 을 넣는다.** 같은 함정이 표에서는 이미 잡혀 있고, `.cm-atomic-table`
의 CSS 주석이 그 사실과 증상("클릭이 한 줄 아래로 라우팅된다")을 그대로 적어 두었다.
mermaid 쪽에는 그 교정이 적용되지 않았다.

**이것은 이 Task 의 변경과 무관한 선재 결함이다.** `table-widget.ts` 를 기준선으로
되돌리고 같은 측정을 해도 drift 는 -39.7 로 동일하다. 표뿐 아니라 문서 아래쪽의
평범한 문단 클릭도 어긋난다:

- 「인용문입니다.」(92행) 클릭 → 커서 **93행**(빈 줄)
- 「[[위키링크]] …」(98행) 클릭 → 커서 **99행**(빈 줄)

브라우저에서 `.dl-mermaid { margin: 0 }` 만 덮어써 drift 를 0 으로 만들면
판정 ② 가 **즉시 PASS** 한다(커서 96행, 위젯 0개, 원문 드러남, 초점 유지).

`.dl-mermaid` 는 테두리와 배경을 갖고 있어 margin 을 padding 으로 바꾸면 상자가
1.2em 커져 보인다. 겉보기를 보존하려면 시각 상자를 바깥 컨테이너로 한 겹 감싸고
그 컨테이너가 여백을 갖게 해야 한다 — `mermaid-blocks.ts` 의 `toDOM` 과 CSS 를
함께 고치는 일이며, `sidecar.files[]` 밖이고 `FR-EDITOR-007` 의 범위도 아니다.

## 3. 판정 ③ — R-08 분기 ⓑ 가 확정됐다

분기 ⓐ 를 먼저 시도했다: 재구성 조건을 선택 이동·초점 변화까지 넓히고 겹침 판정을
경계 포함(`range.from <= to && range.to >= from`)으로 두었다. 그러고도 화살표는
표를 건너뛴다 — drift 를 걷어낸 상태에서도 92 → 93 → **97** 로 94-96 을 통째로 넘는다.

원인은 CM6 의 설계다. 수직 이동은 `posAtCoords(..., scanY)` 를 쓰고, 그 함수는
**Text 블록을 만날 때까지 루프를 돌며 위젯 블록을 의도적으로 건너뛴다**:

```js
block = view.elementAtHeight(yOffset);
if (scanY == null) break;
if (block.type == BlockType.Text) { ...; break; }
let halfLine = view.viewState.heightOracle.textHeight / 2;
yOffset = scanY > 0 ? block.bottom + halfLine : block.top - halfLine;
```

`EditorView.atomicRanges` 와는 무관하며 데코레이션 축으로는 풀리지 않는다. keymap 을
새로 만들지 않는 한 판정 ③ 은 서지 않는다 — 계획 `R-08` 의 분기 ⓑ 조건에 정확히
해당한다. 이 저장소의 다른 블록 위젯(mermaid·코드)도 같은 이유로 화살표 진입이
없으며, 그것들의 브라우저 시험도 클릭으로만 잰다.

## 4. 칸 여백·이미지의 `pointerdown` 취소 — 계획 §5.4 에 남긴다

**앞선 초안에서 「걷을 것이 없다」고 적었던 것은 틀렸다.** 독립 리뷰가 그 오류를
잡았고 브라우저로 다시 재어 확인했다. 실제로는 클릭 지점에 따라 갈린다.

| 클릭 지점 | 결과 | 초점 |
| --- | --- | --- |
| 칸 본문 `.cm-atomic-table-cell-source` | **드러난다** (커서 96행, 위젯 0개) | `.cm-content` |
| 칸 여백 (td 안, source 상자 바깥 2px) | 드러나지 않는다 (위젯 1개, 커서 92행 그대로) | `.cm-atomic-table-cell-source` |

원인은 `pointerdown` 취소다. `attachCellEditing` 의 cell 핸들러는 대상이 source
**바깥**일 때 `preventDefault()` 하고, 취소된 `pointerdown` 은 호환 `mousedown` 을
억제하므로 CM6 가 그 제스처를 보지 못한다. 같은 구조가 이미지 핸들러
(`refreshCellPreview`)와 링크 아이콘 핸들러에도 있다. 칸 본문 클릭은 그 핸들러가
일찍 반환해 취소하지 않으므로 CM6 로 넘어간다.

계획 §5.4 가 이 경로의 조건을 미리 정해 두었다 — 걷었을 때 이미지 처리나 칸 편집이
깨지면 남기되 **칸 본문 클릭 경로는 반드시 서야 한다.** 칸 본문 경로는 위 표대로
선다. 그래서 이 취소는 **걷지 않고 남긴다.** 사유 셋이다.

1. AC-7 본 판정의 대상인 칸 본문 경로가 이미 성립한다 — 걷어야만 서는 것이 아니다.
2. 이미지 핸들러를 편집 모드에서만 걷으려면 `refreshCellPreview` 에 `view`/readOnly 를
   새로 흘려야 한다. 호출 지점이 둘(`makeCell` · `commit`)이라 헬퍼 시그니처가 바뀐다.
3. **그 세 경로를 재는 시험이 저장소에 하나도 없다**(`pointerdown` 을 다루는 시험 0건).
   걷었다가 이미지 칸 편집이 깨져도 어떤 시험도 울지 않는다.

남는 결과는 **클릭 지점에 따른 동작 분기**다: 칸 본문을 누르면 원문이 드러나고,
칸 여백·이미지·링크 아이콘을 누르면 종전대로 칸 편집으로 들어간다. `DI-W1-02`
(원문 노출이 칸 직접 편집보다 우선한다)를 문자 그대로 적용하면 세 경로도 드러나야
하므로, 이 분기는 후속으로 정리할 거리다.

## 5. 확인한 부수 사실

- 칸을 눌러 드러날 때 초점은 `.cm-content` 에 남는다(`view.hasFocus === true`,
  `document.activeElement.className === 'cm-content cm-lineWrapping'`). `R-06` 이
  경고한 초점 유실은 이 경로에서 일어나지 않는다.
- 반대로 칸 여백을 누르면 초점이 `.cm-atomic-table-cell-source` 로 가고
  `view.hasFocus` 가 거짓이 된다 — 위 §4 의 분기가 그대로 관측된다.
