## M1 [MEDIUM] `FR-SHELL-006` — 404 규범 복제와 자기모순

### 맞았는가 — (b) 맞음 · (c) 맞음 · (a) 절반만 맞음

**(b) 복제와 자기모순 — 맞다.** 정본을 직접 읽어 확인했다.

`SEC-ACL-006`(`docs/spec/10.access-control.srs.md:598`) 은 원장 `R94` 를 정본으로 삼고, AC 6건이 딥링크 표면까지 전부 덮는다:

- AC-1 권한 없는 노드 API 요청 → 404
- AC-2 존재하지 않는 노드도 404이며 **본문과 헤더가 동일**
- AC-3 권한 부족 문구·코드 없음, 403 미사용
- AC-4 두 경우가 **같은 코드 경로**
- AC-5 MCP 응답에도 동일 적용
- **AC-6 「딥링크로 권한 없는 노드를 열면 화면이 존재하지 않는 노드와 같은 404 를 보여준다」**

`FR-SHELL-006` 의 옛 AC-3 「권한 없는 노드의 딥링크로 접근하면 존재하지 않는 노드와 구별할 수 없는 404 응답을 받는다」는 AC-6 에 **잔여 없이 포함**된다. 정본이 실제로 덮으므로 삭제가 안전하다.

원장 `R99`(`00.decision-log.md:37`) 자체가 이미 참조 구조였다 — *"권한 없는 노드에 대한 접근은 **404(R94)** 로 응답한다"* 로 괄호 안에 `R94` 를 명시한다. 즉 404 는 `R99` 의 고유 규범이 아니라 `R94` 인용이다. SRS 가 그 인용을 규범으로 펼친 것이 오류였고, 같은 블록 Implementation Notes ①의 *"이 요구가 그 규칙을 복제하지 않는다"* 선언과 문면이 정면으로 모순됐다.

**(c) Trace Links 에 `Requirement` 행 부재 — 맞다.** 옛 Trace Links 는 `Doc … #R99`·`#R99-a` 둘뿐이라 "`ACL` 이 소유한다"는 주장이 그래프에서 검증 불가였다.

**(a) Single Requirement Principle — 절반만 맞다.** 세 규범 중 **404 만 분리 대상**이고 ①③(노드 ID URL · 뒤로·앞으로)은 분리 대상이 아니다. 판정 근거:

- 404 는 scope(`ACL` vs `SHELL`)·소유자·위험 등급(`SEC-ACL-006` 은 `Risk=high`, `FR-SHELL-006` 은 `medium`)이 모두 다르다 → §29.1-②③ 분리 대상. 이미 `SEC-ACL-006` 으로 분리돼 있으므로 **새 ID 를 만들 필요 없이 중복만 제거**하면 된다.
- 브라우저 뒤로·앞으로(옛 AC-5)는 **분리하지 않는다.** ① 원장 `R99` 가 딥링크·노드 ID·뒤로앞으로를 하나의 결정으로 확정한다 ② scope 동일(`SHELL`) · Verification Method 동일(`test`) · 설계서 근거 절 동일(`03.screen-design-shell.md` URL 라우팅 절) ③ URL 이 문서 상태를 반영하는 것과 히스토리 이동은 같은 라우팅 기제의 두 면이라, 분리하면 서로 없이는 만족될 수 없는 요구 둘이 생긴다. §29.1 은 *검증 방법과 소유 scope 가 다를 때* 분리하라고 하며 여기서는 둘 다 같다.

### 무엇을 어떻게 고쳤는가

**① Requirement 문면** (`edit_requirement_fields`)

- before: `문서 딥링크(URL 라우팅)를 제공한다. URL 에는 경로가 아니라 노드 ID 를 사용하고, 권한 없는 노드에 대한 접근은 존재하지 않는 노드와 구별할 수 없는 404 로 응답한다. 브라우저 뒤로·앞으로가 동작한다.`
- after: `문서 딥링크(URL 라우팅)를 제공한다. URL 에는 경로가 아니라 노드 ID 를 사용하고 브라우저 뒤로·앞으로가 동작한다. 권한 없는 노드에 대한 404 통일 규칙은 SEC-ACL-006 이 소유하며 이 요구가 정하지 않는다.`

규범을 지우되 **정본 포인터는 문면에 남겼다** — 이 요구만 읽는 독자가 404 규정이 없다고 판단하지 않게 하기 위해서다.

**② Acceptance Criteria** (`replace_acceptance_criteria`) — 옛 AC-3(404) 제거, 나머지 4건 유지. ID 는 도구가 재번호했다(옛 AC-4→AC-3, 옛 AC-5→AC-4). 요구 ID 는 §11.4-③ 대로 `FR-SHELL-006` 유지.

**③ Trace Links** (`add_trace_link`) — `Requirement | SEC-ACL-006 | depends_on | 404 통일의 정본 — 그 AC-6 이 딥링크 표면을 직접 덮는다` 추가.

**④ Implementation Notes ①** — before: `404 통일의 정본은 ACL scope 가 소유한다 — 상태 코드만이 아니라 오류 메시지와 응답 시간까지 같아야 하며, 이 요구가 그 규칙을 복제하지 않는다.` / after: `404 통일의 정본은 SEC-ACL-006 이며 그 AC-6 이 딥링크 화면 표면까지 덮는다 — 이 요구는 참조만 하고 복제하지 않는다.` 부수적으로 「오류 메시지와 응답 시간까지 같아야」도 `SEC-ACL-006` 문면의 복제라 함께 제거했다. ②③ 은 그대로 두고, 뒤로·앞으로 미분리 판정을 ④로 명기해 다음 검토자가 같은 지적을 되풀이하지 않게 했다.

### 고치지 않은 것

- 옛 AC-5(뒤로·앞으로)를 **별도 요구로 분리하지 않았다.** 위 판정 근거대로다.
- Rationale 의 *"404 통일이라는 재료가 이미 갖춰져 있어"* 는 남겼다 — `R94` 를 선행 재료로 인용하는 설명이지 규범 복제가 아니다.
- 노드 ID 형식 조항(`R76` 계열)으로의 trace link 는 추가하지 않았다 — 지적 범위 밖이고, Implementation Notes ② 가 이미 "노드 ID 조항이 소유한다"로 위임한다.

## M2 [MEDIUM] `FR-ATTACH-011` — `PrincipalPicker` 규범·구체값 복제

### 맞았는가 — 맞다. 두 정본을 직접 읽어 확인했다.

**`CON-PRINCIPAL-006`**(`docs/spec/16.principal.srs.md:1046`, 원장 `R112-c`·`R112-e`)

- 문면: *"**주체를 선택하는 모든 화면**은 단일 공용 컴포넌트 `PrincipalPicker` 로 구현한다. 화면마다 자체 검색 UI 를 만들지 않으며…"*
- AC-1: *"…를 **포함해 주체를 고르는 모든 화면**이 `PrincipalPicker` 를 사용한다"* — 열거는 "포함해"로 열려 있다
- AC-2: *"주체 검색 입력과 결과 목록을 **자체 구현한 다른 컴포넌트가 코드베이스에 존재하지 않는다**"*
- AC-4: *"**새 화면**이 주체 선택을 필요로 할 때 검색 규칙을 다시 정의하지 않고 이 컴포넌트를 배치하는 것만으로 규칙을 물려받는다"* — **Phase 2 신규 화면까지 전방 구속**한다. `CON-PRINCIPAL-006` 이 `phase-1`, `FR-ATTACH-011` 이 `phase-2` 라는 target 차이가 구멍이 되지 않음을 이 AC-4 로 확인했다.

원장 `R112-c` 문면도 *"공유 모달뿐 아니라 주체를 고르는 모든 화면에 적용한다 — 워크스페이스 관리자 지정, 그룹 멤버 추가 **등**"* 으로 열린 열거다. 댓글 멘션 자동완성은 주체를 고르는 화면이므로 자동 포함된다.

**`SEC-PRINCIPAL-003`**(`docs/spec/16.principal.srs.md:990`, 원장 `R112-b`) — AC-1 「2자 미만이면 검색을 수행하지 않고 결과를 반환하지 않는다」 · AC-3 「최대 20건」 · AC-4 「호출 화면이 다른 값으로 덮어쓸 수 있는 경로가 없다」. 옛 AC-3·AC-4 를 잔여 없이 덮는다.

같은 블록 Implementation Notes 가 *"댓글 쪽에서 다시 정의하지 마라"* 로 스스로 금지하는데 AC 가 그대로 정의하고 있었다 — 자기모순이 맞다.

### 무엇을 어떻게 고쳤는가

**① Requirement 문면**

- before: `… R112 계열 주체 검색 규칙을 그대로 따르고, 자체 검색 UI 를 만들지 않고 단일 공용 컴포넌트 PrincipalPicker 로 구현한다.`
- after: `… R112 계열 주체 검색 규칙이 그대로 걸린다 — 공용 컴포넌트 규칙은 CON-PRINCIPAL-006 이, 최소 질의 길이와 결과 상한은 SEC-PRINCIPAL-003 이 소유하며 이 요구가 다시 정의하지 않는다.`

**② Acceptance Criteria** — AC-1(`@` 로 자동완성이 열린다)만 남기고 AC-2·AC-3·AC-4 제거.

지시는 AC-3·AC-4 만 지목했으나 **AC-2 도 함께 제거**했다. 사유: AC-2 *"자동완성은 공용 컴포넌트 `PrincipalPicker` 로 구현되고 댓글 전용 주체 검색 UI 를 따로 만들지 않는다"* 는 `CON-PRINCIPAL-006` AC-1 + AC-2 의 축자 중복이고, 지시가 *"이 블록 고유 규범(AC-1)은 남긴다"* 로 AC-1 만을 고유 규범으로 지목했다. 정본이 덮는 것을 직접 확인한 뒤 지웠고, 규정은 문면 포인터 + `depends_on` trace 두 경로로 남아 있다.

**③ Trace Links** — `Requirement | CON-PRINCIPAL-006 | depends_on` · `Requirement | SEC-PRINCIPAL-003 | depends_on` 추가 (각각 어느 AC 가 덮는지 notes 에 기재).

**④ Implementation Notes** — 제거된 AC 번호를 가리키던 `AC-3·AC-4 의 2자·20건은…` 을 `2자·20건은 원장 R112-b 의 실제 값이지 이 요구가 정한 값이 아니고 그 정본은 SEC-PRINCIPAL-003 이다 —…` 로 교정. 나머지(`G35`-①② 미결 서술)는 그대로.

### 고치지 않은 것

- **Rationale 은 손대지 않았다.** *"최소 질의 2자·결과 상한 20건(R112-b)…"* 처럼 구체값이 나오지만 출처를 명시한 **인용**이라 `R124`(*"한 곳을 정본으로 두고 나머지는 참조"*)가 허용하는 형태다. 규범이 아니라 왜 이 규칙이 걸리는지의 설명이다.
- `Doc … #R112-b`·`#R112-c`·`#R112-e` 세 행은 유지했다. 원장 조항 참조는 요구 참조와 다른 축이고 지우면 원장 추적이 끊긴다.

## M3 [MEDIUM] `FR-SHELL-004` — 소유권 포인터가 틀린 scope 지목

### 맞았는가 — 맞다. 3중으로 확인했다.

1. 원장 `R80-c`(`00.decision-log.md:343`) — *"아웃고잉 링크 패널은 R80 필터의 예외다…"*
2. 배정표 `scope_assignment.json:285` — `R80-c` 는 **`WORKSPACE`** 블록(:262~) 안에 있다. `ACL` 블록(:112~)에 없다.
3. 실제 요구 `SEC-WORKSPACE-005`(`docs/spec/13.workspace.srs.md:441`) 가 `Doc … #R80-c | informed_by` 로 그 정본이며 AC 7건으로 예외를 규정한다.

`ACL` scope 가 이 근처에서 소유하는 것은 `R103-a`(요청 버튼 금지)이지 아웃고잉 예외가 아니다 — `SEC-WORKSPACE-005` 의 Implementation Notes 가 그 구분을 명시한다.

### 무엇을 어떻게 고쳤는가

Implementation Notes ② (`08.app-shell.srs.md:419`)

- before: `그 예외 규칙의 정본은 ACL scope 가 소유하며, 백링크에는 예외가 적용되지 않는다…`
- after: `그 예외 규칙의 정본은 WORKSPACE scope 의 SEC-WORKSPACE-005(원장 R80-c)가 소유하며, 백링크에는 예외가 적용되지 않는다…`

scope 이름만 바꾸지 않고 **요구 ID 와 원장 조항까지 함께 적었다** — M1(c) 가 드러낸 것처럼 scope 이름만으로는 독자가 정본에 도달하지 못한다.

추가로 `Requirement | SEC-WORKSPACE-005 | related_to | 아웃고잉 링크 탭이 이 요구의 권한 필터에서 빠지는 예외 규칙의 정본이다` trace link 를 넣어 포인터를 그래프에서 검증 가능하게 했다. `depends_on` 이 아니라 `related_to` 를 쓴 이유 — `FR-SHELL-004` 가 그 요구에 의존하는 것이 아니라 그 요구가 `FR-SHELL-004` 의 필터 규범에 대한 예외이기 때문이다.

## L1 [LOW] `IR-SHELL-003` — 취소선 조항에서 유입된 한정

### 맞았는가 — 맞다. 다만 지적보다 사실이 하나 더 있다.

- 원장 `R108`(`:60`) 문면 전문: *"**문서 탭 스트립과 문서 헤더를 2단으로 분리**한다"*. 사이드바 한정이 **없다.**
- 그 한정은 `~~R108-a~~`(`:61`) 안에만 있다: *"**〔한정 둘〕 2단은 메인 영역에만 해당한다** — 좌·우 사이드바는 `.workspace-split.mod-left-split .view-header { display:none }` 로 설정과 무관하게 1단이다."*
- **지적이 짚지 못한 사실** — 그 한정은 DocuLight 의 규범이 아니라 **옵시디언 실측 결과에 붙은 한정**이다. `~~R108-a~~` 의 문맥은 *"② 옵시디언의 실제 구조는 2단이고 그것이 기본값이다"* 라는 주장이고, 〔한정 둘〕은 그 **주장의 범위를 좁히는 단서**다. 즉 원래부터 DocuLight 사이드바에 대한 금지가 아니었다. SRS 는 이것을 *"사이드바를 2단으로 만들면 틀린 구현이다"* 라는 **없던 금지**로 바꿔 적었다 — 취소선 인용보다 무거운 결함이다.
- 원장 머리표(`:8`): *"**취소선 조항은 어느 쪽이든 새 논증의 근거로 인용하지 않는다**"*.
- 설계서 근거 확인 — `03.screen-design-shell.md` §3.2.4(`:839`~`:874`)를 전문 읽었다. `R108` 확정 서술·오조작 논거·실측 표·`G30` 서술이 있고 **사이드바 단 구성 한정은 없다.**

### 무엇을 어떻게 고쳤는가

Implementation Notes ① (`08.app-shell.srs.md:1159`)
