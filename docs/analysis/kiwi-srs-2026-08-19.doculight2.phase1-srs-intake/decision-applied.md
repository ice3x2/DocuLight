## 결정 1 — 1.0 은 코드가 아니라 **기능**을 물려받는다

### 내린 결정

> *"코드를 가져다 쓰지 말고 제공하는 기능을 가져옵니다. MCP 를 통한 A-RAG 검색을 제외하고 처음부터 다시 만듭시다. 사실 당신이 기존보다 A-RAG 검색을 더 잘 만들 수 있다면 그렇게 합시다."*

### 원장에 적은 것

| 조항 | 무엇 |
|---|---|
| **`R21` 개정** | *"1.0 에서는 **코드가 아니라 「제공하는 기능」을 물려받는다.** 백엔드·프론트엔드 **전부 신규 작성**한다"* |
| **`R21-a` 신설** | **A-RAG 도 신규 작성한다.** 조건부 위임(*"더 잘 만들 수 있다면"*)이 충족됐다 |
| **`R21-b` 신설** | 물려받는 것의 형태 = **MCP 도구 계약**(이름·인자·기본값·출력·에러 코드) + 화면이 제공하던 동작. 소스·의존성·내부 구조는 아니다. **1.0 을 빌드에 묶지 않는다** |
| **`R21-c` 신설** | 기각된 대안(검색 코어 3파일 이식)과 **재개봉 조건** |

### A-RAG 을 새로 만들기로 한 근거 — 실측

*"더 잘 만들 수 있는가"* 를 판단하려고 1.0 의 A-RAG 을 읽었습니다. **답은 예**이고, 이유가 기대와 달랐습니다.

**1.0 의 의미 검색은 한 번도 실전 동작한 적이 없습니다.** 결함 둘을 코드에서 확인했고 하나는 실행으로 재현했습니다.

| # | 결함 | 결과 |
|---|---|---|
| ① | HTTP MCP 경로에서 벡터 저장소 핸들이 아예 대입되지 않는다 | **항상** 키워드 검색으로 떨어진다 |
| ② | 내장 챗봇 경로에서도 운용 설정이 영속 모드라 유사도 검색이 `TypeError` 로 죽는다 | **조용히** 키워드로 폴백한다 |

검증된 적 없는 389줄을 옮기는 것은 이득이 아닙니다.

### 더 나은 설계 — 요구와도 맞습니다

텍스트 축을 **SQLite FTS5** 로 두는 안이 가장 강합니다. 우연이 아니라 **2.0 의 기존 결정과 맞물립니다**:

- `DR-STORAGE-002` 가 이미 **SQLite 단일 저장소**를 못박았다 → 저장소가 하나로 유지된다
- `SEC-ARCH-002`(MCP 결과를 호출자 ACL 로 거른다)가 **`WHERE` 절 하나로 성립**한다 → 사후 필터가 아니다
- 그래서 *"거른 뒤 N건인가 거르기 전 N건인가"* 라는 존재 오라클 문제(`G36` ③)가 **애초에 생기지 않는다**

그 밖의 개선안(하이브리드 검색 + RRF · 헤딩 경로를 붙인 청킹 · 리랭킹)은 조사 문서에 **얻는 것과 잃는 것을 함께** 적어 두었습니다. 리랭킹은 사내 GPU 여유를 **확인하지 못해** 그대로 표시했습니다.

### 기각한 것과 그 조건

조사는 검색 코어 3파일(약 1,300줄 + 통과하는 테스트 21개)의 이식을 권고했습니다. **결정이 그것을 기각합니다.**

대가를 인지하고 받습니다 — `vector-storage` 의 소프트삭제·컴팩션 구조는 *HNSWLib 이 개별 삭제를 지원하지 않는다* 는 라이브러리 사실에서 나온 것이라, **같은 라이브러리를 쓰면 신규 작성에서도 다시 발명하게 됩니다.**

> **재개봉 조건** — 벡터 저장소로 **HNSWLib 을 그대로 택할 경우에 한해** 이 기각을 다시 논의합니다. SQLite FTS5 + 별도 벡터 계층으로 가면 그 코드는 쓸 자리가 없어 **재개봉 사유가 소멸**합니다.

### ⚠ 제가 앞서 드린 설명 하나를 정정합니다

결정 문서에서 *"1.0 은 JavaScript·CommonJS 이고 2.0 은 TypeScript·ESM 이라 언어 경계를 넘어야 한다"* 를 이식 비용의 근거로 들었습니다. **그 전제가 틀렸습니다.**

`TypeScript` 를 규정하는 요구사항은 **`CON-ARCH-003` 하나뿐**이고 그것은 *"**프론트엔드**는 Vite 와 React 와 TypeScript 기반 SPA"* 입니다. **백엔드 언어를 정한 요구사항은 `docs/spec` 어디에도 없습니다.**

결정 자체는 바뀌지 않지만 **근거가 틀린 자리에 있으면 안 되므로** `R21` 비고에 정정을 적었습니다.

## 결정 2 — 전역 검색을 정의한다

### 원장에 적은 것 — `R149` 계열 6행

| 조항 | 정한 것 |
|---|---|
| **`R149`** | 검색 대상 **넷** — 문서 제목 · 본문 · 태그 · 첨부파일 이름. 소재는 **좌측 검색 탭** |
| **`R149-a`** | 검색창 오른쪽 **필터 버튼 → 팝오버 → 체크박스**로 대상을 고른다 |
| **`R149-b`** | **공백 = AND**, 검색어 사이의 **`\|` = OR** |
| **`R149-c`** | **최소 2자.** AND 는 2자 이상 낱말이 하나라도 있으면 나머지는 1자 허용. **OR 는 모든 항이 2자 이상** |
| **`R149-d`** | 결과는 **1.0 과 동일한 형식** — 문서 제목 아래에 찾은 내용들. 스크롤 |
| **`R149-e`** | **AI 검색은 MCP 로만.** 좌측 검색 탭은 텍스트 검색이며 여기에 섞지 않는다 |

### 한 자리를 확인해 좌측으로 정했습니다

지시 초안이 *"오른쪽 탭바에 결과를 보여준다"* 였는데 `R106-a` 가 이미 *"**좌측 검색 탭이 결과를 소유한다**"* 로 정하고 있었고, 1.0 실제 화면도 검색창 바로 아래 좌측이었습니다. 확인 결과 **좌측**으로 확정했고 **`R106-a` 는 개정하지 않습니다.**

### `R149-c` 의 비대칭에 근거를 붙였습니다

*"AND 는 1자를 섞어도 되는데 OR 는 왜 안 되는가"* — 비용 때문입니다.

- **AND**: 2자 이상 항이 색인을 먼저 좁히므로, 남은 1자 항은 좁혀진 결과 안에서만 걸러집니다
- **OR**: 각 항이 **독립으로 전수를 훑습니다.** 1자를 허용하면 결과가 폭발합니다

> 주체 검색(`R112-b`)의 2자와 값은 같지만 **다른 조항**입니다. 그쪽은 `PrincipalPicker` 소유이고 상한 20건이 함께 붙습니다.

### 정하지 않은 것 — `G36` 으로 열었습니다

`R149` 가 답하지 않은 것을 공백으로 등재했습니다. **이 열거가 전량이라고 가정하지 마십시오.**

| # | 미결 | 왜 지금 못 정하나 |
|---|---|---|
| ① | 필터 팝오버의 **기본값** | 본문까지 켜면 첫 질의부터 무겁고, 제목만 켜면 사용자가 매번 필터를 열어야 한다 |
| ② | AND 와 OR 의 **우선순위·혼용** | `가 나 \| 다` 를 `(가 AND 나) OR 다` 로 읽는가 `가 AND (나 OR 다)` 로 읽는가. 괄호를 지원하는가 |
| ③ | 결과 **건수 상한**과 발췌 길이 | **`R80` 이 결과를 권한으로 거르므로**, 상한을 두면 「거른 뒤 N건」인지 「거르기 전 N건」인지가 갈리고 **후자면 존재 오라클**이 된다 |
| ④ | **첨부 이름** 검색의 권한 판정 | 첨부는 소유 문서의 보기 권한으로 판정하는데(`R66`) 결과 표면에도 그 판정이 걸린다. `R80` 표면 목록에 첨부가 들어가는지 확인이 필요하다 |
| ⑤ | **색인 시점** | `R79` 는 벡터 인덱스만 다루고 텍스트 색인은 어느 조항도 다루지 않는다. `G14`(화면 최신성)와 같은 축이다 |
