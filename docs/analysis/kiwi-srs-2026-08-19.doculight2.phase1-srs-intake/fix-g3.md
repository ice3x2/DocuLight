## L1 — 취소선 조항 `~~R106-b~~` 인용 (FR-CONFIRM-003 Rationale)

> 종결: ~~R106-b~~ · ~~R108-a~~ (**둘은 다른 상태다 … 취소선 조항은 어느 쪽이든 새 논증의 근거로 인용하지 않는다**)

**R106 으로 대체할 수 있는지 직접 판정했다 — 대체 불가.** R106(살아 있음, 2026-08-18 개정)의 비고가 담은 것은 *"초판 R106 의 다수 의견 근거 두 개가 실측 앞에서 무너졌다"* 이고, 그 상세를 **`(R106-b 종결 서술 참조)`** 로 취소선 조항에 넘긴다. 반면 문제의 문장이 주장한 「같은 유형의 결함」은 *닫힌 열거·논리곱 조건절을 쓰는 것 자체가 결함* 이라는 명제이고, 이것은 **오직 ~~R106-b~~ 안에만** 있다:

> **〔트리거 자체가 결함이었다〕** … **R115-d 가 남긴 교훈(닫힌 열거를 쓰는 것 자체가 결함)과 같은 유형이다**

R106 문면에는 이 명제가 없다. R106 을 근거로 갈아끼우면 **살아 있는 조항이 하지 않은 말을 하게 만드는 것**이므로(원장에 없는 것을 지어내지 않는다) **인용을 삭제**했다. 삭제해도 규범 손실이 0 이다 — 이 블록의 규범은 「열린 목록」이고, 그 근거는 바로 앞 문장(2026-08-14 에 두 번 낡은 실제 이력)과 Trace Link `R115-d informed_by` 가 이미 전부 지탱한다.

**before** (`11.confirmation-grades.srs.md:165` 말미)
> … 열거가 규범이 아니면 애초에 낡을 자리가 없다. **같은 유형의 결함이 R106-b 에서 다시 확인됐다.**

**after**

**맞았는가 — 맞았다.** 「조작이 없다」와 「배정이 발효 대기로 남는다」는 독립 명제이고, 하나가 참이어도 다른 하나가 거짓일 수 있다.

## L4 — FR-AUTH-004 다축 결합 → **쪼개지 않음 (판정)**

**맞았는가 — 축이 셋인 것은 사실이나, 분할이 더 낫지 않다고 판정했다.**

블록의 세 축: ① 가입 모드 3종 존재(R7) ② 설정 소재·권한(R24-a) ③ DB 영속화(R96).

**쪼개지 않는 사유 (원장 근거):**

1. **원장이 이 셋을 하나의 질문으로 열고 하나로 닫았다.** 블록 Rationale 이 그대로 인용한다 — *"가입 모드 설정의 소재·권한은 **Q4-b 로 열려 있던 것을** R24-a(설정 모달 인스턴스 구역·슈퍼유저 전용)와 R96(설정은 DB 저장)으로 **종결한 결과다**"*. 하나의 미결을 두 조항이 합쳐 닫은 것이라, 쪼개면 원장의 종결 단위와 SRS 블록 단위가 어긋난다.
2. **§29.1-② 시스템 경계가 갈리지 않는다.** 세 축의 주어가 모두 `인스턴스의 가입 모드` 라는 **한 값**이다 — 존재·설정 지점·저장처는 한 설정값의 속성이지 별개 시스템이 아니다.
3. **§29.1-③ 검증 방법이 같다.** 블록 `Verification Method` 는 `test` 하나이고 AC-1~AC-5 전부 test 로 검증된다. AC 마다 시험 절차가 다른 것(재기동 시험 등)은 정상이며 §29.1-③ 이 겨눈 것은 요구 단위의 검증 방법 상이다.
4. **화면 축의 분해는 이미 끝나 있다.** 인증 경계로 갈리는 화면은 형제 요구가 나눠 갖는다 — ①② 가입 신청 폼은 `IR-AUTH-001`, ③ 직접 등록은 `FR-AUTH-003`. 여기서 또 쪼개면 3중 분할이 된다.

LOW 이고 쪼개는 쪽이 더 나쁘므로 **남기고 사유를 산출물에 기록**했다. 추적 가능하도록 `FR-AUTH-004` Implementation Notes 에도 같은 판정을 남겼다.

**부수 관찰 (수정하지 않음, 보고만).** 검증 지적문은 *"본문과 **AC-5**"* 라 적었으나 든 축은 *"설정 화면·저장"* 으로 실제 AC-5(`pending` 로그인 차단)와 어긋난다. 줄 번호 `:527` 은 AC-4(DB 저장)를 가리킨다 — 지적의 축 서술은 AC-4 를 겨눈 것으로 읽힌다. 별개로 **AC-5 는 `SEC-AUTH-003` AC-2 와 같은 사실을 말한다**(`active` 아닌 계정의 로그인 차단). 이미 `SEC-AUTH-003 depends_on` 트레이스가 걸려 있어 정본 관계는 표시돼 있으나, R124 관점에서 값 중복 소지가 있다. **내 지적 범위 밖이라 손대지 않았다.**

## L5 — SEC-AUTH-018 열거 번호 ①②④ — **번호가 맞다. 사유를 명시했다**

**맞았는가 — 「③ 이 실수로 빠졌다」는 아니다.** 원장 `G33`(`00.decision-log.md:626`)을 직접 읽었다. **열거는 넷이다:**

> ① 비밀번호 변경이 그 계정의 PAT 를 무효화하는가 ② 다른 기기의 세션을 끊는가 ③ **로그아웃이 쿠키만 지우는가 서버 측 세션을 무효화하는가** ④ 현재 비밀번호 재입력을 요구하는가

즉 팀 리드 브리핑이 *"갈래가 셋"* 이라 한 것은 부정확하고 **원장 열거는 넷**이다. 그리고 ③ 은 누락이 아니라 **소유자가 다르다** — `SEC-AUTH-019`(사용자가 자기 세션을 종료한다)가 이미 `G33 related_to` 로 *"미결 공백 G33 — 로그아웃이 서버 측 세션을 무효화하는지 미정"* 을 달고 소유한다.

따라서 **①②④ 는 원장 번호를 보존한 의도적 표기**이고, ③ 을 여기 옮겨 적으면 R124 위반(같은 사실 두 곳)이며, ①②③ 으로 재번호하면 원장과의 대조가 끊긴다. **번호는 그대로 두고 「왜 비었는가」를 문면에 박았다** — 다음 독자가 같은 지적을 반복하지 않도록.

**추가** (`09.auth.srs.md` SEC-AUTH-018 Implementation Notes):
> [2026-08-19] 위 ①②④ 번호는 원장 `G33` 의 열거를 그대로 옮긴 것이며 오기가 아니다. 원장 열거는 넷이고, 건너뛴 ③(로그아웃이 쿠키만 지우는가 서버 측 세션을 무효화하는가)은 이 요구가 아니라 SEC-AUTH-019 가 소유한다. ③ 을 여기 옮겨 적으면 같은 사실이 두 곳에 놓이고, 번호를 ①②③ 으로 다시 매기면 원장과의 대조가 끊긴다 — 원장 번호를 유지한다.

## L6 — FR-PRINCIPAL-005 가 등급 이름 없이 확인 절차를 지정

**맞았는가 — 지적의 골자는 맞다. 단 브리핑의 조항 매핑은 틀렸다.**

**⚠ 브리핑이 든 `R115-g` 는 이 블록의 조항이 아니다.** `R115-g`(`:89`)는 *"**오프보딩 3단계(그룹 멤버십 제거)**는 L2"* 인데, `FR-PRINCIPAL-005` 는 **워크스페이스의 마지막 `관리` 권한자 제거**(원장 `R109`)다. 조작이 다르다. 실제 오프보딩 3단계는 `FR-PRINCIPAL-003` 이 소유하고, 그 확인 등급은 트레이스가 밝히듯 `FR-CONFIRM-023` 이 갖는다. **조항 문면이 이겼다** — `R115-g` 를 쓰지 않았다.

**이 조작의 등급 소재를 원장에서 확인한 결과** — `R115-d ①`(`:86`):

> ① **워크스페이스 마지막 `관리` 권한자 제거**: 가역이고 효과도 즉시(`관리자 없음` 배지가 바로 붙음)라 두 축만 보면 L1 이지만 **R109 가 확인 다이얼로그를 직접 요구**한다

즉 이 확인은 임의 절차가 아니라 **확인 등급 체계의 「직접 지정 우선」 사례**이고, 그 우선 규칙의 정본은 `FR-CONFIRM-003` 이다(그 블록 Implementation Notes 가 이 조작을 사례로 이미 열거한다).

**중요 — 원장은 이 조작에 L 값을 배정한 적이 없다.** R115-d 는 *"두 축만 보면 L1 이지만 R109 가 확인 다이얼로그를 직접 요구한다"* 까지만 적는다. 확인 다이얼로그가 L2 의 어포던스라는 이유로 여기에 `L2` 를 써 넣으면 **원장에 없는 값을 창작**하는 것이고, 그것이 정확히 `R125-b` 가 기록한 사고다:

> 두 설계서가 각자 다른 근거를 창작해 L2 에 착지시켰고, 그 두 근거가 서로 달랐다(R124 위반)

**그래서 등급 「체계」의 이름과 정본 포인터만 쓰고 값은 복제하지 않았다** — `FR-PRINCIPAL-011` 이 HIGH 수정에서 취한 것과 같은 처리다.

**변경 3건:**

1. **Requirement 문면** (`16.principal.srs.md:663`) — 문장 추가 (ID 유지, 앞 두 문장 불변)
   - **after 추가분**: *"이 확인은 확인 등급 체계에서 요구사항이 등급을 직접 지정하는 사례(FR-CONFIRM-003)이며, 가역성·즉시성 배정 기준으로 도출되는 등급보다 이 직접 지정이 우선한다."*
2. **Trace Link 신설** — `Requirement | FR-CONFIRM-003 | related_to | 확인 등급 체계의 직접 지정 우선 규칙 — R115-d 가 이 조작을 그 사례로 든다. 등급값은 이 블록에 적지 않는다`
3. **Implementation Notes 추가** — 등급값을 여기 적지 않는 이유(R115-d 가 L 값을 배정한 적 없음 · 창작 시 R125-b 사고 재발 · FR-PRINCIPAL-011 과 동일 처리).

AC-1~AC-3 은 건드리지 않았다 — 확인 다이얼로그의 존부·취소 동작은 R109 가 직접 정한 규범이라 그대로 유효하다.
