## A 입도

**선택**: **A-4** — *부모 조항 1건 = 요구사항 1건. 하위 조항은 그 요구사항의 Acceptance Criteria. 단 SRS-MD §29.1 의 분리 트리거가 걸리는 하위만 별도 요구사항으로 올린다. 비규범 하위(약 10행)는 요구사항도 AC 도 아니고 `rationale` / `implementationNotes` 로 간다.*

**예상 규모: Phase 1 약 150건** (아래 §B 표 합계 142 + `R43` 컨테이너 분할 +4 + 공백 분리 +4).

### 근거

**1. 원장의 가족 구조가 이미 요구사항 입도다.** 136개 가족 중 70개(51%)가 하위 조항이 없는 단일 행이다. 나머지 66가족의 중앙값 크기는 3이다. 가족을 그대로 요구사항 1건으로 잡으면 AC 는 평균 2.4개, 최대 11개가 된다 — §21(최소 1개)과 §29.1-⑤(AC 목록이 너무 길어지면 분리) 사이에 정확히 들어맞는다.

**2. 하위 조항은 AC 의 문법에 이미 맞춰 쓰여 있다.** 표본 검증:

- `R126-b` *"분모·미도달 건수·하위 집계형 접근자 수치를 표시하지 않는다. `24 / 30` 형태와 "적용되지 않는 항목 N개" 를 금지한다"* → `AC-N: 확인 다이얼로그에 `24 / 30` 형태의 분모 표기가 나타나지 않는다` — 조건·기대결과가 그대로 옮겨진다.
- `R115-i` *"`새 버전 올리기` 의 등급은 대상 형식으로 갈린다 — md 는 L1, 바이너리는 L2"* → AC 2개.
- `R72-c` *"설치 토큰의 수명은 30분"* → AC 1개.

이것들을 각각 **별도 요구사항 블록**으로 올리면, 요구사항 진술이 *"분모를 표시하지 않는다"* 가 된다. **그것은 구현자에게 배정할 수 있는 작업 단위가 아니다.** 아무도 "분모 미표시"를 티켓으로 받지 않는다. 받는 것은 "컨테이너 부여 확인 다이얼로그"이고 분모 금지는 그 수용 조건이다.

**3. §29.1 트리거가 실제로 걸리는 자리는 셀 수 있고 적다.** 전수 점검 결과:

| 트리거 | 걸리는 자리 | 조치 |
|---|---|---|
| ① 행위자 다름 · ⑤ AC 과다 | **`R43`** — 문면이 *"부속 기능 5종을 모두 요건으로 확정한다 (아래)"* 로 **순수 컨테이너**다. `R43-1`(관리자 일괄 회수) `R43-2`(`관리` 전용 시뮬레이션 화면) `R43-3`(감사 목록) `R43-4`(공유 모달) `R43-5`(이동 프리뷰) 는 화면도 행위자도 다르다 | R43 은 요구사항이 되지 않고 5건으로 분해. **+4** |
| ⑦ 일부는 막힘 | `R84`(감사 스키마, 등재 가능) vs `R84-a`(보존 기간, `G27` 미결) / `R58`(PAT 도입) vs `R58-d`(무효 사유, `G33` 미결) / `R16`(Phase 1 범위) vs `R16-a`(9종 목록, `G31` 미결) / `R78`(사이드카) — `G28` | 각 1건씩 분리. **+3~4** |

**4. 추적성이 유지되고 오히려 좋아진다.** 매핑은 요구사항당 `trace` 1행(`Doc | 00.decision-log.md | informed_by | R115 · R115-a~j`)으로 끝난다. 1:1(A-1) 이면 325행의 trace 가 생기고 그중 194행이 부모와 사실상 같은 내용을 가리킨다 — **`R124`(한 사실은 한 곳에)를 SRS 안에서 재발시킨다.**

### 진 후보가 진 이유

**A-1 (1:1, 325건)이 진 이유** — 셋이다.
1. **§29.2-③ 위반**: 하위 조항 다수가 부모의 상술이다. `R127-a`(*"상속이 끊긴 하위에는 적용되지 않습니다를 항상 표시"*)는 `R127`(*"상속 고지를 컨테이너 공통으로 둔다"*)의 조건 하나다. 검증 기준이 같은 화면·같은 테스트에서 나온다.
2. **작업 단위로 못 쓴다** (위 2번).
3. **물리적 비용**: 블록 하나는 메타데이터 표 + 8개 고정 절이다. 325블록 ≈ 13,000행. `R124-a` 가 요구하는 인용 스윕이 매 개정마다 13,000행을 훑어야 한다.

**A-2 (최상위 135건만)가 진 이유** — 네 자리에서 정면으로 깨진다.
1. **`R43`**: 최상위만 세면 `R43` 한 건이 남는데 그 진술이 *"5종을 확정한다"* 라 **검증 불가능**하다(§20 Verifiable 위반). 그리고 그 5종은 서로 다른 화면이다.
2. **`R84` / `R84-a`**: 하나는 등재 가능, 하나는 `G27` 로 막힌다. 한 블록에 넣으면 Status 를 `planned` 로도 `blocked` 로도 정할 수 없다 — §29.1-⑦ 이 정확히 이 경우를 분리하라고 한다.
3. **AC 과다**: `R115`·`R72` 는 하위가 10개씩이다. 부모 1건에 AC 11개는 §29.1-⑤ 에 걸린다.
4. **비규범 하위의 처분이 틀렸다**: A-2 는 *"AC / rationale / implementationNotes 로 흡수"* 라 하는데, 잔여 위험 5건을 AC 로 흡수하면 **통과 조건 없는 AC** 가 생긴다. (A-2 가 rationale 을 선택지로 열어 둔 점은 옳다 — 그 부분만 A-4 가 계승했다.)

**A-3 (독립 검증 가능성으로 분류)이 진 이유** — **판별 기준이 실측상 거의 공허하다.** 194개 하위 조항을 성격별로 기계 분류한 결과 비규범은 약 10행(5%)뿐이고, 나머지 184행은 전부 "독립 검증 가능"에 해당한다. 즉 A-3 의 규칙을 문자 그대로 적용하면 **184 + 135 = 319건**이 되어 A-1 과 사실상 같아진다. A-3 은 방향은 맞지만 **자를 잘못 골랐다** — 잘라야 할 기준은 "독립 검증 가능한가"가 아니라 "§29.1 트리거가 걸리는가"다. A-4 는 A-3 의 방향에 작동하는 자를 끼운 것이다.

### `R{n}` ↔ 새 ID 매핑을 누가 어디에 적는가

**SRS 쪽이 단독으로 소유한다. 원장에는 역참조 열을 만들지 않는다.**

- 정본: 각 요구사항의 `#### Trace Links` 한 행. (§E 참조)
- 별도 매핑 표(`docs/spec/9x.mapping.md` 류)를 **만들지 않는다** — 만들면 `R124-a` 스윕 대상이 하나 더 늘고, 그 표가 뒤처지는 것이 이 프로젝트가 이미 일곱 번 밟은 실패다(`01.design-completion.md` §6.3).
- 역방향 조회는 `grep -r "R115-e" docs/spec/*.srs.md` 로 충족된다. 이것이 `R124-a` 가 요구하는 스윕 그 자체다.
- **커버리지 게이트**: Phase 1 324행 각각이 정확히 한 요구사항의 trace Notes 에 나타나는지 기계 검사한다. 통과하지 못하면 그 배치는 등재로 치지 않는다. (§F 참조)

### 남는 위험

1. **AC 를 어느 고도에서 쓸 것인가**가 입도보다 위험하다. 원장 고도로 쓰면 안정적이다(수명 전체 개정률 5% — 아래 §0 참조). 그러나 화면 설계서(`03`~`06`) 고도로 쓰면 **`03` 에만 미승인 〔판단〕 마커가 46개** 있고 설계 미결이 57건이라 AC 가 대량 churn 한다. **AC 는 원장 문면이 단언하는 데까지만 쓰고, 화면 치수·정렬·문구는 쓰지 않는다.** 이 선을 넘으면 입도가 옳아도 SRS 가 버려진다.
2. 가족 경계가 애매한 자리가 소수 있다. `R116`~`R121` 은 번호상 `R115`~`R142` 사이에 있으나 원장 표에서 `R142` **뒤**에 놓여 있다(L170~179). 확인 다이얼로그 축(`R116`)과 접근자 지표 축(`R120`·`R121`)이 섞인 자리라 배치 판단이 필요하다.
3. `R43` 을 컨테이너로 해체하면 §4 수용 기준 4번(*"R43(부속 5종)이 검증된다"*)이 가리킬 단일 ID 를 잃는다. 완화: 5건 각각의 trace 에 `Requirement | (대표 ID) | related_to` 를 걸고, 수용 기준은 5건을 열거한다.

**확신도: high**

### 근거

**§2.x 18구획을 그대로 쓰면 안 되는 이유는 취향이 아니라 오배치다.** 원장 §2.x 는 *등재 순서*이지 시스템 분해가 아니고, 실제로 세 자리에서 어긋나 있다:

1. **`R84`·`R84-a`(감사 로그)가 §2.14 "초기 상태" 에 있다** (L494~495). 감사 로그 본체 `R137`~`R141` 은 §2.1 에 있다. **같은 주제가 두 구획에 갈려 있다.**
2. **`R72` 계열 11행(설치 마법사 부트스트랩)이 §2.4 "접근 제어" 에 있다** (L270~280). 부트스트랩은 ACL 이 아니라 인증·기동 축이다.
3. **§2.1 "UI · 에디터" 159행 안에 확인 등급 체계 66행 + 감사 로그 34행이 들어 있다.** 확인 등급은 화면 전반을 가로지르는 정책이고 감사 로그는 데이터·관측 축이다. **둘 다 UI 가 아니다.**

18구획을 그대로 옮기면 이 오배치가 SRS 로 이식되고, 그 다음부터는 `docs/spec` 이 SSOT 라서 **되돌릴 근거가 사라진다.**

**§2.1 은 반드시 쪼갠다.** 159행(Phase 1 155행)은 위 표 기준 `SHELL`·`CONFIRM`·`AUDIT`·`PRINCIPAL`·`EDITOR` 다섯으로 갈린다. 실측 블록 크기: 확인 등급 `R113`~`R136` **49행** + `R142` 계열 7행 + `R116`~`R121` 10행 = **66행**, 감사 로그 `R137`~`R141` **34행**, 나머지 셸·설정·계정 59행.

**작은 구획은 합친다.** §2.8(1행)·§2.10(1행)·§2.9(3행)·§2.11(5행)·§2.14(7행)을 `ARCH` 하나로 모았다. 요구사항 1건짜리 scope 문서는 §1~§3·§5~§7 골격이 본문보다 길어진다.

### scope 가 너무 커지면 / 너무 잘게 쪼개면

**너무 커지면** — ① SpecKiwi 는 SRS mutation 잠금을 쓰므로 한 파일이 커질수록 그 파일에 대한 모든 쓰기가 한 줄로 선다. ② `R124-a` 스윕이 파일 전체 읽기가 된다. ③ Git diff 가 §20 Maintainable 을 잃는다. ④ scope 접두사가 정보를 못 준다 — `FR-DOCULIGHT-087` 은 아무것도 말하지 않는다.

**너무 잘게 쪼개면** — ① 각 scope 문서의 §5 Cross-scope Dependencies 가 폭발한다. 이 제품은 결합도가 높다: `CONFIRM` 은 `ACL` 의 넓히기/좁히기 축(`R70`)을 참조하고, `AUDIT` 의 스코프 판정은 `ACL` 판정이며, `ATTACH` 의 `R66` 은 `ACL` 이다. 16 scope 안을 시험 배치해 보니 의존 간선이 scope 수보다 빠르게 늘었다. ② 요구사항의 자연스러운 소속지가 애매해져 **같은 사실이 두 scope 에 적히는 `R124` 위반**이 생긴다. ③ index §2·§4 두 표를 매번 갱신해야 한다.

10 scope · scope 당 9~28 REQ 가 두 실패 사이의 자리다.

### 진 후보가 진 이유

- **18구획 그대로** — 위 오배치 3건. 그리고 §2.8·§2.10 각 1행짜리 scope 문서가 생긴다.
- **4~5개 대형 scope** — `ACL`+`CONFIRM`+`AUDIT` 를 합치면 한 파일에 61 REQ · 2,000행 이상이 되고, mutation 잠금 아래 그 파일이 병목이 된다. 그리고 이 셋은 **검증 방법이 다르다**(ACL=E2E 2계정 / 확인 등급=UI 단언 / 감사=DB 행 검사) — §29.1-③ 의 취지가 scope 수준에서도 유효하다.
- **`WORKSPACE` 독립 scope** — 검토했으나 `R35`·`R38`·`R56`·`R83` 4가족 6행뿐이고, `R35-a`(워크스페이스가 상속 체인의 루트)는 본질이 ACL 이다. `ACL` 에 넣었다.
- **`TRASH` 독립 scope** — 4가족 4행. `STORAGE` 에 합쳤다. 물리 저장 수명주기라는 같은 축이다.

**확신도: medium-high** (배정 자체는 기계 검산했으나, `R116`~`R121` 처럼 경계가 애매한 소수 가족은 작성 중 재배치될 수 있다)

3. `phase` 는 target type 열거에 있고 §16 의 예시(`phase-1`)와도 일치한다.

**진 후보**

- **`Phase 1` 하나만** — Phase 2 행이 미아가 된다. 커버리지 게이트를 포기하지 않는 한 성립하지 않는다.

**확신도: high**

## D Status / Stability

**선택**

| 구분 | Status | Stability | 대상 | 대략 건수 |
|---|---|---|---|---:|
| 기본 | `planned` | **`stable`** | 열린 공백이 지목하지 않고 시한부 표현이 없는 조항 | ~125 |
| 공백에 걸림 | **`blocked`** | **`evolving`** | `R84-a`(G27) · `R16-a`(G31) · `R58-d`·`R144`·`R145`·`R59`(G33) · `R78`·`R63-a`(G28) · `R137`(G29) · `R24-a`·`R143-a`(G10) | ~11 |
| 시한부 문면 | `planned` | `evolving` | `R92`(*"2026-08-19 기준"*) 처럼 문면이 스스로 잠정임을 밝히는 조항 | ~4 |
| Phase 2 | `planned` | **`draft`** | target=`phase-2` 전량 | ~6 |
| `frozen` | — | **쓰지 않는다** | — | 0 |

**Status 근거**

- 브리프가 옳다 — 열거에 **`proposed` 는 없다**(`00.index.md` §5 · 규칙 §14.1 둘 다에서 확인). `planned` 가 *"정의되었으나 아직 구현되지 않음"* 이라 원장의 상태와 정확히 일치한다.
- **`blocked` 는 §14.1 의 정의(*"구현 또는 검증이 막힘"*)에 그대로 맞고, §29.1-⑦(일부는 구현되고 일부는 막혔다 → 분리)의 존재 이유가 바로 이것이다.** 공백에 걸린 조항을 `planned` 로 넣으면 구현자가 미결을 모른 채 착수해 임의로 메운다 — `G17` 에서 `03` 이 *"복사 = L2(항상)"* 으로 공백을 임의로 메웠던 사고가 정확히 그 형태다.
- **`implemented` 는 지금 하나도 쓰지 않는다.** 에디터 표면 일부가 동작하는 것은 사실이나 ① 그 코드는 `src/vendor/atomic-editor` 이식물이고 ② 그 vendor 테스트 7파일이 `packages/editor/vite.config.ts` 의 `include: ['test/**/*.test.{ts,tsx}']` 에 **걸리지 않아 수집되지 않는다**(직접 확인). ③ 자체 테스트는 mermaid 27케이스뿐이고 그 어느 것도 `R16-a` 9종을 덮지 않는다. **`include` 패턴을 고쳐 vendor 56케이스를 수집시키는 것이 어떤 `implemented` 승급보다 먼저다.** 이것은 SRS 작업이 아니라 그 전제다.

**Stability 근거 — 왜 `stable` 인가**

이 판단에 실증을 댄다. 원장 §5 변경 이력 **122행**을 파싱해 개정·정정·폐기 문구에 인접한 조항 ID 를 뽑으면 **17개**다(R3·R24-a·R27·R40·R43-1·R43-5·R44-a·R50·R55·R65·R65-a·R66·R73·R92·R106·R106-a·R111). **341행 중 5%** 이고, 그중 대부분(R3·R27·R40·R44-a·R50·R55·R65·R66)이 **2026-08-11~12 최초 저작 + 3축 정합성 감사 기간**에 몰려 있다. *"요건 확정"* 선언 이후의 개정은 `R92`·`R106`·`R106-a`·`R24-a`·`R111` 다섯이다.

즉 **원장 조항은 실증적으로 안정적이고, `stable`("구현해도 될 만큼 안정") 이 사실 진술이다.**

**`draft` 를 전면 적용하면 안 되는 이유는 브리프가 든 것보다 하나 더 있다.** CLAUDE.md 의 착수 금지 게이트 외에, 규칙 §15.3 이 *"활성 target 안의 비-discarded draft 요구사항은 stability 경고를 보고한다"* 고 규정한다. 전량 draft 는 **첫 `validate` 부터 150건의 경고**를 만들고, 경고가 150건이면 아무도 읽지 않는다 — 경고 채널이 그 자리에서 죽는다.

**`frozen` 을 쓰지 않는 이유**: §15.3 은 frozen 을 *"변경에 심의가 필요"* 로 정의하는데, 변경이 지금 **실제로 도착 중**이다(2026-08-18 `R106` 전복, 2026-08-19 `R24-a` 개정 + `R143`~`R148` 신설). 그리고 열린 공백 13건이 닫히면 `R84-a`·`R16-a`·`R137`·`R58-d` 를 개정한다. **동결 시점은 이미 정의돼 있다** — `01.design-completion.md` §5 의 설계 완성 5조건이 충족되는 때다. 그때 `phase-1` 을 일괄 `frozen` 으로 올려라. 지금은 아니다.

**공백에 걸리는 요구사항을 다르게 다뤄야 하는가 — 그렇다.** Status(`blocked`)와 Stability(`evolving`) 둘 다 다르다. 이유가 다르다: `blocked` 는 *"지금 착수하면 안 된다"* 를, `evolving` 은 *"이 문면이 곧 바뀐다"* 를 말한다. 둘은 독립 축이고 SpecKiwi 가 두 필드를 분리한 이유가 그것이다.

**부수 판단 — Priority · Risk 는 발명하지 않는다.** 원장은 우선순위를 배정한 적이 없다. 150건에 우선순위를 지어내는 것은 사실 위조다. 대신 **증거가 있는 자리에만 넣는다**:
- `Priority`: §4 수용 기준 13개가 지목하는 조항에 `high`. 나머지는 생략(`-`).
- `Risk`: §3.1 감사 해소 매핑이 **CRITICAL 로 등급 매긴 15조항**(`R69`·`R50`·`R65`·`R66`·`R71`·`R72`·`R73`·`R74`·`R75`·`R77`·`R77-a`·`R78`·`R55`·`R79`·`R70`)에 `high`. 나머지 생략. 이것은 원장에 실재하는 등급이지 내 판단이 아니다.

**확신도: high** (`stable` 판단은 변경 이력 실측에 근거함)

## E Trace

**선택**

| 필드 | 무엇을 담는가 | 왜 |
|---|---|---|
| **`trace`** — `Doc` / `informed_by` | `\| Doc \| [결정 원장](./00.decision-log.md) \| informed_by \| R115 · R115-a~j \|` **1행** | **`R{n}` 매핑의 유일한 정본** |
| `trace` — `Requirement` / `depends_on`·`refines` | 원장이 조항 간 의존을 명시한 자리만 | 예: `R43-2`↔`R71-c`(*"R71 이 있어야 R43-2 가 동작 근거를 갖는다"*) |

| `trace` — `Code` | **아무것도 달지 않는다** | 아래 |

**`Doc` vs `ADR`** — §23.2 의 `ADR` 은 architecture decision record 다. 원장은 문자 그대로 "설계 결정 기록"이라 `ADR` 도 성립한다. **`Doc` 을 고른다**: `ADR` 은 관례상 *결정 1개 = 파일 1개*의 불변 형태를 뜻하는데 이 원장은 341행이 한 파일에 든 살아 있는 문서다. `ADR` 을 비워 두면 나중에 진짜 ADR 을 도입할 때 자리가 남는다. (반대 선택도 방어 가능하다 — 대가는 위 한 문장뿐이다.)

**`Relation` 은 `informed_by`** — §23.3 이 *"문서·분석·외부 근거로부터 정보를 받았다"* 로 정의한다. 정확히 이 관계다. `implements`(코드가 요구를 구현)나 `verifies`(테스트가 검증)는 방향이 다르다.

### 각 선택지의 대가

| 선택지 | 대가 |
|---|---|
| **`tags` 에 `R{n}`** | §17-5 가 태그 5개 이하를 권고한다. `R115` 가족은 태그 11개가 필요해 권고를 정면으로 깬다. 그리고 §17-4(*"태그는 status·target 을 대체하지 않는다"*)의 취지대로 태그는 분류 축이지 식별자 축이 아니다. `search_requirements` 로 빨리 찾히는 이점은 있으나 `grep` 이 같은 일을 한다. **기각** |
| **`rationale` 에 산문으로** | 산문 안의 `R115` 는 편집 중 소실되기 쉽고, 구조가 없어 커버리지 검사를 문자열 매칭에 의존하게 만든다. 다만 **rationale 에는 원장의 `비고` 칸(최대 2,557자)이 들어가야 하므로 `R{n}` 이 자연히 함께 나타난다** — 그것을 정본으로 삼지 말고 우연한 중복으로 취급하라 |
| **`relatedDocs` 에 링크로** | §12.4-6 이 마크다운 링크 목록을 요구하는데 **원장의 조항 행에는 앵커가 없다**(표의 행이지 헤딩이 아니다). `[R115](./00.decision-log.md)` 는 파일까지만 도달하고 조항으로는 도달하지 못한다. 링크로서 거짓말이 된다. **기각** |
| **`trace` Notes 에** | Notes 셀은 검증되지 않아 오타가 자동으로 잡히지 않는다. **완화: §F 의 커버리지 게이트가 오타를 미아로 만들어 잡는다** — 324행 중 하나가 어느 Notes 에도 없으면 그 자리에서 드러난다. 이 완화가 있어서 이 선택지가 이긴다 |

**두 곳에 동시에 적지 않는다.** `tags` 와 `trace` 양쪽에 `R{n}` 을 넣으면 `R124`(한 사실은 한 곳에)를 SRS 안에서 위반하고, `R124-a` 스윕이 요구사항당 두 자리를 훑어야 한다. **원장이 자기 규율로 명문화한 규칙을 그 원장을 옮기는 작업에서 어기는 것은 특히 나쁘다.**

### 아직 없는 코드 자리로의 `Code` 추적 — 하지 않는다

`packages/editor` 하나뿐이고 HTTP 서버·API·영속화·인증·ACL 이 전무하다(fetch 0건 직접 확인). `Code | packages/server/src/acl.ts | implements` 를 지금 쓰면 **존재하지 않는 파일을 가리키는 추적**이 된다. §2.7 Verification Evidence First 와 정면으로 부딪치고, 규칙 §23.4-1 이 `Requirement` 참조에 실존을 요구하는 취지가 `Code` 에도 그대로 적용된다. `addition_site` 로 "여기에 생길 것"을 적는 것은 **계획이지 추적이 아니다** — 그 자리는 `implementationNotes` 다.

### 화면 설계 문서(`03`~`06`)로의 추적 — 제한적으로, `relatedDocs` 로만

- `trace`/`verifies` 로 걸면 **설계서가 요구사항을 검증한다는 거짓 주장**이 된다. 설계서는 검증물이 아니다.
- `trace`/`refines` 로 걸면 설계서의 미승인 판단이 요구사항으로 승격된 것처럼 읽힌다. **`03` 에만 미승인 〔판단〕 마커가 46개** 있고, 설계 미결이 `03` 19 · `04` 28 · `05` 10 으로 57건이다.
- 그래서 **관계 의미가 없는 `relatedDocs`** 로만 걸고, 그것도 **원장이 소재를 명시 위임한 자리에 한정**한다(예: `R24-a` 카테고리 표 → `04`, `R139-d` 재조정 대기열 화면 → `04`).

### `R124-a` 스윕이 SRS 까지 닿게 하는 방법

원장 조항이 개정되면 그것을 인용하는 자리를 전수 훑어야 한다. SRS 쪽 인용 자리는 **요구사항당 trace 1행 하나뿐**이므로 스윕 명령이 한 줄로 끝난다:

```
grep -rn "R115-e" docs/spec/*.srs.md
```

**이것이 `trace` 단일 정본을 고른 결정적 이유다.** `tags`·`rationale`·`relatedDocs` 에 흩으면 같은 스윕이 네 곳을 봐야 하고, 네 곳 중 하나가 뒤처지는 것이 이 프로젝트가 반복한 실패(`01.design-completion.md` §6.2 — *"결론은 고치고 그 결론을 전제하던 문장은 안 고친다"*)다.

**확신도: high**

## F 실행 순서와 규모

### 동시 실행 — 하지 않는다

**SpecKiwi 가 SRS mutation 잠금을 쓰고 `00.index.md` 를 공유 갱신한다는 사실만으로 결론이 난다.**

1. 잠금이 있다는 것은 **동시 쓰기가 직렬화되거나 실패한다**는 뜻이다. 병렬 서브에이전트 N개를 띄워도 처리량은 늘지 않고 **잠금 경합과 부분 실패 경로만 늘어난다.**

### ②번호 대역 정리 — 브리프의 판단은 결론은 같으나 근거가 부분적이다

브리프는 *"`scaffold_scope` 가 `07` 부터 배정하므로 해소됐다"* 고 적는데, `00.handoff.md` §7.2 의 실제 요구는 *"결정·감사·설계 문서를 `1x` 대역이나 별도 접두사로 옮기고 **`0x` 는 SpecKiwi 전용으로 비운다**"* 이다. 신규 배정이 `07` 부터라는 사실은 그 요구를 충족하지 않는다 — `00.decision-log.md` 가 `00.index.md` 와, `02.feature-request-live-preview.md` 가 `02.product-architecture.srs.md` 와 대역을 공유하는 상태는 그대로다.

**다만 전개를 막지는 않는다.** §5.2 의 번호 유일성은 **scope SRS 문서**(`*.srs.md`)에 걸리고, 위 세 문서는 scope SRS 가 아니다. 그리고 대역 정리는 `docs/**` 파일 이동을 뜻하는데 그것은 이 세션의 권한 밖이다. **결론: 진행 가능. 다만 "해소됐다"가 아니라 "미해소이나 무해하다"로 기록하라** — 나중에 누가 §7.2 를 열고 "이미 했다"고 오독하는 것이 이 프로젝트의 §6.1 실패 형태다.

### 지금 등재한 요구사항이 설계 완성으로 버려질 위험 — 낮다. 근거 셋

**근거 1 — 설계 완성의 정의가 조항 개정을 포함하지 않는다.**
`01.design-completion.md` §5 가 설계 완성을 5조건으로 정의한다: ① 와이어프레임 존재 ② 공백 13건 종결·이관 ③ 설계 미결 57건 종결·위임 ④ 〔판단〕 마커 승인·승격 ⑤ 〔확인 필요〕 마커 확인. **"확정 조항을 재검토한다"가 없다.** §4.1 은 더 직접적이다 — *"소유 심의와 등재는 2026-08-19 에 끝났다 … **남은 절차는** ① `04` 에 「인증 화면」 절을 신설하고 ② … ③ …"*. **그리는 일이지 정하는 일이 아니다.**

**근거 2 — 지시서 스스로 원장을 SSOT 로 선언한다.**
§4.0: *"이 설계 작업의 요구사항 SSOT 는 `docs/spec/00.decision-log.md` 이다."* 설계 작업이 원장을 소비하지 생산하지 않는다는 자기 선언이다.

**근거 3 — 개정률 실측.** 원장 §5 변경 이력 **122행**에서 개정·정정·폐기 문구에 인접한 조항 ID 는 **17개(341행의 5%)** 이고, 그중 다수가 최초 저작 + 3축 감사 기간(2026-08-11~12)에 몰려 있다. 취소선은 4행(1.2%)뿐이다.

**단, 설계 완성이 조항을 *늘리는* 것은 확실하다.** 5조건 중 ②(공백 종결)와 ④(〔판단〕 승격)는 **새 조항을 만든다.** 2026-08-19 하루에 `R143`~`R145`·`R146`~`R148` 계열이 신설된 것이 그 형태다. 그러므로:

- **버려질 위험은 낮고, 추가될 것은 확실하다.** SRS 는 증분 추가에 강하고(새 ID 할당) 대량 폐기에 약하다(§30 discarded 처리). **위험의 방향이 SpecKiwi 가 잘 다루는 쪽이다.**
- 예상 증분: 공백 13건 종결 → 새 요구사항 15~25건. 〔판단〕 46자리 중 승격분 → 미지수. **`ARCH` scope 에 번호 여유를 두고, 각 scope 문서 §7 Change Notes 에 "설계 완성 이후 증분 예정"을 기록하라.**

### 지시서와의 충돌에 대한 기록

사용자 지시가 문서보다 우선한다는 브리프의 판정에 동의한다. 다만 **문서에 그 사실을 남겨야 한다** — `01.design-completion.md` §4.0 이 *"`00.index.md`·`speckiwi` 계열은 이번 작업의 대상이 아니다"* 라고 적은 채로 SRS 가 채워지면, 다음 세션이 그 문장을 읽고 SRS 를 무시한다. **`00.index.md` §11 Change Notes 에 "R32 전개는 설계 완성에 앞서 사용자 지시로 착수했다. `01.design-completion.md` §4.0 의 배제 선언은 이 시점부로 무효다" 를 기록하는 것이 등재 자체보다 중요할 수 있다.** (이 문서 수정은 이 심의의 권한 밖이므로 권고만 남긴다.)

## 내가 이 브리프에서 발견한 오류

### 1. 조항 행 수 — `336` 은 틀렸다. **실제 341**

`docs/spec/00.decision-log.md` **L303~L307** 의 `R43-1`·`R43-2`·`R43-3`·`R43-4`·`R43-5` **5행**이 집계에서 빠졌다. 이 다섯은 `-a`·`-b` 가 아니라 **숫자 접미사** 하위 조항이라 브리프의 계수 정규식이 `-[a-z]` 만 허용한 것으로 보인다. 파생 오류:

| 브리프 | 실제 |
|---|---|
| Phase 1 행 **320** (최상위 135 + 하위 185) | **325** (최상위 135 + 하위 **190**) |
| §2.4 접근 제어 **55** (22 + 33) | **60** (22 + **38**) |

나머지 17개 §2.x 구획의 수치는 전부 일치함을 확인했다. (`고유 번호 144` · `최대 R148` · `결번 R5·R34·R82·R104` · `취소선 4` · `Phase 2 행 12` · `§4 수용 기준 13개` 도 전부 일치.)

### 2. 이 누락은 산술 오류에 그치지 않는다 — 쟁점 A 의 결정적 반례가 빠졌다

`R43` 의 문면은 *"R14(D안) 채택에 따른 **부속 기능 5종을 모두 요건으로 확정한다 (아래)**"* 다. **부모가 내용을 갖지 않는 순수 컨테이너**이고 `R43-1`~`R43-5` 가 실질이다. 다섯은 각각 다른 화면·다른 행위자다(일괄 회수 / `관리` 전용 시뮬레이션 / 감사 목록 / 공유 모달 / 이동 프리뷰).

이것은 **A-2(최상위만 요구사항)를 단독으로 반증하는 사례**인데 브리프에서는 보이지 않는다. 그리고 §4 수용 기준 4번이 *"R43(부속 5종)이 검증된다"* 로 이 다섯을 직접 지목한다.

### 3. 하위 조항의 성격 분포가 오도된다

브리프 §4 는 하위 조항을 *"185행. 성격이 제각각이다"* 라 하고 비규범 유형 넷(예시·잔여위험·정정·관계서술)을 열거해 상당 비중을 함의한다. **실측: 194개 하위 행 중 비규범은 약 10행(5%)이다** — 잔여위험 5(`R72-j`·`R77-b`·`R126-e`·`R134-b`·`R137-h`) · 등재사유 정정 3(`R134-a`·`R137-g`·`R140-a` 부분) · 예시·비교 2(`R115-b`·`R128-a`). **나머지 약 184행(95%)은 독립 검증 가능한 규범**이다.

이 비중 차이가 **쟁점 A 의 답을 바꾼다.** 브리프의 A-3(*"독립 검증 가능한 것만 별도 요구사항"*)을 문자 그대로 적용하면 319건이 되어 A-1 과 사실상 같아진다 — 즉 **A-3 은 브리프가 의도한 중간항이 아니다.** 그래서 나는 A-4 로 답하며 판별 기준을 §29.1 트리거로 교체했다.

### 4. `{{OQ-N}}` placeholder 는 존재하지 않는 기능이다

브리프 §5 쟁점 G 가 *"관련 요구사항의 AC 에 `{{OQ-N}}` placeholder"* 를 선택지로 든다. `docs/rule/SRS-MD-Rules-v2.5.0.md` 전문에서 `{{` 를 검색한 결과 **0건**이다. §21(AC 규칙)에도 placeholder 문법이 없다. 이 선택지는 실재하지 않는 기능이므로 저울에서 빼야 한다.

### 5. §2.1 확인 등급 체계의 행 수 — `약 45행` 은 과소

브리프 §1 이 *"확인 등급 체계(R113~R136 · L1/L2/L3 · 약 45행)"* 라 적는다. 실측 `R113`~`R136` 은 **49행**이고, 같은 주제인 `R142` 계열 7행(일괄 조작 확인)과 `R116`~`R121` 10행(재조회·용어·접근자 지표)을 더하면 **66행**이다. 감사 로그 *"R137~R141 · 약 34행"* 은 정확하다(34행 ✓).

이 차이는 쟁점 B 에서 §2.1 을 어떻게 쪼갤지에 직접 영향한다 — 확인 등급은 §2.1 의 **41%** 를 차지하는 최대 블록이다.

### 6. 번호 대역 정리를 "사실상 해소"로 본 것은 부분적이다

브리프 §5 쟁점 0 이 *"②번호 정리는 사실상 해소됐다"* 라 적는데, `00.handoff.md` §7.2 의 실제 요구는 *"`0x` 는 SpecKiwi 전용으로 비운다"* 이고 그 상태는 변하지 않았다. **결론(진행 가능)은 같으나 근거가 다르며, "해소됐다"로 기록하면 다음 세션이 §7.2 를 완료로 오독한다.** 자세한 것은 위 쟁점 0 참조.

### 7. (브리프 오류 아님 · 원장에 대한 관찰) `G30` 은 Phase 1 을 막지 않는다

브리프의 *"Phase 1 을 막는 것은 13"* 은 원장 머리표(*"Phase 1 착수 판단에는 13건으로 세라"*)를 충실히 옮긴 것이라 브리프의 오류가 아니다. 다만 **`G30` 의 문면 자체가 *"Phase 2 분할 창의 pane 최소 폭"* 이고 *"Phase 2 사안이라 급하지 않으나"* 라고 적는다.** 분할 창은 `R17` 로 Phase 2 다. 원장의 13 은 `G34`·`G35` 만 Phase 2 로 제외했고 `G30` 을 함께 세지 않은 것으로 보인다. **Phase 1 착수를 막는 것은 12건일 수 있다.** 이것은 원장이 판정할 자리이고, 어느 쪽이든 위 §G 의 처분(오염형 5건 격리)은 바뀌지 않는다.
