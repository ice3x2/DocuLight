## 3. SpecKiwi 제약 (사실)

- SpecKiwi SRS 는 **비어 있다** — 요구사항 0건, Target Map 0행, Active Target 없음. scope 는 `ARCH` 스텁 하나(빈 문서).
- 요구사항 ID 형식: `{PREFIX}-{SCOPE}-{NNN}`, 정규식 `^(FR|NFR|IR|DR|SEC|PERF|REL|OBS|OPS|MIG|CON)-[A-Z0-9][A-Z0-9-]{1,24}-[0-9]{3,4}$`
- 타입 접두사 11종: `FR` functional / `NFR` non_functional / `IR` interface / `DR` data / `SEC` security / `PERF` performance / `REL` reliability / `OBS` observability / `OPS` operational / `MIG` migration / `CON` constraint
- **scope 접두사는 타입 접두사와 같으면 안 된다.**
- scope 문서명 `{NN}.{slug}.srs.md`. `scaffold_scope` 가 번호를 자동 배정하며, dry-run 으로 확인한 결과 **기존 `00`~`06`·`90`·`91` 을 회피해 `07` 부터** 준다. 번호 충돌 문제는 없다.
- `set_active_target --create --type phase` 로 target 을 만들 수 있다 (`type` 열거에 `phase` 가 있다).
- `add_requirement` 필드: type · scope · target · title · requirement · acceptanceCriteria · status · priority · tags · risk · stability · verificationMethod · relatedDocs · rationale · implementationNotes · research · changeNotes · evidence · trace
- SRS-MD §29.1 **분리해야 하는 경우**: ① 행위자가 다르다 ② 시스템 경계가 다르다 ③ 검증 방법이 다르다 ④ 기능 동작과 성능 기준이 섞였다 ⑤ AC 목록이 너무 길어진다 ⑥ 다른 target 에 들어가야 한다 ⑦ 일부는 구현됐고 일부는 막혔다
- SRS-MD §29.2 **합쳐도 되는 경우**: ① 사실상 같은 동작을 요구한다 ② 검증 기준이 완전히 동일하다 ③ 한쪽이 다른 쪽의 단순 반복이다 ④ 유지하면 중복 구현·충돌이 생긴다

## 4.5 SpecKiwi 메타데이터 허용값 (규칙 문서 실측)

| 필드 | 허용값 |
|---|---|
| `Type` | functional · non_functional · interface · data · security · performance · reliability · observability · operational · migration · constraint |
| `Status` | **planned · in_progress · blocked · implemented · verified · discarded** (← `proposed` 는 **없다**) |
| `Stability` | draft · evolving · stable · frozen · deprecated · ~~volatile~~(legacy, 신규 금지) |
| `Priority` | critical · high · medium · low · optional |
| `Risk` | low · medium · high · critical |
| `Target` | 자유 문자열 |

Acceptance Criteria 형식은 **반드시 task list** — `- [ ] AC-{N}: {조건·입력·기대 결과}`. 최소 1개. AC 하나에 기대 결과 하나.

scope 문서 골격: `## 1. Scope Overview` → `## 2. Scope Boundaries`(### In Scope / ### Out of Scope) → `## 3. Assumptions and Constraints` → `## 4. Requirements` → `## 5. Cross-scope Dependencies` → `## 6. Open Questions` → `## 7. Change Notes`

## 5. 심의할 쟁점

각 쟁점에 대해 **후보를 나열하고 하나를 고른 뒤, 진 후보가 왜 졌는지**를 적어라.

### 쟁점 0 — 선행 조건 미충족 상태에서의 전개 (먼저 답하라)

지시서가 든 선행 조건은 둘이다: ① 공백 결정 ② 번호 대역 정리. 그리고 *"`G8`·`G10` 은 전개 시 요구사항이 없어 막히는 자리"* 라고 예고한다.

- ②번호 정리는 사실상 해소됐다 — `scaffold_scope` 가 기존 번호를 회피해 `07` 부터 배정하는 것을 dry-run 으로 확인했다. 남은 것은 기존 `02` 중복 경고(`SRS-W072`) 하나이고 이는 `02.feature-request-live-preview.md`(별도 세션 진행 중 표기 문서) 쪽이라 손대지 않는다.
- ①공백 결정은 미충족이다. 열린 공백 13건이 그대로다.

**답할 것**:
- `G8`(에디터·외모 설정 카테고리의 개별 항목 미정)·`G10`(사용자 스키마 — 이메일 필수 여부·표시 이름 규칙)이 **실제로 막는 요구사항이 무엇무엇인가**? 320행 중 몇 개나 되는가? 원장을 직접 읽고 답하라.
- 나머지 13건의 공백은 각각 몇 개의 요구사항을 막는가? 막는 것이 없는 공백도 있는가?
- **공백에 걸리는 요구사항만 보류하고 나머지를 등재하는 것**이 안전한가, 아니면 전체가 오염되는가?
- 지금 등재한 요구사항이 나중에 설계 완성(§4.1~§4.5)의 결과로 **버려지거나 대폭 개정될 위험**은 얼마나 되는가? 원장 조항은 스스로 "요건 확정"이라 하는데, 설계 완성은 조항을 바꾸는 작업인가 조항을 화면으로 옮기는 작업인가? **근거를 대라.**

### 쟁점 A — 입도 (가장 중요)

Phase 1 320행을 몇 개의 SpecKiwi 요구사항으로 만들 것인가?

- **A-1**: 320행 = 320 요구사항 (1:1)
- **A-2**: 최상위 135행만 요구사항으로 하고, 하위 185행은 그 부모의 **Acceptance Criteria / rationale / implementationNotes** 로 흡수
- **A-3**: 하위 조항을 성격별로 갈라 — 독립 검증 가능한 것만 별도 요구사항, 나머지(예시·잔여 위험·정정 사유)는 부모에 흡수
- **A-4**: 그 밖에 당신이 더 낫다고 보는 것

판단할 때 반드시 고려하라: SRS-MD §29.1/§29.2 · 요구사항 하나가 **구현자에게 주는 작업 단위**로 쓸 만한가 · 원장으로의 추적성이 유지되는가 · `R{n}` ↔ 새 ID 매핑을 누가 어디에 적을 것인가.

### 쟁점 B — scope 분할

몇 개의 scope 로 나누고, 각 이름과 접두사는 무엇인가?

- 원장 §2.x 18구획을 그대로 쓸 것인가, **§2.1(156행)을 쪼갤 것인가**, 작은 구획(§2.8·§2.10 각 1행)을 합칠 것인가?
- 접두사는 타입 접두사 11종과 충돌하면 안 된다.
- scope 하나가 지나치게 커지면 무엇이 나빠지는지, 지나치게 잘게 쪼개면 무엇이 나빠지는지 둘 다 적어라.
- **구체적인 표**로 제시하라: `scope 이름 | 접두사 | 담을 §2.x 또는 조항 범위 | 예상 요구사항 수`.

- target 을 몇 개 둘 것인가? (`Phase 1` 하나 / §4 수용 기준 13개별 / 구현 wave 별 / 그 밖)
- 이름과 `type`(version·release·milestone·phase·objective·experiment 중)은?
- 근거를 적어라.

### 쟁점 D — Status 와 Stability

원장은 스스로 *"문서 상태 = **요건 확정**"* 이라 적고, 조항들은 심의를 거쳐 확정된 것이다. 그런데 **구현은 사실상 0** 이다.

- 신규 요구사항의 `Status` 는 무엇이어야 하는가? (`proposed` / `planned` / 그 밖)
- `Stability` 는? (`draft` / `evolving` / `stable` / `frozen`)
- 이 저장소의 `CLAUDE.md` 는 *"에이전트는 `Stability=draft` 인 요구사항의 구현 전에 멈춰야 한다"* 고 규정한다. 전부 `draft` 로 넣으면 **아무도 구현을 시작할 수 없다**. 이 사실을 판단에 반영하라.
- 열린 공백 `G{n}` 에 걸리는 요구사항은 다르게 다뤄야 하는가?

### 쟁점 E — Trace

구현 코드가 거의 없다. 각 요구사항의 `trace` 에 무엇을 달 것인가?

- 원장 조항으로의 `Document` 추적(`docs/spec/00.decision-log.md` + `R{n}`)?
- 아직 없는 코드 자리로의 `Code` 추적(`addition_site`)?
- 화면 설계 문서(`03`·`04`·`05`·`06`)로의 추적?
- **원장 조항 번호 `R{n}` 을 새 요구사항 어디에 남길 것인가** — `tags`? `rationale`? `relatedDocs`? 각 선택지의 대가를 적어라. 나중에 원장이 개정되면 `R124-a` 스윕이 SRS 까지 닿아야 한다는 점을 고려하라.
