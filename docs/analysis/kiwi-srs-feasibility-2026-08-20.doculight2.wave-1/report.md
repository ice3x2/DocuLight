## 2. 값이 없는 자리 (A) — `FR-WORKSPACE-004`

### 2.0 원장이 실제로 정한 것 — 먼저 확인

`R40-a` 비고가 드는 것: *"한글·공백·특수문자, Windows 예약어(`CON` `PRN` `AUX` `NUL`),
경로 260자 제한을 **워크스페이스 계층에 한하여** 회피한다"*.

`R40-e` 문면: *"Windows 예약어(`CON` `PRN` `AUX` `NUL` **등**)·금지 문자·최대 길이·경로
총길이를 생성·개명·업로드 시 검사해 거부한다"*.

**정해진 것은 예약어 예시 넷과 260 이라는 수 하나다.** 나머지는 열려 있다.

### 2.1 Windows 규칙을 왜 강제하는가 — 근거를 먼저 세운다

원장은 **서버가 Windows 에서 돈다고 말하지 않는다.** 그럼에도 Windows 제약을 적용하는
근거는 요구사항 자신의 Rationale 에 있다:

> 워크스페이스 계층은 해시 디렉토리명으로 예약어·금지 문자·경로 길이 문제를 회피하지만,
> **문서·디렉토리 계층은 실제 이름을 그대로 유지하므로 같은 문제가 그대로 노출된다.
> 그 계층에서는 이 검증이 유일한 방어선이다.**

여기에 `R1`·`R3` 이 세운 옵시디언 호환 축이 더해진다 — 볼트는 OS 를 옮겨 다니는 물건이고,
Linux 에서 만든 `aux.md` 는 그 볼트를 Windows 에서 열 수 없게 만든다.

> **⚠ 이것은 추론이다.** 원장에 *"가장 엄격한 집합을 택한다"* 는 조항이 없다. 아래 권장값은
> **「어느 OS 에서도 열리는 볼트」를 목표로 삼았을 때** 도출되는 값이며, 그 목표 자체가
> 조항으로 서 있지는 않다. 채택하려면 이 근거를 요구사항에 남겨야 한다.

### 2.2 권장값 셋

#### ① 금지 문자 집합

| 분류 | 값 | 근거 |
|---|---|---|
| Windows 예약 문자 | `< > : " / \ \| ? *` | Win32 파일 이름 규칙이 명시적으로 금지한다 |
| 제어 문자 | `U+0000`–`U+001F` | Windows 가 금지하고, `U+0000` 은 POSIX 도 금지한다 |
| 경로 구분자 | `/` (POSIX) · `\` (Windows) | 위 집합에 이미 포함된다. **이름에 들어오면 경로 탈출이 된다** |
| 말단 공백·마침표 | 이름 끝의 `` `` 와 `.` | Windows 가 조용히 잘라낸다 — 저장한 이름과 읽는 이름이 달라진다 |

**예약 장치 이름** (Win32 — `R40-e` 의 `등` 을 닫는 후보 목록):
`CON` · `PRN` · `AUX` · `NUL` · `COM1`~`COM9` · **`COM¹` · `COM²` · `COM³`** ·
`LPT1`~`LPT9` · **`LPT¹` · `LPT²` · `LPT³`**.

> **초판은 상첨자 변종 여섯을 빠뜨린 채 「전량」이라고 적었다**(검증 H-1). Microsoft 는
> ISO/IEC 8859-1 상첨자 `¹`·`²`·`³` 를 숫자로 인식해 `COM#`·`LPT#` 의 일부로 취급하며,
> 그래서 그 이름들도 **모든 디렉토리에서 예약**된다. §2.1 이 세운 목표가 *"어느 OS 에서도
> 열리는 볼트"* 인데, Linux 에서 만든 `COM¹.md` 가 정확히 이 목록이 막아야 했던 사례다.
>
> **이 목록을 「전량」이라고 다시 적지 마라.** 이 저장소가 반복한 실패 형태다
> (`00.handoff.md` §6-g① — *"개수 단정을 뺐더니 범위 단정에서 같은 유형이 재발"*).
> 구현자는 이 목록을 **후보**로 받고, 블록리스트를 확정하기 전에 출처를 다시 대조하라.

**판정은 확장자를 뗀 basename 에 대해 대소문자 무시로 한다.** 요구사항이 이 세부를
*"구현 판단으로 남긴다"* 고 적었고, 근거는 Windows 의 실제 거동이다 — `CON.md` 도
`con.txt` 도 장치 이름으로 해석된다. 확장자를 붙였다고 통과시키면 검증이 무의미해진다.

#### ② 최대 이름 길이 — **255**

| 파일시스템 | 한계 | 단위 |
|---|---|---|
| NTFS | 255 | UTF-16 코드 단위 |
| ext4 | 255 | **바이트** |
| APFS | 255 〔**파일시스템 한계가 아니다**〕 | 출처마다 「바이트」·「문자」로 갈린다 |

> **APFS 행은 확정 사실이 아니다**(검증 M-3). APFS 온디스크 구조의 이름 길이 필드는
> **10비트**라 1023바이트 수준까지 허용하며, **255 는 macOS 가 거는 제한**이지
> 파일시스템 자체의 한계가 아니다. 단위조차 출처마다 갈린다.
>
> **그래도 아래 결론은 산다** — 실질 제약은 **ext4 의 255바이트**이고, 255 UTF-8 바이트는
> NTFS(UTF-16 코드 단위 255)도 APFS 도 넘지 않는다. 고칠 것은 이 표의 한 행이지 권장값이 아니다.

**단위가 갈린다.** 한글은 UTF-8 로 3바이트이므로 ext4 에서는 85자에서 걸리고 NTFS 에서는
255자까지 들어간다. **바이트 기준(UTF-8 인코딩 후 255바이트)으로 검사하는 것이 안전한
쪽**이다 — 그래야 어느 파일시스템에서도 통과한다.

> **대가를 명시한다** — 한글 이름은 실질 85자로 제한된다. 사용자에게는 "너무 긴 이름"
> 이라는 안내가 나가는데 화면에 보이는 글자 수는 85 다. 거부 응답이 위반한 규칙을
> 알려야 하므로(`AC-7`) **바이트 한계임을 문구에 드러내야 한다.**

#### ③ 경로 총길이 상한 — **255** (workspace 루트 기준 상대 경로)

원장이 드는 260 은 Windows `MAX_PATH` 이고, 그것은 **드라이브 문자부터 세는 절대 경로**의
한계다. `docsRoot` 가 어디에 있느냐에 따라 남는 예산이 달라지므로 절대 경로로 검사하면
배포 환경마다 판정이 갈린다.

**워크스페이스 루트 기준 상대 경로에 상한을 두는 편이 옳다.** 권장 255.

- 워크스페이스 디렉토리명이 해시라 길이가 고정된다(`R40`·`R40-a`) — 예산 계산이 결정적이다.
- `docsRoot` 절대 경로가 배포마다 달라져도 볼트 자체는 이식 가능하다.

> **⚠ 초판이 여기에 세 번째 근거로 적었던 *"4단계 계층 상한이 이미 깊이를 묶으므로 255 는
> 넉넉하다"* 를 철회한다**(검증 C-1). **`CON-WORKSPACE-001` 은 깊이를 묶지 않는다.**
> 그 요구사항은 계층의 **종류**를 닫은 것이다 — *"옵시디언의 볼트에 해당하는 별도 계층을
> 두지 않는다 … 그 사이에 **중간 계층을 추가하지 않는다**"* 이고, AC 셋이 전부
> *"어떤 **중간 계층**도 존재하지 않는다"* 형태이며 `Verification Method` 가 `review` 다.
> **디렉토리 중첩 깊이는 한 글자도 나오지 않는다.**
>
> **옵시디언 볼트는 폴더를 임의 깊이로 중첩한다.** 깊이를 세어 거부하는 구현은
> `워크스페이스/a/b/c.md` 를 막고, 그것은 `R1`·`R3` 이 세운 이 제품의 존재 이유를 깬다.
>
> **그래서 255 라는 값의 근거가 약해졌다.** 중첩이 자유로우면 한글 디렉토리 서너 겹으로
> 255바이트에 닿는다(한글 1자 = 3바이트). **이 값은 §5 의 결정 목록으로 올린다.**
>
> 〔공정을 위해 — `CON-WORKSPACE-001` AC-4(*"노드 경로·ID 체계·권한 모델은 4단계를 넘는
> 조상 체인을 전제하지 않는다"*)는 깊이 읽기로도 읽힌다. **모호성은 실재한다.** 결함은
> 어느 쪽이 맞느냐가 아니라 **초판이 그 모호성을 열린 물음으로 세우지 않고 한쪽으로
> 조용히 닫은 뒤 그 위에 값을 얹었다는 것**이다〕

> **정하지 못한 것** — `docsRoot` 절대 경로가 길면 상대 경로가 255 안에 있어도 실제
> 파일시스템 호출이 `MAX_PATH` 에서 실패할 수 있다. **기동 시 `docsRoot` 절대 경로
> 길이를 재서 남는 예산이 255 미만이면 경고를 내는 것**이 최소 방어다. 이것을 조항으로
> 올릴지는 이 분석이 정하지 않는다.

## 3. 설계 판정 (B)

### B-1. 노드 ID 는 어디에 사는가 — **권위는 DB 다. 「DB 에만」은 아니다**

물음은 *"파일 이름에 넣을 수 없고 본문에 넣으면 오염되는데 어디에 두는가"* 였다.
**원장이 답한다 — 노드 ID 의 권위는 DB 이고 경로는 그 매핑의 파생 캐시다.**

1. **`R76` 문면** — *"ACL·버전 인덱스·휴지통 인덱스·첨부 소유는 전부 노드 ID 기준이고,
   **경로는 파생 캐시다**"*. 파생 캐시라는 말은 정본이 다른 곳에 있다는 뜻이다.

   > **그 「다른 곳」을 `R20` 으로 지목하려면 확장이 논증돼야 한다**(검증 M-1). `R20` 은
   > *"**사용자·그룹·ACL** 메타데이터는 SQLite 단일 저장소에 둔다"* 로 **셋을 열거**하며
   > **「노드 ID」는 그 열거에 없다.** 초판은 이것을 *"메타데이터는"* 으로 일반화해
   > 조항이 하지 않은 말을 하게 만들었다. **노드 ID 의 소재를 정하는 조항은 `R20` 이
   > 아니라 `R76` 이고**, `R76` 이 드는 네 소비처(ACL·버전 인덱스·휴지통 인덱스·첨부
   > 소유(`R50-a`))가 전부 DB 에 사는 것이 실제 논거다.

2. **`R4` 와 충돌하지 않는다.** `R4` 는 *"모든 `.md` 문서는… 파일시스템이 **문서의**
   SSOT"* 이고 `DR-STORAGE-001` 은 제목부터 *"**문서 본문**의 SSOT 는 서버 로컬
   파일시스템"* 이다. **본문의 SSOT 와 메타데이터의 SSOT 는 다른 축이다.**

> **⚠ 초판의 논증 하나를 철회한다**(검증 H-2). 초판은 *"**`R77-a` 의 존재 자체가
> 증명이다** — ID 가 파일 어딘가에 적혀 있었다면 이 추측이 필요 없다"* 라고 적었다.
> **원장 안에 반례가 있고, 그것도 이 wave 안에 있다.**
>
> **`R40-b`** — *"각 워크스페이스 디렉토리 안에 **`.workspace.json`** 을 두어
> `{id, name, createdAt}` 을 기록한다"*. **ID 가 파일에 적혀 있다.** 그런데도 `R40-d` 는
> *"권위는 DB 다 … `id` 중복 발견 시 나중 것을 격리"* 로 **여전히 방어적 재조정을 요구**한다.
>
> 즉 원장은 「ID 가 파일에 있다 **그리고** 정본은 DB 다 **그리고** 그래도 재조정이
> 필요하다」를 **이미 한 번 설계했다.** 사이드카는 유실·복제될 수 있으므로 파일에 ID 가
> 있어도 상관 판정은 사라지지 않는다. 그러므로 초판의 전제가 원장 자신에게 반증된다.
>
> **남는 결론** — 권위는 DB 다(`R76` 문면으로 그대로 선다). **무너지는 것은 「DB 에**만**
> 산다」는 범위 단정과 그것을 떠받친 「증명」이다.** `R40-b` 가 워크스페이스 계층에
> 사이드카 선례를 이미 세웠으므로, **문서·디렉토리 노드에도 사이드카를 둘지는 열린
> 선택지**이며 이 분석이 닫지 않는다.

> **구현자가 밟을 함정** — 파일이 SSOT 라는 문장을 「존재도 파일이 정한다」로 읽으면
> `SEC-STORAGE-006`(fail-closed 서빙)과 정면 충돌한다. **본문은 파일이 정하고 존재는
> DB 가 정한다.** B-3 이 같은 자리를 다른 각도에서 본 것이다.

### B-2. `id` 중복인데 기재할 대기열이 없다 — **실제로 열려 있다**

`R40-d` 는 *"`id` 중복 발견 시 나중 것을 격리하고 **재조정 대기열(R139)에 기재**한다"* 고
정한다. 그런데 `R139` 를 담는 `REL-AUDIT-001`(재조정 대기열은 감사 로그와 별개 저장소)은
**wave-9 다.** wave-1 은 기재하라는 명령은 받았는데 받을 그릇이 없다.

**이것은 분해가 만든 문제가 아니라 분해가 드러낸 문제다.** 독립 담당자 B 가 같은 자리를
예견하고 `REL-AUDIT-001` 을 자기 wave-1 로 끌어왔다 — 채택한 분해(C)는 그러지 않았다.

**권장 — wave-1 이 대기열 「테이블」을 만들고 기재한다. 의미·감사 연결·화면은 wave-9 가
소유한다.**

- 대안(기재를 미루고 wave-9 가 소급)은 **서버 재기동에 발견이 증발한다.** `R77` 이
  재조정을 기동 시에 돌리므로, 발견 → 재기동 → 재발견의 고리에서 격리만 반복된다.

> **⚠ 초판의 권장 하나를 철회한다**(검증 H-4). 초판은 *"**참조 감사 행은 nullable 이어야
> 한다** — wave-1 에는 감사 로그가 없다"* 라고 적었다. **그것은 `R139` 를 정면으로
> 위반한다.**
>
> `R139` 문면 — *"일어난 일의 기록은 `audit_log` 에만 두고, 대기열은 유형과 감사 행
> 참조만 갖는다 — **시각 · 대상 노드 · 행위자 · 해소 시각 · 해소자를 자기 칸으로 갖지
> 않고 전부 참조 감사 행에서 읽는다.**"*
>
> 참조를 비우면 그 항목은 **시각도 대상 노드도 행위자도 없다.** 다섯 값의 유일한 출처가
> 참조 감사 행이기 때문이다. 남는 것은 `유형` 하나뿐인 껍데기이고, **격리된 워크스페이스가
> 무엇인지조차 적히지 않아** `R40-d` 가 기재를 요구한 목적 자체가 사라진다.
>
> `R139-a` 가 못을 하나 더 박는다 — 대기열 행이 *"경로·시각·행위자를 자기 칸으로 갖지
> 않고 감사 행 ID 만 참조하므로 `R124` 위반이 아니다"*. **참조가 있다는 것이 `R124`
> 무위반의 조건이다.** 참조를 비우면 그 면제가 사라지고, 값을 채우려면 칸을 뚫어야 하며,
> 뚫는 순간 `R124` 위반이 된다.
>
> **초판이 §6-5 에서 *"`R139` 를 원문 전량으로 읽지 않았다"* 고 신고했는데, 읽지 않은
> 그 문장이 정확히 이 권장을 무효화하는 문장이었다.** 자기신고가 결함의 위치를 정확히
> 가리켰는데도 그 상태로 §5 우선순위 2번에 스키마 결정으로 올렸다.
>
> **다시 세운 권장** — 대기열은 `R139` 형태 그대로 만들고 **참조 감사 행을 비우지
> 않는다.** 그러려면 wave-1 에 감사 행을 쓸 최소 경로가 있어야 하고, 그것이 아래
> **B-5** 가 제기하는 wave 경계 문제와 같은 뿌리다 — **두 자리를 따로 풀지 말고 함께
> 풀어야 한다.**

### B-3. fail-closed 서빙 vs 파일시스템 SSOT — **충돌이 아니다. 의도다**

*"서버 밖에서 파일을 넣으면 재조정 전까지 서빙되지 않는가"* — **그렇고, 그것이 설계다.**

- `R55-b` 가 *"DB 에 대응 레코드가 없는 파일시스템 경로에 대한 모든 요청은 거부"* 를
  정하고, 비고가 그 이유를 적는다 — *"「레코드 없음 → 무제한 허용」으로 구현될 여지를 차단"*.
- 그 공백을 메우는 장치가 `R77` 이다 — *"**기동 시 및 주기적으로** 파일시스템과 DB 를
  전체 재조정한다. 미등록 파일 → 신규 노드 생성(상속 적용)"*.
- **원장은 이 창(window)을 이미 계산했다.** `R77-b` 가 잔여 위험을 명시적으로 수용한다 —
  *"정지 중 이동된 문서가 재조정에서 신규 노드(상속)가 되면 일시적으로 원래보다 넓은
  권한으로 보일 수 있다"*. 완전 차단은 *"운영 마찰이 커서 채택하지 않음"* 이라고 적혀 있다.

구현자가 알아야 할 순서는 이것이다 — **거부가 기본이고 재조정이 그것을 푼다.** 반대로
구현하면 `R55-b` 비고가 지목한 그 결함이 된다.

> **⚠ 초판이 여기를 *"이 자리에 판정할 것이 없다"* 로 닫은 것을 철회한다**(검증 H-3).
> **원장 층위에서는 충돌이 없는 것이 맞다. wave 층위에서 문제가 있다.**
>
> `SEC-STORAGE-006` 의 Trace Links 가 `` REL-STORAGE-001 | depends_on `` 을 **기계
> 판독 가능하게 선언**하고, AC-3 이 *"서버가 돌아가는 동안 docsRoot 에 직접 넣은 파일은
> **재조정으로 등록되기 전까지** 서빙되지 않는다"* 라고 적는다.
>
> **그런데 `REL-STORAGE-001`(= `R77`)은 wave-9 다.** 초판이 *"원장은 이 창을 이미
> 계산했다"* 며 인용한 `R77`·`R77-b` 가 **둘 다 wave-9 조항**인데, **창을 닫는 쪽이
> 8개 wave 뒤에 있다는 사실이 논증에서 통째로 빠졌다.**
>
> 이것은 **B-2 가 `DR-WORKSPACE-002` 에서 정확히 잡아낸 것과 같은 종류**다 — 명령은
> wave-1, 받을 그릇은 wave-9. **같은 검사를 이 요구사항에 적용하지 않은 것이 결함이고,
> 이쪽은 SRS 가 `depends_on` 으로 선언해 둔 자리라 놓치기 더 어려웠어야 한다.**

### B-5. **wave-1 의 경계가 두 자리에서 wave-9 에 걸린다** — B-2 와 B-3 은 같은 뿌리다

두 자리를 따로 보면 이음매지만, 함께 보면 **분해가 만든 경계 결함**이다.

| wave-1 요구사항 | 걸린 곳 | 선언 형태 |
|---|---|---|
| `SEC-STORAGE-006` (fail-closed 서빙) | `REL-STORAGE-001`(`R77` 재조정) — **wave-9** | SRS `depends_on` |
| `DR-WORKSPACE-002` (`id` 중복 기재) | `REL-AUDIT-001`(`R139` 대기열) — **wave-9** | 원장 `R40-d` 문면 |

**wave-1 을 이대로 닫으면 「완료」가 거짓이 된다.** `SEC-STORAGE-006` 의 AC-3 은 재조정이
없으면 **원리적으로 통과할 수 없고**, `DR-WORKSPACE-002` 는 기재할 그릇이 없다.

**권장 — 두 요구사항을 wave-1 로 옮긴다.** 근거 셋.

1. **SRS 가 선언한 의존을 따르는 것이지 임의 재분할이 아니다.** `depends_on` 은 기계
   판독 가능한 계약이고, 그것을 거스르는 순서는 분해가 틀린 것이다.
2. **독립 담당자 B 가 분해 시점에 이 자리를 예견했다** — 자기 wave-1 에 `REL-AUDIT-001`
   을 넣었다. 채택한 안(C)이 그러지 않았을 뿐이고, **세 안 중 하나가 독립으로 같은
   결론에 도달한 것은 약한 신호가 아니다.**
3. **H-4 가 막은 우회로가 이 이동으로 열린다.** 대기열의 참조 감사 행을 비우지 않으려면
   wave-1 에 감사 행을 쓸 최소 경로가 있어야 하는데, `REL-AUDIT-001` 이 wave-1 에
   들어오면 그 경로가 같은 wave 안에 선다.

**대가** — wave-1 이 22 → 24건이 되고, `AUDIT`·`STORAGE` scope 가 각각 한 wave 더 걸친다.
**wave 순서는 바뀌지 않는다** — 앞 wave 가 뒤 wave 의 토대라는 전제는 그대로다.

### B-4. 대소문자 판정이 OS 마다 갈리는가 — **원장이 그 문제 때문에 이 규칙을 만들었다**

`R40-f` 비고가 문면 그대로 답한다:

> **Windows 파일시스템에서 같은 파일인데 경로 기반 판정이 갈리는 문제는 접미사로도
> 해소된다.**

**다만 그것이 이 조항의 존재 이유는 아니다**(검증 M-2). 같은 비고의 **굵게 강조된 뒤
문장**이 진짜 무게중심이다:

> **거부로 두면 "보이는 동명은 거부 / 안 보이는 동명은 접미사" 라는 흐름 차이가 생겨
> R102 가 없앤 존재 오라클이 되살아난다**(R113 위반)

앞 문장의 조사가 *"접미사**로도** 해소된다"* 인 것이 표지다 — **OS 의존성 해소는 덤이고,
존재 오라클 차단(`R102`·`R113`)이 존재 이유다.** 초판은 덤을 존재 이유로 승격시켰다.

규칙은 「대소문자만 다른 동명을 파일시스템이 어떻게 보든 응용 계층에서 충돌로 판정한다」
이고, 그러면 NTFS 와 ext4 에서 **동작이 같아진다** — 파일시스템의 자기 거동이 관측
가능해지지 않는다. 그것이 OS 축의 답이다.

**구현** — 충돌 검사를 파일시스템 거동에 맡기지 말고 **DB/응용 계층의 케이스 폴딩 비교**로
한다. ext4 에서는 두 파일이 물리적으로 공존할 수 있지만, 응용이 **두 번째 이름에 접미사를
붙여 그대로 저장한다.**

> **「거부」라고 읽지 마라**(검증 L-6). `R102` 는 *"보이든 보이지 않든 **항상 자동 접미사**
> + 동일한 안내. **확인 단계를 두지 않는다**"* 이고, 「거부 후 제안」은 그 조항이 폐기한
> `~~R44-a~~` 의 형태다. **이름 검증 실패(§2)는 거부이고 이름 충돌(여기)은 접미사다** —
> `FR-WORKSPACE-004` AC-8 이 두 경로를 명시적으로 갈라 놓았다.

> **정하지 못한 것 — 비-ASCII 케이스 폴딩.** 터키어 점 없는 `ı`/`I`, 독일어 `ß`/`SS`,
> 그리스어 종형 시그마 같은 자리에서 폴딩 규칙이 갈린다. 원장에 규정이 없다.
> **한글은 대소문자가 없어 영향받지 않는다**(이 제품의 주 사용 언어라 실무 영향은 작다).
> 로케일 독립 폴딩(`toLowerCase` 가 아니라 Unicode default case folding)을 쓰는 것이
> 최소 방어이며, 이것을 조항으로 올릴지는 이 분석이 정하지 않는다.

| **5** | `OPS-STORAGE-001` 의 검증 방법 | 운영 요건이라 자동 테스트로 닫히지 않는다. **문서화로 닫을지 스크립트로 닫을지** 정해야 `Verification Method` 가 선다 | **내지 않았다** — 백업 절차는 배포 환경에 달렸고 원장에 근거가 없다 |

## 6. 내가 확인하지 못한 것

1. **`packages/editor` 의 vendor 테스트를 켰을 때 무엇이 깨지는지 모른다.** 담당자 3인이
   각자 이것을 위험으로 지목했고, 켜 보기 전에는 알 수 없다는 것도 셋 다 적었다.
   **케이스 수를 정규식으로 세려다 `it.each(` 를 놓쳤다** — 러너가 보고하게 해야 한다.

2. **`docsRoot` 의 실제 배포 경로를 모른다.** §2.2 ③ 의 경로 예산 계산이 그 값에 달렸다.

3. **비-ASCII 케이스 폴딩 규칙을 정하지 않았다** (B-4). 한글은 영향받지 않으나 영향 범위를
   실측하지 않았다.

4. **`OPS-STORAGE-001` 의 검증 방법을 정하지 않았다** (§5-3).

5. **`R139` 의 대기열 스키마를 원문 전량으로 읽지 않았다** — 조항 행의 앞부분만 봤다.
   **이 미확인이 실제로 결함을 냈다** — 읽지 않은 문장이 정확히 B-2 의 권장을
   무효화하는 문장이었다(검증 H-4).
   B-2 를 확정하기 전에 `R139` 계열을 전수로 읽어야 한다 — **초판이 그 범위를
   `R139-a`~`R139-f` 로 적었으나 `R139-g` 가 있다**(검증 M-5). 하필 `R139-g` 가
   **대기열의 이름과 지시 대상을 확정하는 조항**이다. **「전수로 읽으라」는 지시문
   자체가 한 건을 빠뜨리면 다음 세션도 같은 건을 빠뜨린다** — 범위를 숫자로 닫지 말고
   `R139` 로 시작하는 행을 그때 다시 세라.

6. **22건의 AC 를 전량 정독하지 않았다.** 판정은 요구사항 문면·Rationale·Implementation
   Notes 와 대응 원장 조항에 기댔다. **AC 단위 검증은 이 문서가 하지 않았다.**

7. **이 문서 자체가 검증되지 않았다** (머리표). 특히 §2.2 의 값 셋은 외부 사실(Win32 규칙 ·
   파일시스템 한계)에 기대는데 **그 사실을 문서로 대조 확인하지 않고 지식에서 적었다.**
   검증자는 이 축을 먼저 보아야 한다.
