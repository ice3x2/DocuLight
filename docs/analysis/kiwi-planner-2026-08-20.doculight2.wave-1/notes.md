## 1. 세는 방법 — 개수를 어떻게 얻었는가

**이 저장소는 개수 단정이 예외 없이 나중에 거짓이 된 전력이 있다.** 그래서 계획의 모든 개수를 손으로 세지 않고 스크립트가 계산하게 했다. 아래는 그 방법과, 실제로 손으로 세다 틀린 자리다.

### 1.1 요구사항 24건 · AC 118개

`inventory.json` 을 파싱해 계산했다.

```
reqs = 24
ac_total_sum   = 118   (각 항목의 ac_total 합)
ac_ids_len_sum = 118   (각 항목의 ac_ids 배열 길이 합)
mismatch = []          (ac_total 과 ac_ids.length 가 다른 항목)
stability = { stable: 22, evolving: 2 }
```

두 합이 같고 mismatch 가 비어 있으므로 인벤토리 자체가 자기정합적이다. `evolving` 둘은 `CON-ARCH-009` 와 `FR-WORKSPACE-004` 다.

### 1.2 커버리지 111 / 유예 7 / 미커버 0

계획 생성기가 Task 정의의 `covers` 맵과 `deferred_ac` 목록을 인벤토리에 대조해 계산했다. 생성 시점에 아래 항등식과 불변식을 **기계로** 검사했고 위반 0건이었다.

| 검사 | 내용 |
|---|---|
| 항등식 | 요구사항마다 `ac_covered + ac_deferred + missing_ac_ids.length === ac_total` |
| 존재 | `covers` 가 주장하는 AC ID 가 인벤토리의 `ac_ids` 에 실재하는가 |
| 배타 | 같은 AC 가 covered 이면서 deferred 인 자리가 있는가 |
| stable 게이트 | `stable` 요구사항에 `missing_ac_ids` 가 있는가 |
| 고아 | `req_ids` 가 빈 Task · Task 가 0건인 요구사항 |
| 참조 | `depends_on_task` 가 실재하지 않는 Task 를 가리키는가 |
| TDD | `type=code` 인데 tdd 면제인 Task · green 이 자기 red 를 `depends_on_task` 로 참조하지 않는 Task · `exempt_reason` 이 20자 미만인 Task |
| link_id | `trace_links` 의 `link_id` 중복 |

### 1.3 `R139` 계열 — 8행

**범위를 숫자로 닫지 않고** `docs/spec/00.decision-log.md` 에서 `R139` 로 시작하는 표 행을 정규식으로 직접 셌다.

```
LINE 145  R139     LINE 149  R139-d
LINE 146  R139-a   LINE 150  R139-e
LINE 147  R139-b   LINE 151  R139-f
LINE 148  R139-c   LINE 152  R139-g
TOTAL R139-prefixed rows = 8
```

여덟 행을 전문으로 읽었다. 판정 문서 초판이 `R139-a`~`R139-f` 라고 적어 `R139-g` 를 빠뜨렸던 자리이며(검증 M-5), `R139-g` 가 하필 **대기열의 이름(`재조정 대기열`)과 지시 대상을 확정하는 조항**이다.

### 1.4 예약 장치 이름 28개

`CON`·`PRN`·`AUX`·`NUL`(4) + `COM1`~`COM9`(9) + `COM¹`·`COM²`·`COM³`(3) + `LPT1`~`LPT9`(9) + `LPT¹`·`LPT²`·`LPT³`(3) = **28**.

**「전량」이라고 적지 않았다.** 채택 판본(Microsoft Learn, 2025-04-11)의 열거를 옮긴 것이며, 계획은 구현자에게 블록리스트 확정 전 출처 판본 재대조를 요구한다. `COM0`·`LPT0` 은 그 판본의 목록에 없어 넣지 않았고 그 사실을 계획에 적었다.

### 1.5 실제로 손으로 세다 틀린 자리 — 신고

계획 §1.2 의 scope 분포를 처음에 손으로 적었고 **틀렸다.** `ARCH 6 · WORKSPACE 6 · STORAGE 11 · AUDIT 1` 로 썼는데 합이 24가 되긴 했으나 세 값이 모두 틀린 값이었다. 실제는 `ARCH 7 · AUDIT 1 · STORAGE 9 · WORKSPACE 7` 이다(`OPS-ARCH-001` 을 ARCH 에서, `FR-WORKSPACE-006` 을 WORKSPACE 에서 빠뜨리고 STORAGE 를 부풀렸다).

발견 후 그 줄을 인벤토리에서 계산하도록 바꿨다. **이 사건이 §1 의 방침이 필요한 이유의 실례다** — 합이 맞는다고 항목이 맞는 것이 아니다.

## 2. 결정과 근거

### 2.1 `FR-WORKSPACE-004` 의 세 값

판정 문서 §2.2 가 ①·②의 권장값을 냈고 독립 검증이 그 근거를 Microsoft Learn 원문으로 대조해 **참**으로 확인했다. 그 둘은 검증이 지적한 결함(H-1 상첨자 변종 6개 누락 · M-3 APFS 행 부정확)을 반영해 채택했다.

**③ 경로 총길이 상한은 근거가 철회되어 열려 있었고, 이 계획이 정했다 — 512바이트(워크스페이스 루트 기준 상대 경로, UTF-8).**

도출 과정을 그대로 적는다.

1. **측정 기준을 상대 경로로 두는 근거는 살아 있다.** 판정 문서 §2.2 ③ 이 든 세 근거 중 철회된 것은 세 번째(*"4단계 계층 상한이 이미 깊이를 묶으므로 255 는 넉넉하다"*)뿐이고, 앞의 둘(해시 고정 길이로 예산이 결정적 · `docsRoot` 가 배포마다 달라져도 볼트는 이식 가능)은 그대로 선다.
2. **255 는 못 쓴다.** 깊이가 묶이지 않으므로(§2.2) 한글 디렉토리 서너 겹이 255바이트에 닿는다. 그러면 `DR-WORKSPACE-001` AC-7(볼트를 그대로 넣어도 내부 경로·파일명이 변형되지 않는다)이 깨진다.
3. **그러면 무엇을 근거로 값을 고르는가.** 먼저 고를 수 **없는** 근거를 지웠다 — 「Windows `MAX_PATH` 를 보장하는 값」은 존재하지 않는다. 임의 깊이 중첩 허용과 절대 경로 260자 보장은 동시에 참일 수 없고, 원장은 `R40-c`·`R1`·`R3` 으로 중첩 쪽을 이미 택했다. 그러므로 상한의 목적은 이식성 보장이 아니라 **병리적 입력 차단**이다.
4. **남는 근거는 이름 상한과의 정합성이다.** 경로 상한이 이름 상한(255바이트)의 두 배에 못 미치면 **AC-5 가 허용하는 이름을 AC-6 이 거부**한다 — 상한 길이 디렉토리 하나 아래에 상한 길이 파일 하나를 둘 수 없다. 두 AC 가 서로를 무효화하지 않는 최소 값이 `255 × 2 + 2`(구분자 여유) = **512** 다.
5. 512보다 큰 값을 고를 근거는 원장에 없다. 512는 도출된 값이지 고른 값이 아니다.

**잔여** — Windows 예산 문제는 남는다. 기동 시 `docsRoot` 절대 경로 예산 경고가 최소 방어이지만 **그 동작을 덮는 AC 가 없어 계획에 넣지 않았다.** SRS 가 덮지 않는 동작을 구현하지 않는다는 규칙이 유용함보다 우선한다. 조항 신설 여부는 `OQ-02` 로 올렸다.

### 2.2 `CON-WORKSPACE-001` — 깊이 상한이 아니다

**판정: 계층의 종류를 닫은 조항이다. 깊이를 세어 거부하는 코드를 만들지 않는다.**

근거:

- Requirement 문면이 *"그 사이에 **중간 계층**을 추가하지 않는다"* 이고 AC-1~AC-3 이 전부 *"어떤 **중간 계층**도 존재하지 않는다"* 형태다.
- Rationale 전체가 기각된 3계층(볼트) 안을 닫는 이야기이며 **디렉토리 중첩 깊이는 한 글자도 나오지 않는다.**
- `Verification Method` 가 `review` 다 — 코드로 강제하는 규칙이 아니다.
- 깊이로 읽으면 `워크스페이스/a/b/c.md` 가 막히고, 그것은 `R1`·`R3` 이 세운 제품의 존재 이유와 `DR-WORKSPACE-001` AC-7 을 정면으로 깬다.

**모호성은 실재한다.** AC-4(*"노드 경로·ID 체계·권한 모델은 4단계를 넘는 조상 체인을 전제하지 않는다"*)는 깊이 읽기로도 읽힌다. 그래서 계획은 이것을 **조용히 닫지 않고 `OQ-01` 로 올렸으며**, 판정과 근거를 함께 적고 원의도는 조항 저자만 확정할 수 있다고 명시했다. 그 위에 T-PH002-02 검토가 「깊이 카운팅 코드 0건」을 실제로 검색해 확인한다.

### 2.3 재조정 대기열 스키마 — 참조 감사 행을 nullable 로 만들지 않는다

`R139` 문면이 *"시각 · 대상 노드 · 행위자 · 해소 시각 · 해소자를 자기 칸으로 갖지 않고 **전부 참조 감사 행에서 읽는다**"* 이므로 참조를 비우면 그 항목은 **유형 하나뿐인 껍데기**가 된다. `R139-a` 가 못을 하나 더 박는다 — 대기열이 `R124` 위반이 아닌 **조건**이 「감사 행 ID 만 참조한다」는 것이므로, 참조를 비우고 값을 채우려 칸을 뚫는 순간 `R124` 위반이 된다.

**따라서 wave-1 이 최소 `audit_log` 를 함께 연다.** 이것은 선택이 아니라 강제다 — 대기열을 만들라는 명령(`R40-d`·`DR-WORKSPACE-002` AC-6)과 참조를 비우지 말라는 명령(`R139`)이 동시에 걸리면 감사 행을 쓸 경로가 같은 wave 에 있어야 한다. 판정 문서 §3 B-5 가 `REL-AUDIT-001` 을 wave-1 로 옮기라 한 세 번째 근거가 정확히 이것이었고, 입력 인벤토리 24건이 이미 그 이동을 반영하고 있다.

**경계** — 감사 로그의 정본 스키마는 `R84` 계열(AUDIT scope)이 소유하고 wave-1 에 없다. T-PH003-06 은 재조정이 쓰기에 필요한 최소 칸만 열고 확장을 막는 제약을 걸지 않는다. 이 경계를 `RISK-02` · `OQ-08` 로 올렸다.

**두 테이블을 한 Task 로 묶은 이유**(독립 검증 H-3 처분) — 초판은 `audit_log` 를 별도 쌍(T-PH003-03/04)으로 세우고 그 쌍에 `REL-AUDIT-001` AC-7 을 물렸다. 그런데 그 시점에 대기열 테이블이 아직 없어서 *"대기열에 같은 값을 담은 칸이 없다"* 는 단언이 red 에서도 green 에서도 공허하게 참이었다. **반증할 수 없는 단언은 커버리지가 아니다.** `audit_log` 는 wave-1 에 자기 AC 가 없으므로 그 쌍은 성립하지 않고, 두 테이블을 한 마이그레이션 묶음으로 함께 여는 것이 옳다 — 대기열의 *"참조 감사 행 없이 삽입하면 거부된다"* 시험이 삽입할 감사 행을 요구하므로 그 자리가 `audit_log` 를 강제하는 지점이다. AC-7 은 두 저장소가 다 서고 실제 발견이 기록되는 T-PH006-04 로 옮겼다.

확정한 스키마:

```
reconciliation_finding(id, type)
reconciliation_finding_audit_ref(finding_id NOT NULL, audit_log_id NOT NULL, ordinal)
  · 항목마다 참조 1건 이상을 삽입 경로에서 강제
reconciliation_finding.resolution_audit_id  ← 이 테이블의 유일한 nullable 칸. 비어 있음 = 미해소
없는 칸: 시각 · 대상 노드 · 행위자 · 해소 시각 · 해소자 · 워크스페이스(스코프)
```

스코프를 칸으로 두지 않는 근거는 `R139-e` 다 — 스코프는 참조 감사 행의 대상 노드에서 파생한다.

### 2.4 `OPS-STORAGE-001` 의 검증 방법 — 둘로 가른다

**AC-1·AC-4 는 운영 런북(문서)으로, AC-2·AC-3 은 자동 테스트로 닫는다.**

요구사항 Implementation Notes 가 이미 두 축을 갈라 놓았다 — *"운영 절차 요건이라 자동 검증보다 절차 검토가 검증 방법이다. **복원 후 스캔이 도는지 자체는 재조정 요구의 시험으로 함께 확인된다.**"*

그 갈림이 wave-1 에서 실제로 성립하는 이유는 `REL-STORAGE-001`(재조정)이 같은 wave 에 있기 때문이다. 재조정이 뒤 wave 였다면 AC-2·AC-3 도 문서로 밀렸을 것이다.

**스크립트로 닫지 않은 이유** — 백업 도구·주기·보관 위치를 원장이 정하지 않았다. 스크립트를 쓰면 원장에 없는 결정을 코드에 굳히게 된다. 런북은 그 항목들을 「배포 환경이 정할 자리」로 표시한다.

### 2.5 커버리지 판정 규칙 — covered / deferred 의 경계

이 wave 는 요구사항이 이름으로 드는 주체 중 상당수(ACL·인증·첨부·휴지통·버전·에디터 화면)가 뒤 wave 에 있어서, AC 를 「일부만 관측되는」 상태로 마주치는 자리가 많았다. 규칙을 먼저 정하고 일관되게 적용했다.

- **covered** — wave-1 이 그 AC 에 대한 검증 산출물을 만든다. AC 가 드는 주체 일부가 없더라도 **존재하는 주체에 대해 실제로 시험되면** 커버로 센다. 잔여는 Task 의 `dod` 가 적고 `risks[]` 가 재판정을 예약한다.
- **deferred** — 검증 산출물을 **전혀** 만들 수 없다. §5.4 에 사유와 소유 예상을 적는다.
- **판정의 기준은 「금지 형태냐 긍정 형태냐」가 아니라 「시험할 주체가 wave-1 에 있느냐」다.** 주체가 하나도 없으면 형태와 무관하게 유예다.

이 규칙이 없으면 「공허한 통과」와 「진짜 유예」가 섞여 커버리지 숫자가 의미를 잃는다.

> **초판이 이 규칙을 두 자리에서 스스로 어겼다**(독립 검증 H-1·H-2). 초판은 위 셋째 항목을 *"금지 조작 형태의 AC 는 위반 대상이 없어도 covered 로 센다"* 로 적어 `CON-ARCH-002` AC-7 을 통과시켰고, 넷째 항목의 예시로 `CON-ARCH-003` AC-4 를 들며 *"세 모듈이 SPA 에 없으면"* 이라는 **사실이 아닌 전제** 위에 유예를 세웠다. 둘 다 처분했다(§4). **형태로 가르는 조항 자체가 결함이었으므로 그 두 줄을 지우고 주체 기준 한 줄로 대체했다.**

### 2.6 TDD 쌍의 단위

지시는 *"AC 단위로 red Task 와 green Task 를 분리"* 였다. 문자 그대로 AC 하나당 쌍 하나를 두면 이 wave 만 160여 개 Task 가 되어 계획이 도구로서 쓸모를 잃는다.

**채택한 해석** — 쌍의 단위는 하나의 응집된 AC 묶음이고, **각 쌍이 덮는 AC 를 ID 로 열거**하며 **한 AC 가 두 쌍에 걸치지 않는다.** AC 단위 추적성은 `covers` 맵으로 그대로 유지되고 생성기가 기계로 검사한다. 이 해석을 `TDD-POLICY-02` 로 계획에 명시했다.

결과 — `type=code` 36개 = red 18 + green 18(H-3 처분으로 한 쌍이 흡수된 뒤의 수). `type=code` 인데 tdd 면제인 Task 는 0건이다.

### 4.4 eval 이 확인하지 못했다고 적은 것 중 내가 답할 수 있는 것

- **§7-6 「`notes.md` 를 읽지 않았다」** — 그 결과 §1.5(내가 손으로 세다 틀린 자리를 자진 신고한 항목)를 보지 못했다. eval 의 계수 축 판정이 그 신고와 독립이라는 뜻이므로 오히려 교차검증이 됐다.
- **§7-2 「세 값의 외부 근거를 원문으로 대조하지 않았다」** — 이 축은 내 §3.1-5 의 자기신고와 같다. **feasibility 보고서 · 그 독립 검증 · 이 계획 · 이 계획의 독립 검증 넷 다 Microsoft Learn 을 실행으로 확인하지 않았다.** 구현자가 블록리스트를 확정할 때 출처 판본을 다시 대조하라는 지시를 계획 §5.5 에 남긴 것이 현재로선 최선의 방어다.
- **§7-3 「`expected_failure_signature` 의 실제 실행 가능성」** — M-1 처분으로 신호가 단언 기반이 됐으므로 이제는 **코드를 쓰기 전에 확인할 방법이 원리적으로 없다.** red 를 실제로 돌려야 알 수 있고, 그것이 red Task 의 DoD("러너 출력으로 red 를 확인했다")가 존재하는 이유다.
