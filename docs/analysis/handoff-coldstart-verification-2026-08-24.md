# `/new` 이어가기 검증 보고 — 2026-08-24

**질문**: `/new` 로 완전히 새 세션에서 시작해도 핸드오프 문서만으로 작업을 이어갈 수 있는가.

**답**: **처음 상태로는 안 됐다.** 고쳐서 지금은 「조건부 가능」이다 — 남은 조건은 사람만 답할 수 있는 것 셋뿐이다.

---

## 어떻게 검증했나

제가 쓴 문서를 제가 다시 읽는 것으로는 답이 안 나옵니다. 빈칸을 무의식적으로 메우기 때문입니다. 그래서 **문서 존재조차 모르는 서브에이전트에게 새 세션 사용자가 칠 법한 첫 발화만 주고 실제로 실행시켰습니다.**

| 검증 | 무엇을 했나 |
| --- | --- |
| 콜드 스타트 시뮬레이션 | "이어서 작업하자. wave master 로 끝까지 진행해줘" 만 주고 읽기 전용으로 실행 시도 |
| 대화 의존 감사 | 이전 대화에만 있던 지식을 전제하는 자리 탐지 |
| 최종 검증 | 고치는 과정에서 들어간 새 거짓·자기모순 탐지 |

앞선 회차의 사실 검증 3회를 합쳐 **총 6회**를 돌렸습니다.

---

## 결과 — 어디서 막혔나

문서를 **찾고 읽고 상태를 대조하는 5단계까지는 마찰 없이 통과**했습니다. 상태·카운트·플래그·함정 경고가 실측과 일치했습니다.

**막힌 곳은 정확히 첫 실제 행동이었습니다.**

---

## 가장 위험했던 것 — 사실 오류가 아니라 되돌리기 어려운 지시

제 대체 규약이 이렇게 적고 있었습니다.

> `/kiwi-pipeline` 에는 `--target phase-1` 을 전달하고, 그 wave 의 범위는 `--req-filter` 로 좁힌다.

그런데 `kiwi-pipeline` §7 상 **`--req-filter` 는 `kiwi-planner`·`kiwi-pm` 까지만 흐르고, `kiwi-srs-feasibility` 는 `--target` 만 받습니다.** 그 스킬의 본 동작은 「활성 target 의 SRS **전수** 평가 + `update_stability` **일괄 갱신**」입니다.

즉 문서를 그대로 따랐으면 **wave 마다 `phase-1` 253건 전체의 stability 가 바뀌었을 것**입니다. `--from=planner` 로 진입하면 feasibility 단계 자체를 건너뛴다는 것을 확인해 그것으로 닫았습니다.

## 정반대 방향의 결함 하나

같은 문서가 「wave 실행 중 `update_status` 금지」를 제약으로 걸고 있었는데, `kiwi-pm` 이 T-final 에서 `update_status("implemented")` 를 **반드시** 호출하고 `kiwi-review-fix-loop --close-reqs` 가 `implemented → verified` 를 수행합니다. 제약이 파이프라인을 자기부정에 빠뜨리고 있었습니다 — 첫 코딩 wave 에서 멈춥니다.

금지 범위를 「사람이 손으로 넣는, 그 wave 범위 밖 mutation」으로 좁혔습니다.
