## Exact read state and completion predicates

Use a real query state `loading | ready{card} | error{retry}` keyed by authenticated identity and principal ID. Undefined is loading/unavailable, not empty. Loading displays the heading plus status; failure displays a safe error and actual retry. HTTP401 follows existing session-loss handling; 404 combines unavailable target/insufficient authority without disclosing which. A group/unknown principal also receives current404. On role loss remove cached privileged details and use existing settings fallback. No stale successful payload remains actionable after a failed authorization/query.

Required narrow correctness delta under IR-PRINCIPAL-001 AC2 and FR-PRINCIPAL-003 AC1/2: add authoritative `principalStatus` to the existing superuser card response/type, and derive stage1 `done` from `status === 'suspended'`; stage2 remains `status !== 'active'`. This exposes only already-authorized roster data and changes no authentication policy. Do not derive status from the existing boolean or stale source row. Until that projection is connected, exact stage1 completion is unavailable and must not be claimed.

The outer ordered list always contains four stages with number, title, textual state and optional action. Use `대기`, `진행 중`, `확인 필요`, `완료` qualified by the predicate, and an icon/shape in addition to color. Do not manufacture a persisted current-step index. Later stages are not auto-executed. After a guard rejection stop the active sequence and require explicit retry/back; never continue automatically. The card can describe independently completed later facts even when an earlier stage is incomplete.

Overall copy must not say “all access removed” or “offboarding fully complete” while system-group removal is unproven. Even all four limited predicates do not recover downloaded/copied content. ## Stage1: suspension, confirmation and identity loss

Use existing `setUserStatus(id,'suspended')` → POST `/roster/users/:id/status`; success204, known409 `{rule:'last-active-superuser'}`, 404 unavailable/reserved/unknown as supplied, other errors generic. Do not broaden this card to arbitrary status dropdown/reactivation/signup approval. Required promise adapter returns `{ok:true}` or `{ok:false,reason?:'last-active-superuser'}` without swallowing exceptions; unknown transport outcomes remain unconfirmed and lead to re-read before any retry.

Use one per-person **L2** confirmation: FR-CONFIRM-023 expressly requires stage1 confirmation and settings §2.8 requires the dialog; there is no typing/count requirement. Title `계정을 비활성화합니다`, exact returned target name, current status→정지, and immediate login/session/PAT authentication effects. Account, memberships and ACL records are not deleted by suspension. Do not use the generic delayed-cleanup notice, invent an undo/reactivation button, or request a successor administrator.

Re-query target status on opening and before submit. If already suspended, close without another write and re-render from fresh facts. If status/name/identity changes, show revised context and require explicit confirmation again. The endpoint has no expected-version/CAS token: this preflight is not an atomic reservation and must not be advertised as one. A synchronous per-user pending guard prevents repeated activation. Retain dialog/card until the real request settles; show inline failure, not success on invocation. On accepted204 refresh card and source roster; a refresh error is `변경은 적용됐지만 상태를 다시 불러오지 못했습니다.` with read-only retry, never another suspension POST.

Only the actual last-**active-superuser** floor is enforced. There is no blanket actor==target prohibition. Last workspace administrator is a different warning policy and not a reason to block suspension or demand new admin grants. Known floor409 shows `활성 슈퍼유저가 최소 한 명 남아 있어야 합니다.` and preserves earlier completed operations. Do not infer the floor from the displayed roster.

Self-target is allowed when server guards permit it; warn that the current session will end. Success removes that user's sessions. Route subsequent401 through the existing login/session invalidation flow and clear privileged card data; a local toast cannot survive an auth unmount, so do not require one or promise further steps can execute as the now-suspended actor. Do not keep a frozen superuser actor credential in the frontend. Another authorized session can later reopen the target card using live state.

## Stage3: executable ordinary-group plan and one L2

There is no bulk membership endpoint and card `groups:string[]` must never be converted to group IDs by matching names. A narrowly necessary adapter may reuse **fresh superuser group roster** `{id,name,system,members:[{id,...}]}` and filter actual `system === false` groups whose members contain the exact target user ID. This supplies an ephemeral ordered plan `{userId,groups:[{id,name}]}`. Names from the card are display-only; roster IDs are execution authority. Cross-check completeness of the current ordinary-membership projection; missing/failed/contradictory data blocks execution. Do not infer default membership from stored rows or classify system subtypes from display names.

Fresh plan on opening and again before L2 submit; compare target ID and complete group ID/name set. Membership/name changes invalidate confirmation and render all current names for renewed explicit activation. An empty fresh plan means `제거할 일반 그룹이 없습니다.` and sends no DELETE. List **all** names inside the dialog with wrapping and its own bounded scrolling; no “외 N” truncation. Stable IDs key rows, including duplicate names. Title includes target; explain ordinary groups only, system groups excluded, earlier suspension remains applied and no undo is promised. One L2 per user even if that user has many ordinary groups; never one L2 covering many users or L3 based on group count.

Add a typed client method for existing DELETE `/roster/groups/:groupId/members/:userId`. It currently returns204 or bare400 (401/404 for authorization). Return `{ok:true}` only for accepted204; bare400 is a generic step failure, **not** proof of last-active-superuser or unknown membership. Do not invent detailed rule feedback that this route discards. The domain removal operation records an audit event even for a no-longer-present membership, reinforcing why blind repeat is not safe evidence.

Execute the frozen ordinary-group IDs sequentially in server roster order; lock other destructive card actions/selection. On the first failed/unconfirmed request, stop sending the tail. Preserve ephemeral per-group outcomes `{groupId,state:'accepted'|'unconfirmed'|'not-run'}` for honest status; these are operation feedback, not durable progress or completion flags. Never rollback prior removals, re-add memberships or reactivate the account. Refresh card/roster after outcomes. Subsequent deliberate retry builds a new fresh plan and one new L2; it never blindly replays the original list. Accepted204 plus refresh failure is distinct from mutation failure; retry the read.

The API has no batch snapshot/precondition, so membership races between last read and each DELETE remain possible. Do not remove a group that was added after the confirmed plan. A concurrent new ordinary group keeps the stage incomplete after re-read. Session/authority loss stops the remaining calls. Query-generation checks prevent stale results for userA rendering inside userB. Pending navigation cannot be described as cancelling already-sent work; keep a mounted result owner while requests settle, with auth invalidation always taking precedence.

**System-group removal is blocked in this slice's executable plan.** The actual projection excludes superuser and default, while prior §2.8 discusses superuser removal with its own floor/self-confirmation constraints. Do not silently add system IDs to the ordinary plan, remove automatic default membership, or claim stage3 proves their removal. A full offboarding-membership scope/preview contract and applicable self-superuser confirmation must be agreed before that behavior is exposed. Ordinary-group removal itself cannot exercise the superuser-membership floor branch, so it must not be offered as evidence that that missing branch is complete.

## Stage4 and audit boundaries

Card has only current residual direct-ACL count, navigation and server-derived completion. No duplicate influence table, L3, direct grant/revoke or private per-workspace total. #69 owns complete selected-subject preview, scope, fresh L3 typing, execution order/partial outcomes and last-workspace-admin warnings where provided. The offboarding handoff must not bypass any blocked preview or execution gate. Return always re-reads the card: #69's visible/eligible revocation set can differ from the card's raw ACL count, so an accepted bulk action is not proof `remaining=0`.

Superuser revocation scope is the full authorized instance as returned by server; a workspace manager remains in #69's managed scope without the privileged card. ACL revocation does not change membership and is not subject to the active-superuser floor. Removing the last workspace-admin ACL is permitted with its existing warning; no successor grant is inserted. If current #69 preview lacks a required warning/context, retain its execution blocker rather than using offboarding as a shortcut.

Existing status/member/ACL services own audit records. UI acceptance does not imply a separately verified audit write and no event ID/audit deep link is supplied by these callbacks. Preserve existing operations, actor/subject identities and outcomes; do not synthesize a workflow-complete event, expose third-party PAT data, or promise evidence about content already copied. Actual API/server tests inspect existing audit rows and no duplicate mutation/audit events after read retry.
