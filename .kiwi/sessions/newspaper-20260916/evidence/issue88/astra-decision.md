## Registration, ownership and allowed information

SettingsModal supplies a stable registration capability only to the mounted active category. A registration has exactly `{ ownerId, dirtyCount, onContinue, onCancel }`: ownerId is an opaque per-mounted-child identity, count is a nonnegative integer count of changed fields, and callbacks close over the child's own state. Registration returns an owner-bound cleanup function. Callback names mean confirmed discard and cancelled departure; they do not perform parent navigation or secretly save. The parent alone owns the requested category/close continuation.

No baseline/draft/value strings, validation text containing values, token/password, field names/value maps, serialized DOM or mutation payload enters registration, parent state, logs, analytics or browser storage. InstanceSettings counts exact changed known keys against its latest confirmed baseline, as #71 already does: its maximum is five, invalid partial input still counts if changed, an explicit reset becomes zero, successful reconciled save becomes zero only for the saved generation. A count of zero is clean, not a second interpretation of validity.

The parent may hold only this minimal registration, an opaque session/category/mount epoch, the pending navigation descriptor and ordinary DOM focus reference. These lifecycle/navigation facts are not copied form values. Child callbacks must be stable enough that rerendering does not unregister/re-register the owner and accidentally cancel an open prompt.

Single active owner is the contract. Only the capability belonging to the currently active category/mount can register. A second distinct owner while that owner is alive is rejected and leaves the existing guard effective; never use last-write-wins or silently sum unrelated forms. If one category later contains multiple ordinary dirty subforms, that category must aggregate their counts/callbacks locally into one owner before using this interface; that migration is not in #88. Replacement is permitted only after the old owner is explicitly invalidated by category lifecycle/auth generation/unmount. Old cleanup clears registration only when both owner identity and registration epoch still match, so delayed cleanup cannot clear its replacement. StrictMode mount/cleanup/remount must be safe.

Dirty-count changes update the same owner's registration. No stale closure may report the prior render's count when a user edits and immediately activates another category. Registration synchronization must finish before the next usable departure event; do not depend on an arbitrarily delayed passive effect to make an edited form dirty. A missing registration is not interpreted by DOM-inspecting inputs or guessing dirty state.

## One departure arbiter and exact state machine

All user-originated parent category/open changes pass through one `requestLeave` arbiter. Store intent as `category(targetId)` or `close`, together with the current owner/session/category epoch, not an arbitrary mutable destination callback from a later event. Selecting the already active category is a no-op. Reject a forbidden/nonexistent target without unmounting.

| State | Event and transition |
| --- | --- |
| Ready, no ordinary dirty owner | Eligible user request executes once, subject to the active child's stronger PAT/security guard. |
| Ready, ordinary owner count > 0 | Snapshot the first requested intent and current focus; retain mounted category/form; open one L2 risk confirmation. No category/open-state change yet. |
| Confirming | Further category/close/outside requests cannot replace/queue the first intent or open another prompt. Return focus to the existing prompt where needed. |
| Confirming, safe action or topmost Escape | Clear pending intent first; invoke current owner's onCancel once; leave form/category/modal intact; restore focus. Return Ready. |
| Confirming, explicit discard | Revalidate owner/session/category and destination permission. Mark intent consumed synchronously before callbacks; invoke onContinue once; execute original parent intent once only if still valid. |
| Owner removed/replaced, settings closed externally, auth invalidated | Invalidate the intent and prompt; do not execute its callbacks or destination for a new owner. Follow security/parent lifecycle, not user-discard semantics. |
| Callback fails or throws unexpectedly | Consume the attempt, perform no parent transition, retain form where still allowed and show safe inline failure guidance. Do not auto-repeat callbacks or navigation. |

Callbacks are synchronous notifications for child-local discard/cancel handling, with no Promise/async save permission. Child work already in flight must not be awaited through this registration. Expected declines/pending conditions are handled before invocation, not by exceptions for normal control flow. A category switch that unmounts naturally need not manually reconstruct or clear draft in parent memory.

Revalidate again after onContinue because it can trigger a child/security lifecycle change. A consumed intent cannot execute after cancellation, teardown, owner change, destination revocation or a second click. If the target category was removed while confirming, discard that pending navigation and keep the current allowed form with a neutral notice; require a new explicit destination. Never silently substitute `editor` for the requested target.

If current owner count changes while the prompt is open, keep the intent fixed and update `저장하지 않은 변경 N건이 있습니다.` from that owner. If count remains positive, clear any stale armed action until that render's count is shown; ordinary L2 still requires explicit discard. If it becomes zero (e.g. an accepted save readback completed), dismiss the now-unnecessary prompt **without navigating** and restore focus; the user may request departure again. No automatic navigation from a save callback.

## Category, close, Escape and outside-click behavior

- Controlled Radix Tabs value changes, including pointer activation, ArrowUp/Down/Home/End automatic activation and Enter/Space where applicable, enter the same arbiter. Keep the current panel mounted while confirming; a focused target tab is not a committed selection. Same-tab actions and ordinary Tab traversal do not prompt.
- Header close, Dialog `onOpenChange(false)`, topmost settings Escape and pointer-down outside each request the same close intent. Prevent the original Radix dismissal before it commits when dirty. Explicit content dismissal handlers must request the guard, not merely `preventDefault` and silently swallow Escape/outside.
- Normalize overlapping Radix outside/Escape/open-change callbacks into one intent. The first event must neither close settings nor leak into the underlying document, and its following click must not activate a page control after the warning appears. Rely on modal interception and a consumed-event/intent latch; do not add a global document listener.
- Once the risk confirmation is topmost, Escape means `계속 편집`/cancel for that risk layer only. Outside clicking it never approves discard or closes the parent. Page/setting menu Escape first closes that menu, not settings; preserve existing #48 portal/layer ownership.
- PAT specialized guard has priority within the tokens category. Keep its existing issuing/reveal/copying/discard handling and its stronger Escape/outside suppression; the new generic L2 must not convert token plaintext into `dirtyCount=1`, force-unmount TokenPanel or stack another discard prompt. Route category/header-close intentions through the existing PAT continuation with the same one-intent/owner checks. Its disabled Escape/outside is an existing secret-protection exception, not a shortcut for ordinary dirty forms. Regress the real PAT flow without copying plaintext to the parent.

Permission/auth changes are not user navigation. If the selected category becomes unauthorized, stop rendering it immediately, clear its guard/intent and privileged local state, and use #61's neutral unavailable notice/fallback. Do not let an L2 prompt hold revoked content open. All async child completions continue to obey their own mounted owner/request generation checks; ownerless late success cannot revive the form or dismiss a later prompt.

## Pending saves and interaction with issue 87

The guard protects draft departure, not reversal of a sent request. During #71/#87 preflight, preview or save activity, the ordinary dirty registration remains truthful. User departure with a positive count still requires L2; an active retention risk dialog already owns the top layer and must be cancelled/dismissed before a separate departure prompt can be requested. Do not stack L2 draft-discard over retention L2/L3 or let one approval imply the other.

If a user explicitly discards while a PUT is already in flight, navigation may proceed after the warning; it does not cancel or roll back that PUT. The confirmation includes the neutral shared warning `이미 요청한 저장은 취소되지 않습니다.` so the shell needs no new privileged payload or save-state field. The child invalidates its UI generation on unmount; a later result cannot mutate another form. Reopening obtains current settings through GET. Do not claim the server was unchanged or retry a write merely because its initiating form departed. This preserves existing uncertain/accepted-readback semantics without expanding the four-field registration contract.

If a clean form has an in-flight readback, ordinary close is permitted; it is a read, not a lost dirty draft. If a response would make a newer draft clean, the child's #71 generation reconciliation determines that; the parent must never set dirtyCount to zero on behalf of a successful Promise. No synthetic network cancellation is presented as a guaranteed server-side cancellation.

## Confirmation, focus and visual behavior

Use shared ConfirmGate/AlertDialog L2, with title `저장하지 않은 변경`, description `저장하지 않은 변경 N건이 있습니다.`, safe action `계속 편집` and explicit discard `변경 버리고 나가기`. No typing field, retention count or destructive-policy consent is part of this dialog. Existing ConfirmGate currently hardcodes Cancel text; a narrow safe-label parameter may be needed, preserving every other consumer's default. Do not construct a second settings modal or repurpose a token-reveal view.

Initial focus is the safe action. Trap focus only in the topmost risk layer; preserve settings 400/500, settings-owned menu 600, risk 700/800 and risk-owned menu 900. Label title/description programmatically; announce changed count/failure without moving focus. Buttons remain keyboard reachable in long Korean, both themes and forced colors. Enter during IME composition cannot confirm/discard; ordinary explicit activation remains available.

Capture active focus before the leave interaction moves it when possible, without reading the control's value. Cancel restores that connected control in the still-mounted current form, including text selection/caret naturally preserved by keeping the input mounted; otherwise restore the initiating connected control inside settings, then active category tab as a safe fallback. Do not focus a removed target tab, forbidden control or element behind the modal. Pointer activation must not make a target category's focus/aria-selected mismatch trigger an automatic repeat leave request after cancellation.

Confirmed category departure selects the exact requested category and focuses its tab per #61; normal tab-to-panel keyboard traversal follows. Confirmed close restores the original bottom-left gear or existing logical shell fallback. These transitions do not reset the underlying document/editor, URL or theme. Async status changes alone do not steal focus. No theme remount or browser storage is used to preserve the form.
