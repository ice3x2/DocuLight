## Truthful query/action adapters and open capability gaps

Use the existing share query with a node-bound state:

```ts
type ShareQueryState =
  | { state: 'loading'; nodeId: string }
  | { state: 'ready'; nodeId: string; view: ShareViewBody }
  | { state: 'error'; nodeId: string; onRetry: () => void };
type ShareActionResult = { ok: true } | { ok: false };
// Existing grant/revoke/break/inherit callbacks return Promise<ShareActionResult>.
// Fresh confirmation data, bound to the modal's node:
type RefreshShareView = () => Promise<ShareViewBody | undefined>;
```

Forward actual query state instead of inferring it from `view===undefined`. Error takes precedence over stale success. A different node cannot inherit the prior node's data, selected principal, operation status or confirmation. Mutations return true only when their existing POST/DELETE resolves successfully; missing/forbidden/transport failures return false or reject to a safe generic handler. Remove catch-and-report-success behavior only in these sharing adapters. Preserve existing share/tree invalidation, but query-refresh failure is separate from accepted mutation and must not cause an automatic repeated write.

Confirmation refresh uses the existing GET share endpoint and returns fresh server permission/kind/count data. Add only a thin wrapper for the already-existing `/grant-warnings` endpoint where required, bound to the selected principal/entry ID. It returns the existing warning-code list; show supported GrantWarningList text, never raw payloads. Failed confirmation refresh/warning lookup blocks that attempted mutation with an honest retry state, rather than assuming safe L1 or a zero count. Capture source node ID for invalidation; the current global sharingId may have changed while a request was in flight.

**SRS-first correction — authoritative identity is available to the administrator through a fresh read.** `FR-CONFIRM-014` is verified/stable. Its VE-1 requires an actual revoke by entry ID, and VE-2 explicitly owns the App path: grant returns 204, the refreshed share list supplies that principal's entry, and the toast sends DELETE for it. The previous decision's blanket prohibition on resolving the entry from refreshed rows was incorrect and is withdrawn. Preserve this existing supported behavior; 204 does not make the administrator toast generally unsupported. The current schema's unique `(node_id, principal_id, level)` index and repository grant/read behavior make a unique direct row from a fresh, node-bound server response an authoritative identity. No POST-response change is required for this path.

For a successful L1 document grant, capture `{sourceNodeId, principalId, requestedLevel, operationGeneration}` before sending the existing POST. After success, explicitly refresh that same node using the existing share GET, started after the POST resolves. Accept only a response belonging to the same current node/owner/operation generation, with current `level=admin` and non-null rows. Resolve **exactly one** row matching `principalId` and `level===requestedLevel`, `inherited===false`, and non-null `entryId`. Use the server's returned entry ID; never the display name, first principal match, row order, old cache, inherited entry or a different level. The node is bound by the captured GET target. If no unique matching row exists, do not guess. This is the existing VE-2 route made precise, not a new policy or a claim that this operation exclusively created an entry: repeated grants may reference the existing unique entry.

When that identity is resolved, the administrator's L1 toast **must retain an enabled `회수` button**, pass that exact ID to the existing DELETE adapter, await its actual outcome and prevent duplicate clicks. Keep the already-read-content warning and never label it `실행취소`. Pending identity lookup may show an explicitly disabled `회수` with `회수 정보를 불러오는 중입니다.`; a failed/missing match displays `회수 정보를 확인하지 못했습니다. 다시 불러오십시오.` with a real query-only retry. Do not show an enabled no-op, repeat the grant, or classify the accepted grant as failed. Node/owner change or loss of management access clears the resolved capability before another action; the server remains the final revoke authority. Direct manager-row revocation remains supported separately.

**Remaining editor gap:** an editor's `view.rows=null` is intentional under `SEC-ACL-015`. With the current 204 POST response and no authoritative operation-specific entry handoff, that role cannot resolve the toast revoke ID through the administrator route. Preserve the successful grant status and the required already-read-content warning; show the honest limitation `이 화면에서는 방금 부여한 권한의 회수 대상을 확인할 수 없습니다.` and no enabled/no-op revoke control. Do not expose an ACL roster, infer an ID, claim lack of server revoke permission, or silently suppress the contract. This is an explicit **unmet editor L1 product path**, not fulfillment or narrowing of FR-CONFIRM-014. The administrator path is mandatory now; completing the editor path requires a separately authorized authoritative capability/response handoff. This decision does not change server responses or SRS status/AC/evidence.

Other explicit limits: workspace `admin` assignment is not supported by this view/edit-only client/route and belongs to the workspace-management scope; do not add an option that the route silently maps to view. Editor self-grant revocation outside a returned operation capability cannot be enabled from a forbidden roster. Group-member/person-roster expansion, invited-email delivery, missing actor/granted-by metadata and a dynamic parent-entry preview are not supplied; do not synthesize them. Existing manager ACL rows are not the expanded “all reachable people” roster. Document L1 revoke's full undo contract is likewise not invented from a 204 response.

## Exact confirmation policy and fresh context

| Operation | Gate and required context |
| --- | --- |
| Explicit single active/pending user + document view/edit grant | L1 immediate after current warning check; pending alone does not invent suspended warning. After actual success, administrator toast resolves the exact direct principal+level entry from a fresh node-bound read and offers real `회수`; editor identity gap remains explicitly blocked. |
| Group principal on document, or any principal on directory/container | One L2 before grant (FR-CONFIRM-011). |
| Suspended user grant | One L2 with existing neutral inactive-account delayed-effect warning; merge with an otherwise-required L2, never stack two. |
| Direct ACL revoke on document | Existing L1 immediate, exact entry ID; no new pre-confirmation. |
| Direct ACL revoke on directory/workspace | One L2 with target/principal and existing attachment-access notice; no attachment counts. |

| Break inheritance on directory | Admin only, L3, exact fresh server impact count as typing token with no denominator. |
| Parent permission import | Admin only, non-workspace, broken-inheritance state; L2. It imports as existing service defines, not a renamed restore-inheritance operation. |
| Workspace inheritance | No section/toggle/import control; it has no parent to break/import. |

All confirmations identify the selected node (including directory type), selected principal or direct entry as applicable, and requested level. Capture IDs and displayed context atomically; changing node/subject/level invalidates an old confirmation. Dialog cancel preserves the add selection for correction but executes nothing. No confirmation defaults from missing view to `file`, missing count to zero or absent principal to a guessed subject.

For container grant show fresh `적용 하위 N개` **in the confirmation only**, not permanently beside the people metric. Reuse server `reached` through a fresh share view; never derive counts from loaded tree rows. Break-directory shows the supplied impact count and requires its exact numeric token. Opening gates refreshes displayed counts; changed value locks execution and updates display/token under FR-CONFIRM-004. Since current common ConfirmGate has no explicit unlock action, cancel and reopen against the refreshed baseline is the supported recovery; do not silently unlock or keep an old L3 token. Failed refresh leaves execution unavailable with a real retry path.

Container grant always displays the shared inheritance and broken-inheritance notices independent of whether any hidden/broken descendants exist. Do not enumerate unreachable nodes or add a warning only when they exist. Suspended-subject warning comes from the existing server warning contract and says `비활성`, not disciplinary status. Any existing last-administrator warning supplied by the warning endpoint is shown and confirmed according to its governing rule, not guessed by counting displayed names. Source node/path/principal context must survive long-text wrapping and remain visible above the final action.

No widening operation gains L3, no risk gate auto-executes from search selection, and no L2/L3 callback runs before acceptance. Shared RevokeConfirm/ConfirmGate may need a narrow Promise-return adapter so their existing pending guard awaits the real operation rather than closing immediately; restrict changes to this callback ownership, not shared grade policy. Repeated confirm/click triggers one mutation; conflicting operations on the same modal target serialize locally, not a new server lock.

## Results, focus and navigation

On grant/revoke/break/import mutation success show a concise mounted status without leaking payloads; query refresh may separately fail. On mutation failure keep selection/target and show safe action-specific generic wording (`권한을 부여하지 못했습니다.`, `권한을 회수하지 못했습니다.`, `상속 설정을 변경하지 못했습니다.`) plus deliberate retry. Do not clear input or render success before response. Repeating a confirmation-governed action after failure requires its current context/gate again; query failure retry only reloads data, never repeats a write.

L1 grant status retains the semantic warning that revocation cannot recover already-read content. For an administrator, the fresh unique direct principal+requested-level match described above supplies the authoritative ID and **the actionable `회수` toast is required**. Revoke success/failure is the actual DELETE result, not row disappearance. The editor's null-roster case gets the explicit limitation status while its actionable path remains unmet; that partial presentation is not completion evidence. Never use an arbitrary same-name row, stale list or another permission level to fill the gap.

Opening focuses the sharing title or current search field when ready, never a risk action. Keep focus on search/selection during ordinary updates and on a useful error location after failed submission. L2/L3 starts on cancel/explanation, traps focus and inherits #48 overlay ownership. Cancel returns to the exact invoking control if still mounted, otherwise modal heading/allowed control. Success that removes a direct row chooses its next surviving logical row action or list heading only when current focus belonged to that removed row. Never focus by stale array index or steal focus after the user navigated elsewhere.

Close/parent node change invalidates local confirmation/result generations; no late response repaints another node or closes its dialog. Existing mutations already sent are not canceled by closing; show no abort claim. Role loss/read error hides prior manager rows and mutation controls immediately; any unavailable parent/session cleanup is a reported integration limitation, not justification to leave forbidden names in DOM.

Use existing shared Dialog ownership (no duplicate raw Portal/Overlay), accessible title/description and named close control. Page popover 300, dialog overlay/content 400/500, dialog-owned popup 600, risk overlay/content 700/800 and risk-owned popup 900 stay unchanged. Escape dismisses only the topmost eligible layer; a cmdk action does not submit a risk gate. Actual parent modal triggers retain their focus return. No route or document-body change results from merely opening sharing.
