## Durable job and projection contracts

Implement the already-authorized repository port/SQLite migration and one application worker, wired into actual main/server stores. Keep queue/projection tables separate from vector_entry and reconciliation_finding. A pending operation must survive process restart; a component array, timer, vector row count, finding count or in-memory-only backlog cannot satisfy AC1/2.

Each current job is keyed by stable nodeId and has a monotonic request generation/revision, requestedAt, state `pending|running|failed`, and safe failure classification. The worker retains its claimed generation plus an opaque claim/run identity internally. The precise SQL schema is an implementation choice, but these invariants are mandatory:

1. A relevant change durably upserts the latest node request. Repeated events for the same source revision may coalesce; a new revision supersedes an older request, resets it to pending and clears the old error. requestedAt represents that latest request, not original creation time. One queue row per node, not one per save keystroke or one per PDF page.
2. Claim pending work atomically and mark its generation running before extraction. A single worker processes one claim at a time; no distributed-worker infrastructure or user-set concurrency. Scheduling may wake on new enqueue and startup; this is internal worker scheduling, not browser polling.
3. Read the current source through existing storage/PDF boundaries. Before publication recheck the claimed generation and source identity/revision, node existence and eligible type/servability. A running older generation whose node changed must not publish over a later projection, clear the new job, or mark the new job failed. Its result is discarded; the latest pending generation is processed next. In-flight obsolete work is not represented as a second user-visible job.
4. Publish a complete projection and remove only the matching successful job in one durable database transaction. Never expose half of a PDF's pages or a new body paired with old tags. On extraction/write failure mark only that still-current claim failed; retain it for inspection. Last successfully published content may remain searchable while current changed content is pending/failed, subject always to current security gates. Do not claim source content is current merely because an older projection exists.
5. A failed job does not repeatedly retry on a timer. The next applicable node change or next startup moves it to pending under AC2. Startup also converts interrupted running jobs to pending and enqueues missing/stale searchable existing nodes. Source revision/fingerprint comparisons must detect real content changes; a path/name alone is not a freshness token.
6. Remove/invalidate text projection and queue work when a node disappears or becomes ineligible. A deleted/trashed/reserved/hidden node cannot resurrect through a late claimed write. Restore/reappearance is a fresh eligible request. Names/workspace names are resolved from current metadata, never stale projection labels. Type changes between markdown/PDF/nontext retire inappropriate projection content.

**Claim/crash semantics:** a running claim is owned by the one current application worker; it is not a distributed time lease. Startup recovery invalidates previous-run ownership and returns interrupted work to pending before claiming. A process crash between extraction and commit leaves a reclaimable durable job; atomic publication prevents projection-committed/job-unremoved split bookkeeping. Stopping the worker must prevent further claims and drain or invalidate its owned callbacks before the database closes. No timeout-based success, arbitrary lease expiry, cross-process exactly-once claim, or multi-server coordination promise. If actual deployment permits simultaneous processes against one store, that requires explicit coordination scope before claiming safety beyond the one-worker assembly.

## Mutation hooks and search consistency

Place enqueue at common application mutation boundaries so real UI, REST and MCP writes share behavior: document creation after source exists, successful save, new content version/restore, uploaded searchable PDF, searchable file change, and eligible restore/reconciliation discovery. Initial node identity creation before a file is written must not cause a permanent false read failure without a final source-ready request. The current watcher handles add/unlink but lacks a content-change handler; add the narrow text-change enqueue integration required by AC1 without rewriting relocation correlation or creating duplicate nodes. Duplicate own-write notifications coalesce by node/revision.

Persist the indexing obligation before accepting a source mutation, not as a fallible afterthought after changing the source. A worker can be paused while saves still complete; no acknowledgment waits for text extraction/projection completion. Existing synchronous vector behavior remains unchanged. FR-STORAGE-010 AC1's durable request and FR-STORAGE-002's accepted content hash must both hold: an indexing enqueue failure must never turn an already-applied save/create/overwrite into an ordinary rejection that discards the accepted hash or node ID.

### Source-ready outbox invariant — required integration boundary

The current storage model spans filesystem source bytes and synchronous SQLite metadata transactions; a SQLite transaction does **not** roll back an awaited filesystem write. Use the bounded durable indexing outbox within the new repository, rather than claiming those resources are one transaction. This is internal text-work scheduling under AC1/2, not a new user-visible partial-save protocol:

1. Complete existing authorization/name/baseHash preconditions, then persist a **prepared indexing obligation before the first source mutation**. Bind it to the stable nodeId, unique mutation/generation and expected resulting source fingerprint/content hash, with sufficient existing source identity to reconcile it. It contains no document body/token. For creation, stable node metadata allocation and this obligation must share the existing metadata transaction; a failed outbox insert cannot leave a committed newly allocated node/ACL/audit result. Do not hold the synchronous transaction open across awaited filesystem I/O.
2. Prepared work is not source-ready. The worker cannot extract a nonexistent creation file, snapshot the old bytes and clear the obligation, or index partially written content. Existing mutation serialization/source-ready coordination and fingerprint verification must cover create, save, overwrite, version restore and copy/restore hooks, including own-write watcher events. A source-ready obligation becomes the normal pending generation only after the source operation has actually succeeded and its identity/fingerprint matches. A pending display state, if used for durable prepared work, must still obey this internal claim exclusion; no fourth public queue state or premature success is invented.
3. If preparation fails, stop **before** changing bytes or committing creation identity; return existing operation failure safely. If the source operation succeeds, the durable obligation already exists. A later failure to promote it to runnable pending must leave that obligation durable for internal reconciliation; it must **not** change the successful source outcome into a generic failure. Return the existing accepted `{hash}`/stable created `{id,...}` result exactly as the mutation contract requires. This success asserts source acceptance plus a durable indexing obligation, not completed indexing. No new public partial-acceptance flag is needed or assumed.
4. Reconcile prepared obligations as part of the same worker/startup recovery, after live mutation ownership is released or previous process ownership is known dead. Verify current node/source/fingerprint and generation before promotion. A crash after successful source write but before promotion must recover that same identity/generation. A crash or failure before source readiness must not certify the proposed content as saved; cancel the obsolete prepared intent only after comparing actual source state, retaining/backfilling the latest actual eligible source as required by AC2. Never resurrect a missing node, replay a source overwrite, allocate a replacement node, duplicate a version/ACL/audit event or overwrite external newer bytes during indexing recovery.
5. An older prepared obligation cannot suppress a later mutation or publish over it. Promote/coalesce/retire only with expected generation and claim checks; preserve enough durable intent until the latest applicable obligation is secured. If a source operation failed, worker reconciliation observes actual source rather than treating its intended fingerprint as accepted. External file changes are already source facts when observed: retry/backfill their indexing bookkeeping through worker/startup without pretending an API save/create occurred.

This outbox is a required correctness prerequisite, not a claim the existing services already provide it. Implementers must show the concrete common application boundary/metadata transaction for each hooked mutation before enabling the hook. If a path cannot preserve these invariants within the approved storage model, that path remains blocked pending an explicit SRS-backed typed partial-acceptance/reconcile contract and client handling; do not fall back to “write source, enqueue, throw500.” Lost transport responses and broader exactly-once creation remain existing separate concerns; the outbox specifically prevents adding a new post-commit indexing failure that causes false autosave conflicts, duplicate retry creation or replayed overwrite.

Search body/tag/PDF reads only successfully processed projection content; do not silently fall back to live source scanning on an index miss/failure, which would hide the queue and violate AC3. Names and attachment names continue using current metadata. Preserve existing lowercasing/AND groups/OR alternatives/Korean matching and excerpt ordering/deduplication; use current parser/matcher behavior, not a new tokenizer/ranker. A successful empty document/PDF is a valid empty projection. Preserve PDF page numbers including blank pages; no concatenation that renumbers pages, fifth search axis or viewer link.

Immediately before returning search results, revalidate each candidate's node existence, full ancestor serving-state/name rules, deletion state and current effective view permission. An earlier permission batch before awaited work is not the final check. Filter names, excerpts, page evidence and counts together; never serialize a hidden stale row and hide it in React. Attachment-name search remains under owning-node permission. ACL change does not need a text rebuild to prevent disclosure: the next result query must respect it even with an old projection. Keep synchronous vector removal/move semantics and identities; do not route them through this queue.

## Required typed PDF failure channel

Current PdfTextExtractor.extract explicitly returns `[]` for unreadable bytes, and pdfjs adapter catches initialization/parsing failure. That cannot distinguish a legitimate empty extraction from a failed indexing operation. A narrow extension of the existing extraction boundary is required for this worker:

```ts
type PdfExtractionResult =
  | { ok: true; pages: readonly PdfPageText[] }
  | { ok: false; errorCode: 'parse_failed' };
```

Provide a typed strict extraction method/adapter using the same pdfjs implementation, or migrate the port with an explicit compatibility adapter for existing consumers. Preserve legacy empty-result behavior where its existing caller contract requires it; do not reinterpret a bare empty array as failure. Source file I/O failure is `read_failed`; PDF parse/page extraction failure is `parse_failed`; projection/index persistence failure is `index_failed`. Legitimate empty pages/no text succeed and leave no failed queue row. Full-page extraction must succeed before projection publication; a failure after page1 must not publish a partial document. Release PDF resources on all outcomes. No new PDF library, duplicated parser, raw exception body, password field or unsupported encrypted-PDF promise.

## Read API and exact snapshot semantics

Add the already-authorized typed GET `/api/index-queue`, with client helper respecting its existing `/api` prefix convention:

```ts
type IndexQueueSnapshot = {
  counts: { pending: number; running: number; failed: number };
  total: number;
  limit: 100;
  items: Array<{
    nodeId: string;
    name: string;
    workspaceName: string;
    status: 'pending' | 'running' | 'failed';
    requestedAt: string;
    errorCode?: 'read_failed' | 'parse_failed' | 'index_failed';
  }>;
};
```

Authenticate **only through the existing browser-session `actorOf`** passed into workspaceApiRouter. Production main.ts resolves this actor from the session cookie via authenticateSession; this endpoint must not accept bearer/PAT authentication or import the MCP/PAT actor path. Require current superuser at the server. Match the existing privileged roster read denial shape: absent/invalid session401, authenticated non-superuser404 with no queue payload. A valid PAT alone, including a superuser-owned PAT, still has no session actor and receives401. Do not add a workspace-admin exception. Category absence is not the server security boundary.

Counts, total and rows are one consistent request-time read snapshot; `total = pending + running + failed`, rows ordered by requestedAt ascending then nodeId, `items.length <= min(total,100)`. Counts cover all outstanding text jobs, not only the first100. Do not calculate counts from the visible slice, limit before sorting, or expose completed history rows as jobs. The queue contains only currently eligible, existing serving nodes; lifecycle cleanup/filtering must keep stale inaccessible names out and make the counts describe the same eligible operational set. Do not reveal deleted/hard-hidden paths or fabricate generic names while leaving inconsistent totals.

The response contains current display names/workspace names, never absolute paths, source excerpts/body, tokens, parser stacks, raw SQL errors or claim internals. Failed rows carry the safe code; missing/unrecognized safe error code is rendered generically, not guessed. No timestamp of access rights or completion estimate. Queue time is the actual request timestamp and can be formatted as local absolute date/time, with ISO datetime in a semantic time element. No seconds-updating “age” timer.

## Exact settings body, states and interaction

The existing superuser `색인 대기열` category opens one read-only right-body panel. It is distinct from #70's `재조정 대기열`, with no shared findings data/cache key/status/empty copy. Heading `색인 대기열`, explanatory text `텍스트 검색 색인의 처리 상태입니다.`, explicit secondary `새로고침` button. Read on entry and explicit refresh only: no interval polling, websocket/SSE, browser-focus refetch, reconnect refetch, retry-on-error loop or completion push. Configure any reused query helper accordingly. Leaving/re-entering is a new entry read.

State adapter is `loading | ready{snapshot} | error{retry}` bound to auth identity/current superuser context/request generation. Initial loading shows `색인 상태를 불러오는 중입니다.` with no fabricated0. Explicit refresh retains the panel header and busy status but suppresses old actionable/readout data until the authoritative request resolves; preserve the logical scroll/focus anchor. Error shows `색인 상태를 불러오지 못했습니다.` and `다시 불러오기` issuing only this GET. Unauthorized/identity changes clear prior privileged snapshot immediately. Overlapping clicks share one in-flight request/disabled button; stale responses cannot repaint after role change/unmount/new generation.

Ready summary is exactly three text badges: `대기 N`, `처리 중 N`, `실패 N`. They are readonly counts, not filter tabs. Total0 after a real successful read shows `현재 대기 중인 색인 작업이 없습니다.` This includes absence of failed/running jobs, but does not assert that all external changes have already been discovered or that every document is healthy. Failed>0 adds `실패한 작업은 해당 노드가 변경되거나 서버가 다시 시작될 때 다시 처리됩니다.` This is an explanation, not a restart/retry button or remediation guarantee.

Table columns are `이름`, `워크스페이스`, `상태`, `요청 시각`, `오류`. Status labels are 대기/처리 중/실패; errors read `파일 읽기 실패`, `텍스트 추출 실패`, `색인 저장 실패`, or generic `처리 실패`. Nonfailed error cell is `—`. No body, filesystem path, progress bar, percentage, rate, ETA, attempt count, worker-health light or completed count. If total>100 show `전체 N건 중 요청 시각 순으로 최대 100건을 표시합니다.`; otherwise `N건`. This operational total is not a search-results forbidden hidden-denominator pattern: it is the authorized queue's actual total, explicitly required by AC5. No next-page/infinite-scroll/load-more or client filter is promised.

Rows are read-only information, not clickable documents or selectable jobs. nodeId keys preserve identity but no extra metadata lookup/deep link is invented. Long duplicate display names remain readable with supplied workspace context; there is no mutation target requiring name uniqueness. No job retry, cancel, pause/resume, rebuild/reindex, purge, download/export, or batch selection. Thus no L1/L2/L3 gate applies. GET retry is always `다시 불러오기`, never `작업 재시도`.
