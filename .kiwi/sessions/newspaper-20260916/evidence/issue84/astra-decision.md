## Chosen minimal metadata and disclosure boundary

Expose one server-owned boolean, `aclRevokePreservesSuperuserBypass`, in a revocation-specific projection. It means this principal represents superuser bypass that removing its ACL entries does not remove. For a user, derive it from current direct superuser-group membership, not an ACL entry or account name; account activation remains a separate serving gate. For the actual superuser system group it is true; for the default group and ordinary groups it is false. An ordinary group does not become a superuser group merely because one of its members is a superuser. Do not add group member lists, reasons, subtype IDs, membership counts, or a general privilege catalog.

Keep ordinary `GET /api/principals?q=...&for=...` output unchanged. Add the explicit query purpose `purpose=revocation` on that existing endpoint and a narrow typed client call. In that mode require a real `workspace:<id>` scope currently administered by the authenticated requester, reusing the existing workspace policy; reject missing/invalid/out-of-scope targets indistinguishably with the established 404, and unauthenticated requests with 401. `node:` edit permission is insufficient for this extra projection; no fallback to ordinary results with missing capability. Only after that gate return the usual eligible/max20/min-two-character results plus the boolean. Unknown supplied purpose values are rejected rather than interpreted as revocation. The default search behavior and shared picker's other consumers retain their old contract.

Also add authoritative selected-subject metadata to the existing GET revocation preview response: `subject: { id, aclRevokePreservesSuperuserBypass }`. It is mandatory for a valid existing selected subject and independently protected by the existing management diagnostic gate. A deleted/missing subject makes that preview unavailable with a neutral error; do not fabricate false metadata or silently drop it from a multi-subject plan. Preserve existing scope/rows semantics. The mutation response remains the actual removed ACL rows; capability is not a new authorization control or a reason to prohibit removing those rows.

Use a revocation candidate type extending the ordinary row, rather than requiring the new private field on every principal search result. Shared picker accepts the narrow revocation search adapter/mode; do not fork its keyboard/IME implementation. Selected-preview metadata, not a cached candidate object, supplies the current warning in the selected list and L3. Distinguish absent/loading/error metadata from explicit false; absence invalidates a revocation plan until the preview succeeds.

## Warning, freshness and operation semantics

Only a true authoritative signal shows `ACL 회수로 슈퍼유저 우회 접근은 제거되지 않음`. Do not say the account can log in while suspended, or that no other mechanism can remove the privilege. Keep the separate existing generic system-group warning for every `system: true` selection. A superuser system group receives both notices; an ordinary superuser user receives the bypass notice only; default group receives the generic system notice only. Both kinds of system group remain selectable, and their ACL entries remain revocable under the existing permissions and L3 rules.

Refresh selected-subject metadata with every subject preview, including on opening and immediately before accepting the single existing bulk L3. Include boolean values and subject IDs in the confirmed plan identity along with scope/entry identity. A capability flip with unchanged row count invalidates the old consent, displays the refreshed information and requires a new confirmation; do not silently retain old typed consent. This does not add another dialog or change the token: it remains the complete plan's total ACL-entry count, with all-zero blocked and some-zero subjects included.

Bind candidates and selected previews to #83's managed-scope/auth generation. Changing account/anchor/scope or losing management removes old private metadata from state/DOM and cancels the gate; late responses cannot restore it. The server rechecks authority at each read/write. Preserve #69's non-atomic sequential revocation: stop after first unconfirmed result, retain confirmed removals, never auto-retry or automatically remove memberships/suspend accounts. A group membership can change after the final preview; this slice adds an informative fresh snapshot, not an atomic ACL-and-membership transaction. Do not claim perpetual post-revocation access or total denial. Confirmed mutation outcomes remain separate from refresh errors.
