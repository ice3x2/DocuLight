## Precedence and exact copy

State precedence is explicit, not “data exists means success.” It is evaluated within each read owner and cannot overwrite unrelated healthy panels.

1. Session503 plus authoritative `detail.state==='uninstalled'` selects the existing install page. Bare503, proxy HTML or a missing marker is a request error, never installation. Existing installation authentication rules remain unchanged.
2. Actual session401 selects full-page PreAuthScreen with no app shell/settings gear/privileged background. A first anonymous visit shows ordinary login. If this same App previously established a session and no locally owned transition explains it, show origin-neutral `로그인이 해제되었습니다. 다시 로그인하세요.` above the real login form. Prior-session existence plus401 proves neither expiration nor a specific cause: explicit logout, successful password change and other invalidation also produce401. The API has no typed expiry cause, so do not display `세션이 만료되었습니다` as an inferred diagnosis.

   App.signOut must preserve whether its own logout POST was accepted instead of swallowing that result. **Confirmed logout success (204/current accepted response) itself establishes authentication ended; confirmed password-change success likewise establishes the documented session invalidation. Immediately mark the old local authentication generation ended, stop its protected requests, clear its privileged cache/secret state and render the shell-free login surface. Do not wait for a follow-up session GET.** Logout success returns to ordinary login without an expiry diagnosis; confirmed password change may show `비밀번호가 변경되었습니다. 다시 로그인하세요.`. A follow-up GET network error/500/401 cannot retain or resurrect the old protected shell/documents, and an old in-flight200 cannot override this terminal local generation. Only a later actual successful login/new authenticated generation may establish a new session.

   This immediate security transition is conditional on the **pre-mutation secure draft-handoff prerequisite in B1**. If current edits may exist and no authorized handoff proves them safely exported/discarded/isolated, the #76 integration must not send the voluntary logout/password-change POST and then improvise after success. That affected path remains blocked for implementation/completion until the prerequisite is resolved; this is not permission to keep protected content visible after an already-accepted invalidation. Existing product code must not be described as compliant merely because it currently waits for GET.

   An attempted or failed POST is different from accepted success. Current signOut's catch-to-undefined loses this distinction; narrowly preserve its accepted/rejected/unknown outcome before applying presentation. Intent alone must not produce `로그아웃했습니다`, password-change success copy or a typed expiry cause. After a failed/unconfirmed POST, a real subsequent session200 may retain the established shell; session401 ends authentication with origin-neutral wording unless a cause was actually confirmed; session500/network failure reports that current authentication could not be checked and supplies a real read retry, without claiming successful logout/password change. No mutation is automatically replayed. Keep transition context ephemeral, bound to the current authentication generation, and clear stale intent on failed attempt/cancel as applicable, new identity or successful login. A generic request failure still does not establish why authentication ended.
3. Before established session data, pending is `애플리케이션을 불러오는 중입니다.`; terminal session request failure is `애플리케이션을 불러오지 못했습니다.` plus `연결 상태를 확인한 뒤 다시 시도하세요.` and a button calling session.refetch. Existing no-data fallback currently masks this failure as permanent loading; fix that branch. No fake login/install action is shown on arbitrary request failure.
4. With an established session and live shell **and no confirmed authentication-ending mutation**, transient session/tree/body read errors remain explicit query errors. Do not reclassify the user as anonymous, clear editor text or remount DocumentSurface merely because of500/network failure. Privileged fresh readouts that failed cannot be labelled current. Confirmed logout/password-change success has higher precedence than any cached session or subsequent GET failure; actual session401/identity changes also take their security path.
5. Successful tree read with no accessible content shows existing exact FR-AUTH-005 text: `접근할 수 있는 문서가 아직 없습니다.` / `워크스페이스 관리자에게 권한을 요청하세요.` Preserve available settings/personal controls and permitted workspace/container actions. This text is not an access-request button or invite/send-message workflow. Do not infer zero nodes from session.workspaceCount or request failure; do not discard legitimate visible empty-workspace containers when assessing accessible tree state.
6. No requested deep link, no open tab and no document-load failure: central `문서를 선택하세요.` with `왼쪽 목록에서 문서를 열 수 있습니다.` This replaces DocumentArea's empty div and is not the tree's no-access explanation. It has no automatic new-document button or initial focus into the editor.
7. A current requested document after authoritative successful tree/read determination is unavailable: exactly `문서를 찾을 수 없습니다`. Missing, deleted and unauthorized have identical visible/accessible wording and controls under SEC-ACL-006. No forbidden path/name, “권한이 없습니다,” “비공개,” hidden count, contact target or request-access action is added.
8. Initial requested document read pending: `문서를 불러오는 중입니다.` Read failure other than unavailable404: `문서를 불러오지 못했습니다.` plus safe connection guidance and retry for that exact GET. Success with `body:''` is a real empty document, not missing/loading. A failed request is not valid empty markdown.

Read-only category APIs may legitimately return404 for unavailable/unauthorized; use their existing safe generic category text without exposing target existence. Explicit403 from an API whose contract exposes permission rejection can retain its domain-specific message. Do not create one global “access denied” classification for all403/404 or reinterpret node404. Save rejection remains `저장이 거부되었습니다. 편집 중이던 본문은 그대로 남아 있습니다.` unless its domain owner supplies another truthful safe phrase; the generic state renderer must not add a guessed permission cause.

## Narrow query and deep-link adapters

App already has real useQueries results for document bodies but drops their error/pending states before passing bodies/hashes. Add a nodeId-keyed read-state map through AppShell→DocumentArea:

```ts
type DocumentReadState =
  | { state: 'loading' }
  | { state: 'ready' }
  | { state: 'missing' }
  | { state: 'error'; onRetry: () => void };
```

The map is presentation metadata over existing queries, not a second body store. Associate each result/refetch with the current tab's nodeId and identity, never stale array indexes after tabs reorder/close. A missing map entry is loading/unavailable, not ready. For initial markdown load, mount DocumentSurface only after actual body/hash data is available; pending/failure does not create an editor with `''`. The current Surface already avoids constructing its editor before body exists; retain this protection and add visible surrounding states. Nonmarkdown surfaces keep their separate #58 contracts.

Once an editor is mounted and owns local changes, query refetch transitions must not replace/unmount it or force server content over it. Error/refresh notices are adjacent and do not imply local text was saved. A subsequent read404 for an already-open editor is handled with local-recovery protection, not destructive replacement by the generic not-found screen. Initial unknown document404 has no local body to preserve. Retry is a GET only and cannot resolve conflicts/restart autosave/overwrite body; if that cannot be achieved through current Surface contract, keep that retry unavailable and record the integration gap.

Correct deep-link determination in the existing App path: `workspaces.length===0` cannot stand for “tree not received.” Await explicit tree success, including successful empty, before determining requested ID absence. On tree error show query failure, not404 or empty. Preserve current recursive lookup and nodeId identity, and ensure Back/Forward to an unavailable ID shows the same state instead of silently leaving an unrelated document presented as the requested target. No extra pushState during popstate. Route intent/error state is bound to current pathname request generation so a late response forA cannot show underB.

If another tab/editor already contains unsaved/conflict/rejected content, this routing correction must preserve existing replacement-confirmation contracts before discarding it. Do not broaden into a new universal navigation guard; any newly exposed unguarded-loss route is a blocker under the original preservation requirement, not a reason to erase text to display a prettier404.

For tree and other scoped initial reads, terminal error outranks stale cached “ready” when exposing current authority-sensitive metadata. Do not use current App's data-first tree/favorites check as proof of freshness after a failed read. Implement only necessary state-forwarding/precedence corrections, preserving each panel's existing refresh policy and local editor instance. No global loading flag that blanks healthy panels while another query fails.

## Connectivity truthfulness and retry

Current code has no offline detector or server-health contract. A fetch rejection alone can mean connectivity, DNS/TLS/CORS/proxy failure or another transport problem. Use `연결 상태를 확인한 뒤 다시 시도하세요.` rather than an asserted `오프라인입니다` or `서버가 중단되었습니다`. HTTP500/429/503 are request/service responses, not evidence of being offline. Browser `navigator.onLine===true` does not prove server reachability.

A distinct offline presentation is **N/A in the current scoped contract**. Do not add a global online/offline listener, probe endpoint or offline badge just to fulfill a generic inventory word. If an existing future browser signal is explicitly supplied, it may be described only as `브라우저가 네트워크 연결 끊김을 보고했습니다.`; it still cannot assert server availability or successful saved state. No automatic reconnect save/replay, offline-first cache, service worker, retry backoff or “all changes will sync” promise.

Retry is visible only when an actual read callback exists and the operation is safe to repeat. Preserve its identity/parameters and disable duplicate activation while that read is in flight; add a narrow busy/retry-label prop only if current shared ErrorState cannot express it. State owner catches/reports failure; clicking a callback is not success. Do not use page reload as generic retry, replay writes after timeout, call logout to recover a read failure, or clear form values. Existing domain callbacks that are void/swallow failures remain their prior issue's explicit integration limits.

For authenticated401 observed by a non-session request, there is currently no app-wide secure error handoff. Do not build a universal401 interceptor under styling. Initial document error can truthfully offer read retry; useSession401 establishes unauthenticated state, **not why it ended**. Any desired centralized session revalidation must be scoped with the draft-rescue gap below so a save401 does not immediately destroy the only local body.

No parsing of error.message/raw detail.reason/stack inside a shared component. ## Preservation and security blockers

**B1 — authentication ending across root unmount.** Actual session401 switches App to PreAuthScreen and unmounts DocumentSurface; the live editor owns the newest body, while App/query bodies may be older. Rendering a login notice does not preserve that draft. FR-EDITOR-005/IR-SHELL-009 AC5 require actual rescue evidence, so preservation across expiration or other session invalidation cannot be claimed from the current contract;401 itself does not distinguish those causes. A secure editor→authentication handoff must be separately defined before implementation: exact draft ownership/lifetime, explicit export/discard, isolation from a subsequent account, and no persistence/logging of protected source. Do not copy stale query body and call it recovery; do not leave the authenticated shell behind a preauth form, retain a PAT secret, or expose a previous user's draft after login. No localStorage/sessionStorage/server draft upload is authorized here.

For voluntary logout/password change, that handoff is a **precondition before sending the invalidating POST**, not a reason to delay the immediate transition after success. The owning integration must establish from actual live editors that no unpreserved local body remains, or finish an explicitly authorized export/discard/isolation handoff before submission. Cached `saved` labels/query bodies are not that proof. The secure handoff itself is not invented by this decision and remains separately scoped; until it exists, affected invalidating-mutation integration with possible drafts is blocked in #76. Do not disable authentication cleanup after a mutation has already succeeded, or retain the shell to offer late rescue. Involuntary invalidation still requires the separately defined preservation/isolation contract and remains an unclosed acceptance gap. These blockers cannot be waived by passing clean-document auth tests.

**B2 — mounted-editor read/route denial.** Existing body error state is missing and readonly/refetch boundaries do not establish safe editor-to-root recovery. Initial loading/not-found presentation can be completed; any path that would unmount local edits while resolving route404 or session loss stays blocked until the exact preservation handoff is proven. Do not conceal this with a passing mocked download callback. Existing rejected-save download in the still-mounted #57 editor must remain functional and download actual current text.

**B3 — failure-cause/connection precision.** Existing autosave collapses every non409 request failure into rejected, so the global UI cannot truthfully label it offline/expired/permission loss without a new typed hook contract. Preserve the generic rejection and body rescue; richer diagnosis/automatic retry is outside #76. No server-health or durable-offline capability exists.

Normal session-error presentation, no-selection/no-access/not-found states, query retry, and source-safe domain state styling can proceed with the narrow adapters above. These supported changes do not waive B1/B2 from whole-issue completion claims.
