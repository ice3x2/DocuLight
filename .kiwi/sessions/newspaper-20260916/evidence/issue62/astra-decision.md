### Required editor preference state handoff — authorized #62 amendment

IR-SHELL-004/DR-SHELL-002 define the exact keys and existing persistence; IR-SHELL-006 AC7/9 and live #62 require their truthful immediate-save feedback. Complete this within #62, not a deferred follow-up or a fabricated component-only state. Existing `savePersonalSetting(key,value)` PATCH `/personal-settings` returns204/400 and `usePersonalSettings(userId)` supplies the identity-keyed GET. No endpoint or new setting is required.

App owns the actual read/write state and transient attempted values. AppShell/SettingsModal forwards those props without another fetch/store; PersonalSettings renders them and calls supplied pick/retry callbacks. A concise contract is:

```ts
type EditorPreferenceKey = 'default-view-mode' | 'default-edit-subview';
type EditorPreferenceLoadState =
  | { state: 'loading' }
  | { state: 'ready' }
  | { state: 'error'; onRetry: () => void };
type EditorPreferenceSaveState =
  | { state: 'idle' }
  | { state: 'saving' }
  | { state: 'saved' }
  | { state: 'error'; outcome: 'rejected' | 'unknown'; onRetry: () => void }
  | { state: 'error'; outcome: 'auth-ended' };
// editorLoadState and editorSaveStates: Record<EditorPreferenceKey, ...>
// values remain the supplied render source; no state is inferred from void onPick.
```

- Read loading/error disables both editor selects and displays `에디터 설정을 불러오는 중…` or `에디터 설정을 불러오지 못했습니다.` with actual `다시 불러오기`. If identity failed, retry identity; if the current user's preference GET failed, retry that exact query. Unknown/missing state is unavailable/loading, not success/defaults. Errors must not be masked by an old user's cached values. These props do not change #46 theme load/save state or runtime.
- Ready selects use current-user confirmed values or the existing missing-key defaults. Selecting a changed allowed option immediately sends **one PATCH containing only that key**. Display the selected attempted value as a transient **parent-supplied** overlay and per-field `저장 중…`/aria-busy, never as confirmed data. No global Save button, debounce policy, document-mode preview or component-local duplicate values.
- Lock only that key synchronously while its request is pending, including callback reentry, and disable its select/retry to prevent overlapping writes for the same key. Do not queue duplicate events. The other editor preference stays independently usable; two keys may save concurrently. This avoids pretending a client latest-response guard controls the ordering of multiple same-key server writes.
- Actual204 is accepted persistence for the exact submitted validated value. Merge **only that key** into `QUERY_KEYS.personalSettings(owner)` using the latest cached object, clear that key's attempted overlay and mark `저장됨`. Do not overwrite another key/theme from a captured whole-object snapshot. No extra GET is needed merely to manufacture saved status; server readback/reload is still required as regression evidence. An unrelated query failure after accepted204 cannot turn that write into a rejected save or replay it.
- The error state's required `outcome` determines copy and retry; it cannot be inferred from an optional error string. **HTTP204 alone is accepted; the current endpoint's HTTP400 is confirmed `rejected`** (validation rejected before writing). Rejected clears only that key's attempted overlay, displays the latest confirmed value/default and says `설정을 저장하지 못했습니다. 마지막 확인값으로 복원했습니다.` with per-field `다시 시도`. This describes this request's rejection and the displayed value, not a guarantee that another session has not changed the DB.
- **HTTP401 is `auth-ended`**, because this route returns it before a session actor/write exists. Clear attempted editor values and all retry intents for that authentication generation, stop further preference writes/disable editor controls, and show `로그인이 필요합니다. 다시 로그인한 뒤 설정을 확인하세요.` while this form remains mounted. There is no PATCH retry callback in this state and no invented login button/expiry cause. Preserve the existing owner-level authentication handling; this outcome must not be used to add a global401 interceptor, unmount a live editor or bypass the separately scoped secure-auth/draft handoff. Fresh confirmed authentication and its successful preference read are required before enabling new writes; do not replay the old attempt after login. Missing parent login/session navigation remains its previously documented integration boundary.
- **Every other response/outcome is `unknown` for this preference mutation**: network rejection, timeout/abort after dispatch, malformed/unexpected response, unexpected non2042xx,403/404/409/413/429/5xx or other status. Do not assume proxies/unknown statuses prove no write occurred or diagnose account/permission/validation from them. Show `저장 여부를 확인하지 못했습니다. 마지막 확인값을 표시합니다.`, clear that key's attempted overlay and display its last confirmed value without claiming server rollback. Preserve intended key/value only for a current-generation explicit retry. Retry sends that same assignment once through the existing endpoint; no automatic replay. A new deliberate selection supersedes old retry intent/status. If the server accepted a lost response, subsequent authoritative reads may legitimately reveal that value.
- The current generic `call<void>` treats all HTTP2xx as fulfillment and loses successful status. To enforce the exact boundary, authorize only the minimal **editor-preference request status preservation/expected204 check** at the existing `savePersonalSetting` adapter seam (for example an opt-in expected-success-status option used only by these two keys). Keep the same PATCH path/body/credentials; do not globally change call<T>, #46 theme request semantics or other APIs. An unexpected200 must not be relabelled as204 success because the old helper resolved. Client-side rejection before any request (invalid key/value or disabled/obsolete owner) is a guard/no-op, not a successful write or fabricated HTTP outcome.
- Bind read, write and retry to authenticated user ID **and an authentication generation**, plus per-key request generation. Recheck owner before sending after any awaited work and again before cache/status changes. A retry retained from an old user cannot execute under the new user's cookie. Logout/session loss/user change clears editor overlays/status/retry intent; late old-generation reads/writes cannot repaint or recreate cleared user state. Re-login as the same ID is still a new generation.
- Prevent pre-write/obsolete personal-settings GET responses from overwriting accepted writes using the existing query client's exact-key cancellation/invalidation facilities and generation checks. Cancel relevant stale reads before write/cache adoption as needed, without canceling theme mutations or changing theme runtime. Concurrent different-key204 responses merge independently. A genuinely later authoritative GET may update displayed confirmed values; never preserve an optimistic value as DB truth indefinitely. No cross-tab last-writer/CAS guarantee is invented.
- Saved/error labels sit beside their corresponding fields with stable accessible descriptions and nonduplicated live regions. Successful saves do not move focus. If a disabled pending control loses focus, retain a field-associated status/focus anchor and restore only when the user has not moved elsewhere. Retry failure stays at that field; do not collapse both fields into one shared success/error label.

The exact implementation scope addition is App's two-key preference load/save/result logic, AppShell/SettingsModal prop/type forwarding, PersonalSettings state rendering, the minimal editor-only response-status check at the existing savePersonalSetting client seam, and necessary scoped tests. This replaces the earlier “separate parent state wiring” restriction **only for these two settings**. Keep #46 saveTheme/optimisticTheme/cache/runtime contracts intact; do not build a generic settings engine. Document-opening consumption of the defaults stays outside #62: test/report it separately and never equate persistence with application to a newly opened document.

Theme semantics are unchanged: light/dark fixed, system follows prefers-color-scheme at first paint and live OS changes; DB overrides valid identity-keyed current-tab memory. Logout/session invalidation/user change clears that cache and returns anonymous theme to system. No persistent local/session storage, anonymous last-user preference or new settings fetch is added. Changing theme never clears form input, remounts editor/document, moves cursor or resets undo.
